# 最初のひと月

新しいデプロイが最初に持つのは空のベースである。このページは、そこから
エージェントが実際に検索でナレッジを見つけ、それが育ち始める状態までの
一本道である。四つの段があり、順序に理由がある。範囲を決めて問いを書き
出す、骨格を投影する、種類ごとに中身を書く、見つけられることを確かめる、
そして週次で育てる。

手順が文書として出荷されているのは、来てくれる人がいないからである(C4、
[surface.md](../surface.md))。オントロジーを売るプラットフォームは、この
作業を何度もやった常駐エンジニアを寄越す。ochakai にはそれがないので、
代わりに読んで走らせられるページがある。

このページは背骨で、各段の詳細は既にある場所を指す。BigQuery カタログの
初日の全手順は
[`skills/build-the-first-catalog`](../../examples/bigquery-catalog)、ループ
そのものの説明は[改善ループ](../loop.md)、golden query の継続実行は
[canary ガイド](golden-query-canary.md)にある。

## 0. 始める前に: 範囲と、二十の問い

**範囲を小さくする。** データセット二つ、テーブル 5〜10 個で初日は十分で
ある。理由はレビューキューの側にある。このベースが持つ三つのフィードは、
人が空にできることを前提に設計されている。数千件の未裁定 draft は、キュー
が読まれなくなる典型的な形である。三つ目のデータセットは来週足せばよく、
それは後退ではない。

エージェント向けのカタログや semantic layer を売っている製品は、どれも同じ
ことを言う。初期対象はテーブル 5〜15 個、価値の 8 割を生む 2 割、全社
ダッシュボードではなく scope の狭い高価値ドメイン一つ。全テーブルを同時に
文書化する計画は、3 割ほど埋まったところで止まる。

**そして、チームが実際に訊いている問いを 10〜20 個書き出す。**

```
「先月の売上はいくらだったか」
「リピート購入率は先月から動いたか」
「チャネル別の内訳は」
…
```

これは後で二度効く。何を書くかの順序をこれが決め、§3 で検索が効いている
かを判定する材料にもなる。思いつかない場合は倉庫が知っている。ジョブ履歴
で何度も撃たれているクエリがそれであり
([draft-from-query-history](../../examples/bigquery-catalog))、社内チャット
で繰り返されている質問がそれである。

先に問いを書くのは、この分野で最も合意のある助言である。評価用の質問集を
設定作業より前に作れと言う製品があり、着手前にステークホルダーの最頻出
質問 20 問を棚卸しさせる製品がある。後から作ると、自分が書いたナレッジが
答えられる問いを書いてしまう。

## 1. 骨格を投影する

スキーマは自分で撃って、答えを渡す。ochakai は倉庫に接続しない。

```sh
bq query --max_rows=100000 --format=json --nouse_legacy_sql \
  'SELECT table_schema, table_name, column_name, data_type, is_nullable, description
     FROM `your-project.your_dataset.INFORMATION_SCHEMA.COLUMNS`
    ORDER BY ordinal_position' \
  | ochakai seed --project your-project - | ochakai import -
```

**`--max_rows` は省けない。** `bq query` が既定で表示するのは先頭 100 行
だけで、打ち切ったことを何も言わない。カラムが合計 100 本を超えるデータ
セットは、エラーも警告も無しに一部のテーブルだけが入る。行数を数えるのは
投影の前なので、`seed` が最後に出す「seeded N tables」の N を自分のテーブル
数と突き合わせるのが、その場でできる確認である。

投影は全件 draft で着地する。投影されたスキーマは骨格であって、まだナレッジ
ではない([0085](../design/0085-the-empty-base-and-what-fills-it.md) §3)。
出てくるのは数千行の主張ではなく、数千個の問いである。

id の prefix は、この日の唯一「後から変えると高くつく」決定である。
`--prefix` を後で変えても改名は起こらず、二つ目のカタログが隣に建って、
一つ目は誰も見ていない場所で古びる。毎日の同期、attester、住所の決め方は
[`skills/build-the-first-catalog`](../../examples/bigquery-catalog)にある。

## 2. 種類ごとに書く

ここが仕事の本体である。型ごとに、上から書く。

| # | 型 | 何に答えるか | 最初の目安 |
|---|---|---|---|
| 1 | `BigQuery Table` / `Dataset` | このテーブルは何で、何に注意するか | 投影済み。一つだけ人が書き足す |
| 2 | `Glossary Term` | その語が指すもの(「完了した注文」とは) | エージェントが取り違えた語だけ、5 個ほど |
| 3 | `Policy` | 数字を決める規則(収益認識、会計年度) | 2〜3 個 |
| 4 | `Metric` | 定義。`SUM(price)` の側 | semantic layer があるなら省いてよい |
| 5 | `Attested Computation` | sanctioned なクエリ本体 | §0 の問いに一対一で 10〜20 本 |
| 6 | `Insight` | 数字の読み方。ベースライン、季節性、しきい値 | 最初は 3〜5 個 |
| 7 | `Skill` | 手順。「このクエリの走らせ方」 | 最後。無くてもよい |

**なぜこの順か。** 下から書くと、指す先が無い。golden query は `sources` で
テーブル concept を指し、Insight はメトリクスを指す。リンクは本文から導かれ
るので([architecture](../architecture.md))、指される側が先にいる必要がある。
テーブルを一つも記述していないベースに置かれたクエリは、コメントの付いた
SQL でしかない。

**5 が最も効き、6 が他のどこにも無い。** text-to-SQL の公開実験では、スキーマ
だけを渡した場合の正答率が 3% 前後、質問と検証済み SQL の対を検索して渡した
場合が 75〜80% だった。効くのはモデルではなくクエリライブラリのほうである。
一方 `Insight` は、semantic layer もカタログも持たない型である。100 という
数字が良いのか悪いのか、8 月がいつも 15% 低いことは何も意味しないこと。
ochakai がある理由の半分はここにある([ポジショニング](../positioning.md))。

**7 を最後に置くのは、書きすぎると効かなくなるからである。** この分野の製品
は自由文の指示を優先度の最下位に置いており(「他の手段で解決できない場合の
最終手段」)、かつてシノニム集を勧めていた製品はそれをやめた。現行のモデル
ではトークンを消費するだけだったためである。手順が要るときだけ `Skill` を
書く。

**書くのはエージェントである。** 全部を自分で書こうとしないこと。幅を下書き
するのがエージェントで、判断の要る中核を検証するのが人である
([改善ループ](../loop.md))。テーブル concept を開いて渡し、こう頼む。

> このテーブルについて、クエリを書く前に知っておくべきことを
> `# Caveats` に書き足して ochakai に保存して。必ず要るフィルタ、
> 嘘をつくカラム、タイムスタンプのタイムゾーン。

一ヶ月で verified が 20〜30 個あれば、十分に育ったベースである。骨格のまま
残る draft は誰の邪魔もしない。検索では verified が上に来るので、裁定しない
ことの代償は小さい。全部を verify する計画から得られるものは、たいてい何も
無い。

## 3. 見つけられることを確かめる

**ここを飛ばさない。** 書いたことと、エージェントが検索で見つけられること
は別である。ナレッジ管理製品のオンボーディング文書はここをほぼ扱っておらず、
扱っているのはエージェント向けの semantic layer の側だけである。投入したら、
それに当たるはずの問いを撃って、呼ばれることを確認する。

§0 で書き出した問いを、そのまま撃つ。

```sh
while read -r q; do
  printf '\n=== %s\n' "$q"
  ochakai search "$q" --limit 3
done < questions.txt
```

`ochakai search` は、エージェントがデータの問いに答える前にする読み取りの
入口そのものである。ここで返るものが、エージェントが見るものである。結果は
三通りに分かれる。

- **期待した concept が返った。** その問いは済んでいる。
- **何も返らない。** 書くものが足りない。これは `ochakai stats` の gap 行にも
  出る。何も返さなかった検索が、訊かれた回数の多い順に並ぶので、そのまま
  「次に書くものの一覧」になる。この確認そのものも記録される(公開デプロイ
  だけは何も残さない。`stats` は `misses -` と言い、ゼロではなく「測って
  いない」と答える)。
- **別のものが返った。** 語の問題であることが多い。検索は concept の本文を
  読むので、チームが実際に使う語をその concept の中に書くのが直し方である
  (タイトルだけを直しても効かない)。長すぎる concept が後半で引けなく
  なっている可能性もあり、`ochakai stats` の `truncated` がそれを言う
  ([改善ループ](../loop.md))。

**外した問いを捨てない。** `questions.txt` に残して、直したらもう一度全部
撃つ。失敗した問いを評価セットに還流させて通るまで直すのは、エージェント
向けの製品が揃って収束した形である。ochakai では、その評価セットのうち SQL
を伴うものが `Attested Computation` になり、
[canary](golden-query-canary.md) として CI で走り続ける。

verified が上に来るという順位の性質上、一度も裁定していないベースではこの
確認が本来より悪く出る。デモを入れた直後なら、`ochakai verify` を一つ打って
から撃つ。

## 4. 育てる: 二周目から

**エージェントを繋ぐ**([MCP クライアント](mcp-clients.md))。想起と書き戻し
を習慣ではなく仕組みにするなら、
[Claude Code のフック](../../examples/claude-code)を入れる。

**一週間走らせてから、裁定の順番を決める。**

```sh
ochakai list usage --status draft    # 直近 90 日で実際に触られた順
```

初日はここが全部 0 である。意味を持つのは二周目からで、そのとき上に来る十件
が、チームが実際に触っている十件である。裁定の順番はそれが決める。最も読ま
れていて、まだ誰も請け合っていないものからである。これは他の製品が「閲覧数
× 未検証」や「クエリ回数 × 利用者数」で作っている順位と同じもので、ここでは
キューが最初からそう並ぶ。

**週に一度、三つのキューと gap 行を見る。**

```sh
ochakai stats                 # 三つのキュー、フロー、返らなかった問い
ochakai stats --exit-code     # cron: 誰かが裁定を負っている間は 2 で落ちる
```

空になるのは要レビューのフィードだけである。検証の古さのフィードは concept
を落とさず全件を並べ替えるので、その大きさはナレッジベースの大きさになる。
ゼロにはならないし、する必要もない([改善ループ](../loop.md#feeds))。

**検証済みの割合を目標にしない。** 全社ナレッジを人が見て回る前提の製品には
「検証スコア 80% 以上」のような目標があるが、ここでの前提は逆で、骨格の大半
が draft のまま残るのが正常である。測るのは割合ではなく、エージェントに実際
に返っている concept が verified かどうかである。`ochakai list usage` の上位
が draft で埋まっているなら、そこが裁定すべき場所であり、下の方に未裁定が
何千件あるかは誰の問題でもない。

## ひと月後にあるもの

エージェントが出会うテーブルが投影され、そのうち何割かに人しか知らなかった
ことが書かれ、§0 の問いの大半が `ochakai search` で答えを返す。golden query
が canary として週次で走り、間違いは `report_outcome` で再検証フィードに
浮く。裁定のキューは、読まれている順に並んでいる。

そこで止まってよい。あとは §2 と §3 の繰り返しで、この先に別の段は無い。
