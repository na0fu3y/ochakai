# 最初のひと月

新しいデプロイが最初に持つのは空のベースである。このページは、そこからエージェ
ントが検索でナレッジを見つけ、それが育ち始める状態までの手順である。四つの段
があり、順序に理由がある。範囲を決めて問いを書き出す、骨格を投影する、種類ご
とに中身を書く、見つけられることを確かめる、そして週次で育てる。

この手順が文書として出荷されているのは、代わりに来てくれる人がいないからであ
る(C4、[surface.md](../surface.md))。オントロジーを売るプラットフォームは、
この作業を何度もやった常駐エンジニアを寄越す。ochakai にその役はないので、読
んで自分で走らせられるページを置いている。

このページは通しの手順だけを書き、各段の詳細は既にある文書に譲る。BigQuery
カタログの初日の全手順は
[`skills/build-the-first-catalog`](../../examples/bigquery-catalog)、ループ
そのものの説明は[改善ループ](../loop.md)、golden query の継続実行は
[canary ガイド](golden-query-canary.md)にある。

## 0. 始める前に: 範囲と、二十の問い

**範囲を小さくする。** データセット二つ、テーブル 5〜10 個で初日は十分である。
小さく始めるのは、レビューが追いつかなくなるからである。このベースが持つ三つ
のフィードは、人が空にできることを前提に設計されている。未裁定の draft が数
千件あるキューは、じきに誰も開かなくなる。三つ目のデータセットは来週足せばよ
い。

エージェント向けのカタログや semantic layer を売っている製品も、そろって同じ
ことを言う。初期対象はテーブル 5〜15 個、価値の 8 割を生む 2 割に絞る、全社
ダッシュボードではなく範囲の狭い高価値ドメインを一つ。全テーブルを同時に文書
化する計画は、3 割ほど埋まったところで止まる。

次に、チームが実際に訊いている問いを 10〜20 個書き出す。

```
「先月の売上はいくらだったか」
「リピート購入率は先月から動いたか」
「チャネル別の内訳は」
…
```

この一覧は後で二回使う。§2 で何から書くかを決める材料になり、§3 で検索が効い
ているかを判定する材料にもなる。思いつかないときはウェアハウスのジョブ履歴を
見る。何度も実行されているクエリと
([draft-from-query-history](../../examples/bigquery-catalog))、社内チャット
で繰り返し訊かれている質問がそれである。

先に問いを書くのは、この分野で最も合意のある助言である。評価用の質問集を設定
作業より前に作れと言う製品もあれば、着手前にステークホルダーの最頻出質問 20
問を棚卸しさせる製品もある。後から作ると、自分が書いたナレッジで答えられる問
いばかりを選んでしまう。

## 1. 骨格を投影する

スキーマは自分で取得して、その答えを渡す。ochakai はウェアハウスに接続しない。

```sh
bq query --max_rows=100000 --format=json --nouse_legacy_sql \
  'SELECT table_schema, table_name, column_name, data_type, is_nullable, description
     FROM `your-project.your_dataset.INFORMATION_SCHEMA.COLUMNS`
    ORDER BY ordinal_position' \
  | ochakai seed --project your-project - | ochakai import -
```

**`--max_rows` は省けない。** `bq query` が既定で表示するのは先頭 100 行だけ
で、打ち切ったことは表示しない。カラムが合計 100 本を超えるデータセットでは、
エラーも警告もないまま、一部のテーブルしか入らない。行数は投影の前に確認する。
`seed` が最後に出す「seeded N tables」の N を自分のテーブル数と突き合わせれ
ば、その場で分かる。

投影したものは全件 draft で入る。スキーマは骨格であって、まだナレッジではな
い([0085](../design/0085-the-empty-base-and-what-fills-it.md) §3)。ここでで
きるのは、まだ誰も説明を書いていないテーブルとカラムの一覧である。

id の prefix は、この日に決めるものの中で唯一、後から変えると高くつく。
`--prefix` を後で変えても改名は起こらない。二つ目のカタログができるだけで、
一つ目は誰にも読まれないまま古くなる。毎日の同期、attester、住所の決め方は
[`skills/build-the-first-catalog`](../../examples/bigquery-catalog)にある。

## 2. 種類ごとに書く

ここが仕事の本体である。型ごとに、上から書く。

| # | 型 | 何に答えるか | 最初の目安 |
|---|---|---|---|
| 1 | `BigQuery Table` / `Dataset` | このテーブルは何で、何に注意するか | 投影済み。一つだけ人が書き足す |
| 2 | `Glossary Term` | その語が指すもの(「完了した注文」とは) | エージェントが取り違えた語だけ、5 個ほど |
| 3 | `Policy` | 数字を決める規則(収益認識、会計年度) | 2〜3 個 |
| 4 | `Metric` | 定義。`SUM(price)` の側 | semantic layer があるなら省いてよい |
| 5 | `Attested Computation` | sanctioned なクエリ本体 | §0 の問いに一対一で 10〜20 本 |
| 6 | `Insight` | 数字の読み方。ベースライン、季節性、しきい値 | 最初は 3〜5 個 |
| 7 | `Skill` | 手順。「このクエリの走らせ方」 | 最後でよい。無くても動く |

この順にするのは、後ろの型が前の型を指すからである。golden query は
`sources` でテーブル concept を指し、Insight はメトリクスを指す。リンクは本
文から導かれるので([architecture](../architecture.md))、指される側が先にいる
必要がある。テーブルを一つも記述していないベースに置かれたクエリは、コメント
の付いた SQL でしかない。

効果が大きいのは 5 で、他の道具が持っていないのは 6 である。text-to-SQL の公
開実験では、スキーマだけを渡した場合の正答率が 3% 前後、質問と検証済み SQL
の対を検索して渡した場合が 75〜80% だった。差を作っているのはモデルではなく、
検証済みクエリの蓄積である。一方 `Insight` は、semantic layer もカタログも持
たない型である。100 という数字が良いのか悪いのか、8 月がいつも 15% 低いこと
に意味があるのか。それを書いておける場所が他に無いことが、ochakai がある理由
の半分である([ポジショニング](../positioning.md))。

7 を最後に置くのは、書きすぎると効かなくなるからである。この分野の製品は自由
文の指示を優先度の最下位に置いている(「他の手段で解決できない場合の最終手段」)。
かつてシノニム集を勧めていた製品も、現行のモデルではトークンを消費するだけだっ
たためにそれをやめた。手順が要るときだけ `Skill` を書く。

**書くのはエージェントである。** 全部を自分で書こうとしないこと。幅広く下書
きするのがエージェントの役目で、人は判断の要る中核だけを検証する
([改善ループ](../loop.md))。テーブル concept を開いて渡し、こう頼む。

> このテーブルについて、クエリを書く前に知っておくべきことを `# Caveats` に
> 書き足して ochakai に保存して。必ず要るフィルタ、嘘をつくカラム、タイムス
> タンプのタイムゾーン。

一ヶ月で verified が 20〜30 個あれば、十分に育ったベースである。骨格のまま残
る draft は誰の邪魔もしない。検索では verified が上に来るので、裁定が追いつ
かなくても影響は小さい。全部を verify する計画に見合う成果は、たいてい無い。

## 3. 見つけられることを確かめる

**ここを飛ばさない。** 書いたことと、エージェントが検索で見つけられることは
別である。ナレッジ管理製品のオンボーディング文書はここをほとんど扱っておらず、
扱っているのはエージェント向けの semantic layer の側だけである。投入したら、
それに当たるはずの問いを実行して、呼ばれることを確かめる。

§0 で書き出した問いを、そのまま実行する。

```sh
while read -r q; do
  printf '\n=== %s\n' "$q"
  ochakai search "$q" --limit 3
done < questions.txt
```

`ochakai search` は、エージェントがデータの問いに答える前に必ず通る入口であ
る。ここで返るものが、そのままエージェントの見るものになる。結果は三通りに分
かれる。

- **期待した concept が返った。** その問いは済んでいる。
- **何も返らない。** 書くものが足りない。これは `ochakai stats` の gap 行に
  も出る。何も返さなかった検索が、訊かれた回数の多い順に並ぶので、そのまま
  「次に書くものの一覧」になる。この確認そのものも記録される(公開デプロイだ
  けは何も残さない。`stats` は `misses -` と表示し、ゼロではなく測っていない
  ことを示す)。
- **別のものが返った。** 語の問題であることが多い。検索は concept の本文を読
  むので、チームが実際に使う語をその concept の中に書くのが直し方である(タイ
  トルだけを直しても効かない)。長すぎる concept が後半で引けなくなっている場
  合もあり、それは `ochakai stats` の `truncated` に出る
  ([改善ループ](../loop.md))。

外した問いは捨てずに `questions.txt` に残し、直したらもう一度全部実行する。
失敗した問いを評価セットに戻して通るまで直すやり方には、エージェント向けの製
品が揃って行き着いている。ochakai では、その評価セットのうち SQL を伴うもの
が `Attested Computation` になり、[canary](golden-query-canary.md) として CI
で走り続ける。

検索は verified を上に置くので、一度も裁定していないベースでは、この確認が本
来より悪く出る。デモを入れた直後なら、`ochakai verify` を一つ実行してから確
かめる。

## 4. 育てる: 二周目から

エージェントを繋ぐ([MCP クライアント](mcp-clients.md))。想起と書き戻しを習慣
ではなく仕組みにするなら、[Claude Code のフック](../../examples/claude-code)
を入れる。

**一週間走らせてから、裁定の順番を決める。**

```sh
ochakai list usage --status draft    # 直近 90 日で実際に触られた順
```

初日はここが全部 0 である。この一覧が意味を持つのは二周目からで、そのとき上
に来る十件が、チームが実際に触っている十件である。裁定はそこから始める。最も
読まれていて、まだ誰も裁定していないものが先である。他の製品が「閲覧数 × 未
検証」や「クエリ回数 × 利用者数」で作っている順位と同じもので、ここではキュー
が最初からそう並ぶ。

**週に一度、三つのキューと gap 行を見る。**

```sh
ochakai stats                 # 三つのキュー、フロー、返らなかった問い
ochakai stats --exit-code     # cron: 誰かが裁定を負っている間は 2 で落ちる
```

空になるのは再検証のフィードだけである。検証の古さのフィードは concept
を落とさず全件を並べ替えるので、その大きさはナレッジベースの大きさそのものに
なる。ゼロにはならないし、ゼロにする必要もない
([改善ループ](../loop.md#feeds))。

検証済みの割合を目標にしない。全社ナレッジを人が見て回る前提の製品には「検証
スコア 80% 以上」のような目標があるが、ここでの前提は逆で、骨格の大半が
draft のまま残るのが正常である。見るのは割合ではなく、エージェントに実際に返っ
ている concept が verified かどうかである。`ochakai list usage` の上位が
draft で埋まっているなら、そこが裁定すべき場所である。下の方に未裁定が何千件
あっても、特に問題にはならない。

## ひと月後にあるもの

エージェントが使うテーブルはひと通り投影され、そのうち何割かには人しか知らな
かったことが書かれている。§0 の問いの大半は `ochakai search` で答えが返り、
golden query は canary として週次で走る。間違いは `report_outcome` で再検証
フィードに上がり、裁定のキューは読まれている順に並んでいる。

そこで止まってよい。あとは §2 と §3 の繰り返しで、この先に別の段は無い。
