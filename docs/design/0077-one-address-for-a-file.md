# ochakai 設計ドキュメント 0077: ファイルの住所は一つである

Status: Accepted(2026-08-03)。**CLI がファイルを名指す綴りの現行
ドキュメント。** 何も Superseded にせず、何も改訂しない —
[0075](0075-the-bundle-is-the-address-space.md) §§1・4 が決めた
「パスが住所である」を CLI に適用し、
[0064](0064-rest-stops-at-api-v1.md) §8 が別 issue に切り出した二本
(issue [#470](https://github.com/na0fu3y/ochakai/issues/470))を畳む。
Date: 2026-08-03

## 1. 何が残っていたか

0075 §1 は「**`attach` / `detach` という操作も消え、ファイルを置くことは
`PUT`、外すことは `DELETE` である**」と書き、0064 §6 は wire から
`attachment` の綴りを退役させ、§8 はリビジョンの動詞を
`add_file` / `remove_file` に改めた。**それでも CLI には二本残っていた。**

```
ochakai attach <concept id> <file...>   [--name <名前>]
ochakai detach <concept id> <名前>
```

この二本が持っていた問題は綴りだけではない。**ファイルをバンドルパス
ではなく「concept の id と、その中での名前」で名指していた。** 0075 §5
が帰属を本文からの導出にした以上、ファイルが「どの concept のものか」は
住所ではない — 住所はファイルが置かれているパスそのものである。
`detach` はそれを知っていて、`GET` で concept を読み、同名のファイルの
`path` を探してから `DELETE` を撃っていた。**一つのオブジェクトに二つの
住所があるとき、片方は必ずもう片方を引くコードになる。**

そして `ochakai put` と `ochakai delete` は、既に同じ二つの HTTP 操作を
送っていた。0046 §3.5 が REST から畳んだ「第二の住所」と、同じ形の
ものが CLI に残っていた。

## 2. 決定: `put` と `delete` が両方のオブジェクトを扱い、二本は畳む

| 前 | 後 |
|---|---|
| `ochakai attach <id> <file>` | `ochakai put <バンドルパス> -f <file>` |
| `ochakai attach <id> <f1> <f2>` | シェルのループ |
| `ochakai attach <id> <file> --name <名前>` | `ochakai put <…>/<名前> -f <file>` |
| `ochakai detach <id> <名前>` | `ochakai delete <バンドルパス>` |

新しいフラグは無い。`put` は元から `-f` で本文をファイルから読み、
`--json` で書いたものを JSON で出す。**畳めたのはコマンド二本
(CLI 26 → 24)で、覚えるフラグは一つも増えていない**
([docs/surface.md](../surface.md))。

### 2.1 書き込みは、バイト列が決める

`ochakai put` が concept を書くのかファイルを置くのかは、**引数の綴りでは
なく渡されたバイト列が決める**。frontmatter に `type` があれば concept で、
その住所は `<id>.md`(0064 §5)。無ければファイルで、住所は引数そのもので
ある。**これはサーバーの規則をそのまま鏡写しにしたものである** —
`internal/restapi` は `.md` を落としたパスと `okf.CarriesType` で同じ判定を
しており、CLI は REST の薄いクライアントである([0067](0067-four-faces-and-what-they-decline.md) §2)。

**これは「一つのコマンドが二つの能力を持つ」([0068](0068-how-a-face-is-added-and-removed.md) §1)
ではない。** 0068 が名指す欠陥は、`--sort` の有無で検索と一覧という
**別の行為**が切り替わることだった。ここで起きるのは一つの行為である —
一つの住所にオブジェクトを一つ置く。何が置かれたかはサーバーが決め、
`ochakai put` はそれを二度目に決め直さない。二本に割るほうが、
**wire に無い区別を CLI が発明する**ことになる。

JSON 入力だけが例外で、それは CLI 自身の入力形式であってバンドルに
保存される形ではない。だから JSON が concept として読まれるのは、
引数が concept の住所(拡張子なし、または `.md`)を名指すときだけである
— そうでないと `ochakai put schemas/orders.json -f orders.json` が
JSON **ファイル**を concept として読み、type が無いと言って断る。

### 2.2 削除は、綴りが先に指した住所から

`delete` にはバイト列が無いので、**引数の綴りがどちらの住所を先に問うかを
決める**。拡張子を持たない引数は id なので `<id>.md`、自分の拡張子を持つ
引数はパスそのもの。**もう一方は、先に問うた住所に何も無かったときだけ
試す。** そこにあるものが取り違えられることはなく、ドットを含む id も、
拡張子の無い名前のファイルも、どちらも消せる。往復が二回になるのは、
一回目が 404 だった場合 — つまり以前ならそこで終わっていた場合 — だけで
ある。

### 2.3 貼るためのリンクは、`put` が引き継ぐ

`attach` は書き込みのあとに、本文に貼るための相対リンク
(`![weekly.png](reading-revenue/weekly.png)`)を stderr に出していた。
**これは capability である。** 0075 §5 が帰属を本文からの導出にしたので、
**誰もリンクしないファイルは誰にも見つからない**。黙って落とせば、
「置いたのに出てこない」という形で後から気づくことになる。

`put` は同じ行を出す。ヒントの計算元は concept の id ではなくパスに
なった — ファイルが座るディレクトリの最終セグメントと名前をつないだもの
で、`<id>/<name>` に置いたときは以前と同じ文字列になる。

### 2.4 落ちる便宜、二つ

- **一度に複数ファイル。** `for f in *.csv; do ochakai put "tables/orders/$f" -f "$f"; done` である。
  行指向の出力とシェルでの合成が CLI の値打ちで、ループはシェルの仕事である。
- **`--name`。** パスそのものが名前になったので、置き先の名前を別の
  引数で言う場所が無い。`--name` という綴りは `ochakai use` に残るので、
  覚えるフラグの数は動かない。

## 3. Web UI は CLI と同じ語を使う

0064 §8 は Web UI の `Attach` / `Detach` ボタンを「wire の値ではなく
CLI と同じ利用者向けの語であるため、**対称に残す**」と決めた。CLI の語が
変わった以上、対称であり続けるということはボタンも変わるということである
— `Add files` と `Remove`。**§8 の決定を覆すのではなく、それに従っている。**
UI の構造は動かさない。

## 4. やらないこと

- **`ochakai get <path>` でファイルのバイト列を出すこと。** 読む側は
  `ochakai get <id> --download <dir>` が既に持っており、`browse` が
  ディレクトリのファイルを出す。**この記録が畳むのは書き込みの第二の
  住所であって、読みの面を作り直すことではない。**
- **移行期間。** 0.x に非推奨期間は無い([compatibility.md](../compatibility.md))
  ので、畳んだ二本は「そんなコマンドは無い」で落ちる。
- **`internal/store` の内部識別子と SQL テーブル**(`PutAttachment`・
  `attachment_embedding` ほか)。0064 §6 が引いた境界のとおり対象外で
  ある — どのクライアントからも見えない。
- **ファイルの MCP ツール。** 0075 §7 の「エージェントが増やすべきもの
  ではない」を動かさない。

## 5. 壊れるもの

**BREAKING**。`ochakai attach` / `ochakai detach` を打っていた人と
スクリプトは §2 の表のとおり読み替える。ファイルの置き場所も中身も
1 バイトも動かない — 変わるのは、それを名指す綴りだけである。
