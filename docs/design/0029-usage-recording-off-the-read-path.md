# ochakai 設計ドキュメント 0029: 利用測定を読み取りパスから外す

Status: Accepted(2026-07-26)。[0051](0051-instance-metrics-and-search-misses.md)
が同じバッファ・同じフラッシュ・同じ 180 日の刈り取りを、エントリに紐づかない
事実(ヒット 0 の検索)にも広げた — 決定そのものは変わらない
Date: 2026-07-26

## 1. 背景: 決定はランドしていたが、記録されていなかった

利用テレメトリは 0001 §9.2 が決めた中核機能である — どのナレッジが実際に
使われたかを測り、[0025](0025-closing-the-loop.md) の再検証フィード
(`sort=usage`、`sort=failed`)がその上に乗る。

その**記録方法**は 2026-07-21 の PR #107 で書き換わり、SIGTERM 後の
ドレイン猶予は PR #119 で調整された。しかしこの決定は設計ドキュメントに
書かれないままコードだけがランドし、コメントは存在しない節
(「0025 §10」「0025 §11」)を引いていた。本ドキュメントはその決定を
事後に記録し、宙に浮いた参照の宛先を与える。決定自体は変更しない。

## 2. 問題

利用イベント(`search_hit`、`fetched`)は**読み取りのたびに**発生する。
以前はその場で `knowledge_event` に INSERT し、`knowledge_usage` の
running total を UPDATE していた。つまり検索 1 回が、ヒット件数ぶんの
書き込みを読み取りパスに載せていた。

- 検索・get_context のレイテンシが、測定のための書き込みに引きずられる。
- 書き込みが失敗すると、**読み取り自体**が失敗しうる — 統計の副作用が
  本来の機能を落とすのは倒錯している。
- Cloud SQL の f1-micro(0003 の想定インスタンス)では、この書き込みが
  読み取りと同じ接続プールを奪い合う。

## 3. 決定

**利用イベントはメモリにバッファし、背景ループが定期フラッシュする。**
記録は読み取りパスに一切触れない(`Store.RecordEvents` は append して
即座に返る)。

### 3.1 利用測定は best-effort である

これが本決定の芯である。利用統計は**失われてよい**。失われてはいけない
のはナレッジ本体であり、「このエントリは何回引かれたか」の端数ではない。
この非対称を明示的に選ぶことで、以下がすべて素直に決まる:

- **バッファ上限は 20000 イベント**(`usageBufferMax`)。DB が停止して
  バッファが伸び続けるくらいなら、超過分を捨ててプロセスを守る。捨てた
  ことは呼び出し元に返り(`errUsageBufferFull`)、ログに残る — 静かに
  減るのではなく、減ったと分かる形にする。
- **フラッシュ間隔は 5 秒**(`usageFlushInterval`)。
- **フラッシュがエラーになったら、そのバッチは失われる**。再試行キューは
  持たない。エラーは可視化のために返す。

`report_outcome`(worked / failed)は**この扱いに含めない**。結果報告は
読み取りの副作用ではなく意図的な書き込みであり、0025 の再検証ループが
それに依存している。`Store.RecordOutcome` は従来どおり同期的に書き、
失敗はサーフェスに返る。

### 3.2 集計は 1 文で行う

フラッシュは 1 バッチを 1 ステートメントで書く — `knowledge_event` への
一括 INSERT と、そこから集計した `knowledge_usage` の running total 更新を
CTE でつなぐ。`last_at` は両辺の GREATEST を取るので、たまたま古い
occurrence を含むバッチが total を巻き戻すことはない。

### 3.3 シャットダウンで取りこぼさない

フラッシュループは `Close` で停止する際、**もう一度ドレインしてから**
終わる。したがって順序が意味を持つ: HTTP サーバーがドレインを終えてから
`Store.Close` を呼ぶ。逆順にすると、最後の数秒に処理していたリクエストが
記録したイベントが最終フラッシュの後に積まれ、失われる。

SIGTERM 後のドレイン猶予は 5 秒とする(PR #119)。Cloud Run が SIGTERM と
SIGKILL の間に与えるのは 10 秒で、その全部をドレインに使うと最終フラッシュが
書き込み途中で殺される — ドレイン中のリクエストが記録したイベントを
守るために設けた猶予が、そのイベントを失わせることになる。5 秒はここの
どのハンドラにも十分であり、それを超えて走るのは export のストリームだけで、
途中で切れたバックアップはこのプロセスで最も安く失えるものである。

### 3.4 生イベントの保持期間

`knowledge_event` の生行は 180 日で刈る(プロセスあたり 1 日 1 回まで)。
running total は `knowledge_usage` に残るので、`/usage` の値は刈っても
正確なままである。

## 4. 壊れるもの

- **利用カウントは最大 5 秒遅れる。** 書いた直後に `/usage` を読むテストは
  `FlushUsage` を明示的に呼ぶ必要がある(そのために公開している)。
- **クラッシュ(SIGKILL・OOM)では最大 5 秒ぶんのイベントが失われる。**
  §3.1 の通り、意図的な取引である。
- `knowledge_event` に外部キーを張らない。フラッシュは purge / move の
  後に着地しうるので、消えた id を含むバッチが 1 行の失敗でバッチ全体を
  巻き添えにしないためである。
