## 0. この記録が決めたこと

**二つの記録が一つの絵であること。** 0078 は 0073 の**設定面だけ**を
改訂する記録だった — 何を埋め込むかは 0073、どう書くかは 0078。決定と
しては正しく分かれていたが、**読む側には分かれていなかった。**

分けたままにできなかった理由は一つで、それは体裁ではない。**0073 の
散文は、退役した綴りを生きた設定として書いている** — §1.1 と §1.3 と
§1.4 は `OCHAKAI_VERTEX_PROJECT` を、§2 は `OCHAKAI_EMBEDDING_DIM` を、
読者が設定できるものとして名指す。0078 がそれを畳んだので、0073 だけを
読んだ人は**存在しない変数を置く**。片方だけ読んで害の無い分割ではなく、
片方だけ読むと間違える分割だった。

決定は一つも動かない。動くのは §7 の一項目で、そこは 0073 が書いた
ときから**コードと違っていた**(§7 の「許可する形式」)。

## 1. Google Cloud の上では、埋め込みが既定である

**この製品でいちばん効く機能が、いちばん奥に置いてあった。** 日本語の
字句検索は trigram 索引が二文字のパターンを引けないためスキャンで答える
ことになり、答えは「埋め込みを有効にすること」だと ROADMAP 自身が書いて
いた。その答えに至るには、長いデプロイガイドの中ほどにある任意設定の節を
読み、API を有効にし、IAM ロールを付け、環境変数を置き、`reembed` を打つ
必要があった。

**中核の想定利用者(日本語で書かれた知識ベースを持つチーム)にとって、
既定の検索は最良の検索ではなかった。** それが既定だったのは、埋め込みが
外部 API を呼ぶからであって、要らないからではない。

### 1.1 プロジェクトは設定ではなく発見する

何も名指されていないとき、メタデータサーバに自分がどのプロジェクトで
動いているかを訊き、その答えで埋め込みを有効にする。Cloud SQL IAM 認証が
短命トークンを取っているのと同じ出所であり、**新しく持つものは何も無い**。

メタデータサーバが無い環境 — 手元の開発機、CI、Google Cloud の外 — は何も
変わらない。ADC の資格情報からプロジェクトを取る案は**採らない**:
手元の `gcloud auth application-default login` まで拾って、開発機が黙って
課金を始める。メタデータサーバは「Google Cloud の上で動いている」をそのまま
意味する。

### 1.2 使えるかどうかを決めるのは IAM であって、設定ではない

**ochakai は要求し、IAM が答える。** サービス ID に `roles/aiplatform.user`
が無ければ Vertex AI は答えず、そのデプロイに埋め込みは無い。設定を増やさずに
済むのはこの性質のためで、[0065](0065-identity-and-provenance.md) §1 の
「認可を持たない」と同じ考え方である — 誰が何をしてよいかを製品が二重に
持たない。

答えは**起動時に一度だけ、一語の埋め込みで**訊く。訊かずに走ると、権限の
無いデプロイは書き込みのたびに失敗を記録し続けることになる。呼び出しは
10 秒で打ち切る — cold start は API の不応答を待つ場所ではない。

### 1.3 発見された既定は落ちてよい。名指しされた設定は落ちない

| 埋め込みの出所 | Vertex AI / pgvector が使えないとき |
|---|---|
| 発見(未設定・`on`) | 警告を一行出し、**字句検索だけで動く** |
| resource name(名指し) | **起動しない** |

名指しした利用者は意味的検索を頼んでおり、黙って劣化した検索を返されるより
なぜ無いのかを知りたい。発見された既定は頼まれたものではないので、知識を
配ることを止める理由にはならない — **落ちた先は、この決定の前にその利用者が
得ていたものである。** 同じ区別が pgvector にも及ぶ。

## 2. 一つの変数が、このデプロイはどう埋め込むかを言う

`OCHAKAI_EMBEDDINGS` 一語で言う — 未設定 / `on` / `off` / Vertex AI の
モデル resource name:

```
未設定・on   メタデータサーバが答えたプロジェクトで、製品既定のモデルと
             リージョンで埋め込む(§1.1)
off          埋め込まない。Vertex AI を一度も呼ばない
resource     そのプロジェクト・リージョン・モデルで埋め込む
             projects/<project>/locations/<location>/publishers/google/models/<model>
```

かつてここには五つの変数があり、うち三つ(project・location・model)は
**Vertex AI が既に一つの文字列で言っていること**を分解して持っていた —
上の resource name が、呼び出し先の URL に現れる綴りそのものである。

**畳めたのは、五つが一つの問いの答えだったからである** — 「このデプロイ
はどう埋め込むか」。[0066](0066-four-postures-one-word.md) が四つの姿勢を
一語にしたのと同じ形である。ここで書き下せなくなるのはモデルだけを変えて
プロジェクトを既定に残すといった**部分的な設定**だが、モデルはリージョンに、
リージョンはプロジェクトに依存する(`gemini-embedding-2` は
`global`/`us`/`eu` にしか居ない)ので、三つを独立に置けることは自由では
なく、**合わない三つ組を書ける余地**であった。

**三つのどれでもない綴りは、起動エラーである。** `=true` も
`=my-project` も `=gemini-embedding-2` も起動を拒否し、三つの形を名指す。
既定に落とさないのは 0066 §4 と同じ理由で、しかもここでは外し方が二方向
ある — off のつもりで `false` と書いたデプロイは頼んでいない課金を書き込み
のたびに払い、モデルを名指したつもりで綴りを外したデプロイは**既定のモデル
で埋め込み続ける**。後者に気づくのはログではなく検索結果のほうであり、
しかも検索は動いているように見える。順位が悪くなるだけである。
**推測して外す方向がまずい種類の設定**である。

**名指すことは、要求することである。** resource name を書いたデプロイは
§1.3 の「名指し」側に立つ。意味は少し広くなった: プロジェクトだけを名指す
ことはできず、モデルを選ぶこともまた「意味的検索を頼んだ」ことになる。
それでよい。既定でないモデルを選ぶデプロイは、そのモデルで検索が効くことを
期待しており、黙って既定に落ちることを望んでいない。

Terraform 側はモジュールの変数一つ(`embedding_model`)で同じことを言う。

## 3. 幅はモデルのものであって、デプロイのものではない

**すべてのベクトルは、それが指すオブジェクトから再計算できる。** だからこそ
ベクトルのテーブルは番号付き migration の外にあり、`reembed` が存在する。
保存されている列の幅がモデルの幅と違うとき、ochakai はベクトルのテーブルを
作り直す。かつてここは起動を拒否し、`psql` で `DROP TABLE` を手で打てと
言っていた — **製品の中で唯一、スキーマ操作を利用者にやらせていた箇所**で
ある。拒否そのものは正しかった(幅の違う列に書けば全部壊れる)が、製品が
自分でできることだった。誰も問い合わせない空間を捨てて失われるのは、詰め
直すための埋め込み呼び出しだけで、知識は触れられない。

**詰め直しは自動でやらない。** 作り直したテーブルは空で、埋めることは利用者
の口座から支払うことである。作り直したときはログの一行が `ochakai reembed`
を名指しする。その間も**答えは返る** — 融合は片側が欠けても成立する。幅が
同じでモデルだけ変わった場合、古い行は消さない(検索はモデルで絞るので、
新しいモデルのクエリからは見えないだけである)。

**幅は設定ではない。** モデルごとの定数としてコードにある(現在は
`gemini-embedding-001` も `gemini-embedding-2` も 768 で、Gemini の埋め込み
は Matryoshka 表現学習なので短い出力は長い出力の接頭辞であり、一つの幅が
両方に効く)。768 は変えられない値である — 保存済みのベクトルはすべてこの
幅で書かれており、変えれば全部が別空間の遺物になる。だからこの数は設定の
既定値ではなく、テストが読み戻す**決定**である。

### 3.1 知らないモデルは、起動エラーにする

ochakai が幅を知らないモデルを名指されたとき、既定の 768 を当てにいく道は
採らない。**知らないモデルの幅は、推測である。** 外した場合に起きることは
§2 の二番目と同じ形をしていて、もっと静かである — 書き込みごとに幅違いで
拒否され、検索は字句だけになり、ログの外からは「埋め込みが効いていない」
としか見えない。エラーは知っているモデルを名指すので、直し方はメッセージの
中にある。

**型とモデルは、閉じているかどうかの問いが別である**
([0071](0071-the-recommended-type-vocabulary.md) と照らして選んだ): 型は
利用者が書いて ochakai が解釈せずに往復させる値であり、知らない綴りを拒む
理由が無い。モデルは ochakai 自身が呼び出し、その答えの幅で**列を作る**値
である。知らないものを受け取るというのは、知らない幅で列を作るということ
である。

代償は正直に言える: Google が新しい埋め込みモデルを出した日に、ochakai の
リリースを待たずにそれへ移ることはできない。待つのは表の一行であり、その
間もデプロイは既定のモデルで動き続ける。**待てるものと、取り返せないものを
比べている** — 幅の合わないベクトル空間は、埋め直しの請求書でしか取り返せ
ない。

## 4. 検索は三本のリストを融合する

- **字句** — 問い合わせを断片に割り、`search_text` がそれをいくつ含むかで
  点を付ける。**ファイル名もこのハイスタックに入る**ので、`seeds` や
  `q3-report` のような断片で、それを持つ concept が当たる。埋め込みの無い
  デプロイにもそのまま効き、バックフィル不要で全ファイルに即座に働く。
- **concept のベクトル。**
- **ファイルのベクトル** — 書き込み時に埋め込み、検索では concept ごとに
  最良の一件を取って concept のヒットに写像する。

三本を RRF で融合する。**本文でもファイルでも当たる concept は両方のリスト
から寄与を得て上がる** — 根拠ごと当たる concept が最初に来るのは意図どおり
である。

**変えない原則が二つある。**

1. **ファイルは独立して返らない。** 検索がヒットするのは所有する concept で
   あり、ファイルはその中のメタデータとして現れる。ファイル自体を検索結果と
   して返すかは「ファイルが一級か」ではなく「検索面が何を返すか」の問いで、
   ここでは決めない。
2. **ochakai はファイルを解釈しない。** OCR もキャプションもパースもしない。
   **埋め込みは決定的なエンコーダであって解釈ではない**ので、この線は越えて
   いない。ファイルを読んで本文に書き戻せば、それは本文として検索に載る。

## 5. ファイルが載るかはモデルが決める

画像と PDF のベクトルを持てるかは埋め込みモデルによる。ファイル入力を取れる
モデル(`gemini-embedding-2` 系)ではバイト列を埋め込み、取れないモデルでは
静かにスキップして**ファイル名の字句一致だけで見つかる**。テキストファイルは
どのモデルでも本文を埋め込む。

**既定のモデルは変えない。** ベクトルはクエリと同じ空間になければ比較できない
ので、画像と PDF を検索に載せるには知識ベース全体をそのモデルで運用することに
なる。既定を切り替えれば既存デプロイの保存済みベクトルが全て別空間の遺物に
なるため、移行は運用者が決める。

**既存ファイルのバックフィルはしない。** 埋め込みは書き込み時のみ、という
姿勢のままである — 後から有効にしたデプロイで埋め込まれるのは以後の書き込み
だけで、詰め直したければ `reembed` がある。字句のファイル名検索は即座に全件に
効くので、「見つからない」ことはない。

## 6. 何を差し出しているか

- **既定パスが Vertex AI に依存する。** [0003](0003-gcp-only.md) が守って
  いるのは secret-zero であって依存の数ではなく、Vertex AI の認証も ADC
  なので**持つ秘密は増えない**。増えるのは「本番で動かす」の敷居である。
- **書き込みが支出になる。** 認可が無い(0065 §1)ので到達できる誰もが書け、
  書き込みは埋め込み呼び出しを生む。逃げ道は二つあり、どちらも明示的である —
  ロールを与えない、または `OCHAKAI_EMBEDDINGS=off`。
- **cold start が一回の Vertex AI 呼び出しぶん伸びる。**
- **退役した四つの変数は黙って無視される。** 幅を既定以外にしていたデプロイ
  は次の起動でベクトルテーブルが 768 で作り直されて空で戻り、モデルを変えて
  いたデプロイは古い行が新しいモデルのクエリから見えなくなる。どちらも
  **知識は失われない**(ベクトルは導出物である)。失われるのはベクトル空間と、
  それを詰め直すための支払いである。

## 7. やらないこと

- **PDF のテキスト抽出・OCR。** 解釈はクライアントのエージェントの仕事で
  ある(§4)。
- **どのファイルが当たったかの帰属表示。** 既存の検索も字句とベクトルの
  どちらで当たったかを出していない。
- **ファイル本文の DB への複製。** バイト列は GCS のみで、Postgres に本文の
  写しを持ち込む二重管理はしない。
- **受け取る形式を埋め込みの都合で狭めること。** 0073 §6 はここに「許可
  リストは『Claude が読めて Gemini が埋め込める』交わりのまま」と書いたが、
  **書き込み側に許可リストは無い** — 0013 が置いた五形式の拒否は
  [0075](0075-the-bundle-is-the-address-space.md) の「バンドルに入ったものは
  出てくる」が撤回しており、渡されたファイルは媒体型で拒まれない。五形式が
  いま決めているのは**埋め込み呼び出しに値するのはどれか**だけで、拒否は
  受け取りではなく**配信**(何をインラインで見せるか)に移っている。
- **旧変数の互換読み取り。** 黙って読み替えれば、五つの変数が一つ増えた
  状態で生き続ける。0066 も同じ選択をしている。
- **モデルごとの幅を設定可能にすること**、および**未知のモデルを既定の幅で
  受け入れること**(§3)。
- **リージョンとモデルの組み合わせの検証。** 居ないリージョンを指せば
  Vertex AI がそう答え、名指したデプロイは起動しない — 製品が Google の
  リージョン表を持ち歩くより、答えを訊くほうが正しい。
- **モデル切り替え時の自動再インデックス**、および**次元変更後の自動
  reembed**(§3)。支払いは頼まれてから行う。
- **`references/` という慣習を ochakai が解釈すること。** SPEC §6 が名付ける
  置き場所は往復で保たれる**パス**であって、意味ではない。ここを解釈し始める
  ことは、ochakai がバンドルの中身を読んで判断する製品になることである。
- **幅ごとにベクトルのテーブルを残すこと。** 誰も読まないテーブルに行が残る
  ことは purge —「消したものは消える」— と両立しない。
