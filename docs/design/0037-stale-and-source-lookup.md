# ochakai 設計ドキュメント 0037: 宣言した期限と引用元から引けるようにする

Status: Accepted(2026-07-27)。[0036](0036-okf-schema-first.md) §5 の 2 項目
(`stale_after` のフィード、`sources` の逆引きと GIN index)を撤回して実装する。
[0025](0025-closing-the-loop.md) にフィードを 1 つ足す(性質が異なるので §3.1 で
区別を明示する)。実装は同 PR、0.14.0 で出る。
[0046](0046-bundle-address-space.md) §3.11 が `source` フィルタを frontmatter の
jsonb 上の containment に置き換える(引けるという決定は不変)
Date: 2026-07-27

## 1. 目的

0036 で `stale_after` と `sources` は封筒フィールドになった。**書けるように
なったが、引けない。**

- `stale_after` は詳細画面を開けば「Stale since 2026-12-31 — due for a
  re-check」と出るが、**期限切れのエントリを一覧する手段が無い**。1 件ずつ
  開いた人にしか見えないということは、誰も気づかないということである。
  期限を宣言しても運用に乗らない。
- `sources` は「この外部資料に由来するエントリ」を引けない。引用元が改訂
  されたとき — 会計方針が変わった、スキーマドキュメントが更新された —
  影響範囲を出す手段が無い。これは 0034 §3.7 が封筒化の再検討条件として
  挙げた例そのものであり、0036 はその前提(封筒に持つこと)を満たしただけで
  逆引き自体は作っていなかった。

どちらも列にはあるが、**WHERE 句にも ORDER BY にも一度も現れない。**

0036 §5 は両方を「やらないこと」に置き、`sources` の逆引きは「実装する
ときに GIN index と併せて設計する」、`stale_after` のフィードは「実際に
使われ始めてから 0025 の改訂として検討する」と条件を書いていた。両方とも
本ドキュメントで満たす。

## 2. 決定

### 2.1 `sort=stale_after` — 期限切れフィード

`sort` の値に `stale_after` を足す。**`stale_after` が今日以前のエントリ
だけ**を、超過の大きい順(日付の古い順)に返す。

```sql
WHERE ... AND stale_after IS NOT NULL
  AND stale_after <= (now() AT TIME ZONE 'UTC')::date
ORDER BY stale_after ASC, id
```

- **未来の期限は入れない。** 0025 がフィードに求めた性質は「レビュアーが
  終わらせられるキュー」であって、増える一方の台帳ではない。まだ切れて
  いない宣言は作業ではないので入れない。既存の `sort=failed` が
  `u.failed > 0` で絞るのと同じ形である。
- **「今日」は UTC で、明示的にそう書く。** 0036 §3.9 が `stale_after` を
  素の `date` 列にしたのは、陳腐化の判定にタイムゾーンを持ち込まないため
  だった。ところが `current_date` はデータベースセッションの `TimeZone` に
  従うので、そのまま使うとまさにその判断を接続設定に委ねてしまう —
  **同じエントリが、ある環境では期限切れで別の環境ではそうでない**という
  ことが起こる(実装中に実際に踏んだ: JST の開発機と UTC の DB で 1 日
  ずれた)。`(now() AT TIME ZONE 'UTC')::date` と綴って固定する。
  日付粒度の助言的な信号なので、UTC より東の地域では最大数時間の遅れが
  出るが、環境によって答えが変わるよりはよい。
- 空になりうる。宣言を持つエントリが無い、あるいは全部まだ有効なら 0 件で
  あり、それが正常な状態である。

### 2.2 このフィードは verify では空にならない(0025 との違い)

**0025 の 2 フィードとは空き方が違う。** ここは混同すると運用が壊れるので
明示する。

| フィード | 並ぶ根拠 | 空にする操作 |
|---|---|---|
| `sort=verified_at` | サーバーが観測した検証時刻 | **verify**(新しい `verified_at` が入る) |
| `sort=failed` | サーバーが集計した失敗報告 | **verify**(0025 §6.2) |
| `sort=stale_after` | **書き手が宣言した期限** | **エントリを編集する** |

`stale_after` は書き手の宣言であり、サーバーが観測した事実ではない。
**verify しても `stale_after` は動かない** — 動かしたら、サーバーが書き手の
宣言を書き換えたことになる(0036 §2.2 の provenance と同じ理屈)。
期限切れを解消する正しい操作は「再確認したうえで期限を引き直す」であり、
それは内容の変更、すなわち update である。

したがって典型的な運用は **verify(確認した事実を記録)+ update(期限を
引き直す)の 2 手**になる。verify に `stale_after` を自動で延ばさせる案は
採らない — 何日延ばすかはサーバーが知らないし、知るべきでもない。

### 2.3 `source` フィルタ — 引用元からの逆引き

`type` / `status` / `tag` と同じ位置に `source` フィルタを足す。値は
**source の `resource`(引用先の URI / パス)完全一致**。

```
GET /api/v1/knowledge?source=https://wiki.example/finance/revenue-recognition
```

- **フィルタであってフィードではない。** `q` とも `sort` とも組み合わせ
  られる(「この資料を引用していて、かつ期限切れのもの」が 1 回で引ける)。
  0036 §2.3 が言う「別軸」は、まさにこう直交させるべきという意味である。
- **`source` だけを指定した場合は一覧になる。** 「この資料に由来するのは
  何か」には順位づけの根拠になるテキストが無いので、検索ではなく id 順の
  一覧を返す(`ListBySource`)。空クエリの検索は従来どおり 400 のままで、
  `source` があるときだけこの経路に入る。これが逆引きの主用途である。
- **`resource` だけで照合し、`id` では引かない。** `sources[].id` は本文の
  footnote から参照するための**そのドキュメント内のキー**であって、
  エントリをまたいで同じものを指す保証がない。跨いで照合できるのは
  `resource` だけである。
- **前方一致・部分一致はしない。** 完全一致に限る。理由は 2 つ:
  containment(`@>`)なら GIN index がそのまま効くこと、そして「この URL が
  変わった」という問いに対して部分一致は誤検出を増やすだけであること。
- **単一値で、繰り返せない。** `tag` は繰り返せて OR で結合する
  (`tags && $n`)が、`source` は 1 つに限る。用途が「ある 1 つの資料が
  変わった」であることに加え、OR の選言は `@>` の containment に落ちず
  **GIN index が効かなくなる**。複数を引きたい需要が出たら、そのとき
  索引ごと設計し直す。

### 2.4 索引(マイグレーション 0021)

```sql
CREATE INDEX knowledge_sources ON knowledge USING gin (sources);
CREATE INDEX knowledge_stale_after ON knowledge (stale_after)
    WHERE deleted_at IS NULL AND stale_after IS NOT NULL;
```

- `sources` は既定の `jsonb_ops` GIN。`sources @> '[{"resource": "…"}]'` を
  そのまま拾う。0036 §3.13 が「引くものが無いのに索引だけ先に作らない」と
  して見送った索引であり、引くものができたので張る。
- `stale_after` は部分索引。宣言を持たない行(大多数になるはず)を索引から
  外し、フィードの `ORDER BY stale_after` と `<= current_date` の両方に効く。
- どちらも**データは書き換えない**。列も足さない。`updated_at` は動かない。

### 2.5 各サーフェス(0015 §4)

- **REST = yes。** 唯一の契約。`sort=stale_after` と `source` パラメータ。
- **CLI = yes。** `ochakai search --sort stale_after` と `--source <uri>`。
- **MCP = yes(2 つとも)。** 0015 の原則は no だが、どちらもエージェントの
  ループに乗る:
  - 期限切れフィードは、既に `get_context` の指示が「`stale_after` を
    過ぎたエントリは*間違い*ではなく*再確認が必要*として扱え」と書いている
    知識を、**能動的に拾いに行く**手段である。書き戻しループを回す
    エージェントが自分で期限切れを見つけて直せる。
  - 逆引きは「この資料が変わった → 影響範囲を出して直す」という保守作業
    そのもので、人間が一覧を作ってエージェントに渡すより、エージェントが
    1 コールで引くほうが短い。
  - **新しいツールは作らない。** どちらも `search_knowledge` の引数
    (`sort` の値 1 つ、`source` 1 つ)として載る。0015 §2 の
    「ツール数は予算」に触れない。
- **Web UI = yes。** 期限切れフィードは既存の 2 フィードと同じチップと
  ルートで。逆引きは詳細画面の Sources 欄から、その資料を引用している
  他のエントリへ辿れるようにする — 人がその資料を見ている、まさにその
  場所に置く。

## 3. 壊れるもの

**無い。** 追加のみである。

- `sort` の値が 1 つ増える(既存の 3 値は不変)。
- クエリパラメータ `source` が増える。指定しなければ従来どおり。
- マイグレーション 0021 は索引 2 本を作るだけで、列もデータも変えない。
  既存行の `updated_at` は動かないので ETag も無効化されない。

## 4. やらないこと

- **`verify` が `stale_after` を自動で延長すること**(§2.2)。何日延ばすかは
  サーバーが知らない。
- **期限切れエントリを検索結果から隠す/降格すること。** 期限切れは
  「再確認が必要」であって「間違い」ではない(SPEC §5.5)。フィードで
  浮上させるだけで、通常の検索順位には触れない。
- **期限切れの通知・メール・webhook。** ochakai は浮上させる面を持つだけで、
  誰にいつ知らせるかは持たない(0025 §5 の「権限で縛らない」と同じ姿勢)。
- **`source` の前方一致・部分一致・正規表現**(§2.3)。
- **`sources[].id` での逆引き**(§2.3)。
- **未来の期限のカレンダー表示**(§2.1)。「今月切れるもの」を見たい需要が
  実際に出てから、フィードとは別の面として考える。
- **`usage_window` / `usage_count` での絞り込み。** これらは consumer が
  重み付けに使う信号であって、ochakai が採点も比較もしない(0036 §3.7)。
