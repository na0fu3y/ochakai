# ochakai 設計ドキュメント 0124: ディレクトリは、自分の管理者を持てる

Status: Accepted(2026-08-23)。[0109](0109-a-directory-has-readers-and-writers.md) §3 の
「ポリシーを編集できるのは `OCHAKAI_ADMINS` が名指す者だけ」を、**一つの
subtree について**改訂する — 床は動かない。0122 が「最初の一行を置ける
のも管理者だけ」と閉じた扉の、**内側に一枚**扉を足す決定である。
[0120](0120-the-policy-is-replaced-only-as-it-was-read.md) の前提条件と、
[0123](0123-the-numbers-say-what-they-counted.md) の宣言の両方が、
この形のために要る。[0119](0119-an-operated-fleet-is-deployments-or-directories.md) §5 の
宿題の二番目、その三つ目
Date: 2026-08-23

## 1. 何が高すぎたか

**ディレクトリを一つ預けるのに、バンドル全部を預けることになっていた。**

0109 §3 の床は正しい — ポリシーを編集できる者をポリシーの中で決めれば、
編集できる者は自分に何でも付与できる(回転扉)。だから
`OCHAKAI_ADMINS` は設定である。**それは文書**全体*について正しく、
一つの subtree については粗すぎた。**

具体的に払っていたもの:

- **チームに自分のディレクトリの境界を任せると、他の全チームの境界を消す
  権限も渡す。** 文書は丸ごと置き換わるので([0109](0109-a-directory-has-readers-and-writers.md) §2)、
  悪意が無くても事故で起きる。
- **組織ごとに一行足す自動化**([0119](0119-an-operated-fleet-is-deployments-or-directories.md))は、
  そのために**恒久的に完全な管理者**でいなければならない。受け入れの
  処理が、既存の全組織を締め出せる資格を持ち続ける。

## 2. 決定: `may_admin` は prefix に縛られた三つ目の力

付与は二つの力(読む・書く)を持っていた。三つ目を足す —
**この prefix 以下の*規則そのもの*を編集してよい。**

- **`may_write` を含み、それは読むことを含む。** 読めないディレクトリを
  administrate するのは、0109 §2 が断った盲打ちである。
- **根には置けない。** `prefix: ""` の `may_admin` は「ポリシー全体を誰が
  編集できるか」をポリシーの中に置くことで、それが回転扉そのものである。
  **書かれた場所で断り**、断りは `OCHAKAI_ADMINS` を名指す。
- **床は一字も動かない。** prefix 管理者を作れるのは完全な管理者だけで、
  取り上げられるのも完全な管理者だけである。prefix 管理者が完全な管理者に
  なる道は無い — 外に規則を書けず(§3)、設定は ochakai を通しては誰も
  触れない(0109 §3)。

## 3. 見えるものと、置き換えられるもの

**prefix 管理者が読むのは、自分が編集してよい規則だけである。** 残りは
他人の名前と他人のディレクトリで、そこはスコープ外の読みが 404 である
のと同じ理由で見せない(0109 §4)。

**そして、丸ごと置き換える文書との組み合わせが危ない。** 見えない規則を
含まない文書をそのまま PUT すれば、素直な実装は**他人の規則を全部消す**。
`ochakai access --json > f; $EDITOR f; ochakai access -f f` が、その一番
普通の手順である。

だから: **自分の subtree の外にある規則は、書き込みを跨いで保たれる。**
文書に入れられなかったものについて、その文書は何も言っていない。

- **保存と前提条件は同じトランザクションの中で行う** — 0120 が閉じた窓を
  開け直さないため、分割も比較も store の中、advisory lock の下である。
- **版は読んだものを覆う。** prefix 管理者が受け取る `ETag` は自分の
  subtree の規則のハッシュで、**見えない規則が動いても 412 にならない**。
  見えないものの変化で失敗する前提条件は、直しようがない。
- **外の規則を送ったら 403 で、黙って落とさない。** 落とせば、呼び出し元は
  置いたつもりの境界を持たないまま動き続ける(0065 §3 の「静かな降格」)。

**自分より浅い規則は自分のものではない。** `teams/growth` の管理者は
`teams/growth/metrics` の規則を持ち、`teams` の規則は持たない —
**自分を含んでいる規則を編集できれば、subtree はバンドルへ育つ。**

## 4. 塞げないもの

**自分の subtree への実効的なアクセスは、自分に見える規則より広いことが
ある。** `prefix: ""` に `*` の読み取りを与えた規則は `teams/growth` にも
効くが、`teams/growth` の管理者にはそれが見えず、消せもしない。

これは欠陥ではなく §2 の帰結である — 浅い規則はそれを置いた管理者のもの
である — が、**言わずに配れば「自分のディレクトリは自分が決めている」と
読まれる**。0109 §4.1 が本文の id について取ったのと同じ扱いで、ここに
書いておく。約束しているのは**規則を編集する権限の範囲**であって、
その subtree に誰が到達できるかの全体像ではない。

## 5. 面

**数はどれも動かない。**

| 面 | 現れ方 |
|---|---|
| REST | `AccessRule` に `may_admin` が増える。スキーマの属性であって、操作もパラメータもヘッダも増えない |
| CLI | `ochakai access` の文書に一つ増えるだけ。**フラグは増えない** |
| MCP | **載せない**(0109 §5 のまま) |
| Web UI | 表に「付与」列が増え、編集の文書が同じ欄を運ぶ。根の `may_admin` はページ側でも断る |
| ENV / VOCAB | 動かない — `may_admin` は列挙語彙ではなく真偽値である |

移行 0045 は追加的で既定 false なので、**この移行の前に書かれたポリシーは
一字も意味が変わらない。**

## 6. 検査する不変条件([0035](0035-verifiability.md))

- prefix 管理者の読みが、自分の subtree の外の規則を一行も運ばないこと。
- prefix 管理者の書き込みが、**見えなかった規則を保つ**こと。
- 外側の prefix を含む文書が **403** で、部分的に適用されないこと
  (根・他人の subtree・自分の一つ上、の三つ)。
- 根の `may_admin` が、書かれた場所で断られること。
- prefix 管理者の版が、全体の版と**異なる**こと — 同じなら、見えない
  変化で 412 になる。

## 7. やらないこと

- **prefix 管理者に export・`move`・`reembed` を開くこと。** それぞれ
  0109 §3 と [0123](0123-the-numbers-say-what-they-counted.md) §4 の理由が
  そのまま効いている。`stats` は 0123 が既に絞っており、prefix 管理者も
  自分の数を読める。
- **`may_admin` を持つ者に、自分より浅い規則を見せること**(§3)。
- **付与の履歴**(0109 §7 のまま)。誰が誰に何を預けたかを追いたければ、
  ポリシーを git に置く経路が既にある。
- **`OCHAKAI_ADMINS` に prefix の綴りを足すこと。** 設定は「誰が床か」を
  答える場所で、**どのディレクトリを誰に預けたかはポリシーの側の事実**で
  ある。設定に書けば、預け先が増えるたびに再デプロイになる。
