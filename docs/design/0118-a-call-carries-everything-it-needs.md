# ochakai 設計ドキュメント 0118: 一回の呼び出しが、必要なものを全部運ぶ

Status: Accepted(2026-08-23)。`/mcp` を stateless streamable HTTP にし、
MCP プロトコル 2026-07-28 で答えるようにする。
[0067](0067-four-faces-and-what-they-decline.md) §3 の「MCP 面は streamable
HTTP」を改訂する — 面もツールも一つも動かず、変わるのは転送の姿勢だけである。
[0065](0065-identity-and-provenance.md) §4 の「無ければ initialize の
`clientInfo` をフォールバックとして読む」を改訂する(§3)。同じ
プロトコルが list に足した TTL のヒントを ochakai 自身が答えること(§7)は
この記録の内側の規則で、未リリースのうちにここへ畳んだ(0048 §2.3)。
Date: 2026-08-23

## 1. 何が起きていたか

ochakai は MCP を [SDK](https://github.com/modelcontextprotocol/go-sdk) で
話し、その SDK は v1.7.0 で 2026-07-28 に対応した。にもかかわらず、
**ochakai に 2026-07-28 で話しかけることはできなかった**。SDK は
stateless なハンドラからしか新プロトコルを出さず、session を持つ
ハンドラは 2025-11-25 に上限を掛ける。ochakai は `nil` オプションで
ハンドラを組んでいたので、既定の stateful のまま — 最新の SDK を積み、
最新の仕様を拒む状態だった。

黙っていたのが問題である。バージョン交渉は成功し、ツールは動き、
どこにもエラーは出ない。**新しいクライアントは、自分が古い方に
降ろされたことを ochakai から知らされない。**

session を持っていたことの代償は他にもあった。SDK の `SessionTimeout`
は既定が 0、すなわち **idle な session は永遠に閉じない**。そして
session はインスタンスのメモリにあるので、`max_instance_count` を
2 にした瞬間に壊れる — 今それが 1 なのは、そう決めたからではなく、
そう決めざるを得なかったからである。

## 2. 決定

`/mcp` は stateless で提供する。`Mcp-Session-Id` は発行も参照もせず、
GET と DELETE は 405(`Allow: POST`)、一回の POST が protocol version・
クライアントの名前・capabilities を `_meta` で自分で運ぶ。

**ochakai が失うモードは、一度も使っていないモードである。** roots も
sampling も logging も使わず(どれも 2026-07-28 で非推奨になった)、
サーバから客への要求も無く、通知も要らない。ochakai の状態はナレッジ
ベースであって接続ではない — それは 0081 が「ochakai とは何か」を
決めたときから変わっていない。**session は、この設計に最初から
無かったものの置き場だった。**

得るものは三つある。新プロトコルで答えられること。session が溜まらない
こと。そして**インスタンスを増やせること** — round-robin の後ろに
何台並べても、どの一台も前の呼び出しを覚えていない。0003 が選んだ
Cloud Run の姿勢に、ようやく転送が追いついた。

## 3. 代償: 古いクライアントの `clientInfo`

0065 §4 は producer をこう決めていた — ヘッダ `Ochakai-Producer` が
契約で、無ければ MCP の `clientInfo` をフォールバックとして読む。
2026-07-28 では `clientInfo` は毎回の `_meta` に乗るので、**新しい
クライアントでは何も変わらない**。

変わるのは古いクライアントである。2025-11-25 では名乗りは `initialize`
にしか無く、stateless ではその `initialize` は使い捨ての session で
完結して消える。後続の `tools/call` は別の POST として届き、名乗りは
どこにも載っていない。**実測した**: 2025-11-25 を手で書いたクライアント
の呼び出しは、stateful では `claude-desktop/1.2` を記録し、stateless
では producer が空になる。

これは静かな劣化であり、[0117](0117-a-person-recorded-as-a-process-says-so.md)
が「静かな降格は明示的な失敗より常に高くつく」と書いたばかりの形に
似ている。**それでも受け入れる**理由は、0117 との違いにある。0117 で
黙って書き換わっていたのは **identity** — 誰が書いたか — であり、
これは台帳の正しさそのものである。ここで落ちるのは producer、すなわち
**自称**であって、0065 §4 が「認可でも identity でもない、記録である」
と位置づけたフィールドである。`created_by` の人も process も一字も
変わらない。

そして代替がある。`Ochakai-Producer` はどのクライアントからも送れて、
0065 §4 がもともと「契約はここだけ」と呼んだ経路である。落ちるのは
**契約ではなく好意**のほうで、しかもクライアントが 2026-07-28 に
移った日に自動的に戻る。

**畳んだもの**: この決定は表面を一つも増やさない。エンドポイントも
ツールも環境変数も同じ数で、`Mcp-Session-Id` という「クライアントが
実装しなければならないプロトコル」が一本消えた。

## 4. 選ばなかった道

**stdio 橋に `initialize` を覗かせて `Ochakai-Producer` を付ける。**
古いクライアントの名乗りを ochakai が制御できる経路の分だけ取り戻せる。
断ったのは、0067 §3 が `mcp-stdio` を「JSON-RPC を解釈しない経路」と
決めているからである — 解釈しないことは、後から仕様に足された何かが
橋を素通りできる理由そのものだった。**半年で消える劣化のために、
その性質を恒久に手放すのは釣り合わない。**

**stateful のまま据え置き、クライアントの移行を待つ。** 新プロトコル
で話しかけられないことがどこにも現れないので、待っている間に何も
学べない。そして待つ理由が producer であるなら、それは §3 のとおり
自称であり、待つ側の重さが足りない。

**`allowsessionsinstateless=1`(SDK の互換フラグ)で両立させる。**
stateless のまま古い session ヘッダも受け付ける。SDK が v1.9.0 で
消すと宣言している逃げ道であり、消える日に同じ判断をもう一度する
ことになる。今する。

## 5. 面ごとの着地(0067)

- **REST**: 変化なし。`/api/v1` は MCP の転送とは無関係である。
- **MCP**: これ自体。ツールは 6 本のまま、常駐バイトも動かない。
- **CLI**: 変化なし。`mcp-stdio` は SDK のクライアント転送を使うので、
  新プロトコルのヘッダ(`Mcp-Method`・`Mcp-Protocol-Version`)は SDK が
  付ける。
- **Web UI**: 変化なし。`ochakai ui` / `serve-ui` は `/mcp` をそのまま
  前段に通すだけで、session を読んでいなかった。

## 6. 検証

`internal/mcpserver/stateless_test.go` が三つを外から確かめる。
`server/discover` の `supportedVersions` に 2026-07-28 が居ること
(stateful に戻せば落ちる)、`initialize` の応答が `Mcp-Session-Id` を
持たないこと、GET と DELETE が 405 と `Allow: POST` を返すこと。
古いクライアントが今も通ること自体は二つ目のテストが `initialize` の
成功で言っている。

## 7. 一覧は、いつまで持つかを言う

2026-07-28 は list 系の結果に `ttlMs` と `cacheScope` を足した。SDK は
その二つを応答のたびに埋める — `cacheScope` は `"public"`、`ttlMs` は 0
— そして仕様は 0 を「直ちに古いものとみなすべき」と読む。つまり ochakai
は全クライアントに「この一覧はいま古い」と言っていた。**誰もそう決めて
いない。** ゼロ値がそう言っていただけで、`omitempty` が無いので黙って
省略されもしない — 0064 §2 が未知キーについて言ったのと同じ、規則を
書いていない場所で機構が答えている形である。

**構築時に決まる三つの一覧 — `tools/list`・`resources/list`・
`resources/templates/list` — は 5 分持つと答える。** `newServer` が
登録したあとに登録するものは無いので、一つのプロセスの中で一覧は定数で
ある。数字が答えているのは「一覧がいつまで正しいか」ではなく、**プロセス
が入れ替わったあと古い答えをいつまで信じてよいか**であり、それを変える
のはリリースしか無い。5 分はその尺度に対して短く、接続に対して長い:
§2 の stateless な転送は一覧を掛けておくセッションを与えないので接続
ごとに引き直す実装は引き続け、5 分はその一まとまりの作業を覆う。一方で
改名された名前が答え続ける一リリース(0088)の内側に収まるので、古い
一覧を掴んだままアップグレードを跨いだクライアントが握っているのは、
まだ動く名前である。

**`resources/read` は 0 のまま。** 線は「一覧かどうか」ではなく**知識
かどうか**である — concept は誰かが書けば変わり、カーソルを持つ途中の
ページは歩いている場所であって掴んでおくものではない。**`cacheScope` は
SDK の既定 `public` が正しい**: 一覧は姿勢の性質であって呼び出し元の
性質ではなく、認可は呼び出しごとに `service` で効く(0109)。実装は
一行も無いが、0109 のあとでは確かめる価値のある一致なのでテストが
固定しており、付与が一覧を細らせる日にその行が落ちる。

買っていないもの: エージェントのコンテキストは一バイトも減らない
(MCP-BYTES はツールの項目を数えており、応答の封筒ではない)。断った
もの: デプロイが選べる値(環境変数が一つ増え、正しい値はここにある
情報から導かれる)、`prompts/list`(登録していない)、`initialize` の
結果(接続ごとに一度で、クライアントの識別を運ぶ — §3)。
