# ochakai 設計ドキュメント 0040: デプロイ単位の read-only

Status: Accepted(2026-07-27)。[0002](0002-authn-authz.md) の「認可を持たない」
を維持したまま、デプロイ全体を読み取り専用にできるようにする。0002 を改訂は
しない — §2.1 でその理由を述べる。[0015](0015-surface-consistency.md) の
面一貫性に従い 4 面すべてに現れる。§2.2 の「利用測定は凍結の外」は
[0049](0049-instance-metrics-and-search-misses.md) の検索ミスにもそのまま
及ぶ(§3.4)。**綴りは [0060](0060-one-word-for-the-posture.md) が改訂
した** — `OCHAKAI_READ_ONLY=true` は `OCHAKAI_MODE=read-only` になった。
この記録が決めたこと(何を拒否するか、認可ではないこと、4 面すべてに
現れること、利用測定は凍結の外)はどれも不変である
Date: 2026-07-27

## 1. 目的

ochakai には**読み取り専用にする手段が無い**。0002 の帰結として
「到達できた者は読み書きできる」だけであり、`OCHAKAI_READ_ONLY` に相当する
つまみは存在しない。そのため次のどれもできない。

- **公開デモを置けない。** SECURITY.md は「publicly invokable で動かしては
  ならない」と書き、README は「それは misconfiguration であってデプロイ
  モードではない」と書いている。この 2 つが正しい以上、現状の ochakai で
  「誰でも触れるデモ」を立てることは、自分の掲げた方針を破ることになる。
  評価者に製品を見せる手段が、スクリーンショットしか無い。
- **参照専用のインスタンスを配れない。** 社内で「このナレッジベースは
  読むだけ」という配り方(BI ツールの読み取り専用レプリカに相当)ができない。
- **凍結ができない。** 移行中・監査中に「今の内容を固定したい」ときに、
  Cloud Run IAM で到達そのものを切る以外の方法が無い。読めなくなるのは
  やり過ぎである。

## 2. 決定

**`OCHAKAI_READ_ONLY=true` を足す。真のとき、そのデプロイはナレッジを
一切変更しない。**

### 2.1 これは認可ではない

0002 が持たないと決めたのは**認可**、すなわち「誰が何をしてよいか」を
呼び出し元ごとに判定する機構である。read-only はそれではない。

- **呼び出し元を区別しない。** 全員に等しく効く。運用者にも、サービス
  アカウントにも、IAP を通った人間にも同じように効く。「あなたには書けない」
  ではなく「**このデプロイは書かない**」である。
- **provenance の解釈を変えない。** 誰の書き込みも記録しないので、
  信頼の判断材料は増えも減りもしない。
- **エントリ単位の権限を導入しない。** 特定のエントリだけ守る、という
  使い方はできない。できてしまえばそれは認可であり、その線は越えない。

したがって 0002 は改訂しない。0002 が退けた「呼び出し元によって挙動を
変える機構」は、依然として無い。

### 2.2 強制点はサービス層に 1 つだけ置く

REST と MCP は同じ `service.Service` を通る。したがってそこで拒めば、
**どの面からも漏れない**。ルーティング側で HTTP メソッドを見る実装は、
新しい書き込みエンドポイントを足した人が middleware の存在を知らなければ
穴が開く。

対象は知識を変えるすべて: `Create` / `CreateKeepingCurated` / `Update` /
`Delete` / `Verify` / `Purge` / `Move` / `ReportOutcome` / `Attach` /
`Detach` / `Reembed`。

**例外は利用テレメトリである。** 検索ヒットや取得回数の記録
([0029](0029-usage-recording-off-the-read-path.md))は read-only でも
動き続ける。これは
呼び出し元が書いた内容ではなく**サーバー自身の観測**であり、止めると
`sort=usage` のフィードが凍って製品が壊れて見える。デモで見せたいものが
まさにそのフィードである以上、ここを止める判断はしない。

### 2.3 各面での現れ方(0015)

| 面 | 現れ方 |
|---|---|
| REST | 書き込みは **403**。全 `/api/v1` 応答に `Ochakai-Read-Only: true` を付ける(`Ochakai-Unchanged` と同じ、ヘッダで状態を伝える既存の作法) |
| MCP | 書き込みツールを**そもそも登録しない**。常に失敗するツールを見せるのは、agent の context を無駄に食わせたうえで失敗させることであり、0015 §3.1 のツール予算の考え方に反する |
| CLI | `whoami` が read-only と表示する。書き込みコマンドはサーバーの 403 をそのまま見せる |
| Web UI | Verify / Reject / Edit / New を出さない。押せるが必ず失敗するボタンは嘘である |

MCP がツールを消し、REST がヘッダで告げるという非対称は意図的である。
MCP には能力を宣言する仕組み(tools/list)があり、REST には無い。
それぞれの面が既に持っている語彙で伝える。

## 3. 検査する不変条件

[0035](0035-verifiability.md) に従う。

- **書き込みメソッドの網羅。** read-only のサービスに対して、上記の
  すべてのメソッドが `ErrReadOnly` を返すことをテストで確かめる。
  メソッドを足した人がここに足し忘れたら落ちる。
- **MCP のツール集合。** read-only のサーバーが提供するツールが、
  読み取りツールのみであることを確かめる。
- **REST の 403 とヘッダ。** 書き込みエンドポイントが 403 を返し、
  読み取りが 200 のままであることを確かめる。

## 4. やらないこと

- **エントリ単位・呼び出し元単位の read-only。** §2.1 のとおり、それは
  認可である。必要なら Cloud Run IAM で到達を分ける。
- **実行時の切り替え。** 環境変数のみ。API で切り替えられれば、それを
  叩ける者が解除できてしまい、保証が保証でなくなる。
- **read-only を安全機構として売らない。** これは*運用モード*であって、
  敵対的な相手に対する防御ではない。到達制御は依然として Cloud Run IAM の
  仕事である(0002)。公開デモに使う場合、守っているのはナレッジの内容で
  あって、インスタンスそのものではない。
- **書き込み系 REST エンドポイントの削除。** 404 ではなく 403 を返す。
  経路が消えたのではなく、このデプロイが断っている、という区別が要る。
