# ochakai 設計ドキュメント 0120: ポリシーは、読んだままの姿でだけ置き換わる

Status: Accepted(2026-08-23)。[0109](0109-a-directory-has-readers-and-writers.md) §2 の
「文書一枚を丸ごと置き換える」に**前提条件**を足す — 置き換えの規則も、
付与だけを持つことも、管理者の床も動かさない。
[0030](0030-optimistic-locking.md) が concept に置いた機構の、二つ目の文書への
適用であり、0109 §2 が自分で「If-Match が既に解いている」と書いた当のもので
ある。[0119](0119-an-operated-fleet-is-deployments-or-directories.md) §5 の
宿題の二番目、その最初の一つ
Date: 2026-08-23

## 1. 何が起きるか

**ポリシーは読んで、直して、丸ごと返す文書である。** 二人が同じものを読み、
片方が `teams/sales` の行を足し、もう片方が `teams/support` の行を足すと、
**後に保存したほうの文書には前者の行が無い。** 400 も 409 も出ない —
どちらの文書もそれ自体は正しく、サーバは言われたとおりに置き換える。
消えたことに気づく契機は、消された側の人が「読めない」と言ってくることだけ
である。

0109 §2 はこの形を予期して、**それが concept では解けていることまで書いて
いた** — 「per-row にすれば避けられるように見える並行編集の問題は、
If-Match が concept について既に解いているものである」。予期して、そちらには
足さなかった。

**足す理由は 0119 である。** 付与を置くのが人ではなく自動化になると、この
競合は例外ではなく**通常の経路**になる。組織を受け入れるたびに一行足す
処理は、まさに「読んで、足して、返す」であり、二つが同時に走れば片方の
組織は境界の外に落ちる。落ちた側は 404 を見るので、**障害は境界が効き
すぎた形で現れ、原因の側からは何も見えない。**

## 2. 決定: `If-Match` は concept と同じ意味を持つ

`PUT /api/v1/access` は `If-Match` を受ける。

- **在れば前提条件。** 読んだときの版をポリシーがまだ持っている間だけ
  置き換わり、そうでなければ **412** で、**何も書かない**。符号は
  `precondition_failed` で、[0083](0083-an-error-carries-a-code.md) の
  語彙は一つも増えない。
- **無ければ後勝ち。** concept と同じで、既存の呼び出し元は一つも壊れない。
- **`*` は 400**(0064 §20.1 のまま)。
- **`If-None-Match` は 400 である。** ポリシーは常に存在する一枚の文書で、
  作成専用の前提条件には**意味する対象が無い**。黙って無視するのではなく
  名指すのは 0064 §2 の規則そのものである。

**版は前提条件と同じトランザクションの中で読む。** 外で読んで比べれば、
比較と置き換えの間に窓が開く — 閉じようとしている当のものである。
空のポリシーには行が無く行ロックが効かないので、書き込みは
advisory lock を取る。**空の状態こそ二つの自動登録が最も競う状態**だから
であり、そこを守らない前提条件は、いちばん要る場面で効かない。

## 3. 版は付与を数え、時刻を数えない

版は**付与(prefix・principal・may_write)だけ**のハッシュである。

`granted_at` と `granted_by` は書くたびに動く。それを含めると、**付与が
一つも変わらない書き込みが、誰かの持っている前提条件を無効にする** —
0030 が concept について既に断った形で、あちらは verify も却下もファイル
添付も版を動かさない(`etagOf` は文書だけを見る)。同じ規則をここでも
使う。

**順序はこちらで課す。** 行は両側から整列して届く —
`ValidateAccessRules` は Go で、store の問い合わせは SQL で — が、
**この二つは同じ関数ではない**。SQL 側を決めるのはデータベースの照合順で
あり、二つのデプロイが一つのポリシーを二通りにハッシュしても、どちらも
間違っていない。版は集合についての約束なので、集合を先に一つの順序へ置く。

**空のポリシーにも版がある。** これは副産物ではなく §2 の要点で、
付与を持たないデプロイに最初の一行を置く書き込みが、二つの自動登録が
最も競う書き込みだからである。名指すものが無ければ、そこには前提条件を
置けない。

## 4. 版はヘッダにも本文にも載る

`ETag` に載り、応答本文の `version` にも載る。**二つ目の綴りではなく、
concept が既にしていることである** — あちらは `summary.content_hash` が
本文にあり、同じ値が `ETag` に立つ。買っているのは、`ochakai access --json`
が出力した文書が、**それを条件付きで書き戻すのに要るものを全部持っている**
ことである。

**要求本文の `version` は読まない**(契約は `readOnly` と宣言する)。
前提条件はヘッダであり、本文の版を二つ目の経路にすれば、二つが食い違った
ときにどちらが勝つかという問いが増える。**受け取って無視するのは、
`--json` の出力が `-f` の入力である**という 0109 の約束を保つためだけの
ことで、宣言してあるので黙ってはいない(0112 と同じ線)。

## 5. 面

**一つも増えない。**

| 面 | 現れ方 |
|---|---|
| REST | `If-Match` を `PUT /api/v1/access` に、`ETag` を両操作の応答に、412 を一つ。**`HEADER` は 13 のまま** — この面は名前で数えており、`ETag` も `If-Match` も既にそこにいる |
| CLI | `ochakai access --if-match <version>`。**`FLAG` は 28 のまま** — `--if-match` は `put` と `delete` の綴りで、面は名前を数える。読みは版を最後の一行に出す(`--json` では `.version`) |
| MCP | **載せない。** 0109 §5 がポリシーそのものを載せていない |
| Web UI | 読んだ版を保存時に送り、412 は「別の誰かが保存した、上書きせずに止めた」と言う。**書いたものは欄に残す** — concept のエディタが 0030 の前提条件で既に取っている形である |

**同じ数え方が、この記録の代金を零にしている。** 面の天井が名前を数えて
いるのは偶然ではなく、`If-Match` が[0030](0030-optimistic-locking.md) の
全部を運ぶ一語だからで([docs/surface.md](../surface.md) の HEADER 節)、
**二つ目の文書に同じ語を使うことが、綴りを増やさない唯一の方法**である。

## 6. ついでに直したもの — 空のポリシーは `null` を返していた

これを wire で試す統合テストを書いて初めて出た: 付与を一つも持たない
デプロイの `GET /api/v1/access` は `{"rules": null}` を返しており、契約は
`rules` を**必須の配列**と宣言している。**すべてのデプロイが最初はその
状態である**にもかかわらず、空のポリシーを HTTP 越しに読むテストが一つも
無かったので、契約チェックには見るものが無かった。spec から生成した
クライアントは、いちばん普通の応答を拒んでいたことになる。

0035 の言う「規約を信じるのではなく外から読む」検査が、**書かれた
テストの範囲でしか効かない**という当たり前の事実の実例である。修正は
`[]` を返すことで、既存の呼び出し元への影響は無い(`null` を読めた
クライアントは `[]` も読める)。

## 7. 採らなかった案

- **行ごとの操作**(`POST`/`DELETE` で一行ずつ)。0109 §2 が断ったままで
  ある — 面が三つになり、それでも全体をレビューできる形が別に要る。
  そして**この記録が足した前提条件は、行ごとにしても要る**: 二人が同じ
  行を触る競合は消えない。
- **本文の `version` を前提条件として読むこと**(§4)。
- **`If-Match` を必須にすること。** 既存の呼び出し元と `ochakai access -f`
  の手作業が全部壊れる。concept 側と同じく、**要るときに書くもの**である。
- **ポリシーに履歴を持たせること。** 0109 §7 のまま。412 が言うのは
  「あなたの読んだものはもう無い」ことで、何がどう変わったかは読み直せば
  分かる — 台帳をもう一つ持つ理由にはならない。
- **競合したときに併合すること。** 付与の集合の併合は、**消す編集を
  上書きに変える**。ポリシーは「無い行」が答えを決める文書なので、
  併合は境界を黙って広げる方向にしか間違えない。
