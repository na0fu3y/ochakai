## 1. 目的

0036 は「OKF のスキーマを真とする」と基準を引き、SPEC が定義するキーを
封筒フィールドに持ち上げた。正しい一歩だったが、**写像そのものは残った**。
ochakai は今も 1 つの知識を 3 つの表現で持っている — 封筒 20 余列の
Go 構造体 / DB 行、REST・MCP の JSON、そして OKF 文書 — そして 3 表現の
あいだの写像を自前で維持している。その維持費が、現行ドキュメントの
以下の箇所に形として現れている:

- **status の写像表**(0036 §3.4)。ochakai の 4 値と OKF の 3 値 +
  `verified` キーが重ならないため、インポートに 8 行の対応表が要る。
  `rejected` の往復は非可逆で、外来バンドルの `stable` は表現できずに
  draft へ降格する。
- **往復規則の一覧表**(0036 §3.12)。18 行。SPEC が動くたびに全行を
  読み直すことになる。
- **封筒と attrs の二重底**。同名キーの 400(0036 §3.5)、エクスポート側の
  `reservedKeys`、`attrs` から封筒への一回性の移行(マイグレーション
  0020)、YAML の日付型付けへの対処(`yamlScalar`)— どれも「同じ知識が
  2 つの置き場を持つ」ことの帰結である。
- **`updated_at` の三役**(0036 §3.2)。ETag の版(0030)と OKF の
  `generated.at` と行の書き込み時刻を 1 列が兼ねるため、「verify と添付でも
  進む(進めないと楽観ロックが壊れる)ので `generated.at` は厳密には
  last meaningful change でない」という妥協が明文化されている。

このコストは理論上のものではない。v0.2 対応は一度 0034 として書かれ、
マージ・出荷までされてから封筒の基準の誤りが分かり、文書ごと 0036 に
置き換えられた(0036 §1.1)。**写像を自前に持つ限り、SPEC の一挙一動が
写像の再設計になる。**

互換方針([docs/compatibility.md](../compatibility.md))は 0.x のあいだ
全インターフェースの破壊を許しており、0036 §2.4 は「過去の ochakai との
互換より OKF との互換を優先する」と線を引いた。本ドキュメントはその線を
**表現の水準まで**貫く: OKF 文書を保存とワイヤの唯一の正とし、写像を
恒等に潰す。

### 1.1 実装を伴わない採択について

これまでの慣行は「実装は同 PR」だった。本ドキュメントは決定だけを先に
採択する — 変更が保存形・ワイヤ・4 サーフェスの全部に跨り、レビュー可能な
1 PR に収まらないためである。0034 の教訓はそのまま適用される: 実装が
本ドキュメントの規則の誤りを明らかにしたら、リリース前であれば部分改訂を
積まず本ドキュメントごと置き換える(0036 §1.1、CONTRIBUTING の
改訂チェーン回避)。

## 2. 世界観

### 2.1 OKF 文書が唯一の正

**保存もワイヤも、正準化された OKF 文書(YAML frontmatter + Markdown)
そのものにする。DB は文書の索引と、インスタンス固有の台帳に徹する。**
ochakai は「索引と台帳の付いた OKF バンドル」になる。

0036 の基準「SPEC が定義するキーは封筒に持つ」は、「すべてのキーは文書に
ある。封筒は存在しない」に置き換わる。0015 が求める「4 サーフェスが同じ
形を語れる」の *形* は OKF 文書そのものであり、UI や検索結果が使う
型付きの投影は文書から**片方向に導出**される(§3.5)。往復しない投影に
写像の維持問題はない。

SPEC がバージョンを上げても、保存形とワイヤ形は動かない。判断が要るのは
「新しいキーを索引・投影・検証に足すか」だけであり、additive な変更が
構造的に additive になる。

### 2.2 知識文書とインスタンス台帳の分離(0009 §3.1 の貫徹)

0009 §3.1 と 0036 §2.2 の世界観 — **バンドルは知識を運び、provenance は
このインスタンスの観測である** — を、テーブルの水準まで貫徹する。

| | 中身 | 所有 |
|---|---|---|
| **文書** | type / title / description / resource / tags / sources / usage_window / status / status_note / stale_after / 契約(runtime …)/ 拡張キー / 本文 | 書き手。バンドルが運ぶ |
| **台帳** | 検証(§3.2)・却下(§3.3)・利用(0001 §9)・リビジョン(§3.9) | インスタンス。バンドルは運ばない |
| **観測列** | created_by / generated(内容を最後に変えた actor と時刻) | インスタンス。エクスポートに注入され、読み戻さない |

サーバー所有キー(`generated` / `verified` / `created_by` /
`rejected_*`、v0.1 の綴り)は**文書に保存しない**。エクスポートの瞬間に
台帳と観測列から注入される。現行実装では「attrs に入れない」「値を
採らない」という規則だったものが、置き場が存在しないという構造になる。

### 2.3 内部語彙を SPEC に一致させる — 写像は恒等でなければならない

status は OKF の 3 値をそのまま持ち(§3.2)、「人が確認した」は status では
なく検証台帳の行で表し(SPEC §5.3 と同型)、actor の語彙は SPEC §7 の
綴りに合わせる(§3.8)。写像が恒等になったとき、OKF 互換のコードとして
残るのは**検証(validation)と正準化だけ**である。

### 2.4 継承する決定

本ドキュメントは表現を置き換えるのであって、意味論の決定は引き継ぐ。
0017(パスが住所)・0019 §2(ID 文字種)・0022(ファイル名が名前)・
0038(型の語彙)・0024(リンクは本文から)・0013(添付)・0027(委譲)は
そのまま前提である。0036 のうち §2.1(推奨はするが強制しない)、
§2.2(provenance を読み戻さない — `verified` の存在だけ読む)、
§3.7-§3.10 のキーの意味と検証規則、§5(実行しない・dereference しない・
採点しない)の全項目も維持する。0001 の中核制約(LLM ゼロ・SQL 非実行)には
触れない。

## 3. 決定

### 3.1 保存形: 文書 + 導出索引 + 台帳

`knowledge` の封筒列群を置き換える:

| テーブル | 中身 |
|---|---|
| `concept` | `id`(バンドルパス、0017)、`doc`(正準 OKF 文書、§3.7)、`content_hash`(§3.4)、観測列(`created_by_*` / `generated_by_*` / `content_changed_at` / `created_at` / `deleted_at`)、導出索引列 |
| `verification` | `id` / `by`(actor)/ `at`。append-only(§3.2) |
| `rejection` | `id`(一意)/ `by` / `at` / `note`(§3.3) |
| `revision` | `id` / `rev` / `change` / `changed_by` / `changed_at` / `doc`(§3.9) |
| `knowledge_event` / `knowledge_usage` / `attachment` | 現行のまま(0001 §9、0029、0013) |

- **導出索引列**(type / folded type / title / description / tags /
  status / stale_after / sources / search_text / embedding)は書き込み時に
  文書から展開する。矛盾したら文書が正であり、索引は再構築できる。
  0037 の GIN index(source 逆引き)、0041 の prefix 照合、trigram /
  pgvector の検索は索引列の上でそのまま動く。
- **embedding の入力は変わらない。** `embeddingText` が読むもの
  (id / title / description / tags / 拡張キー `question` / 本文)は
  文書から同じ値で取れる。**再 embed は不要**である。

### 3.2 status は OKF の 3 値、検証は台帳

`status` は `draft | stable | deprecated`(SPEC §5.4 の語彙そのもの)を
保存する。**「人が確認した」は status ではなく `verification` 行**で
表す — SPEC §5.3 が `verified` キーの有無で trust tier を決めるのと同型で
ある。0036 §3.4 の写像表は消え、インポート・エクスポートの status は
**恒等**になる。

- **エクスポートの `verified` は検証台帳の全行**(時系列)。SPEC §5.2 の
  リスト形が初めて中身を持つ — 0036 §3.2 は「将来複数の検証を保っても
  ワイヤ形が変わらないようリスト形で出す」と書いたが、内部が単数のまま
  だった。再検証(0025 §6)は上書きではなく**追記**になり、検証の履歴が
  一級市民になる。`sort=verified_at` フィードは最新の検証で並ぶ。
- **インポートの `verified` キーは存在だけ読む**(0036 §2.2 維持)。
  存在すれば、取り込んだ actor — 0009 §3.2 の「レビューゲートを通した者」
  — による検証 1 行を起こす。`by` / `at` の値は採らない。v0.1 文書の
  `verified_at` の存在も同じことを言うので、そちらも見る。
- **外来バンドルの `stable` は `stable` のまま入る。** 0036 §3.4 は
  「OKF の stable は『消費してよい』であって『人が確認した』ではない」
  として draft に降格させていたが、それは正しい読みを**表現できない**
  ための妥協だった — ochakai に「stable だが未検証」という状態が
  なかった。3 値 + 台帳はその状態をそのまま持てる。信頼の判定
  (verified か)と消費可否の宣言(stable か)は独立の信号であり、
  どちらも失わずに入る。
- **`status` 省略は「未設定」として通す**(0036 §3.4 維持)。create なら
  draft、update なら現状維持。`verified` キーがあれば検証行は起きるが、
  status はやはり書き込み経路の既定に委ねる — 検証と lifecycle は
  独立である。
- **verify(`POST /api/v1/verify/{id}`)は台帳への追記であり、文書に
  触れない。** ETag も `generated` も動かない(§3.4)。draft のまま
  検証されたエントリは SPEC 上合法であり(§5.3 / §5.4 は独立)、
  lifecycle を進めるのは書き手の編集である。Web UI は verify の際に
  「stable に上げるか」を**別の編集として**提案してよい — 2 つの操作、
  2 つの記録。

### 3.3 却下は台帳 — rejected という status は消える

`rejected` は lifecycle の値ではなく、**このインスタンスの裁定**である。
0036 §3.4 が「rejected はエクスポートで deprecated になり、往復は
非可逆」と認めていた歪みは、rejected を文書の属性として運ぼうとした
ことから来ていた。運ばない。

- `rejection(id, by, at, note)`。行があるエントリは status フィルタ
  未指定の検索・一覧から除外する(0001 §9.1 の挙動そのまま)。
  `rejected=true` を明示すれば取得でき、エージェントが起草前に同種の
  却下を確認する経路も従来どおり。
- **`POST /api/v1/reject/{id}`**(note 付き)で裁定し、
  **`DELETE /api/v1/reject/{id}`** で解除する。文書の status は動かさない
  — 却下された draft は draft のままである。「かつて正しかった」
  (deprecated)と「正しいと認められなかった」(rejected)の混同が
  対象消滅する。
- 却下理由は台帳の `note` に書く。`status_note` は文書のフィールド
  (書き手の言葉)として残り、deprecated の理由に使う。
- エクスポートは従来どおり拡張キー `rejected_by` / `rejected_at` を
  歴史的記録として出し、インポートは値を採らない(0009)。裁定は
  インスタンス固有なので、バンドル経由で別インスタンスに伝わらないのは
  仕様である — 現行の「deprecated に化けて伝わる」より正直になる。
- **MCP のキュレーション保護(0015 §3.1)の判定**は「人が裁定したか」を
  台帳で読む: 検証行がある ∨ rejection 行がある ∨ status が
  deprecated。現行の `CuratedStatuses` と同じ集合を、状態の出所に即して
  言い直したものである。

### 3.4 版は内容のハッシュ(0030 §3.1 の改訂)

**ETag = 正準文書(§3.7)の SHA-256。** If-Match の機構 — opt-in、
条件付き UPDATE の中での判定、412(0030 §3.3-§3.5)— は維持し、版の
表現だけ差し替える。

- **verify・reject・添付の付け外しで ETag が動かない。** これらは文書に
  触れないからである。0036 §3.2 の妥協 —「verify と添付も `updated_at`
  を進める。進めないと楽観ロックが壊れる」— は対象消滅する。編集者の
  条件付き PUT が、内容と無関係な操作で 412 になることがなくなる。
- **`generated.at` = `content_changed_at`、`generated.by` = その変更の
  actor。** 文書が変わったときだけ動く。0036 §3.3 が例外規則として
  書いていた「verify と attach/detach ではスタンプしない」は、規則では
  なく構造から出るようになる。`generated.at` が SPEC §5.2 の "last
  meaningful change" と厳密に一致する。
- 0030 §3.2 の精度不変条件(タイムスタンプのマイクロ秒切り詰め)は
  対象消滅する — ハッシュに時計はない。
- `SameContent` は正準形の一致に縮退する。引用や parameters の順序は
  正準形に残るので、並べ替えが no-op に飲まれない(0036 §3.12 の
  順序敏感性は保たれる)。

### 3.5 ワイヤ: 文書で書き、文書 + 台帳で読む

**書き込み** — `PUT /api/v1/knowledge/{id}`、本文は OKF 文書そのもの
(`text/markdown`)。

- PUT は create-or-replace である。`If-None-Match: *` で「新規のみ」、
  `If-Match: "<hash>"` で条件付き置換、どちらも無ければ従来どおり
  last-write-wins(0030 §3.5)。JSON フィールドを組み立てる書き込み面は
  廃止する。
- 文書中のサーバー所有キー(§2.2)は**剥がして受ける**。400 にしない —
  `ochakai get` はエクスポート形(注入済み)を返すので、get → 編集 →
  update の往復で書き手は自分が受け取ったものをそのまま出せなければ
  ならない。現行の「値を採らない」と同じ意味論である。
- 検証は 0036 §3.10 の表のまま: 書き込みは 400、インポートは note。
  `attrs` の同名キー 400(0036 §3.5)だけは**対象消滅** — 衝突する
  2 つの置き場がもう無い。

**読み取り** — `GET /api/v1/knowledge/{id}` は JSON で返す:

```jsonc
{
  "id": "metrics/revenue",
  "document": "---\ntype: Metric\n…\n---\n\n本文…",   // 正準形。サーバー所有キーなし
  "summary": { /* 投影: type, title, description, status, tags,
                  stale_after, verified, rejected, links … */ },
  "observed": {
    "created_by": {…}, "generated": {"by": {…}, "at": "…"},
    "verified": [{"by": {…}, "at": "…"}, …],
    "rejection": {"by": {…}, "at": "…", "note": "…"}   // 無ければ省略
  },
  "attachments": [ … ]                                  // 現行のまま
}
```

- **投影(summary)は読み取り専用の導出**であり、書き込みには存在しない。
  検索・一覧・browse・context の行はこの投影である。status は 3 値、
  `verified` / `rejected` は台帳から導いた bool として並ぶ。0033 の
  「hits は順位に徹する」は不変で、rank の行に `verified` が加わる。
- `Accept: text/markdown` は**エクスポート形**(サーバー所有キー注入済みの
  文書)を返す — 1 エントリ分のエクスポートそのものであり、`ochakai get`
  が編集に使う形である。
- `attrs` フィールドはワイヤから消える。拡張キーは文書の中にある。

export / import はほぼ恒等写像に縮退する: export = `doc` + サーバー所有
キーの注入 + `index.md` の再生成、import = サーバー所有キーの剥離 +
検証 + PUT の繰り返し(0036 §3.14 のとおりクライアント側)。

### 3.6 SPEC が構造を定義するオブジェクト内側の未知キーを保存する(0036 §3.5 の撤回)

0036 §3.5 は per-source / per-parameter のプロデューサ拡張キーを note 付きで
落としていた。根拠は「封筒に上げた目的は 4 サーフェスが 1 つの形を語れる
ことであり、`additionalProperties` は UI の行エディタと MCP のスキーマを
無力化する」だった。書き込み面が文書になったことで、この根拠は前提を
失う — 保存形は何でも保持でき、投影は知っているキーだけ出せばよく、
スキーマが要るのは投影(読み取り専用)だけである。

**未知キーは、トップレベルでも構造化オブジェクトの内側でも、原表記の
まま文書に残り、往復する**(SPEC §4.1)。検証が見るのは SPEC が REQUIRED
と定めるキー(0036 §3.10 の表)だけである。

### 3.7 正準化

書き込みとインポートは、パース → 検証 → **正準形への再シリアライズ**を
通ってから保存される。`content_hash` はこの正準形の上で計算する。

正準形の規則は 0036 §3.12 のエクスポート規則をそのまま引き継ぐ:
frontmatter は SPEC の族順(base → provenance → trust → lifecycle →
computation → 拡張キー、拡張キーは原表記で末尾)、時刻成分の無い日付は
素のスカラ(`yamlScalar`)、CRLF は LF に正規化、本文は(改行正規化を
除き)バイト保存、末尾に改行 1 つ。**0.15 のエクスポートが書く形と
一致させる** — 既存バンドルを git で持つ利用者の diff を、§4 に挙げる
意味のある変更以外で動かさないためである。

### 3.8 actor 語彙を SPEC §7 に一致させる(0036 §3.11 の改訂)

`agent:` をやめ、**`human:` / `process:`** を使う。ワイヤの Actor は
`{kind: human | process, name, via}`。

0036 §3.11 は「意味の違う `process:` に読み替えたりはしない」と述べた。
しかしその意味の差 —「LLM エージェントか、ただのプロセスか」— は
どこにも効いていない: SPEC §5.3 は human 以外を一括で machine-confirmed
とし、ochakai 自身も kind で分岐しない。効いていない区別のために SPEC の
綴りから外れることは、写像を恒等にするという本ドキュメントの方針と
矛盾する。`<producer>/<version>` 形式は引き続き使わない(IAM サービス
アカウントはバージョンを持たず、偽のバージョンを作らない — 0036 §3.11 の
この判断は維持)。

委譲は従来どおり mapping 内の拡張キー `via` で表す(0027、0036 §3.2)。
`sources[].author` が文字列のまま往復するのも変わらない。

### 3.9 リビジョンは文書のスナップショット

`revision` は Go 構造体の JSON ではなく**正準文書のテキスト**を持つ。
形のアンカーが OKF なので世代を問わず読め、diff が人に読める。
change の語彙は現行のまま(create / update / move / delete / attach /
detach — 後 2 者は文書が動かない監査行であり、doc 列は直前と同じ値を
持つ)。

0036 §3.13 の「リビジョンのスナップショットは書き換えない。履歴は当時の
形を保つ」は撤回する(§3.10)。あれは互換の姿勢であり、本ドキュメントは
その互換を切る側にいる — 履歴の形が読み手の知識(全世代の Go 構造体)に
依存する状態こそが歪みである。

### 3.10 マイグレーション(0022)

起動時に一方向で適用される、表現の一括移行である:

- 各行の封筒列 + `attrs` から**正準文書を合成**し(エクスポート器から
  サーバー所有キーの注入を除いたもの)、`doc` と `content_hash` を書く。
- `verified_by` / `verified_at` → `verification` 1 行。
- status の移行: `draft` → `draft`、`verified` → `stable`(検証行が
  「人が確認した」を運ぶ)、`deprecated` → `deprecated`、`rejected` →
  **`draft` + `rejection` 行**(`rejected_by` / `rejected_at` から)。
  却下は「受け入れられなかった」であって「かつて正しかった」ではない —
  0.15 までのエクスポートが deprecated に畳んでいたのは語彙不足の妥協で
  あり、保存し直すときにその妥協を写さない。
- actor の kind `agent` → `process`(全列、§3.8)。
- **リビジョンも同じ合成器で文書化する。** 各スナップショットを現行の
  形として読める範囲で読み、読めない断片(退役したフィールド)は落ちる。
  当時のワイヤ形の完全な再現は保証しない — 0036 §3.13 の姿勢の撤回で
  ある(§3.9)。
- `content_changed_at` は `updated_at` から引き継ぐ。**再 embed は
  不要**(§3.1)。

### 3.11 各サーフェス(0015 §4)

- **REST = yes。** 唯一の契約。knowledge の書き込みが文書(PUT)になり、
  読み取りが文書 + 投影 + observed になり、`POST /api/v1/reject/{id}` /
  `DELETE /api/v1/reject/{id}` が増える。`openapi.yaml` は文書 string と
  投影・observed のスキーマを記述する。
- **CLI = yes。** `ochakai get` / `update` は**既に**文書で編集している
  (0036 §3.15)— 本ドキュメントはその一面を全サーフェスの正に昇格させる
  ものである。`ochakai reject` / `reject --lift` を足す。export / import は
  ほぼ恒等になる。
- **MCP = yes。** `create_knowledge` / `update_knowledge` の引数は
  `{id, document}` に縮む。0036 §3.15 が恐れた「全置換フィールド列挙に
  新フィールドを足し忘れるとエージェントが値を消す」問題は、列挙が
  消えることで対象消滅する — エージェントは受け取った文書を編集して
  返す。frontmatter + Markdown は LLM エージェントが JSON スキーマより
  自然に扱える形でもある。**reject は出さない** — 検証と同じく人の裁定で
  あり、エージェントは `report_outcome` か代替 draft で応える(0015
  §3.1、0025)。verify も従来どおり出さない。
- **Web UI = yes。** 一覧・詳細は投影、編集は文書エディタと、既知キーの
  フォーム糖衣の二本立て。糖衣は文書の read-modify-write として実装し、
  未知キーを保存する — 0036 §4 が直した「フォームが `resource` を落とす」
  類のバグは、部分ペイロードという概念ごと消える。verify / reject の
  ボタンは台帳を叩く。

## 4. 壊れるもの

**基準線は 0.15.0**(0038-0042 を積んだ次のリリース)である。本ドキュメントの
実装はその次のリリースに束ねて出す。

**ワイヤ(REST / MCP / CLI)**

- knowledge の読み書きの形が置き換わる。JSON フィールドでの create /
  update(`POST /api/v1/knowledge`、JSON PUT)は消え、文書の PUT になる。
  読み取りは `document` + `summary` + `observed` + `attachments` になり、
  トップレベルの封筒フィールドと `attrs` は消える。
- status の語彙が 3 値になる。`verified` / `rejected` は status 値では
  なく bool(台帳の導出)として現れ、検索フィルタも `status=draft|stable|
  deprecated` + `verified=` + `rejected=` に変わる。
- ETag が時刻からハッシュになる。If-Match に `updated_at` を送っていた
  クライアントは `content_hash`(ETag ヘッダの値そのもの)を送る。
  verify・添付で ETag が動かなくなるのは挙動の改善だが、ETag を
  「最終更新時刻」として読んでいたクライアントは壊れる。
- MCP ツールの引数・返答の形が変わる(§3.11)。
- verify の応答、`sort=verified_at` の並びの意味(最新の検証)、
  usage 系は形を保つが、行の投影は上記のとおり変わる。

**保存**

- マイグレーション 0022(§3.10)。一方向で、ダウングレード経路は無い
  (従来どおり)。リビジョンのスナップショットは文書に再合成され、
  現行の形として読めない断片は失われる。

**バンドル(エクスポート / インポート)**

- `verified` が検証台帳の全行を列挙する(1 要素固定でなくなる)。
- 却下されたエントリの `status` が `deprecated` ではなく実際の lifecycle
  (通常 `draft`)で出る。`rejected_by` / `rejected_at` 拡張キーは
  従来どおり。
- actor の綴りが `agent:` から `process:` になる。git 管理された既存
  バンドルは、次回エクスポートでこの 2 点と verified リストの diff が出る。
  キー順・日付・その他の値は 0.15 と同一である(§3.7)。
- 外来バンドルの `stable` が draft に降格しなくなる(§3.2)。
- per-source / per-parameter のプロデューサ拡張キーが保存・往復される
  ようになる(§3.6)。0.14-0.15 が note を出して落としていたものが残る —
  破壊ではなく回復である。

## 5. やらないこと

- **Git / GCS を保存にしない。** DB が真実の源であることは変えない
  (0009 §3.1)。同時書き込み、条件付き更新、pgvector、利用測定は DB の
  仕事であり、文書はその**値**になるだけである。永続層を Cloud Storage に
  置き換える提案は 0026 として一度出て、ランドせずに欠番になっている —
  本ドキュメントはその再来ではない。
- **型付き JSON の書き込み面を残さない。** 「JSON でも書けるように」は
  二重表現の再導入であり、本ドキュメントの出発点に戻ることになる。
- **部分更新(PATCH / frontmatter マージ)を作らない。** 全置換 +
  If-Match(0016、0030)で足りる。マージ意味論は競合解決の複雑さを
  持ち込むだけである。
- **`log.md` への履歴エクスポートをしない。** 文書スナップショット
  (§3.9)は道を開くが、`log.md` は OKF の予約ファイルであり、その中身の
  規約は SPEC が決めることである。必要が実在してから別の決定として
  提案する。
- **退役綴りのデータ移行をしない。** `Semantic Model` / `Golden Query` を
  持つ既存エントリはそのまま自由型として残る(0038)。これは互換シムでは
  ない — 型は書き手の語彙であり(SPEC §4.1)、サーバーが書き手の語彙を
  書き換えることこそ「解釈しない」(0001)からの逸脱である。
- **provenance の読み戻し・実行・dereference・採点をしない。** 0036
  §2.2 / §5 の全項目(`executor` を走らせない、`resource` を取りに
  行かない、`# Citations` をパースしない、`usage_count` と利用集計を
  相互変換しない)は一字も変えずに維持する。
