# ochakai 設計ドキュメント 0149: エージェントが提案し、問うた人が適用する

Status: Accepted(2026-09-25)。[0142](0142-ochakai-carries-a-data-agent-that-does-not-rule.md)
§3 の「エージェントの書き込みは新しい id の draft だけで、置き換えは一度も
しない」を改訂する — まだ誰も裁定していない draft に限り、エージェントは
次の版を**提案**でき、問うた人が適用したときだけそれが書かれる。0142 §2 の
「スキーマを刈り取って concept にする経路は作らない」は改訂する — 問われた
ときに、問うた人の身元でクエリ履歴を読み、一回 5 件までの draft にすることは
刈り取りではない(§4)。ROADMAP の第三段(2026-09-25)
Date: 2026-09-25

## 0. この記録が決めたこと

1. **エージェントは、裁定されていない draft の次の版を提案できる**
   (`propose_revision`)。書き込みはしない。提案は答えの `revisions` に載り、
   turn と一緒にサーバーに残る(§1)。
2. **問うた人が適用する。** `POST /api/v1/agent/turns/{id}/revisions/{concept}`
   は本文を受け取らず、turn が残した文書をそのまま書く。記録は
   `process:ochakai via <問うた人>`(§2)。
3. **draft でなくなったもの、裁定されたもの、提案のあと動いたものには
   書かない。** 提案した時点の内容ハッシュが、書き込みの前提条件になる(§2)。
4. **エージェントは、空の description を会話とプロファイルから埋める
   手順を持つ**(§3)。**クエリ履歴は、問われたときにだけ読む**(§4)。

## 1. 誰が詰まったか

`ochakai seed` と、同じ投影をページから行う取り込み
([0148](0148-the-empty-base-fills-from-the-page-too.md))は、テーブル一つに
つき一つの draft を作る。**description は空で、それは意図である** — 誰も
書いていない一文を frontmatter に置けば、その後の全員がそれを信じる。
その結果、初日のベースは数十から数千の空の draft になる。空を埋めるのは、
そのテーブルを知っている人の言葉と、テーブルを実際に数えた事実である。

デプロイ自身のエージェントは、その二つを集めるのに向いている — 問うた人に
二、三問だけ訊き、行数・鮮度・NULL の割合を本人の身元で確かめられる
(0142 §4)。**それを書く手段が無かった。** エージェントの書き込みは新しい
id の draft だけで(0142 §3)、seed の draft の空は、その draft の中にある。
別の id に書けば、同じテーブルに二つの concept ができ、どちらを読むかを
読む側が迷う。ROADMAP の第三段が「初日から効く」を C4(FDE なし)の勝負所と
呼んだのは、この空のことである。

**外のエージェントには、これは最初からできる。** MCP の `put_concept` は
裁定されていない concept の置き換えを許し、拒むのは verified と deprecated
だけである([0145](0145-four-faces-and-an-answer-that-shows-its-result.md)
§6)。デプロイ自身のエージェントだけが一段強く縛られていた。この記録は
その縛りを外すのではなく、**外のエージェントには無い一段 — 人のクリック —
を足して**、同じところまで開く。

## 2. 提案と適用

**提案。** `propose_revision(id, document)` は、その id の concept が
呼び出し元の書ける範囲にあり、裁定が無く、status が draft であり、文書が
status を draft のまま保つときだけ受け付ける(`put_concept` の拒否と同じ
判定に、draft であることを足したもの)。何も書かない。その時点の内容
ハッシュを添えて、答えの `revisions` と turn に残す。一回の答えで 5 件まで
で、同じ id は一度だけ。dry run(0146)と read-only のデプロイでは道具
そのものを出さない。

**適用。** 本文の無い一本の POST が、turn の残した文書を書く。

- **本文を受け取らない。** ページが文書を送る形にすると、誰の文でも
  エージェントの名で書けてしまう。台帳の「エージェントが書いた」が
  本当であるためには、書かれるバイトがエージェントの出したものでなければ
  ならない。署名で守るには鍵が要り、鍵は secret である(C2)。サーバーが
  自分で残したものを書くのが、secret 無しで言える唯一の形である。
- **記録は `process:ochakai via <問うた人> using ochakai/<版>`**、エージェントが
  draft を書くとき(0142 §3)と同じである。人が押したことは `via` が言う。
  人の書き込みとして記録すると、エージェントの文が人の文として残る。
- **適用できるのは問うた人だけ**で、判定と同じ規則である。ほかの人、
  180 日を過ぎた turn、提案に無い concept は 404。
- **前提条件は提案時の内容ハッシュ。** 提案のあとで誰かが draft を
  直していれば、あるいはこの提案がもう適用されていれば、412 になり、
  何も上書きしない。裁定されていれば 400 で、`put_concept` と同じ理由を
  言う。
- **適用は裁定ではない。** draft は draft のまま、unverified のままで、
  レビューのキューに残る。確かめるのは、それを読んだ人の verify である。

**Web UI** は、提案ごとに差分(今の draft と提案)を開ける形で置き、書ける
デプロイで問うた人にだけ「適用する」を出す。

## 3. 空を埋める手順

プロンプトが持つ(`internal/agent/prompt.go`)。要点だけをここに置く。

- **作らない。** 何のためのテーブルかはスキーマに書いていない。問うた人に
  一度に一〜三問(目的、一行が何を表すか、使うときの注意)を訊いて待つ。
- **数えて確かめる。** 行数、日付の列の最古と最新、主な列の NULL の割合、
  値の少ない列の値を、一度に一本ずつ SQL で提案する。実行するのは問うた人
  (会話ごとの同意があれば自動で — 0145 §5.4)。
- **書くのは出所のある文だけ。** description は一文で、問うた人の言葉と
  確かめた事実からだけ書く。本文の「# 注意」に、注意とその出所(誰の
  言葉か、どの SQL をいつ走らせたか)を並べる。

## 4. クエリ履歴

**問われたときにだけ読む。** 「このデータセットでよく使われている集計は?」
と訊かれたら、エージェントは問うた人の身元で
`INFORMATION_SCHEMA.JOBS_BY_PROJECT` から直近 30 日の SELECT を数える
SQL を提案し、繰り返し走っている集計を Metric か Attested Computation の
draft にする — 一回 5 件まで、本文に「直近 30 日に N 回」と出所を書き、
確かめられていないと書く。

0142 §2 が作らないとした「スキーマを刈り取って concept にする経路」は、
**誰も問わないのに、まとめて、人の目を通さずに**ベースを埋める経路の
ことだと読む。ここで起きるのは、人が一つ問い、エージェントが数件の
draft を出し、人がそれを一件ずつ裁定することで、その三つがどれも無い。
パイプラインも、定期の取り込みも、上限を超える一括の書き込みも作らない。
コネクタで自動収集しない(0142 §8)は動かない。

Anthropic の分析エージェントでは、過去のクエリ数千本を直接読ませても
正答率は 1% も動かなかった。履歴は答えを作る材料ではなく、**何を書くかの
候補**として読む。書かれたものが効くかどうかは、人の裁定と `ochakai eval`
(0146)が言う。

## 5. 面

- **REST** に一本(17 → 18、天井を上げる決定)。答えの `revisions` と
  turn の `revisions` は応答だけの追加である。
- **Web UI** は答えの下に提案の差分と「適用する」を置く。
- **MCP** には載せない。外のエージェントは `put_concept` で同じことが
  すでにでき、デプロイのエージェントは MCP に載らない(0145 §5.1)。
- **CLI** には載せない。エージェントへの問いが CLI に無いのと同じ理由で
  (0145 §5.3)、能力は REST に残る。

## 6. 退けた案

- **エージェントが裁定されていない draft を直接書く。** 外のエージェントと
  同じ扱いで一番速いが、書かれる前に人が一件も見ない。初日のベースでは
  数十の draft が一度に動き、どれが人の言葉に基づくかが台帳からしか
  読めなくなる。
- **ページが提案の本文を `PUT` で書く**(人の書き込みとして)。表面は
  増えないが、エージェントの文が人の文として残る(§2)。
- **ページが本文を送り、サーバーがエージェントとして書く。** 誰の文でも
  エージェントの名で書ける(§2)。
- **別の id に書き、元の draft からリンクする**(0142 §3 のまま)。同じ
  テーブルに concept が二つでき、読む側が迷う(§1)。
- **提案を転送ごとに署名して、サーバーに残さない。** 鍵が要る(C2)。
- **クエリ履歴を読まない**、または**まとめて読んで取り込む**。前者は
  繰り返し走る集計という最もよい候補を捨て、後者は §4 の三つを失う。
