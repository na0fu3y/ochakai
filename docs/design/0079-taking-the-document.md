# ochakai 設計ドキュメント 0079: 文書を受け取る

Status: Accepted(2026-08-04)。**取り込みが文書を拒む条件と、CLI が送る
バイト列の現行ドキュメント。REST は一文字も変えない**(§1、§6 —
[0064](0064-rest-stops-at-api-v1.md) の凍結に足す規則は無い)。
[0075](0075-the-bundle-is-the-address-space.md) の §3(CLI が送る
バイト列)と §4.2(予約ファイルの note)を改訂する。
[0074](0074-the-document-and-the-vocabulary-that-asks-it.md) §1 の
「SPEC より狭かった」を、型の書かれていないキーにも広げて改訂する。
どちらの決定も変えない — 変えるのは、その決定が守れていなかった場所である
Date: 2026-08-04

## 0. この記録が決めたこと

**SPEC §11 における consumer の仕事は、文書を受け取ることである。**
そして ochakai が文書を拒んでいたところは、そのどれもが**利用者の
バイト列が消えうる場所**だった。0075 は「バンドルに入ったものは出てくる」
と書いたが、**concept として受け取れなかった `.md` は、その約束の外に
落ちていた。**

SPEC §11 が conformance に課すのは三つだけである — frontmatter が
パースできること、`type` が空でないこと、予約ファイルが §8 / §9 の形で
あること。そして「consumer はそれ以外の制約を soft guidance として
扱うべきであり、特に**未知の追加キー・未知の型・欠けた任意フィールド・
壊れたリンク・index.md の不在**を理由にバンドルを拒んではならない」。

**そのうち二つは、ochakai 自身の規則を SPEC のものと取り違えていた**
(§2、§3)。note にもエラーメッセージにも `SPEC §10.2` と書いてあったが、
§10.2 はその要求をしていない。

**そして一つは、直さないと決めた**(§1)。書き込み経路が拒む文書を
残すには `PUT /api/v1/bundle/{path}` に規則を一つ足すしかなく、その規則は
0064 の凍結に永久に載る。**約束のために凍結を汚すほうが高くつく** —
拒否は報告され、取り込み元のバンドルは手元にある。

## 1. 拒んだ concept は、拒んだと言うだけである — ワイヤには足さない

**書き込み経路の判断は変えない。** SPEC §10.2 は Attested Computation に
`runtime` を REQUIRED としており、それが無い契約はどの consumer にも
実行できない。名指しで一つの文書を書く呼び出しに 400 を返すのは
0075 §3.3 と同じ姿勢であり、**利用者が意図した値を黙って落とすほうが
悪い答えである**([0036](0036-okf-schema-first.md) §3.4)。

そして**この拒否をワイヤで迂回することもしない。** 一度は「取り込みは
拒まれた concept を自分のパスにファイルとして書く」ことにしかけた。
実装してみて、それが `PUT /api/v1/bundle/{path}` に**永久に revise
できない規則を一つ足す**ことだと分かった時点で取り下げている。

- **サーバーは `type` キーだけで concept かファイルかを決める**
  (0075 §4)。拒まれた文書のバイト列をファイルとして残すには、`.md`
  のアドレスで concept 経路を通らない道が要る。**それを `Content-Type`
  で分けるしかなかった** — `application/octet-stream` なら残し、
  `text/markdown` なら 400。**同じバイト列を同じアドレスに送って、
  ヘッダ一つで結果が変わる規則である。**
- **その規則の「きれいな形」は採れない。** ヘッダ条件を外すと
  `ochakai put` が壊れた契約を(note 付きとはいえ)成功として飲み込む。
  **きれいな形が受け入れられず、出荷できる形が但し書きを必要とする
  規則は、凍結してよい規則ではない。** ワイヤは
  [0064](0064-rest-stops-at-api-v1.md) で凍る。
- **保存形そのものが嘘になる。** `type` を持つ frontmatter の `.md` が
  concept のアドレスに**ファイルとして**座ることになる。SPEC §11 は
  それを concept だと言い、第三者の OKF リーダはそう読む — ochakai
  だけが検索にも一覧にも trust にも出さない。**形式が言っていることと
  保存が言っていることが食い違う。**
- **失われるものは、思っていたより小さい。** 取り込み元のバンドルは
  そのまま手元にある。拒否はパスと理由を添えて `skipped` に出て、
  `--strict` は落ちる。**そして ochakai 自身の export にこの文書は
  そもそも入らない**(書き込み経路が拒んだのだから) — 往復しないのは
  「ochakai が索引しないと決めた文書を持つ他人のバンドル」だけであり、
  それは取り込み時に一件ずつ報告される。
- **ワイヤに足さないことと引き換えに、報告を厚くする。**
  `skipped` の行は「concept として拒否され、保存していない。取り込み元の
  バンドルには残っている」と言う。

**代わりに直したのは、拒否が伝染していたことである。** 拒まれた concept
の本文が指していたファイルは、**その concept ごと捨てられていた** —
一つの拒否が、その文書が名指したファイルすべての代償になっていた。
帰属は本文からの導出であって保存された関係ではなく(0075 §5)、
ファイルは自分のパスに座るバンドルのオブジェクトである。**書く。**
どの concept のものでもないと分かるように、行がそう言う。

## 2. `executor.receipt` は SPEC の要求ではなかった

SPEC §10.2 が REQUIRED と書いているのは `runtime` だけである。executor に
ついては「`resource` は実行の手順やコードを指す」「`receipt` は実行が
返すべきフィールドを宣言する」としか書いておらず、どちらにも要求語が
無い。そして §11 は、**任意フィールドが欠けていることを理由に concept を
拒むことを禁じている。**

- **`executor` は `resource` があれば有効である。** 実行するものを何も
  指していない executor は何も言っていないので、それだけは落とす。
- **`receipt` を書かなかった文書には、`receipt` を書き戻さない**
  (0075 §3 と同じ規則)。
- **note とエラーメッセージから `SPEC §10.2` の引用を外した。** 引用は
  規則の出所を示すためにあり、**出所でないものを指した引用は、読んだ人が
  SPEC を読み直す動機を奪う。**

## 3. 型の書かれていないキーは、書かれたとおりに読む

SPEC §4.1 は `title` / `description` / `resource` / `status` /
`status_note` / `stale_after` / `runtime` / `computation` に YAML の型を
与えていない。`title: 2026` は producer が引用符を省いた題であって、
壊れた文書ではない。

ochakai はこれらが非文字列スカラーのとき、**文書全体を拒んでいた**。
そして取り込みでは、その拒否が**沈黙していた** — ファイルは loose な
markdown に降格し、note にも `skipped` にも何も出ないまま、バイト列だけ
残して知識であることをやめていた。

- **非文字列スカラーは、書かれたテキストとして読み、note を出す。**
  日付を再描画する `yamlScalar` が既にやっていることの一般化である。
- **`tags` の要素も同じ**(`tags: [1, 2]` は二つのタグである)。
- **スカラーの位置にマッピングやリストが来たら、それは落とす** — 読み替える
  テキストが無いからである。もちろん note を出す。
- **ハードエラーは SPEC §11 が非 conformant とするものだけに残す** —
  パースできない frontmatter と、空の `type`。

## 4. 予約ファイルは、消えたことを言う

`index.md` と `log.md` は ochakai がバンドルから生成する導出面であり
(0075 §4.2)、取り込みで読み戻さないことは変わらない — SPEC §8 は
index.md を再生成可能とし、§11 は不在を許している。

**変えるのは、手書きの予約ファイルが黙って消えないことである。** ここは
取り込みが何も言わずにバイト列を捨てていた最後の場所で、`--strict` から
も見えなかった。**note を一行出す。**

その代償は正直に書いておく: **`ochakai export` が書いた `index.md` を
`ochakai import --strict` に戻すと、ディレクトリの数だけ note が出て
落ちる。** 生成物を生成物として認識する規則を持てば黙らせられるが、それは
「ochakai が書いたものだけ黙って捨てる」という規則であり、他人の
バンドルにとっては何の保証にもならない。**黙って捨てないほうを採る。**

## 5. CLI は、渡された文書をそのまま送る

0075 §3 は「保存するのは受け取ったバイト列そのもの」と決めたが、
`ochakai put` と `ochakai import` は**パースしたフィールドから正準形を
描き直して送っていた** — producer のコメントも、キーの順序も、スカラーの
綴りも、family reader が field を持たなかったものも、そこで消えていた。
その関数の doc コメントは「サーバーが保存するのと同じレンダラ」と言って
いたが、0075 §3(旧 0046 §2.2)以降それは真ではない。

**入力が文書なら、そのバイト列を送る。** JSON 入力だけが正準形になる —
送るべき文書を持っていないからである。これで**同じファイルに対する CLI の
書き込みと REST の書き込みが同じものを保存する。**

## 6. やらないこと

- **書き込み経路の Attested Computation 規則をゆるめること**(§1)。
- **拒まれた文書を残すためにワイヤへ規則を足すこと**(§1)。
  `PUT /api/v1/bundle/{path}` は 0064 で凍る。**この記録は REST を
  一文字も変えない** — 変えたのは CLI が何を送り何を報告するかと、
  parser が何を受け取るかだけである。
- **主張の読み戻し**、**`received:` を一級市民にすること**、その他
  0075 §7 と 0074 §7 が挙げたものは何も変わらない。
