# ochakai 設計ドキュメント 0110: 第一列は、並べてくれと言った鍵である

Status: Accepted(2026-08-17)。**BREAKING** — `ochakai search` と
`ochakai list --source` / `--links-to` の人間向け出力から第一列を落とす。
[0068](0068-how-a-face-is-added-and-removed.md) §3 が `min_score` を
ワイヤから降ろした理由を、同じスコアを印字していた面に及ぼす。0068 の
決定は何一つ変えない。
Date: 2026-08-17

## 1. 何を変えるか

`ochakai search` の各行は今日まで五つの意味を持つ第一列を持っていた。

```
1.730	ochakai://metrics/revenue	stable	売上 — 完了した注文の…
```

この `1.730` を落とす。行は `uri / status / title — description` になる。
`ochakai list --source` と `--links-to` も同じ列を持っていたが、そこでは
値が**常に 0.000** だった(逆引きは住所順で、ストアはスコアを 0 のまま
返す)ので、同時に落ちる。

フィード(`usage`・`verified_at`・`failed`・`stale_after`)の第一列は
**残る**。そこは読み手が「これで並べてくれ」と言った鍵そのもので、上下の
行と比較できる数か日付である。

`--json` と REST の `score` は**変えない**。較正した呼び出し元のための
型付きデータであって、端末に出す散文ではない。

## 2. なぜ — 0068 §3 が既に答えている

0068 §3 は `min_score` を廃したとき、こう書いた:

> スコアはモード依存で較正されておらず(レキシカルはフラグメント一致
> 重み、ハイブリッドは RRF の ~0.02 スケール)、片方で意味のある床は
> もう片方では無意味である。

同じ数が、床としては降ろされたまま、**人間向けの第一列としては残って
いた**。スケールは三つある。

| 経路 | score の正体 | 範囲 |
|---|---|---|
| lexical のみ | クエリ断片の重み付き被覆率 + 一致ボーナス | 0〜3 程度 |
| vector | `1 - (embedding <=> query)` | 0〜1 |
| 融合 | `Σ 1/(rrfK+rank+1)` + verified 分 | 0.016〜0.05 |

`rrfK = 60` なので融合の上限は約 0.049 である。つまり**同じクエリが、
埋め込むデプロイでは 0.033、埋めないデプロイでは 1.730 を出す**。行の
どこにも、どちらを見ているかは書いていない。埋め込み呼び出しが失敗して
lexical に降格した場合も同じで、サーバは warn を吐くがクライアントには
何も出ない。

**較正の手順を製品が説明できない数を、読み手の目の前に置いていた。**
0068 §3 が「製品が自分で『使うな』と書いている面」と呼んだものの、
最後の一つである。

順位そのものは行の並びが既に持っている。列が足していた情報は無く、
足していたのは「桁が変わったことが伝わらない」という害だけだった。

## 3. Web UI が先に同じ結論に達していた

`internal/webui/static/js/views/explore.js` は生のスコアを**一度も
描画していない**。内部信号として読み、`hits[0].score > 0.05` で
lexical か融合かを判定してから弱ヒットの床を当てる。同じ 0.05 が、
同じ理由で、独立に置かれていた。

MCP も `search_concepts` の説明文でスコアに一切触れていない。
**四つの面のうち、生の数を読み手に見せていたのは CLI だけだった。**

## 4. 破壊的変更として何が壊れるか

`docs/compatibility.md` は CLI の契約に「the shape of what they print」を
含める。壊れるのは第一列に依存したパイプラインである。

- `ochakai search q | cut -f2` は id を取っていた → `cut -f1`
- `ochakai search q | cut -f1` はスコアを取っていた → **移行先は無い**。
  `--json | jq '.hits[].score'` が持つ

フィードは一列も動かないので、`ochakai list usage | cut -f1` は不変で
ある。0069 が `ochakai stats` について約束した `cut -f2` も別の
コマンドで、影響しない。

## 5. 採らなかった案

**第一列を順位(1, 2, 3…)に替える。** 列は残るので `cut` は壊れないが、
順位は行の並びが既に持っている情報の二度書きで、`head -3` した出力に
「3」が残るだけの列を足す。列の意味を黙って替えるのは、落とすより悪い。

**スケールを正規化して 0〜1 に揃える。** 較正できないのはスケールでは
なく**意味**である。lexical の 0.8 と融合の 0.8 は違うことを言っており、
両方を 0.8 と印字しても読み手は同じだけ誤解する。

**モードを行に足す(`1.730(lexical)`)。** 読み手が次に問うのは「では
lexical の 1.730 は良いのか」で、それは 0068 §3 が説明できないと書いた
当のものである。答えられない問いを誘発する列になる。

**何もしない。** これが既定の答えだったが、0068 §3 が同じ数について
既に反対側の判断を下しており、面の間で判断が割れたままになる。

## 6. 面の数は動かない

`docs/surface.md` の 10 個の数はどれも変わらない。フラグでもコマンドでも
環境変数でもなく、既にあるコマンドが印字する列だからである。**天井を
上げずに済む変更**であり、代金は互換性の手続きだけである。

## 7. 見直す条件

較正の手順を製品が説明できるようになったら — つまり `score` が
デプロイの姿勢によらず同じ意味を持つようになったら — 列を戻してよい。
そのときは 0068 §3 の `min_score` も一緒に戻る話になる。
