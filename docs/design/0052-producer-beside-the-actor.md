# ochakai 設計ドキュメント 0052: 名乗りは actor の隣に置く — SPEC §7 の `<producer>/<version>`

Status: Accepted(2026-07-29)。[0043](0043-document-first.md) §3.8 の
「`<producer>/<version>` 形式は引き続き使わない」を改訂する(その決定は
[0046](0046-bundle-address-space.md) §2.4 が一字も変えずに引き継いでいた
もので、actor の綴りが `human:` / `process:` の 2 つであることは**変えない**)。
[0027](0027-delegated-provenance.md) が委譲について立てた合成規則
(「自称は認めるが、認証済みの名前は記録から消さない」)を 2 つ目の
自己申告フィールドに適用する。**provenance に何を記録するかの現行
ドキュメント**は 0002 / 0027 / 本ドキュメント。
[0048](0048-decision-records-for-wire-contracts.md) §2.3 の「未リリースの
決定は元のドキュメントを差し替える」を検討したうえで番号を取っている —
改める文は 0046 が**別領域から一行継承しているだけ**であり、決定そのものは
identity / provenance の領域(0002 / 0027、いずれもリリース済み)に属する。
0046 の中に埋めると、この領域の読み手が最も見ない場所に置かれることになる。
Date: 2026-07-29

## 1. 問題: 下書きを書いたエージェントが記録に残らない

ochakai の中核ループは「エージェントが下書きし、人が検証する」
([0001](0001-architecture.md))である。そのループを回している人が最初に
問う数字は「モデルを上げたら下書きの質は上がったか」だが、**いまの記録は
その質問に答える材料を持っていない**。

書き込みの actor は認証から来る([0009](0009-provenance-portability.md))。
実際に残るのは 2 つの形のどちらかで、どちらもエージェントを名指さない。

- **埋め込みアプリ経由**。actor は `human:tanaka@… via process:app@…`
  (0027)。呼び出し元のサービスアカウントは「どの統合か」までは言うが、
  **どの版か**は言わない。SA のメールアドレスはデプロイをまたいで不変で
  あり、それが SA の利点である。
- **エージェントが人の資格情報で動く場合**。MCP stdio ブリッジ
  ([0039](0039-mcp-stdio-bridge.md))や CI から `ochakai` を呼ぶ形では、
  資格情報は開発者本人のものなので actor は `human:tanaka@…` になる。
  **人が書いていない文章が、人名義で残る。**

2 つ目は単なる欠落ではなく歪みである。trust tier は動かない — SPEC §5.3
が読むのは検証台帳の `human:` であって created_by ではない
([0043](0043-document-first.md) §3.2)— が、「誰が書いたか」を読んだ人間は
確実に誤読する。

そして**これは後から復元できない**。過去の書き込みに producer は無く、
いま埋めれば server が観測していない事実を捏造することになる。
[0051](0051-instance-metrics-and-search-misses.md)(#293)が計測について言った
「その場で集計しなかったものは消える」と同じ非可逆性が、provenance 側にも
ある。記録を先に始めること自体が決定である。

## 2. なぜ 0043 §3.8 は「使わない」と決めたか、そしてどこが足りないか

0043 §3.8 の理由は正しい。

> `<producer>/<version>` 形式は引き続き使わない(IAM サービスアカウントは
> バージョンを持たず、偽のバージョンを作らない)

SPEC §7 の 3 つの形 — `human:<id>` / `process:<id>` /
`<producer>/<version>` — は **actor の位置に入る択一**である。ochakai の
書き込みには常に認証済みの who が居るのだから、その席を自称の文字列に
明け渡す理由は無い。0009 が拒否した「ペイロードが運ぶ自称 provenance」を
actor の位置で復活させることになる。

足りないのは次の一点である。**producer は actor の代替ではない。**
「誰が」と「どのソフトウェアが」は択一ではなく、同時に真な 2 つの事実で
ある。SPEC §7 が 1 つの席しか持たないことは、ochakai が 2 つ目の事実を
捨てる理由にはならない — SPEC §4.1 が producer 拡張キーを用意しているのは
まさにこのためであり、0036 §3.2 は `via` について既に同じ判断をしている。

## 3. 決定

### 3.1 producer は actor の**隣**に記録する

`Actor` に 4 つ目のフィールドを足す。

```json
{"kind": "human", "name": "tanaka@example.co.jp",
 "via": "process:app@example.iam.gserviceaccount.com",
 "producer": "insightflow/1.4.0"}
```

`kind` / `name` は認証が観測した値のままで、**綴りは `human:` /
`process:` の 2 つのまま**である(0043 §3.8 のこの部分は維持)。
`producer` は呼び出し元の自称であり、ochakai が記録するフィールドの中で
唯一「認証から来ない」ものである。

**隣に置くことが、自称を認めてよい条件そのものである。** 認証済みの名前の
*代わり*に置けば「誰が書いたか」は誰でも名乗れる文字列になる(0009)。
*隣*に置く限り、その主張は必ず「Google が検証した呼び出し元がそう言った」
という形でしか記録されない。これは 0027 §3 が委譲について立てた合成規則の
2 度目の適用であり、新しい原則ではない。

**allowlist は持たない。** `OCHAKAI_DELEGATING_CALLERS` が要るのは、委譲が
*他人の* identity を名乗る行為だからである。producer が名乗るのは呼び出し元
自身のビルドであり、その呼び出し元は同じ actor の中に認証済みで記録されて
いる — 詐称する相手が居ない。同じアプリの 2 つのデプロイは、SA が残るので
今までどおり区別できる。

### 3.2 形は SPEC §7 のまま、版の綴りは検査しない

`<producer>/<version>`。スラッシュちょうど 1 つ、両側非空、空白・制御文字
なし、**コロン禁止**、128 バイト以内。

コロンを拒むのは SPEC §7 が 3 つの形を**まさにその文字で**見分けるからで
ある。コロンを含む producer は、この規約を適用する読み手にとって identity に
見える — このフィールドが決して作ってはならない唯一の混同である。

版の側はそれ以上解釈しない。SPEC §7 は版の綴りを定めておらず、semver を
強いれば `claude-code/2026.07` も git sha も記録できなくなる。provenance が
記録するのは**書き手が自分を何と呼んだか**であって、文法を発明すれば
正直な書き手だけが記録不能になる。

不正な値は **400 で拒否する。黙って落とさない。** 版を刻んでいるつもりの
統合が、最初のエクスポートで何も記録されていなかったと気づく — 0027 §5.2 が
拒否した静かな降格そのものである。

### 3.3 出所: サーフェスごと(0015)

| サーフェス | producer の出所 |
|---|---|
| **REST** | `X-Ochakai-Producer: insightflow/1.4.0`。契約はここだけ |
| **MCP** | 上のヘッダ。無ければ initialize の `clientInfo`(`name` + `/` + `version`)。プロトコルが既に運んでいる値であり、誰も何も足さずに済む |
| **CLI** | 環境変数 `OCHAKAI_PRODUCER` を上のヘッダに載せる。ここで名乗るものを持つのは CLI を叩くエージェントであり、サブコマンドごとのフラグではなくプロセスに 1 回置く形が合う。`whoami` が申告値を出す — 見えない申告は間違っていても誰も気づかない |
| **Web UI** | **出さない(意図的な省略)**。Web UI は人が自分で書く編集面であり、名乗るソフトウェアが無い。書き手は人であり、それは actor が既に言っている |

MCP の `clientInfo` は**フォールバックであって上書きではない**。ヘッダを
送った呼び出し元は「この呼び出しで何を動かしているか」を言っており、
`clientInfo` が言うのは「誰がセッションを開いたか」である。1 つのセッションに
複数のエージェントを通すホストは、ヘッダでしか両者を区別できない。
セッション側を黙って優先するのは、0027 §5.2 が拒否した誤帰属の一段下の形で
ある。逆に、SPEC §7 の形に収まらない `clientInfo` は**落とす** — クライアントは
provenance を送ると言ったわけではなくプロトコルに名前を訊かれただけなので、
綴れない版でツール呼び出しを落とすのは礼儀を障害に変えることになる。

producer の解決は**委譲の後**に行う。委譲があるとき最終的な actor は
エンドユーザーであり、`human:tanaka via process:app@… using insightflow/1.4.0`
が真なことを言う — 人が行為し、アプリが呼び、そのビルドが文章を書いた。

**公開読み取り専用デプロイでは読まない**([0042](0042-public-read-only.md))。
自称が許されるのは認証済みの名前が隣にあるからであり、そこには呼び出し元が
居ない。

### 3.4 記録範囲

actor が既に `via` を持つ場所すべて — `object` の created_by / updated_by、
`knowledge_verification`、`knowledge_rejection`、`knowledge_revision`、
`knowledge_purge`。列は `NOT NULL DEFAULT ''`(名乗らなかったことと空である
ことは同じ状態)。

- **`knowledge_event` と `search_miss` には足さない。** 0027 §5.3 と同じ
  理由で、どちらの actor も書き込み専用のテレメトリであり 180 日で刈られ、
  どのサーフェスも読み戻さない(0051 の検索ミス面が返すのは query と件数で
  あって、誰が訊いたかではない)。読まれない列は何も記録しない。
- **ファイルの行(`object` のうち concept でないもの)は今のまま**、
  actor を kind + name だけで持つ。ファイルは `via` も持っておらず、
  producer だけ足せば不揃いが深まる。ファイルの書き込みの producer は
  リビジョン台帳の側に残る(`changed_by_producer`)ので、行為の記録は
  失われない。
- **バックフィルしない。** 埋めるべき値が存在しない。この移行より前の
  エントリは producer について何も言わない、というのが事実である。
- **どの時刻も動かない。** 記録できる場所が増えただけで、エントリの内容は
  変わらない — ETag も `generated.at` も embedding も無関係である。

### 3.5 表示と往復

`Actor.String()` は末尾に `" using <producer>"` を足す。全サーフェスの
provenance 行・`log.md`(0046 §3.8)・Web UI の表示はここに集約されている
ので、1 か所で揃う。

OKF はイベント mapping の**兄弟キー** `producer` に出す。`via` と同じ位置
づけ(0036 §3.2)であり、`by` は SPEC §7 の actor のままなので trust tier
(§5.3)は正しく読める。

```yaml
generated: { by: human:tanaka@example.co.jp, via: process:app@example.iam.gserviceaccount.com, producer: insightflow/1.4.0, at: ... }
```

**インポートは読み戻さない。** trust family 全体と同じ非対称であり
(0009、0036 §2.2)、他インスタンスのバンドルが運ぶ producer はそれを
裏づける認証を持たない — §3.1 の条件を満たさない自称そのものである。
`examples/demo` のバンドルが既に `by: analysis_agent/gemini-2.5-pro` と
`by` の位置に `/` 形式を書いていることは、この非対称の実例である:
SPEC §7 の正しい文書であり、ochakai は落とさず受け取り、値は採らない。

## 4. これは認可ではないし、trust tier でもない

作らないものを明示する。producer で読み書きを制限しない。producer で
ランキングを変えない。SPEC §5.3 の trust tier は検証台帳の `human:` だけ
から導かれ、本ドキュメントはそこに触れない。producer は**記録**であり、
判断は参照側が provenance を見て行う(0002)。

producer 別の集計面も、いまは作らない。それは
[0051](0051-instance-metrics-and-search-misses.md) が引いた `GET /api/v1/stats`
の側の問いであり、**記録が先、集計が後**という順序自体が §1 の非可逆性から
来ている。0051 が「その場で集計しなかったものは消える」と言ったのと同じ
理由で、いま記録を始めないと後から足せる値が無い。

## 5. 検討して採らなかった案

- **actor の位置に `/` 形式を入れる。** SPEC §7 に最も忠実で、issue が
  最初に想定した形でもある。採らない理由は 2 つ。認証済みの名前を自称で
  置き換えることになる(§2)、そして委譲と同時に起きたとき席が足りない —
  「InsightFlow 1.4.0 が tanaka のために書いた」を表すには actor と via の
  2 席では足りず、`via` を連鎖させることになる。連鎖した `via` は
  「A via B via C」という、どの位置が認証済みか読み手に分からない文字列を
  作る。
- **`attrs` の producer 拡張キーに書く**(`generator: claude-opus-5` のように)。
  SPEC §4.1 の正しい使い方に見えるが、`attrs` は**内容**である — 誰でも
  書けて、content_hash を動かし、リビジョンを増やし、インポートで往復する。
  producer は書き込みという行為についての事実であって、書かれた知識の一部
  ではない。
- **`via` に入れて SA を落とす。** 0027 §3 が却下した「置き換え」そのもの。
- **producer ごとの allowlist**(委譲と同じ形)。名乗る対象が自分自身なので
  詐称の相手が居ない(§3.1)。必要になれば 0027 と同じ形で後から足せる。
- **User-Agent から推測する。** ヘッダを 1 本増やさずに済むが、User-Agent は
  HTTP スタックが書き換える値であり、SPEC §7 の形にもならない。推測した
  provenance は provenance ではない。
- **サーバが版を検査する**(semver を強制する、既知の producer 名に限る)。
  §3.2 のとおり、正直な書き手だけが記録不能になる。
