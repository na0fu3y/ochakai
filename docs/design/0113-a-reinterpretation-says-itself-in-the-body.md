# ochakai 設計ドキュメント 0113: 読み替えは、本文でも言う

Status: Accepted(2026-08-17)。[0097](0097-a-write-says-what-it-did-in-the-body.md)
§4 が「同じ形の問題であり、同じ答えになるはずだが、これは `plan` の決定
ではない。別の記録で決める」と残した `Ochakai-Note` を決める。0097 が
決めたことは一つも動かない — これはその隣に一つ足すだけである。
[0082](0082-what-the-freeze-holds-still.md) §2 の下での**応答専用スキーマ
への追加**であって、ヘッダの移設ではない(§2)。表面の数は一つも動かない
(§5)。
Date: 2026-08-17

## 0. この記録が決めたこと

1. **concept の書き込みの応答本文に `notes` が乗る** — 読み替えの一つ
   ごとに一行、`View` のフィールドとして(§1・§3)。
2. **`Ochakai-Note` ヘッダは残る。** 外すのは 1.0 の仕事である(§2)。
3. **MCP の綴りは動かさない。** 既に本文で返しており、入れ子の深さが
   違うのは面ごとの応答の形であって、後で払う借りではない(§3)。
4. **Web UI が読み替えを言うようになる**(§4)。
5. **CLI と `text/markdown` 表現はヘッダを読み続ける**(§5)。

## 1. 読み替えを誰も見ていなかった面が二つあった

`Ochakai-Note` が運ぶのは、**サーバが受け取ったが、書かれた通りには
読まなかった値**である — OKF のライフサイクルにない `status`、解釈でき
なかった日付、この instance の観測ではなく文書自身の主張として保管した
trust family。「再解釈は黙って行われない」([0075](0075-the-bundle-is-the-address-space.md)
§3.1)が理由であり、書いた側が次の読みで気づくのではなく**その場で**
知るための一行である。

その一行は、これまでヘッダにしか無かった。0097 §1 が `plan` について
書いたことがそのまま当てはまる:

```
$ curl -X PUT --data-binary @revenue.md .../api/v1/metrics/revenue.md
{"id":"metrics/revenue","document":"---\ntype: Metric\n…
```

`status: retired` と書いて送ったのに、それが OKF の値ではないので
`draft` として読まれた、ということは**この出力のどこにも無い**。`jq` に
通せばヘッダは消える。生成クライアントはヘッダをモデルに持たない。

そして本当に効いたのは Web UI である。**キュレーションの面**
([0067](0067-four-faces-and-what-they-decline.md) §1)で人が文書を編集
して保存したとき、読み替えを受け取っていたのは fetch の
`Response.headers` で、ページはそれを一度も読んでいなかった。**直せる
のはその人だけなのに、その人にだけ届いていなかった。**

MCP は最初から本文で返している(`notes`)。つまり届いていない面が二つ
あって、届いている面が一つあり、値は三つとも同じである。

## 2. 移設ではなく追加である — 0097 と同じ取引

0082 §2 が凍結の対象に「**ヘッダ名**」を挙げている。`Ochakai-Note` を
応答から外すのは住所を消すことであり、[0064](0064-rest-stops-at-api-v1.md)
§11 が「凍結を破ってよい唯一の理由はセキュリティ上の欠陥」と書いた
その理由には当たらない。**足すほうは凍結が止めているものではない** —
`View` は応答専用スキーマで、知らないキーはデコーダが無視する。

だから 0097 が `plan` で受けた取引をそのまま受ける: **二箇所が同じこと
を言い、片方は 1.0 で消える側だと分かっている。**
[#597](https://github.com/na0fu3y/ochakai/issues/597) の「1.0 を待つもの」
に `Ochakai-Note` の行を足すのがこの記録の後始末であり、`Ochakai-Plan` /
`Ochakai-Unchanged` の隣に並ぶ。

## 3. 置き場所は `View` で、MCP は動かさない

REST の**本文が `View` そのもの**なので、`notes` はそこに乗る — `plan`
が乗ったのと同じ位置である(0097 §3)。

MCP の答えは封筒で、`knowledge` と `notes` と `hint` が並んでいる。
つまり JSON のパスは REST の `notes` と MCP の `notes` で**深さが違う**。
これを揃えないと決める:

- MCP を `knowledge.notes` に移すのは MCP の破壊である。
  [compatibility.md](../compatibility.md) の下で 0.x の MCP は破壊して
  よいが、**買えるのは綴りの対称性だけ**で、しかもエージェントの読む
  位置が concept の下に潜る。
- REST を封筒にするのは凍結の内側の本文の形を変えることで、できない。

**揃える先が両方とも悪いなら、揃っていないのは借りではない。** 面ごとに
答えの形が違い、その形の中で同じ場所 —「答えのいちばん上」— に置いて
ある、というのが今の姿である。#597 の「1.0 を待たないもの(束ねるだけ)」
に積む項目ではない。

`domain.View.Notes` を REST だけが埋めるのはそのためで、型のコメントが
そう書いてある。

## 4. Web UI は、読み替えを言う

編集画面の保存が出す一行に足す。**`plan` を読んで「変更はありません。」
と言えるようになったのと同じ経路**で(0097、`saved.plan`)、
`saved.notes` があればそれを続ける:

```
保存しました。 ただし: status "retired" is not an OKF lifecycle value
(draft | stable | deprecated); read as draft
```

トーストの表示時間はこのときだけ伸ばす。既定の 2.2 秒は「保存しました。」
— 読み手が既に予期している確認 — の長さであり、文書の一行について
サーバが何をしたかを名指す文はその長さで読めない
([0094](0094-the-page-runs-under-a-policy.md) §4 が `#toast` を live
region にしてあるので、読み上げにも同じだけ乗る)。

**バナーにはしない。** 保存は成功しており、エラーではない。画面に留めて
直させるのも採らない — 保存後の版と手元の版が食い違ったまま次の保存が
`If-Match` で落ちる形を作る。

## 5. やらないこと

- **ヘッダを外すこと**(§2)。1.0 の仕事である。
- **`text/markdown` の応答に乗せること。** 本文が文書そのものなので、
  置く場所が無い。そこではヘッダが唯一の運び手のままであり、
  `Ochakai-Note` が残る理由の半分はこれである。
- **CLI にヘッダを読むのをやめさせること。** `internal/apiclient` は
  JSON と文書のどちらの表現でもヘッダから読めており、片方の表現でしか
  読めない経路に替えるのは、動いているものを狭くする。0097 §4 が
  `plan` で同じ判断をしている。
- **ファイルの書き込みに乗せること。** バイト列は読み替えられない。
- **`notes` を語彙にすること。** 中身は人が読む文であって、クライアント
  が分岐する値ではない — だから [surface.md](../surface.md) の `VOCAB`
  は動かない。同じ理由で `HEADER` も 13 のままである(応答本文への追加
  はどの次元にも現れない、と 0097 が HEADER の節に書いた通り)。
