# ochakai 設計ドキュメント 0066: 四つの姿勢を、一語で言う

Status: Accepted(2026-08-02)。**デプロイの姿勢の現行ドキュメント。**
[0040](0040-read-only-mode.md) を Superseded にし、
[0042](0042-public-read-only.md) を Superseded にし、
[0060](0060-one-word-for-the-posture.md) を Superseded にする。
**三つが決めたことは何一つ変えない** — 変えるのは、それが三冊に分かれて
いたことだけである。identity をどう読み、誰として記録するかは同じ統合の
片割れである [0065](0065-identity-and-provenance.md) が持ち、この記録は
その上に「このデプロイは何をするか」を置く(issue
[#471](https://github.com/na0fu3y/ochakai/issues/471))
Date: 2026-08-02

## 1. 四つの姿勢は二軸の四象限である

実際にある軸は二つ — **呼び出し元が特定されるか**と、**誰かが書けるか**:

|  | 書ける | 書けない |
|---|---|---|
| **identity を読む** | 既定([0065](0065-identity-and-provenance.md) §1) | `read-only`(§2) |
| **identity を読まない** | `dev`(ローカル専用) | `public`(§3) |

四象限がすべて意味を持ち、しかも互いに排他である。だから
`OCHAKAI_MODE` 一語で言う — 未設定 / `read-only` / `public` / `dev`。

```
未設定       Cloud Run IAM が到達を決め、到達した者は読み書きできる(0065 §1)
read-only    呼び出し元は特定される。すべての書き込みを拒否する(§2)
public       identity を一切読まない。すべての書き込みを拒否する(§3)
dev          認証を切る。すべて human:anonymous で、書ける。ローカル専用
```

ブール三つ(かつての `OCHAKAI_READ_ONLY` / `OCHAKAI_PUBLIC_READ_ONLY` /
`OCHAKAI_INSECURE_DEV`)で符号化すると八通り書けてしまい、余った符号を
規則で潰すことになる — 黙って補正する含意が二つ、起動を拒否する組み合わせが
一つ。デプロイする人が読むものは変数三つと規則三つだった。一語なら
**規則は消えるのではなく、書き下せなくなる。**

`dev` が姿勢の一つだと見えにくかったのは、かつての名前が姿勢ではなく機構
(「認証を切る」)を言っていたからである。`OCHAKAI_MODE=dev` は名前で
**用途**を伝え、危険の伝達は [configuration.md](../configuration.md) と
デプロイガイドに移る。**型で防げるものを型で防ぎ、防げないものを文章に
任せる**ほうが順序として正しい。

## 2. `read-only`: このデプロイは書かない

呼び出し元は特定されるが、知識を変える操作をすべて拒否する。これで公開
デモを置け、参照専用のインスタンスを配れ、移行や監査の間に内容を凍結できる
— どれも、それまでは Cloud Run IAM で到達そのものを切るしかなかった。

**強制点はサービス層に一つだけ置く。** REST と MCP は同じ
`service.Service` を通るので、そこで拒めばどの面からも漏れない。ルーティング
側で HTTP メソッドを見る実装は、新しい書き込み面を足した人が middleware を
知らなければ穴が開く。

**例外は利用テレメトリである。** 検索ヒットや取得回数の記録
([0029](0029-usage-recording-off-the-read-path.md))は read-only でも動き
続ける。これは呼び出し元が書いた内容ではなく**サーバー自身の観測**であり、
止めると `sort=usage` のフィードが凍って製品が壊れて見える — デモで見せたい
ものが、まさにそのフィードである。

面ごとの現れ方([0015](0015-surface-consistency.md)):

| 面 | 現れ方 |
|---|---|
| REST | 書き込みは **403**。全 `/api/v1` 応答に `Ochakai-Read-Only: true` を付ける |
| MCP | 書き込みツールを**そもそも登録しない**(常に失敗するツールは agent の context を無駄に食わせる) |
| CLI | `whoami` が read-only と表示する。書き込みはサーバーの 403 をそのまま見せる |
| Web UI | Verify / Reject / Edit / New を出さない(押せて必ず失敗するボタンは嘘である) |

MCP がツールを消し、REST がヘッダで告げるという非対称は意図的である —
MCP には能力を宣言する仕組み(tools/list)があり、REST には無い。それぞれの
面が既に持っている語彙で伝える。

書き込み系の REST 面は**削除しない**。404 ではなく 403 を返す — 経路が消えた
のではなく、このデプロイが断っている、という区別が要る。

## 3. `public`: identity を一切読まない

`internal/httpauth` は Cloud Run が転送した ID トークンを**署名検証せずに**
読む — 非公開の Cloud Run サービスでは Google が検証済みで、署名は
`SIGNATURE_REMOVED_BY_GOOGLE` に置き換わって届くからである。公開したまま
これを続けると二つのことが起きる。トークンが無ければ **401** になって訪問者は
ページを開けず、しかも**偽造トークンが通る**(実測で、未署名のトークンで
`ceo@example.com` を名乗ったリクエストが 200 を返した)。**読み取り専用に
しただけでは、どちらも解消しない。**

だから公開デプロイは identity を読むのをやめる:

- `Authorization` / `X-Serverless-Authorization` を読まない。検証できない
  ものを読むくらいなら、読まない方が正しい。
- `Ochakai-On-Behalf-Of` を読まない — 委譲(0065 §3)は信頼済みの呼び出し元
  を前提にするが、ここにはそれが居ない。
- すべての呼び出し元が `human:anonymous` になり、**401 は返さない**。
- 検索ミスのクエリ文字列も残さない
  ([0051](0051-instance-metrics-and-search-misses.md) §3.4)。

**書き込まないから、provenance を読まないことが正当化される。** 書き込みが
無ければ記録すべき作者もいない。だから公開と read-only は別々のつまみで
あってはならず、`public` が両方を一語で言う。

**トークンを本物として検証する道は採らない。** 検証器を内蔵すれば鍵の
取得先・キャッシュ・audience 設定という運用面が生える — secret-zero
([0003](0003-gcp-only.md))は「認証は前段が済ませている」という前提の上に
成り立っている。そしてデモに必要なのは identity ではない。**誰が読んだかを
知る必要が無い。**

## 4. 綴りが読めなければ起動しない

`OCHAKAI_MODE=readonly` や `=true` は**起動エラー**にする。既定に落とさない
([0053](0053-embeddings-by-default.md) §2.4 と同じ理由)— read-only のつもりで
書ける姿勢になったデプロイは、ログではなく**知識のほうで**それに気づく。

`OCHAKAI_MODE` の三つの綴りは `docs/surface.md` の VOCAB に数えない。VOCAB が
数えるのは**キュレーターが頭に入れておく語**であり、姿勢はデプロイする人の
語である — それは ENV が既に数えている。

## 5. どちらも認可ではない

- **read-only** は呼び出し元を区別しない。運用者にもサービスアカウントにも
  IAP を通った人間にも等しく効く。「あなたには書けない」ではなく
  「**このデプロイは書かない**」であり、エントリ単位の権限も導入しない。
  provenance の解釈も変えない — 誰の書き込みも記録しないので、信頼の判断材料は
  増えも減りもしない。
- **public** は provenance すら読まないところまで下がる。判断材料が減るだけで
  判断機構は増えない。**identity を読まないことは、認可を足すことの反対で
  ある。**

したがって [0065](0065-identity-and-provenance.md) §1 の「認可を持たない」は
不変である。0065 が退けた「呼び出し元によって挙動を変える機構」は、依然として
無い。

## 6. 検査する不変条件([0035](0035-verifiability.md))

- **書き込みメソッドの網羅** — read-only のサービスで、知識を変えるすべての
  メソッドが `ErrReadOnly` を返す。足した人がここに足し忘れたら落ちる。
- MCP のツール集合が読み取りのみであること、REST の書き込みが 403 とヘッダを
  返し、読み取りが 200 のままであること。
- **公開かつ書き込み可能が書き下せない**こと(§1 の一語で、型が防ぐ)。
- `public` で、偽造トークン付きのリクエストとトークン無しのリクエストが
  **同じ actor に解決される**こと。主張は「anonymous になる」ではなく
  「入力に依存しない」である。
- `public` で委譲ヘッダが actor を変えないこと、401 を返さないこと。

## 7. やらないこと

- **エントリ単位・呼び出し元単位の read-only。** それは認可である(§5)。
  要るなら Cloud Run IAM で到達を分ける。
- **実行時の姿勢切り替え。** 環境変数のみ — API で切り替えられれば、それを
  叩ける者が解除できて、保証が保証でなくなる。
- **read-only を安全機構として売ること。** 運用モードであって敵対的な相手への
  防御ではない。公開デモに使う場合、守っているのは知識の内容であって、
  インスタンスそのものではない。到達制御は依然として Cloud Run IAM の仕事で
  ある。
- **公開かつ書き込み可能なデプロイ**、および匿名の書き込みを一部だけ許すこと
  (フィードを荒らす経路になり、しかも誰が荒らしたか記録できない)。
- **レート制限や濫用対策。** 必要なら Cloud Run の同時実行数と Cloud Armor が
  担当する。ochakai は知識を返すだけである。
- **姿勢を CLI フラグや設定ファイルにすること。** Cloud Run の設定面は環境
  変数であり(0003)、第二の設定経路は C4(No FDE)を悪くする。
