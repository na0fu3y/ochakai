# ochakai 設計ドキュメント 0093: 予算は応答全体を縛り、一位は名前だけでは返らない

Status: Accepted(2026-08-10)。[0067](0067-four-faces-and-what-they-decline.md)
§4 を改訂する — 「`hits` は**バイト予算の外**に置く」を撤回し、予算は応答
全体を縛る。§4 の他の決定(`hits` は全サーフェスで順位に徹する、順位は
fetch を判断できるだけの情報を持つ)はそのままである。0067 は現行のまま。
[0033](0033-context-hits-are-a-ranking.md)(0067 が引き継いだ)の
「concept は丸ごとか、名前だけか」も、§2 の一点を除いてそのままである。
Date: 2026-08-10

## 0. この記録が決めたこと

1. **`budget` は応答全体のバイト数である** — `hits`・`outline`・
   `concepts` の合計。順位と outline は**床**であって常に返り、予算が
   買うのは**丸ごとの concept** である(§1)。
2. **一位が予算に収まらなかったときだけ、その outline 行が本文の冒頭を
   運ぶ**(`excerpt`)。コードフェンスの手前で切る(§2)。
3. **近似重複の除去はしない**(§4)。

## 1. 予算の外に何かがあるなら、それは予算ではない

0067 §4 は `hits` を予算の外に置いた。理由は「本文を持たず件数にも上限が
ある」だった。**どちらも本当で、それでも足りない。**

`hits` は `2*limit` 行あり、`limit` の上限は 20 なので最大 40 行 —
実測で約 5 KB である。MCP の既定予算は 12,000。**呼び出し側が
`budget=12000` と言って受け取るのは 12,000 + 自分では計算できない量**で
あり、それはコンテキスト窓を見積もるための数として機能しない。

同じ議論は一度通っている。`outline` を予算の内側に入れたときの理由が
これだった — 「配った concept だけを縛る予算は、応答全体を縛らないまま
にする。呼び出し側が窓に収めなければならないのは応答全体である」。
**`hits` は、その論理が届いていなかった最後の一つ**である。

**買うものと床を分ける。** 予算が買うのは丸ごとの concept であり、
`hits` と `outline` は床 — 「何が在ったか」は常に返る。予算を上げられる
のは、そこに何かが在ったと知っている呼び出し側だけだからである
(0033 が outline の床に与えたのと同じ理由)。順位は**削らない**: 削れば
「在ることを知らせない」ことになり、床の意味が消える。

**予算より床が大きいときは、concept をゼロ個配って床を返す。** 減算を
そのまま渡すと `budget <= 0` が「上限なし」と読まれ、**最も小さい予算が
最も大きい応答を返す**という正反対の挙動になる。ここは実装ではなく決定
なので書いておく。

**実際の変化は小さい。** 既定の `limit` は 5 で、`hits` は 10 行・約
1.2 KB — 12,000 の 10% である。大きいのは `limit=20` を明示した
呼び出し側で、そこは自分で選んだぶんだけ concept が減る。

## 2. 一位は、名前だけでは返らない

0033 は「concept は丸ごとか名前だけか」と決め、理由をこう書いた —
**半分になった attested computation の SQL は、それでも実行できるように
見える**。この規律は正しく、ここでも変えない。`concepts` に入るものは
今までどおり丸ごとである。

変えるのは**一つの穴**である。予算より大きい concept は、順位が一位でも
outline 行になる。MCP の既定 12,000 バイトでは、**最重要の一件が既定で
保留され**、それを取りに二往復目が要る — `get_context` が防ぐために存在
する、その往復である。

そこで、**一位が outline になったときだけ、その行が本文の冒頭を運ぶ**。
0033 の理由は**反論せずに満たす**:

- **切るのは本文であって文書ではない。** frontmatter は行が既に運んで
  いるフィールドであり、そこから始める抜粋は自分の予算で行の複製を書く
  ことになる。
- **最初のコードフェンスの手前で止まる。** だから抜粋が query の一部を
  含むことはない — 0033 が挙げた失敗そのものが、構造的に起きない。
- **段落境界を優先する。** 書き手が考えを切ったところで終わる。
- 名前は `excerpt`、同じ行の `bytes` が「あとどれだけあるか」を、`id` が
  「どこにあるか」を言う。**全文だと読める場所が一つも無い。**

**一位だけ、そして予算の四分の一まで。** 予算が抜粋と同じ桁のときに
抜粋を置くと、それは**一件が下の全部を飢えさせる**ことになり、greedy
packing がまさに防いでいる形である。四倍に満たない予算は、名前だけを
返す。

## 3. 面への出方

| 面 | 何が変わるか |
|---|---|
| REST | `budget` の説明が「応答全体」になる。`ContextOutline.excerpt` が増える — 応答専用スキーマへの追加なので凍結の外([0082](0082-what-the-freeze-holds-still.md))、golden は同じ PR で再生成 |
| MCP | `budget` のスキーマ文が同じく変わる。抜粋があるときだけ hint が一文増える — スキーマは会話の間ずっと常駐するが、hint はその応答にしか乗らない |
| CLI | 変わらない。`--json` が応答をそのまま出す |
| Web UI | 変わらない。`get_context` はエージェントの面である(0067 §4) |

## 4. やらないこと

- **近似重複の除去。** 「同じメトリクスの言い換えが 5 件返る」のは、
  ベースに 5 件あるということである。検索時に隠すのは直さずに覆うこと
  で、しかもどれを残すかをサーバが黙って決める。重複はキューにして人が
  裁定するものであり、その前に**距離の分布を測る**のが順番である
  ([0089](0089-a-half-embedded-concept-says-so.md) §4 と同じ規律)。
- **配る concept の切り詰め。** `concepts` は丸ごとのままである(§2)。
- **outline の全行に抜粋を付けること。** 抜粋は「そうでなければ存在ごと
  見えない最良の一致」のためであって、予算が落とした行すべてのためでは
  ない。
- **順位を削ること**(§1)。
- **予算の既定を上げること。** 12,000 が窮屈になったなら、それは
  呼び出し側が決める数である。
