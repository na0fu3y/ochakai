# ochakai 設計ドキュメント 0045: 取り込んだ検証と、この場で下した検証を分ける

Status: Accepted(2026-07-28)。[0043](0043-document-first.md) §3.2 の
「インポートの `verified` キーは存在すれば取り込んだ actor による検証 1 行を
起こす」1 点を改訂し、検証行に `source` を足す。台帳そのものの姿
(追記のみ・複数可・文書に触れない)は 0043 が現行のままである。
実装は同 PR。
Date: 2026-07-28

## 1. 目的

0043 §3.2 は外来バンドルの `verified` キーの扱いを決めた —
**存在だけを読み、値は捨て、取り込んだ actor による検証 1 行を起こす**。
値を読まない部分は正しい。provenance は認証から来るのであって payload から
来ない(0002、0009 §3.2)。

残ったのは**起こす**部分である。帰結が 2 つある。

### 1.1 明示されない断言

`ochakai import` を 1 回叩くと、`verified` キーを持つ全エントリに対して
実行者名義の検証行が起きる。66 件のバンドルなら、1 コマンドで 66 件の
信頼表明を発行したことになる。実行者はそれを求めていない —
求めたのは取り込みである。

CLI の他のどの操作も、1 回の呼び出しで N 件の信頼表明を発行しない。
`verify` は明示的に id を並べたときだけ、並べただけ発行する。

### 1.2 区別できない記録

台帳の行は `{by, at}` だけである。**この場で人が読んで下した検証**と、
**外部バンドルを取り込んだ副作用で生えた検証**が、6 か月後の読み手にとって
同一に見える。

README が前面に置く "memory layers remember what happened; ochakai curates
what's true" は、この 2 つが違うことに賭けている。同じ見た目になるなら、
賭けの分だけ主張が緩む。

## 2. 何が問題ではないか

先に 2 つ潰しておく。

**payload が名乗っているのではない。** `verified: by: alice@corp` と
書いても alice は台帳に載らない。0043 の実装は値を捨て、認証された
呼び出し元を記録する。0009 §3.2 の原則は守られている。問題は
**誰が記録されるか**ではなく、**その人がそれを意図したか**である。

**注記では届かない。** import は既に何をしたかを出力する。しかし検証は
永続する記録であり、スクロールバックは残らない。0035 の規準で言えば、
機械が検査できない不変条件を人間の注意力に預けている状態である。

## 3. 決定

### 3.1 取り込みは検証を起こさない — `--adopt-verified` が要る

`ochakai import` は既定でバンドルの `verified` キーから検証行を起こさない。
キーを持つエントリを数え、報告するだけである。

```
imported 66 entries (66 created, 0 updated, 0 unchanged, 0 adopted, 0 attachments, 0 skipped, 1 notes)
note: 66 entries carry a verified key and none was adopted;
      pass --adopt-verified to confirm them in your name
```

`--adopt-verified` を渡したときだけ 0043 §3.2 の挙動になる。理由は 2 つ。

- **信頼の表明は明示の行為である。** 66 件の検証を発行するのは
  `ochakai verify` に 66 個の id を渡すのと同じ重さの行為であり、
  同じだけ意図的であるべきである。
- **既定が真になる。** 取り込み直後の状態は「バンドルの中身はあるが、
  この場では誰も保証していない」であり、それは事実である。そこから人が
  `verify` で上げるのが 0001 §9 の双方向ループそのものである。

代償を認めておく: `export` → `import` の往復で検証台帳が落ちる。これは
0009 の「バンドルは知識のみを運び、provenance はインスタンス固有」と
整合しており、落ちるのが正しい。自分のインスタンスのバックアップを
戻すときは `--adopt-verified` を渡す — それは「これらは私のものだった」
という表明であり、まさに明示されるべき表明である。

### 3.2 検証行は出所を持つ

`Verification` に `source` を足す。**空がこの場で下した検証**、
**非空がどこから採ったか**である。

| | `by` | `source` |
|---|---|---|
| 人がレビューして verify | 認証された actor | 空 |
| `import --adopt-verified` | import を実行した actor | `okf-bundle:<引数>` |

`by` は変わらない。取り込みを実行した者が保証したという読みは 0043 の
ままである。`source` が足すのは**その保証がどういう行為だったか**であり、
それは `by` からは復元できない。

台帳は追記のみなので、既存行の `source` は空 —「この場で下した」という
読みになる。0043 以前から居る行にとってそれは正しい(status が
`verified` だった行の移行であり、その status を書いたのは
このインスタンスへの書き込みである)。

### 3.3 `source` は信頼の境界ではない

`source` は**検証者自身の申告**であり、サーバーが裏を取る値ではない。
`rejection.note` と同じ種類の値である。`POST /api/v1/verify/{id}` を
直接叩いて `source` を省けば、誰でも「この場でレビューした」形の行を
書ける。

それでよい。省いても得はしない — 省くのは**自分の主張を強める**方向で
あり、それができるのは既にその名前で verify できる人だけである。
`source` の仕事は攻撃者を止めることではなく、**普通の経路が本当のことを
言うようにする**ことである。認可を持たないという 0002 の姿勢はここでも
変わらない。

### 3.4 各面(0015)

- **REST**: `POST /api/v1/verify/{id}` は任意の body
  `{"source": "..."}` を受ける。省略・空 body は今までどおり。
  応答の `observed.verified[]` の各要素が `source` を運ぶ。
- **CLI**: `import --adopt-verified` が `source` を埋める。
  **`ochakai verify` には `--source` を生やさない**(意図的な不作為)。
  端末で `verify` を叩く人はレビューしている人であり、「実はしていない」
  と言うための語彙を渡す理由がない。取り込みという別の行為には
  別のコマンドがある。
- **MCP**: 変更なし。verify はもともと MCP ツールではない —
  ループの人間側だからである(0025、`service.Verify` のコメント)。
- **Web UI**: 検証履歴に出所を表示する。レビューキューを読む人が
  「これは誰かが読んだのか、バンドルが持ってきたのか」を区別できることが、
  この変更の目的そのものである。

### 3.5 保存

`knowledge_verification` に `source text NOT NULL DEFAULT ''` を足す
(マイグレーション 0025)。既存行は空のまま。索引は足さない —
`source` で引く需要はまだ無い。

### 3.6 エクスポート

`source` は**出ていかない**。OKF SPEC §5.2 の `verified` は
`{by, at}` のリストであり、`source` はこのインスタンスが自分の
記録について付けた注記である。却下(0043 §3.3)がバンドルに乗らないのと
同じ理由で、これも乗らない。

次のインスタンスにとっての採用は**そのインスタンス自身の行為**であり、
`--adopt-verified` を渡した時点でそのインスタンスの `source` が付く。
連鎖はそれぞれの正直さで保たれる。

## 4. 採らなかった案

**(a) 0043 の自動採用を残し、印だけ足す。** 記録は読めるようになるが、
実行者が選んでいない断言を 66 件発行することは変わらない。§1.1 が
主要な害であり、印はその二次的な帰結を可読にするだけである。

**(b) 明示化だけして印を足さない。** 行為は直るが記録は直らない。
半年後に台帳を見た人は、採用とレビューを区別できない。§1.2 は
`--adopt-verified` を渡したかどうかがどこにも残らない以上、
フラグだけでは解けない。

**(c) 取り込みは検証を一切起こさない。** 自分のインスタンスのバックアップを
戻す場合に台帳を丸ごと失い、しかも「これらは私のものだった」と言う手段が
無くなる。`--adopt-verified` はその手段である。

**(d) payload の `verified.by` を読む。** 0002 と 0009 §3.2 に真正面から
反する。検討していない。

**(e) `source` を列挙型(`review` / `adopted`)にする。** 「どのバンドルが
持ってきたか」を失う。66 件の出所を後から辿れることには実用上の価値が
あり、自由文字列の代償(雑な値が入りうる)は §3.3 のとおり
信頼の境界ではないので受け入れられる。

## 5. 影響

- **破壊的変更。** `import` の既定の振る舞いが変わる。0043 の実装は
  未リリースなので、**リリース済みのどのバージョンから見ても**
  「バンドルの verified が自動で自分の検証になる」挙動は世に出ていない
  — 0.15.0 では `verified` キーは status を verified にしていた。
  したがって利用者から見た変更は「バンドルの verified は既定で
  引き継がれない」の 1 点であり、それは 0.15.0 からの変更としても
  1 度で説明できる。
- `Verification` の JSON に `source` が増える(省略可能)。
- 移行は列の追加のみ。既存の台帳は読み方が変わらない。
