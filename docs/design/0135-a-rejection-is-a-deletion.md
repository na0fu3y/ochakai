# ochakai 設計ドキュメント 0135: 却下は削除であり、理由は log が運ぶ

Status: Accepted(2026-08-28)。
[0104](0104-a-ruling-travels-with-its-reason.md) を Superseded にし、
[0068](0068-how-a-face-is-added-and-removed.md) §4 の裁定の語彙を改訂し、
§1 の畳む規則を `reject` と `delete` の対に当てる(§7)。
[0075](0075-the-bundle-is-the-address-space.md) §3.1 の観測と主張の分離と
[0009](0009-provenance-portability.md) §3.2 は**動かない**。この記録は
同じ分離を、frontmatter ではなく OKF SPEC §9 の log で満たす。
Date: 2026-08-28

## 0. この記録が決めたこと

1. **却下は削除である。** `ochakai reject` は `ochakai delete --note` に
   畳まれ、却下は concept を soft-delete する(§7)。
2. **理由はその出来事のものになる。** note は削除を記録したリビジョンに
   載り、OKF SPEC §9 の `log.md` がそれを刷る。却下台帳
   (`knowledge_rejection`)はテーブルごと消え、export の frontmatter から
   `rejected_by` / `rejected_at` / `rejected_note` の三キーも消える(§2)。
3. **裁定は何も塞がない。** 却下された id は**どの面からも書き直せる** —
   `--note` の有無で変わるのは理由が記録されることと log の語が `reject`
   になることだけで、振る舞いは変わらない(§3)。
4. **`withdrawn` は無くなる。** 取り消すものが無い(§4)。
5. **`rejected` フィルタは無くなる。** 却下された concept は検索にも
   一覧にも**存在しない** — 隠されているのではなく、消えている(§3)。

## 1. 却下だけが減衰しなかった

検証には `stale_after` があり、期限切れは `sort=stale_after` のフィードに
並ぶ([0069](0069-the-loop-and-what-measures-it.md) §2)。却下には期限が
無く、どのフィードにも並ばなかった。そのうえ:

- 更新は裁定を持ち越す。**文書を全面的に書き直しても no は残り**、
  裁定は内容ではなく id に貼り付いていた。
- 検索も一覧も既定で隠す。理由が古びても、誰も掘り返せと言われない。

三つが重なると、**一度の却下がアドレス一本を恒久的に埋める**。
「なぜ却下したか」は刻々と変わるのに、その記録だけが変わらない。0104 は
理由を*運ぶ*ようにしたが、*思い出させる*ようにはしていない。

**却下は保存すべき状態ではなく、起きた出来事である。** 状態として持つ
限り減衰の面が要り、それは面を足すことになる。出来事として持てば要らない。

## 2. OKF に否定の段は無い。書ける場所は §9 だけ

SPEC v0.2 の語彙を総当たりした。

| 候補 | なぜ置けないか |
|---|---|
| `status: deprecated` | 「kept for links and history; no longer current」— 一度も受け入れていないことではない |
| `status: draft` | draft は正常な状態であり、裁定者も理由も落ちる |
| `stale_after` | 減衰であって拒絶ではなく、**著者の宣言**であって裁定ではない |
| `verified` の不在 | trust 段は unverified / machine-confirmed / human-reviewed の**単調な三段**で、否定の段が無い(§5.3) |
| `tags` | frontmatter の主張として旅し、import で読み戻る |
| `sources` / `attester` / `executor.receipt` | どれも肯定側の信号。§10.6 の verification と attestation は両方とも肯定 |
| 拡張キー(§4.1) | **現行**。規格違反ではないが、観測が主張の位置に居ることは変わらない |
| `index.md`(§8) | 現存する物の列挙であって履歴ではない |

**OKF の信号は単調である。** だから否定を frontmatter のキーに乗せると、
乗せ方によらず「このインスタンスの観測が、他所へ旅する主張になる」に
帰着する。0009 §3.2 と 0075 §3.1 が禁じているのはそれである。

`log.md`(§9)だけが例外になる。三つの理由による:

- §9 は「record the history of changes to that scope」— **イベントの記録
  であって concept の主張ではない**。
- 先頭の太字語は「`**Deprecation**` is a convention, not a requirement」
  なので `**Rejection**` は適合する。
- §6.1 が「Consumers MUST tolerate broken links」— リンク先が存在しなくて
  よい。**消えた concept について書ける、規格の中で唯一の語彙**である。

ochakai は既にこれを出している。`RenderLog` がリビジョンを
`okf.LogDocument` に流し、階層の各段に `log.md` を書き出す(CLI は
`ochakai log`)。`change` の語彙には `reject` が既にある — 却下は今日
すでに §9 のイベントとしてバンドルを旅している。**足りないのは一行が
note を持たないことだけ**であり、この記録はそれを足す。

## 3. 理由は出来事のものであって、壁ではない

却下は soft-delete になり、**`--note` はその削除がなぜ行われたかを
リビジョンに書く**。変わるのはそれだけである — 墓標は普通の墓標のままで、
`--note` の有無で蘇生できるかどうかは**変わらない**。却下された id は
MCP の `put_concept` からも書き直せる。

**フラグの有無で永続性が変わる形を採らなかった**のは、驚きが壊れる側に
落ちるからである。`--note` は「理由を書く」と読めるフラグで、それが
「この住所を閉じる」を意味するなら、丁寧に書いた人ほど踏む。**記録した
理由は情報であって、次の書き手を止める権限ではない。**

だから台帳ごと無くなる。`knowledge_rejection` は蘇生を止めるためだけに
存在していたので、止めるのをやめれば読む者がいない。理由は**リビジョンの
列**になり、§9 の `log.md` が刷る — この記録が §2 で「理由は log が運ぶ」と
言ったことが、そこで文字通りになる。

塞ぐ側に残るのは二つだけで、どちらもこの決定の外である
([0015](0015-surface-consistency.md) §3.1): **検証済みだった concept の
墓標**と **deprecated だった墓標**。人が保証した内容が、判断されたことの
無い draft として戻ってくるのを止める規則であり、却下とは関係がない。

## 3.1 何を失うか

**「同じ提案が返ってこない」は無くなる。** 却下された id にエージェントが
書き戻すのを止めるものが無い。理由はリビジョンと `log.md` に残り、読めば
分かる — **読ませる強制力はゼロ**である。README と
[positioning](../positioning.md) の「memory of *no*」は、その線で書き直す。

代わりに得るものが二つある。**リセットを持つデプロイが種を失わなくなり**
(§5)、**サンドボックスで訪問者が却下した concept も次の import で戻る**。
そして裁定が古びたとき、**誰かが解除して回らなくても新しい提案が通る** —
これは §1 で数えた不満そのものへの答えである。

## 4. 取り消しは無くなる

`withdrawn` は「保証はしないが no は取り下げる」という最も稀な操作の
ために四つの綴りを使っていた(0068 §4)。**取り消すものが無くなった** —
却下は状態ではなく出来事であり、出来事は取り消せない。id に書き直せば
新しい concept がそこに立ち、log には却下も再提案も両方残る。

## 5. リセットを持つデプロイが種を失わなくなる

匿名で誰でも書けるデプロイ([0087](0087-a-sandbox-says-it-is-one.md))では、
訪問者が種の concept を却下できる。生きた却下は通常の一覧のどれにも出ず、
`import` もその id への着地を拒むので、**リセットの輪から永久に外れて
いた** — 職は「18 件を戻した」と報告し、生きているのは 17 件だった。

却下が削除になり、その墓標が誰にも塞がれなくなると、`import` は普通に
蘇生させる。リセットは自分で閉じる。墓標を列挙する新しい面は要らない。

## 6. 面ごとの着地

| 面 | 何が変わるか |
|---|---|
| REST | 却下は `DELETE /api/v1/bundle/{path}?note=` になる。`POST /api/v1/review/{id}` の `ruling` は `verified` 一値になり、`rejected` と `withdrawn` が落ちる。`GET /api/v1/search` から `rejected` が落ち、`Revision` と `Change` に `note` が生える(応答専用なので凍結の外) |
| CLI | `ochakai reject` が `ochakai delete --note` に畳まれる。`--withdraw` と `--rejected` が落ちる。**`--if-match` が却下にも効くようになる** — 読んだ版に対してだけ却下できる(`reject` は持っていなかった) |
| MCP | `search_concepts` から `rejected` が落ちる。裁定の面は無いまま(0067 §6) |
| Web UI | 「却下」のボタンは残る — 変わるのは呼ぶ先だけである。`Withdraw rejection` と却下済みの一覧が落ち、履歴パネルが理由を出す |

## 7. 却下した案

- **`ochakai reject` を残す。** 0068 §1 が verify と reject を畳まなかった
  のは「行為が違う」からだが、あれは**その二つについての判断**であって、
  reject と delete の対についての判断ではない。却下が削除になった以上
  能力は一つであり、裁定が載るかどうかは `--note` の有無で表せる —
  コマンドを二本にしないと表せない差ではない。残す側の理由は二つとも
  弱かった: レビューのループが verify / reject の対で書かれているという
  **対称性**はヘルプと Web UI のラベルで解ける命名の問題であり、
  **爆風半径**の違いは `delete` の `--if-match` がむしろ却下を安全にする。
  決め手は逆側にある — 却下が削除になった後も `reject` という綴りを残すと、
  **打った人は concept が消えると思わない**。綴りが結果を言わない面を、
  0104 が直した直後にこちらの手で作ることになる。
- **却下を `status: deprecated` に畳む。** §2 のとおり意味が違い、
  インスタンスの裁定が文書の主張になって旅をする。
- **墓標を列挙する面を足す。** §5 の問題のために検討したが、蘇生が
  経路を閉じるので要らなくなった。面を足さずに済むほうを採る。
- **`concepts.rejected` を墓標の数として残す。** 消えたものは concept の
  数ではない。数えたいのは出来事であり、それは `log` の側にある。
- **`--note` を付けた削除だけ蘇生を塞ぐ。** 最初に書いた形で、§3 の
  とおり却下した。フラグの有無が永続性を切り替えるのは、`git tag` の
  `-m` と同じ驚き方をする。
- **人の削除をすべて裁定にする。** 驚きは消えるが、放棄された draft の
  id までエージェントに永久に閉じ、しかも断られた側には「決めて断った」
  のか「片付けた」のか区別がつかない。常時かかる摩擦のほうが高い。
- **理由を DELETE の本文で送る。** クエリ文字列に散文を載せるのは美しく
  ないが、DELETE の本文は経路によっては落ちる。代償は正直に言う —
  **理由がアクセスログに載るデプロイがある**(最大 2000 バイト)。

## 8. 表面

足すのは三つで、どれも**既にある面の中身**である: `delete` の `--note`、
REST の任意クエリパラメータ `note`、そして応答の `Revision.note` /
`Change.note`(任意パラメータの追加も応答専用スキーマへの追加も凍結の外で
あることは [0082](0082-what-the-freeze-holds-still.md) /
[0101](0101-a-level-can-be-walked.md))。`log.md` の一行が note を運ぶのも
同じ — 新しい面ではない。

落ちるのは **CLI のコマンド一つ**(`ochakai reject`)とフラグ二つ
(`--withdraw` / `--rejected`)、パラメータ `rejected`(三面)、符号四つ
(`ruling.rejected` / `ruling.withdrawn` / `change.withdraw` /
`error.no_rejection`)、ワイヤの `Summary.rejected` と `concepts.rejected`、
そして export の frontmatter キー三つである。`change.reject` は残る —
それが §9 のイベントの語だからである。

## 9. 凍結を破る — どの約束が、なぜ動くか

`/api/v1/bundle` と `/api/v1/search` は OKF コアとして凍結されている
([0107](0107-the-freeze-holds-the-okf-core.md))。この記録はそれを
**意図して破る**。動くのは四つである:

| 動く行 | 何が起きるか |
|---|---|
| `GET /api/v1/search` の `rejected` | 消える |
| `Summary.rejected` | 消える(必須の応答フィールドだった) |
| `Observed.rejection` と `Rejection` スキーマ | 消える |
| `Error.code` の `no_rejection` | 列挙から消える |

`DELETE /api/v1/bundle/{path}` の `note` は**破りではない** — 任意の
クエリパラメータの追加は [0082](0082-what-the-freeze-holds-still.md) /
[0101](0101-a-level-can-be-walked.md) が最初から外に置いている。

**[compatibility](../compatibility.md) が認めていた三つの理由のどれにも
当たらない。** セキュリティ欠陥ではなく、消えるのは REST の JSON 射影で
あって OKF 文書ではないので 0100 の「OKF 非適合な出力」でもなく、規格が
定める綴りの重複でもない。だから四つ目の理由として書く:

**能力ごと退く面は、その面が残した形も連れて退く。** 却下という操作が
無くなったので、`rejected` フィルタは常に空を答え、`Summary.rejected` は
常に `false` を答え、`no_rejection` は決して出ない。**残す道はあった** —
四つとも新しいモデルの下で正しい値を返し続けるので、宣言したまま凍結を
守れた。採らなかったのは、**決して変わらない値を持つフィールドは、読む
人に「まだ何かある」と言い続ける**からである。凍結が守るのはクライアント
が握った形であって、能力が消えた後もその形を飾っておく約束ではない。

代価は正直に言う: この四つを読んでいるクライアントは壊れる。`0.x` の
minor で、`docs/compatibility.md` が「免責文ではなく実際のポリシー」と
書いている面を破ることになる。だから CHANGELOG は **BREAKING** で、
compatibility.md の一覧は三つから四つになる — **理由を増やしたのだから、
そう書いてある場所も増やす。**
