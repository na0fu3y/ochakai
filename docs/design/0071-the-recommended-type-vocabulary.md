# ochakai 設計ドキュメント 0071: 推奨する型の語彙

Status: Accepted(2026-08-03)。**型の語彙の現行ドキュメント。**
[0038](0038-type-vocabulary-realignment.md) を Superseded にし、
[0063](0063-two-unused-recommended-types-leave.md) を Superseded にする。
**二つが決めたことは何一つ変えない**(§0)。§1 が挙げる規則のうち
「`/` 不可」は [0064](0064-rest-stops-at-api-v1.md) §18 が撤回した — OKF
SPEC §4.1・§11 が未知の型への寛容を MUST で求めており、`acme/Table` は
正当な OKF の型である。残る規則(自由文字列・照合は大小文字非依存・
保存は原表記・NFC・128 バイト以内)は生きている。
Date: 2026-08-03

## 0. この記録が決めたこと

**二つの記録が一つの絵であること。** issue
[#471](https://github.com/na0fu3y/ochakai/issues/471) が始めた統合の三回目
である。決定は一つも動かない。

早見表は既に「型の語彙は 0063。**改訂の履歴は 0038**」と書いていた —
読む先ではないと明記された記録が 241 行のまま残り、しかもその 241 行は
11 型の表を現在の姿として掲げていた。**現行の記録が 9 型と書き、その隣で
退役した記録が 11 型の表を持っている**状態は、早見表の一行では消せない。

## 1. 型は自由文字列であり、綴りがそのまま意味である

型は閉じた集合ではない。照合は大小文字非依存、保存は原表記、NFC 正規化、
`/` 不可、128 バイト以内 — この規則はすべて生きている。**推奨語彙に無い型を
書くことはでき、それは第一級である。**

だから以下が数えているのは**製品が教える語彙**であって、書ける値の全体では
ない。それでも数えるのは、綴りが `--type` のヘルプにも MCP スキーマにも
[architecture.md](../architecture.md) の表にも載る以上、**利用者が払っている
もの**だからである([docs/surface.md](../surface.md) の VOCAB)。

## 2. 推奨語彙は 9 型

| 型 | 何を持つか |
|---|---|
| `Metric` | メトリクス定義、同義語 |
| `Attested Computation` | 認可された計算と、その実行を検証する手段(golden query はこれ) |
| `Skill` | 手順そのもの — `executor.resource` が指す実行手順 |
| `Insight` | メトリクスの読み方: ベースライン、季節性、注意点、閾値 |
| `Policy` | 数字の決め方を定める規範。`sources[].resource` の典拠になる |
| `Glossary Term` | 用語 |
| `BigQuery Dataset` | データセットのカタログエントリ |
| `BigQuery Table` | テーブルのカタログエントリ |
| `Reference` | 外部資料の写し |

並びは「定義 → 実行 → 解釈と規範 → カタログ資産 → 外部の写し」である。

## 3. 何を根拠に語彙を決めるか

**SPEC は語彙を推奨していない。** §4.1 の並びは "Example values" であり、
同じ節が続けてこう言う — 型は中央登録されず、producer は descriptive で
self-explanatory な値を選ぶべきで、consumer は未知の型を寛容に扱わなければ
ならない。したがって「SPEC の例示に無いから外す」も「例示にあるから足す」も、
それ単独では論法にならない。

判断の材料は三つある。

1. **綴りだけで意味が立つか。** `Insight` や `Reference` は振る舞いが無くても
   立つ。`Semantic Model` は立たなかった — Apache Ossie という外部仕様を
   知って初めて何を入れるかが決まる、**綴りの外に意味がある型**だった。
   語彙は振る舞いのレジストリではないが、self-explanatory であることは要る。
2. **OKF が実際に綴りを与えた証拠。** SPEC の例示、SPEC 本文の worked
   example、そして同じリポジトリの
   [リファレンスバンドル](https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/okf/bundles)。
3. **その綴りで誰かが実際に書いたか。** 2 は「仕様が綴りに触れたか」しか
   問わない。予算を払い続けるかを決める材料としては、こちらのほうが近い。

**3 が効いた実測がある。** ochakai 自身の `examples/` と OKF 公式の 4 バンドル
78 ファイルを数えると、9 型はいずれかに実例があり、`Playbook` と
`API Endpoint` だけが両方ゼロだった — SPEC の散文が例に挙げているだけで、
**OKF 自身も ochakai も一度もその綴りで書いていない**。`Playbook` には
SPEC §4.4 の worked example 全文という強い根拠があったが、**散文の例は教材
であって実例ではない**。実運用を模したリファレンスバンドルにすら現れない
ことは、その綴りが実際の需要からではなく説明のために書かれた、という
見立てによく合う。

外れた綴り(`Semantic Model`・`Golden Query`・`Playbook`・`API Endpoint`)は
**自由型として第一級のまま**である。将来 examples がどれかを実際に使う
ようになれば、そのとき教える語彙に戻せばよい — 外したのは推奨からだけで
ある。

## 4. 語彙が背負っていること

**`Skill` と `Playbook` は別の型だった。** どちらも「手順」だが、誰が従うか
ではなく**何に指されるか**が違う — `Skill` は `executor.resource` の指し先
として機械的に参照され、`Playbook` は何にも指されない。畳んで一つにすると
契約の指し先を検索で絞れなくなる。だから `Playbook` を語彙から外したのは
`Skill` に畳んだからではなく、実例が無かったからである(§3)。

**`Policy` と `Skill` は、既にあるグラフの辺に両端の名前を与える。**
`sources[].resource` は典拠を、`executor.resource` は実行手順を指す。指し先に
推奨語彙の名前が無かった状態を埋めたのがこの二つで、`attester.resource` に
型は要らない — 指し先はコードであり、concept ではなくファイルである。

**サーバーの振る舞いは型から一つも増えない。** 型に schema を課す例外は
`Attested Computation` の `runtime` ただ一つに留まる。

## 5. 保存済みエントリは触らない

**マイグレーションは書かない。** 語彙から外れた型は自由型としてそのまま
生き続け、検索も export も import もリビジョンも更新もこれまでどおり動く。

型を機械的に `Attested Computation` へ改名する案は**採らない**。`runtime` は
SPEC §10.2 で REQUIRED であり、書き込み経路の検証は空の `runtime` を 400 に
する。改名だけしたエントリは読めるが**次の更新で弾かれる**状態になり、かと
いって ochakai が `bigquery` と埋めるのは知らない事実を書き込むことである。
**runtime を知っているのは著者だけである。**

移行したい利用者は通常の編集で `type` と `runtime` を書き換えればよい。それは
知識の編集であって、サーバーの都合で走らせるものではない
([0009](0009-provenance-portability.md))。

## 6. 語彙を述べる場所は一つ

語彙はかつて **11 箇所にハードコードされ、長さが 3 通りに割れていた** —
9 型を教える場所、`Semantic Model` を落とした 8 型の場所、
`Attested Computation` も落とした 7 型の場所。同じ穴をもう一度掘らないため、
Go から出る文字列はすべて `domain.TypesHint()` 由来にし、静的資産
(`api/openapi.yaml`・Web UI・MCP の jsonschema タグ)は
[0035](0035-verifiability.md) の流儀で外から検査する — **退役した綴りが推奨
として残っていないこと**と、**現行の型が欠けていないこと**をテストで固定
する。

## 7. やらないこと

- **型を閉じた集合にすること。** 語彙が 9 でも、10 個目を利用者が書ける
  ことは変わらない。
- **保存済みエントリの改名・削除・マイグレーション**(§5)。
- **`Policy` に「規範だから編集を制限する」ような振る舞い**、および
  `Skill` に「手順が本文にあること」を課すこと(§4)。
- **`attester.resource` 用の型を足すこと**(§4)。
- **`Metric` を外すこと。** コンパイルが撤去されても
  ([0070](0070-what-was-retired-and-why.md))、メトリクスの定義は散文の
  知識として意味がある。
- **段階的な deprecation。** 消えるのはヒントだけで、旧綴りの型はエラーに
  ならず自由型として通る。
