# ochakai 設計ドキュメント 0049: キューの長さを数える — ループが人を呼べるようにする

## 1. 問題: 誰も見に行かなければ、キューは無いのと同じ

0025 が締めた書き戻しループには、いま 3 本のキューがある。

| キュー | 一覧 | 空になる条件 |
|---|---|---|
| 下書きレビュー | `sort=usage` + `status=draft` | 公開する編集(`status: stable`)/ reject |
| 誤りと報告されたもの | `sort=failed` | 最後の失敗報告より後の verify |
| 宣言した期限切れ | `sort=stale_after` | 書き手が期限を宣言し直す編集(0037 §2.2) |

3 本とも**空にできる**。0025 §6.1 が「空にできないキューは読まれなく
なる」と書き、そのために verify を独立した操作にしたからである(下書きの
キューだけは verify では空にならない — 確認と公開は別の行為なので、
verify はライフサイクル値に触れない: 0043 §3.2)。

だが**空にできることと、誰かが見に行くことは別である**。いまキューは
pull しか持たない — Web UI を開くか、`ochakai search --sort …` を打つか。
どちらも「今日はレビューする日だ」と人間が思い出すことに依存している。
思い出すことに依存したループは止まるし、止まったとき

> **レビューキューが静かなのと、レビューキューが空なのは、外から
> 見分けがつかない。**

これは 0025 §6.1 と同じ形の欠陥である。あちらは「処理しても短くならない
キュー」を直した。こちらは「処理されているかどうかが誰にも分からない
キュー」を直す。

## 2. 世界観: 押すのは数であって、通知ではない

ochakai は LLM を持たず(0001)、スケジューラも持たない。secret を
持たないので、宛先・トークン・SMTP・Webhook URL のいずれも置けない
(0002・0003)。したがって「人に届ける」機構を製品の中に作る道は最初から
閉じている。

閉じていない道が 1 つある。**すでに運用者が持っている通知経路に、
ochakai が乗せられる形の答えを 1 つ返すこと**である。cron・CI・シェル
プロンプト・Cloud Scheduler — どれも「終了コード」か「小さな JSON」を
読む。ochakai がやることは、**3 本のキューの長さを 1 回の読み取りで
返す**ことだけでよい。届けるのは運用者の仕組みで、ochakai は数を持つ。

これは新しいデータを 1 バイトも作らない。3 本のフィードは既にあり、
足りないのは「何件あるか」を一覧せずに聞く方法だけである。

## 3. 決定

### 3.1 3 つの数は `GET /api/v1/stats` の `queues` キー

```json
{ "queues": { "drafts": 12, "reported_wrong": 1, "past_expiry": 0 } }
```

各値は、対応するフィードが同じ条件で返す件数と**一致する**。除外(削除
済み・却下済み)もフィードと同じで、フィードの述語をそのまま
`count(*) FILTER (…)` にした 1 本のクエリで数える。1 つのエントリが
2 本のキューに入ることはあり、その場合は両方で数える — レビュアーが
処理する「作業の口数」を数えているからである。

**入れ子を 1 段持つ**(`queues` キー)。#293 が求めている instance
metric(検証済み比率の推移、ゼロヒットのクエリ)は、この数の**兄弟キー**
として入るべきものである。フラットな数の袋にしておくと、後から性質の
違う値が同じ平面に並ぶ。

そしてこの入れ子が、面を 1 つ減らした。0051 §3.5 は兄弟キーを
`GET /api/v1/stats` の応答に置き、その中に `queues` をそのまま入れた
— 同じキーで、同じ問い合わせから。**その時点で、3 つの数だけを返す
第二の住所は、能力を 1 つも持っていなかった。** §3.3 の `prefix` が
唯一の例外だったので、それを `stats` に移した(下記)。

面を数えるとはこういうことである(docs/surface.md): 足したときには
「1 回の読み取りで 3 つの数」に見えたものが、隣に置かれた面と並べると
同じ数への 2 本目の経路だった。**畳んでも失われる能力が無い**ことが、
畳んでよいことの条件である。

### 3.2 数えるのは「空にできるキュー」だけ

4 本目のフィード `sort=verified_at`(検証 age、カナリア用)は**数えない**。

これはランキングであってキューではない。対象は検証済みエントリ全部で、
件数はナレッジベースの大きさそのものであり、**誰にも 0 にできない**。
0 にできない数を「待っている仕事」として並べれば、他の 3 つの数の意味まで
薄まる。カナリア運用はフィードを上から N 件取る運用であって
(docs/guides/golden-query-canary.md)、残件を数える運用ではない。

### 3.3 受け取るフィルタは `prefix` だけ — そして `stats` が受ける

`prefix` は 0041 が入れた「チームの部分木」であり、1 つのデプロイを共有
するチームが**自分のキュー**を聞くために要る。それ以外(type / status /
tag / trust / fm.)は受けない。数に対して任意のフィルタを許すのは数の上に
クエリ言語を作ることであり、「何件あるか」の次に来る「どれか」は
フィードが答える場所である。

§3.1 の畳み込みで、この `prefix` は `GET /api/v1/stats` のパラメータに
なった(0051 §3.6)。**移したのであって、落としていない** — そして
移した先で広くなった。以前はチームが自分のキューの長さは数えられて
自分の知識は数えられなかった。いまは `prefix` がエントリに紐づく数を
すべて絞る。紐づかない数は 1 つだけあり、それは検索ミスである
(0051 §3.6)。

### 3.4 CLI `ochakai queues` と、終了コード

```
$ ochakai queues
12	drafts	ochakai search --sort usage --status draft
1	reported wrong	ochakai search --sort failed
0	past expiry	ochakai search --sort stale_after
```

各行が**次に打つコマンドを持っている**。`--prefix` を付けて聞いたときは
その scope が提案にも入る。

`--exit-code` を付けると、**どれか 1 本でも空でない間 2 で終了**し、3 本
とも空なら 0 で終了する。これが 1 ではなく 2 なのは、1 が「コマンドが
失敗した」だからである。**「サーバーに届かなかった」が「やることは無い」
と読まれてはならない。** `git diff --exit-code` と `grep -q` の慣習に
従う。既定は 0 のまま(対話的に打った人のシェルの `$?` を汚さない)。

**名前を `status` にしない。** 提案(issue #299)の名前は
`ochakai status` だったが、`status` はこのプロジェクトではライフサイクル
値 1 語である — 0043 §§3.2-3.3 がそう狭め、0047 が `fm.status` を 400 で
拒否してまで守っている語である。同じ CLI で `ochakai status` が
「キューの長さ」を意味し `--status draft` が「ライフサイクル」を意味する
のは、直近 2 本の設計ドキュメントが取り除いてきた種類の曖昧さである。
数えているものの名前で呼ぶ。

### 3.5 各サーフェス(0015)

- **REST**: `GET /api/v1/stats` の `queues` キー(§3.1)。唯一の契約で
  あり、他の面はそのクライアントである。**面は足していない。**
- **CLI**: `ochakai queues`。完全性の面であり、cron / CI に載るのは
  ここである。REST の面が 1 つでもコマンドは残る — 0015 §2 が CLI に
  求めているのは REST 操作との 1 対 1 ではなく、打てるコマンドが
  あることである。3 つの数と次に打つコマンドだけが欲しい人に
  `stats` の全体を読ませる理由は無い。
- **Web UI**: Review タブに待ち件数のバッジ、レビューキュー画面に 3 つの
  数(それぞれのフィードへのリンク)。ここは人がレビューをする場所なので、
  「静かなのか空なのか」が最初に分かるべき面である。0 は画面では出し、
  タブのバッジでは出さない — 常にあるバッジは風景になる。
- **MCP**: **出さない。** ツールスキーマはエージェントのコンテキストを
  食うので本数は予算である(0015 §3.1)。「人間のレビューが溜まっている
  か」はエージェントのループに要らない。エージェントのループ側の口は
  `put_knowledge`(下書き)と `report_outcome`(失敗報告)であり、
  どちらもキューを**長くする**側で、既にある。

## 4. やらないこと

- **配送。** メール・チャット・Webhook・宛先リスト・購読設定 — どれも
  持たない。secret-zero(0002・0003)を保つには宛先も資格情報も置けず、
  仮に置けたとしても「誰に何を送るか」は ochakai がナレッジについて持って
  いる知識ではない。**押すのは運用者の cron / CI であり、ochakai は
  終了コードと 3 つの数を返す。** これは #299 の選択肢 3(Cloud Scheduler
  から読み取り、文面は外で組む)を*塞がない*: そのジョブが叩く先が
  この読み取りである。
- **スケジューラ。** サーバーは自分で目を覚まさない。デプロイは
  Cloud Run の 1 リビジョンであり、常駐ジョブを足せば「リクエストを
  受けている間だけ動く」という前提が崩れる。
- **閾値と抑制。** 「10 件を超えたら赤」「金曜は黙る」の類は入れない。
  空か空でないかは ochakai が正直に言える唯一の線で、そこから先の政策は
  運用者の cron 側にある(`--json` があるのはそのためである)。
- **保存された集計・ロールアップ。** 3 つの数は都度数える。#293 が求める
  *推移*(先週何件が verified になったか)は保存が要り、生イベントが
  180 日で刈られる以上その設計は別に要る。本ドキュメントはその答えを
  先取りしない — 代わりに §3.1 の入れ子で**置き場所だけ**空けておく。
  (0051 がその場所を埋め、埋めた結果この面が要らなくなった。)
- **自動的な処理。** 期限切れを自動で draft に落とす、報告の多い
  エントリを自動で deprecated にする、といった遷移は入れない
  (0025 §4 と同じ理由)。数は浮上させるだけである。

## 5. 壊れるもの

- **無い。** 追加のみである。3 本のフィードの述語・並び・ワイヤ形は 1 つも
  変わらず、既存クライアントは新しい面を知らないまま動く。REST に足した
  面は 0 で、3 つの数は `stats` の応答の 1 キーとして入る(§3.1)。
- CLI に 1 コマンド、終了コードに 1 つの意味(2 = 待っている仕事がある)が
  増える。他のコマンドは 2 を返さない。
- Web UI の Review タブに、待ち件数がある間だけバッジが出る。
