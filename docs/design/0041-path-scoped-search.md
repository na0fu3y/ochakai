# ochakai 設計ドキュメント 0041: 住所で検索の範囲を絞る — prefix フィルタ

Status: Accepted(2026-07-28)。[0017](0017-path-addressing.md) の「パスが住所」を
検索と context に届かせる。[0014](0014-folder-browse.md) の prefix ブラウズと同じ
概念を、人がツリーを辿る面だけでなくフィルタとしても持つ。実装は同 PR
Date: 2026-07-28

## 1. 目的

外部レビューで挙がった要求はこうだった —— **「チーム独自の指標、部署での用語、
全社の共通言語」を区別して検索したい。** ローカルなドキュメントなのか
グローバルなドキュメントなのかを判断できる仕組みが欲しい。

ochakai には既に答えの半分がある。**id はパスであり、パスは住所である**
(0017)。`teams/growth/metrics/activation` と `company/glossary/mau` は、
置き場所そのものがスコープを表している。0014 はその階層を prefix で 1 階層ずつ
辿るブラウズを持っている。

**足りないのは残り半分である。** 検索(`GET /api/v1/knowledge`)と
`get_context` のフィルタは type / status / tag / source の 4 つで、**id は
一度も WHERE 句に現れない**。住所で絞れるのは人がツリーを辿るときだけで、
エージェントが 1 コールで引く経路には無い。0037 が `stale_after` と `sources`
について書いたのと同じ形の穴である —— 列はあるのに、引けない。

穴の代償は「できない」では済まない。スコープを表現しようとすると、パスと
**二重になる別の手段**(全エントリに tag `team:growth` を付ける)に逃げる
しかなくなる。tag は住所ではないので階層を持たず、move(0021)にも追随せず、
そして必ずパスとずれる。

### 1.1 需要の強さは正直に書いておく

**この決定の根拠は、実際に詰まった利用者ではない。** 出所は外部レビューの
「まだ実装していないが検討中」という一項であり、0037 の 2 項目(封筒に載って
いるのに引けない、という自分で作った不整合)より弱い。0036 §5 が
`stale_after` のフィードに課した「実際に使われ始めてから」という基準を、
この機能は満たしていない。

それでも採るのは、**クライアント側で代替できないから**である。検索は
`limit` を適用してから返すので、呼び出し側で id を見て絞ると「上位 10 件を
取って 2 件に減る」ことになり、スコープを狭めるほど結果が痩せる。
`get_context` に至ってはパッキングとバイト予算がサーバー側にあるので、
外から絞る手段そのものが無い。加えて MCP には browse が無い(0015 §3.1)ので、
**エージェントにはパスで絞る経路が 1 本も存在しない。**

もう一点、狭い適用範囲も認めておく。**ディレクトリが種類で切られている
コーパス(`examples/demo` の `metrics/` `glossary/` `queries/sales/` が
まさにそれ)では、prefix は `type` フィルタとほぼ重複する。** この機能が
効くのは、ディレクトリが型では言えないもの — チーム、ドメイン、テナント —
を表しているときだけである。ochakai はそのレイアウトを推奨も強制もしない
(§2.9)。

## 2. 決定

### 2.1 `prefix` フィルタを足す

type / status / tag / source と同じ位置に `prefix` フィルタを足す。値は
**id の前方部分パス**で、そのサブツリー —— prefix 自身のエントリと、その下に
ある全エントリ —— に絞る。

```
GET /api/v1/knowledge?q=活性化&prefix=teams/growth&prefix=company
```

- **フィルタであってモードではない。** `q` とも `sort` とも組み合わせられる。
  「このサブツリーの、期限切れのもの」「このチームの、失敗報告が付いたもの」が
  1 回で引ける。0037 §2.3 が `source` について言った直交性と同じである。
- **空文字列はフィルタから落とす。** 空の prefix は root、すなわち全体を指す
  (browse と同じ)。絞らないという指定は、絞らないという結果になる。

### 2.2 セグメント境界で照合する

`prefix=metrics` は `metrics/revenue` と `metrics` 自身に当たり、
**`metrics-legacy/churn` には当たらない**。

```sql
EXISTS (SELECT 1 FROM unnest($n::text[]) AS p
        WHERE k.id = p OR left(k.id, length(p) + 1) = p || '/')
```

素の文字列前方一致ではない。パスはセグメントの列であって、`metrics` と
`metrics-legacy` は**別のディレクトリ**である。素の前方一致にすると、隣に
ディレクトリを 1 つ作っただけで他人のスコープが混入する —— スコープという
用途では、これが最も高くつく形の誤りになる。

prefix 自身のエントリを含めるのは、`teams/growth` に索引的なエントリが
置かれているとき、それだけが漏れるのを避けるためである。サブツリーとは根を
含む。

LIKE を使わないのは browse と同じ理由 —— id は `_` を含みうるし、LIKE は
それをワイルドカードとして扱う(0014)。

### 2.3 繰り返せる(選言)

`type` / `status` / `tag` と同じく繰り返せ、OR で結合する。`source` を単一値に
したのとは逆の判断であり、根拠は要求そのものにある。

**この機能の主用途は「自分のスコープ*と*全社スコープ」である。** 単一値に
すると、その最も普通の問いが 2 往復とクライアント側マージになる ——
`get_context` が「1 コールで全部」のために存在すること(0015 §2)と正面から
衝突する。しかも 2 回に分けて引いたスコアは別々のランキングから来るので、
マージした順位に意味が無い。

`source` を単一値にした理由(選言は `@>` の containment に落ちず GIN index が
効かなくなる、0037 §2.3)は、ここには当てはまらない。prefix には効かせる
索引が初めから無い(§2.5)。

### 2.4 正規化と検証は browse と同じ

`Service.Browse` と同じ扱いにする:

- **NFC 正規化する**(0022)。macOS のパスから貼った NFD の prefix が保存済みの
  NFC の id に当たらないのでは使い物にならない。
- **末尾の `/` を落とす。** `teams/growth/` と `teams/growth` は同じスコープを
  指す。
- **`domain.ValidIDPrefix` で検証**し、不正なら 400。browse と同じ検証・同じ
  文言なので、「browse で開けるパスは prefix にそのまま渡せる」が成り立つ。

正規化はサービス層で行う。REST / MCP / CLI のどこから来た prefix も同じ 1 か所を
通る(0015 §2「契約はサーバー側に一元化する」)。

### 2.5 索引は張らない

`left(id, n) = p` は主キーの btree に乗らない。乗せるなら
`id >= p || '/' AND id < p || '0'` という範囲述語に書き換えることになるが、
**これは照合順序(collation)に依存する** —— `text` の `<` は collation 順で
あって、バイト列の前方一致と一致する保証が無い。0037 §2.1 が `current_date` で
踏んだのと同じ罠である: **環境によって答えが変わる。**

正しさを索引と引き換えにはしない。想定コーパス(数千〜数万件)では、検索は
GIN / HNSW が候補を絞った後の残りをフィルタするだけであり、`sort` のフィードは
元から全走査してソートしている。**測って足りなくなったら**、`text_pattern_ops`
の索引を明示的に張り直す —— その演算子クラスは collation に依らずバイト順なので、
範囲述語を安全に使える。索引を足す判断は、その時に根拠を持って行う。

### 2.6 context のリンク展開には効かない

`get_context` の prefix は**一次ヒットの検索にだけ**効く。リンクで引き寄せ
られる companion は id で直接引かれるので、スコープの外にあっても入ってくる。

これは既存の挙動(type / tag も companion には効かない)であり、prefix でも
これが正しい。**チームの指標が全社の用語を引用しているなら、その用語は一緒に
来なければ意味が無い** —— それこそが get_context がリンクを 1 ホップ展開する
理由である。スコープで展開まで切ると、狭いスコープほど文脈の欠けた答えになる。
返るエントリは id を持つので、どこから来たかは呼び出し側から見える。

### 2.7 ベクトル検索では取りこぼしうる

HNSW のスキャンは WHERE 句より先に走る(`efSearch`)。狭い prefix では、
スキャンが拾った近傍がフィルタで落ちて limit を満たさないことがある。type /
status / tag と共通の性質で、prefix 固有の問題ではない。網羅が要るなら
`sort` のフィード(全走査)に prefix を合成する。

### 2.8 各サーフェス(0015 §4)

- **REST = yes。** 唯一の契約。`GET /api/v1/knowledge` と `GET /api/v1/context`
  に、繰り返し可能な `prefix`。
- **CLI = yes。** `ochakai search --prefix` と `ochakai context --prefix`
  (どちらも繰り返し可)。
- **MCP = yes。** 0015 の原則は no だが、これは「エージェントのループが 1 コールで
  必要とするもの」の典型である。エージェントは答える前に「どのスコープで訊くか」を
  決める必要があり、決めた結果を渡す場所が無ければ機能そのものが届かない。
  **新しいツールは作らない** —— `search_knowledge` / `get_context` の引数
  `prefixes` として載る(0015 §2「ツール数は予算」)。
- **Web UI = yes。** フィルタバーに prefix の入力を置く。加えて browse の
  ツリーから「ここを検索」で prefix を積んで Explore に渡す —— 人がその
  ディレクトリを見ている、まさにその場所に置く(0037 §2.5 が逆引きを詳細画面の
  Sources 欄に置いたのと同じ理屈)。

### 2.9 スコープの規約は機構ではなくドキュメントで示す

`teams/<team>/…` と `company/…` のようなパス設計は**規約であって機構ではない**。
ochakai は id が何を意味するかを知らないし、知るべきでもない(0017: パスは型を
主張しない)。サーバーには一切埋め込まない。

**同梱バンドルの規約は変えない。** `examples/demo` は種類で切った
(`metrics/` `glossary/` `queries/sales/`)ままにする。スコープ用途の
レイアウトを推奨として配ると、0017 が「パスは型を主張しない」と決めたのと
逆向きに、今度は「パスはスコープを主張する」を規約として押しつけることに
なる。README には**機構の説明と、それが効く条件**(ディレクトリが型では
言えないものを表しているとき)を書くに留め、レイアウトの指示はしない。

## 3. 壊れるもの

**無い。** 追加のみである。

- クエリパラメータ `prefix` が増える。指定しなければ従来どおり。
- **マイグレーションは無い。** 列も索引もデータも変えない。`updated_at` は
  動かないので ETag も無効化されない。
- browse の `prefix` の意味論は変えない(直下の 1 階層を返すまま)。名前が
  同じなのは同じ概念だからで、browse が「その直下」を返すのに対しフィルタは
  「その下すべて」に当たる、という違いは §2.2 のとおり。

## 4. やらないこと

- **認可ではない。** prefix は誰からも見え、誰でも任意の値を渡せ、指定しなければ
  全体が返る。**閲覧を制限する機構ではない**(0002「到達できた者は読み書き
  できる」)。閲覧境界が必要ならインスタンスを分ける、という 0002 §1 の答えは
  変えない。ここを明示しておくのは、スコープ検索と読み取り ACL が外から見ると
  似ており、混同されたまま運用されると 0002 が事実上骨抜きになるからである。
  **prefix を渡さないクライアントには何も隠れていない。**
- **スコープの自動判定。** 「この質問はチームローカルか全社か」を ochakai は
  判断しない(0001: LLM ゼロ)。機構(スコープを指定できること)までがサーバーで、
  どのスコープを引くかの判断は呼び出し側にある。
- **スコープのレジストリ・封筒フィールド。** `scope: team-growth` のような
  新しいフィールドは足さない。住所が既にスコープであり(0017)、二重に持てば
  必ずずれる。move(0021)でスコープが変わることも、パスなら自然に表現される。
- **部分一致・glob・正規表現。** `*/metrics/*` のような照合はしない。索引にも
  乗らず、「どこかに metrics を含む」は住所ではないので意味も曖昧になる。
- **prefix 単独をモードにしない。** `source` は単独指定で一覧になる
  (0037 §2.3)が、prefix はならない —— クエリも sort も無ければ従来どおり
  400 である。サブツリーの列挙には既に面があるからである: 木として辿るなら
  browse、平らな一覧なら任意の `sort` フィードとの合成
  (`?prefix=teams/growth&sort=usage`)。`source` に単独モードを与えたのは、
  「この資料を引用しているもの」を返す面が他に無かったからで、ここでは
  その条件が成り立たない。
- **検索順位へのスコープの重み付け。** 「自分のスコープを優先して上位に」は
  しない。フィルタは含める/含めないだけを決める。重み付けを入れると、呼び出し側が
  持つべき方針(ローカル優先か全社優先か)がサーバーの定数になる。
