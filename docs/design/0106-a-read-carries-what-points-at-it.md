# ochakai 設計ドキュメント 0106: 読みは、自分を指すものを連れて返る

Status: Accepted(2026-08-16)。[0067](0067-four-faces-and-what-they-decline.md)
§5.1 の「被リンク」の項を改訂する — 「`get_context` が同梱済み」という
理由を「単読が行を運ぶ」に置き換える。結論(被リンクのツールを持たない)
は動かない。
Date: 2026-08-16

## 0. この記録が決めたこと

1. **concept の単読は `linked_from` を運ぶ。** `GET /api/v1/bundle/{id}.md`
   の JSON、MCP `get_concept`、`ochakai get` の応答に、その concept を
   本文から指している concept の**行**が付く(id / type / title /
   description / status / trust)。住所順、上限 20、却下済みの linker は
   出ない。応答専用スキーマへの追加なので凍結の外である
   ([0082](0082-what-the-freeze-holds-still.md))。
2. **行はポインタであって配達ではない。** 行に本文は無く、行を返しても
   その concept の fetched は記録しない(§3)。
3. **`links_to` フィルタは畳まない。** 完全でページングできる逆引きは
   引き続き検索面の仕事である(§2)。

## 1. 文書が自分について言えない唯一のこと

リンクは本文からの導出で([0024](0024-links-from-body.md))、順方向は
文書に見えている — metric の本文を読めば、それが引く用語も query も
見える。**逆方向だけが他人の文書に住む。** metric を「どう読むか」を言う
insight は metric を指すのであって、その逆ではない
([0001](0001-architecture.md) のループがそう設計した)。だから metric を
いくら読んでも、**それを読む前に知っているべき注意書きの存在**は
見えない。

今日この穴を埋めているのは `get_context` の逆向き展開
([0067](0067-four-faces-and-what-they-decline.md) §5.1)だけで、
search → get のプリミティブの経路には無い。読みの経路がプリミティブに
寄るほど、この穴は get 自身の不完全性になる — 単読を完全にするのが
本記録で、pack の面の行き先はそれを前提に別の記録が決める。

## 2. 既にある逆引きとの重なり

同じ答えの面は既に一つある: `?links_to=`
([0046](0046-bundle-address-space.md) §3.5 が専用エンドポイントを
畳んだ先)。二本目を作るのかという問いには、役割で答える。

- **`links_to` は、尋ね方を知っている呼び出し元の面である。**
  「この資材に何が依存しているか」を尋ねる者に、完全な集合を、
  フィルタと cursor つきで返す。
- **`linked_from` は、尋ねなかった者に届く同じ答えの先頭である。**
  `get_context` の逆展開が存在した理由がこれだった — **尋ねなければ
  届かないポインタは、追われない**。エージェントは concept を読む。
  読んだものに行が付いていれば追え、付いていなければ逆引きの綴りを
  思い出す必要がある。

完全性はあちらに、同梱はこちらに。行が 20 で切れた先を歩く綴りは
応答の説明が `links_to` を名指す。行に cursor は付けない — 付ければ
二本目の完全な入口であり、[0068](0068-how-a-face-is-added-and-removed.md)
§1 の「二本目の入口は二本目の説明を持ち、そちらだけが腐る」に落ちる。

## 3. 行の形と、記録しないこと

- **行の基準は [0093](0093-the-budget-governs-the-whole-response.md) の
  outline と同じ**: 呼び出し元が fetch を判断できるだけの情報で、
  description が重みを持つ。score は無い — 逆引きの答えは集合であって
  順位ではない(`links_to` が一覧である理由と同じ)。
- **20 で静かに切れる。** [0068](0068-how-a-face-is-added-and-removed.md)
  §2.1 の「上限で静かに止まらない」は一覧の規則で、これは一覧ではなく
  同梱物である。hub になった用語集の一件が、自分の読みを際限なく
  太らせないための上限で、完全な集合の住所は行の隣に書いてある。
- **却下済みの linker は出ない。** 検索の既定と同じ
  ([0043](0043-document-first.md) §3.3): 受け入れなかった知識は
  尋ねられずに再浮上しない。
- **fetched は記録しない。** 行は名指しであって配達ではない。配達で
  ないものを需要として数えれば、レビューフィードを駆動するシグナルが
  膨らむ — outline が fetched に数えられないのと同じ理由である。

## 4. 面への出方(0067)

| 面 | 何が変わるか |
|---|---|
| REST | `View` に `linked_from`。応答専用の追加で凍結の外([0082](0082-what-the-freeze-holds-still.md))、golden は同じ PR で再生成 |
| MCP | `get_concept` の応答に同じ JSON。**スキーマは 1 バイトも動かない** — [0103](0103-the-tool-result-travels-once.md) が outputSchema を消しているので、応答のフィールドは常駐費用を持たない |
| CLI | `ochakai get` の JSON にそのまま出る。フラグは増えない |
| Web UI | ページは同じ REST を読むので行は既に届く。描くかは curation 面の判断で、今回は変えない |

## 5. やらないこと

- **`links_to` を畳むこと。** 完全な逆引きはあちらの仕事である(§2)。
- **行に文書を載せること。** 配達は fetch の仕事で
  ([0043](0043-document-first.md) §3.5)、文書を同梱する読みは pack で
  あって単読ではない。
- **MCP に backlinks ツールを足すこと。** 0067 §5.1 の結論は動かない。
- **行の順序に順位を持ち込むこと。** 更新順・信頼順は「どれが大事か」を
  サーバが黙って決めることで、集合には住所順がある。
