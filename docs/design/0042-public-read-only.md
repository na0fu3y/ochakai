# ochakai 設計ドキュメント 0042: 公開読み取り専用という姿勢

Status: Accepted(2026-07-27)。[0040](0040-read-only-mode.md) の read-only を
前提に、**identity を一切読まない**姿勢を足す。[0002](0002-authn-authz.md) の
「到達制御は Cloud Run IAM の仕事」は変えない — §2.1 で、この姿勢が
その外側にあることを述べる
Date: 2026-07-27

## 1. 目的

0040 で「書かないデプロイ」は作れるようになった。だが**公開デモはまだ
立てられない。** 認証層が邪魔をする。

`internal/httpauth` は Cloud Run が転送した ID トークンを
**署名検証せずに**パースする。パッケージのコメント自身がそう書いている
— 非公開の Cloud Run サービスでは Google が検証済みであり、
`X-Serverless-Authorization` の署名は `SIGNATURE_REMOVED_BY_GOOGLE` に
置き換わって届くからである。その帰結として:

- **トークンが無ければ 401。** デモの訪問者はまさにこれで、ページを
  開くことすらできない。
- **偽造トークンが通る。** 署名を見ないので、公開されたサービスに対して
  誰でも任意の identity を名乗れる。実測で、未署名のトークンで
  `ceo@example.com` を名乗ったリクエストが 200 を返すことを確認した。

Terraform モジュールが `allUsers` を表現不可能にしているのは、まさに
2 番目のためである(「公開されたサービスでは誰でも任意の人物を名乗れる」)。
その判断は正しい。**読み取り専用にしただけでは、この 2 点はどちらも
解消しない。**

## 2. 決定

**`OCHAKAI_PUBLIC_READ_ONLY=true` を足す。真のとき、このデプロイは
identity を読まず、書き込まない。**

具体的には:

- **Authorization / X-Serverless-Authorization を読まない。** 検証できない
  ものを読むくらいなら、読まない方が正しい。トークンが有っても無くても
  結果は同じ。
- **`X-Ochakai-On-Behalf-Of` を読まない。** 委譲(0027)は「信頼済みの
  呼び出し元」が前提であり、ここには信頼済みの呼び出し元がいない。
- **すべての呼び出し元が `human:anonymous`。** 401 は返さない。
- **read-only を含意する。** 公開かつ書き込み可能は、この設定では
  作れない。

### 2.1 これは 0002 の改訂ではない

0002 は「認可を持たない — 到達できた者は読み書きできる」と決め、到達制御を
Cloud Run IAM に委ねた。本ドキュメントはその委任を解除しない。

**identity を読まないことは、認可を足すことの反対である。** ochakai は
0002 で「ヘッダから読むのは provenance だけ」と決めた。この姿勢は
その provenance すら読まないところまで下がる。判断材料が減るだけで、
判断機構は増えない。

そして **provenance を読まないことが正当化されるのは、書かないから**で
ある。書き込みが無ければ記録すべき作者もいない。だからこの 2 つは
別々のつまみであってはならず、片方がもう片方を含意する。

### 2.2 なぜ「トークンを検証する」ではないのか

公開のまま ID トークンを**本物として検証する**道もありうる(JWKS を引き、
署名と audience を確認する)。採らない。

- ochakai の秘密ゼロ(0003)は「認証は前段が済ませている」という前提の
  上に成り立っている。検証器を内蔵すれば、鍵の取得先・キャッシュ・
  audience の設定という**運用面が生える**。
- デモに必要なのは identity ではない。**誰が読んだかを知る必要が無い。**
  必要でないものを検証する仕組みを足すのは、面を増やして得るものが無い。

Cloud Run IAM で守る運用は今までどおりであり、そこでは何も変わらない。

### 2.3 `OCHAKAI_INSECURE_DEV` を流用しない

「全員 anonymous」という挙動は insecure dev と似ている。だが流用しない。

insecure dev は**委譲を誰にでも許す**(埋め込みホストを開発する人が、
自分のヘッダが効いていることを見られるように)。公開の場でそれをすれば、
訪問者が任意の人物として振る舞える。SECURITY.md は「insecure dev の挙動を
非開発構成で到達可能にすること」を脆弱性として明記している。**同じ言葉で
呼ばないことに意味がある。**

## 3. 検査する不変条件

[0035](0035-verifiability.md) に従う。

- **公開かつ書き込み可能は起動しない。** 含意が効いていることを、
  設定の読み取り段で確かめる。
- **トークンを見ない。** 偽造トークン付きのリクエストと、トークン無しの
  リクエストが、**同じ actor** に解決されることを確かめる。0042 の主張は
  「anonymous になる」ではなく「入力に依存しない」である。
- **委譲が効かない。** `X-Ochakai-On-Behalf-Of` を付けても actor が
  変わらないことを確かめる。
- **401 を返さない。** 匿名の読み取りが 200 で返ることを確かめる。

## 4. やらないこと

- **公開かつ書き込み可能なデプロイ。** 設定として存在しない。
- **匿名の書き込みを一部だけ許す**(例: report_outcome だけ)。フィードを
  荒らす経路になり、しかも誰が荒らしたか記録できない。
- **レート制限や濫用対策をここに置かない。** 必要なら Cloud Run の
  同時実行数と Cloud Armor が担当する。ochakai は知識を返すだけである。
- **この姿勢を「安全な公開方法」として一般に薦めない。** 用途はデモと
  参照専用の配布であり、それ以外では Cloud Run IAM が正しい答えである。
