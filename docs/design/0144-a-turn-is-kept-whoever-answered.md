# ochakai 設計ドキュメント 0144: 答えたのが誰のエージェントでも、turn は残る

Status: Accepted(2026-09-24)。[0142](0142-ochakai-carries-a-data-agent-that-does-not-rule.md)
§6 の「会話の記録」の書き手を、デプロイ自身のエージェントから**ナレッジを
読んで答えたすべてのエージェント**に広げる。残す形・保持・export に載せない
ことは 0142 §6 のまま動かない。面の配分は
[0143](0143-four-faces-and-an-agent-that-answers-behind-one.md) の規則に
従い、MCP と CLI には載せない(§5)
Date: 2026-09-24

## 0. この記録が決めたこと

1. **turn はどのエージェントの答えでも残せる。** `POST /api/v1/agent/turns`
   が、問いの文・読んだ concept の id・提案した SQL を受け取り、0142 §6 と
   同じ形で残す(§2)。`OCHAKAI_AGENT` を入れていないデプロイでも動く。
2. **turn は誰が答えたかを言う。** 記録した呼び出しの `via` と `producer`
   を持つ。デプロイ自身のエージェントの turn は `producer` が
   `ochakai/<版>` になる(§3)。
3. **turn は REST から読める。** `GET /api/v1/agent/turns` が、エージェントの
   内部ツール `list_turns` と同じ範囲の規則(バンドル全体を読める呼び出し元は
   全員分、ほかは自分の分)で一覧を返す(§4)。turn は問うた人を `by` として載せる。
4. **判定は変わらない。** 外から残された turn も、問うた本人だけが
   `POST /api/v1/agent/turns/{id}` で一度だけ判定し、判定は本人の結果報告に
   なり、何も検証しない(0142 §3)。

## 1. 誰が詰まったか

自前のチャットエージェントと自前の MCP サーバーを持つ社内のデータ分析
アシスタントに ochakai を埋め込んでいる運用者である(2026-09-24)。問いの
大半はそのアプリのエージェントが受け、ochakai はその読み先になっている。

その運用者は、ナレッジを読んだあとのセッションが上手く行ったかを、アプリの
イベントログから LLM-as-judge で逆算し、concept ごとに自前の点数を付けて
いた。検索品質の回帰比較も、本番の検索ログをサンプリングした自前のリプレイ
で行っていた。**どちらも 0142 §1 がエージェントを持つ理由に挙げた入力
(人の判定の付いた結果報告と、正解の付いた問い)そのものであり、それが
ochakai の外で、ochakai の測定とは別に作られていた。**

`OCHAKAI_AGENT` を入れても解決しない。問いを受けるのはアプリのエージェント
であって ochakai のエージェントではないので、軌跡は一件も集まらない。

**既存の面では回避できない。** `report_outcome`(`POST /api/v1/usage/{id}`)
は concept 一件への報告で、「どの問いに対して」が落ちる。一つの問いは
複数の concept を読み、比較のセットが持ちたいのは問いと読んだ組の方である。

0142 §2 は「自分のエージェントも、その契約の読み手の一人にすぎない」と
書いた。読みについてはそのとおりだったが、**ループに入力を返せるのは
自分のエージェントだけだった**。この記録はその非対称を閉じる。

## 2. 残す

`POST /api/v1/agent/turns` の本文は三つである。

| キー | 必須 | 意味 |
|---|---|---|
| `asked` | yes | 会話の最初の問い。1000 バイトまで |
| `read` | yes | 答えるために読んだ concept の id。100 件まで、空でもよい |
| `sql` | no | 提案した SQL の文。16 KiB まで |

**答えの文と SQL の結果は受け取らない**(0142 §6 と同じ線)。0142 §6 の
`latest`(この turn が答えた発言)は外から受け取らず、`asked` と同じ値で
残す — 外のエージェントの会話の途中を ochakai は知らず、比較のセットが
欲しいのは最初の問いである。

**上限を超えた値は切らずに 400 にする。** デプロイ自身のエージェントは
自分の turn を 1000 バイトに切って残すが、それは内部の書き込みである。
ワイヤで受け取った値を黙って切ることは、[0064](0064-rest-stops-at-api-v1.md)
が退けた「黙って値を落とす」形である。

**`read` の各 id は、呼び出し元が読める concept でなければならない。**
存在しない id と読める範囲の外の id は、区別せずに 400 で名指す
([0109](0109-a-directory-has-readers-and-writers.md) §4: 範囲の外には何も
無い)。判定の `good` はこれらの concept への `worked` になるので、読めない
ものを読んだと言う turn は、判定の時点で報告の宛先を失う。入口で断る方が
正直である。

turn の持ち主は**記録した呼び出しの actor**である。
`Ochakai-On-Behalf-Of: human:<x>` を載せた呼び出しなら `human:<x>` で、
判定できるのもその人だけになる(0065 §3)。返るのは残した turn そのもの
(`{"turn": {…}}`)で、その `id` は `POST /api/v1/agent` が返す `turn` と
同じ意味を持つ。

姿勢は判定と同じである。書き込みを断る `read-only` と `public` は、これも
断る — 判定できない turn を残しても、ループには何も入らない。

## 3. 誰が答えたかを残す

外から turn が入ると、比較のセットには二種類の答えが混ざる。**どちらが
答えたかを読めなければ、比較は比較にならない。** 台帳が書き込みについて
既にそうしているとおり、turn は actor のほかに `via` と `producer` を持つ
([0065](0065-identity-and-provenance.md) §3、`Ochakai-Producer`)。

- デプロイ自身のエージェントの turn は `producer` を `ochakai/<版>` に
  する。SPEC §7 の `<producer>/<version>` の形そのままで、新しい語は
  要らない。
- 外から残された turn は、その呼び出しが送った `Ochakai-Producer` を残す。
  送らなければ空で、`via` と actor が残る。

**`producer` は自己申告である。** 外のエージェントが `ochakai/…` を名乗る
ことは止めない — `Ochakai-Producer` をどこでも止めていないのと同じ理由で、
名乗った呼び出し元は actor と `via` に認証されたまま残る。見分けたい読み手は
`via` を読む。

これは保存形の変更である(マイグレーション 0049)。既存の turn は `via` も
`producer` も空で、書き戻さない — 0.28.7 以前の turn はすべてデプロイ自身の
エージェントのものだが、それを後から書き込むのは観測ではなく推測である。

## 4. 読む

`GET /api/v1/agent/turns` は新しい順に turn を返す。

- **範囲はエージェント内の `list_turns` と同じ**: バンドル全体を読める
  呼び出し元 — 管理者と、根に付与を持つ者 — は全員分、ほかは自分が問うた
  分だけ。**アクセスポリシーの無いデプロイでは全員がバンドル全体を読める
  ので、全員が全員分を読む** — そこでは concept もそうであり、turn だけを
  狭める理由は無い([0065](0065-identity-and-provenance.md) §1、0109)。どの turn も問うた人を
  `by`(`kind:name`)として載せる — 管理者の読みでは、誰の問いかが
  それで分かる。
- 絞り込みは `verdict`(`good` / `bad`)と `keep`(比較のセットに選ばれた
  もの)。ページングは既存の `limit`(既定 30、上限 100)と `cursor`。
- 180 日を過ぎた turn は無い(0142 §6)。

これで、比較のセットを読む面がエージェントの中にしか無い状態が終わる。
測定を読む口が無いと、読みたい人は測定を別の測定で作り直すことになる —
§1 の運用者のリプレイがそれだった。

## 5. 面

- **REST** に二操作が入る(15 → 17)。パラメータは `verdict` と `keep` が
  増える(18 → 20)。ヘッダ・環境変数・MCP のツールは増えない。
- **MCP には載せない。** turn を残すのは、問うた人との会話を持つアプリで
  あって、MCP の向こうのエージェントではない — 判定するのはその人であり、
  エージェントが自分の turn を残して自分で判定する形は、0142 §3 が
  「👍 は検証ではない」で退けたものの縮小版になる。MCP の既定は no
  (0143 §1)。
- **CLI には載せない。** 0143 §5.3 がエージェントへの問いを CLI に載せない
  理由と同じで、能力は REST に残り、完全性は欠けない。見直す条件は、シェル
  から比較のセットを読めずに実際に詰まった一件が出たとき。
- **Web UI** は変わらない。エージェントのタブは自分の会話の turn だけを
  判定し、外から残された turn の判定は、それを残したアプリの画面が持つ。
- **`stats` の `agent`** が数える turn には外から残されたものも入る。
  `agent.enabled` はデプロイ自身のエージェントの有無を言うままである。

**何も畳めない。** 単調に増やしてよい理由は、これが C7(改善ループが
測れる)を、ochakai のエージェントを使わないデプロイにも届かせる唯一の口
だからである。ochakai 側で畳めるものは無いが、§1 の運用者の側では
LLM-as-judge の自前の点数とリプレイの自前のログが畳める。

## 6. 残された turn が変えられないもの

誰でも turn を残せることは、配るナレッジを誰でも動かせることを意味しない。

- turn は**順位にも trust tier にも入らない**。検索は turn を読まない。
- 判定が生む結果報告は、判定した本人が `report_outcome` で既に書けるもの
  である。turn が加えるのは「どの問いに対して」であって、新しい書き込みの
  能力ではない。
- 比較のセットに入るのは、本人が `keep` を付けたときだけである(0142 §6)。

`read` を偽る turn は、自分の問いの記録を偽るだけである。

## 7. 退けた案

- **委譲する呼び出し元(`OCHAKAI_DELEGATING_CALLERS`)に限る。** 要望は
  それでよいと言っていた。限れば、turn の持ち主が必ず人になる。退けたのは、
  限ることで守れるものが無いからである — §6 のとおり turn が動かせるものは
  本人が既に動かせるもので、持ち主が process なら判定も process の結果報告に
  なるだけである。規則を一つ増やす理由にならない。
- **`POST /api/v1/usage/{id}` に `asked` を足す。** concept 一件ずつの
  報告に問いを載せると、一つの問いが読んだ concept の数だけ複写され、
  「一つの問いと読んだ組」が再構成できない。単位は turn である。
- **答えの文を受け取る。** 0142 §6 が残さないと決めたもので、外から来ても
  同じである。答えはナレッジにならない(0142 §1)。
- **別の住所(`/api/v1/turns`)に置く。** 判定は既に
  `/api/v1/agent/turns/{id}` にあり、集合とその要素は同じ住所の上にある
  べきである。`agent` は「ochakai のエージェント」ではなく「答えた
  エージェント」と読む。
- **評価の呼び出しを数えないヘッダ(`Ochakai-Record: none`)。** 同じ
  要望の中にあった。観測を消せるヘッダは、隠す道具にもなる。評価の呼び出しは
  残したまま、読む側が分けられるようにする方が数の純度を保つ — その集計軸は
  0141 の内側の規則として別に扱う。
