# ochakai 設計ドキュメント 0032: Web UI の書き込みを IAP の検証済み identity で記録する

Status: Accepted(2026-07-26)
Date: 2026-07-26

## 1. 決定

`ochakai serve-ui` のプロキシは、

1. ブラウザから来た `X-Ochakai-On-Behalf-Of` を**常に捨てる**。
2. `OCHAKAI_IAP_AUDIENCE` が設定されているとき、IAP の署名付きアサーション
   (`X-Goog-IAP-JWT-Assertion`)を検証し、その `email` クレームから
   ヘッダを**作り直す**。
3. audience が設定されているのに検証できないリクエストは **403 で拒否**する。

`ochakai ui`(ローカル)は 1 のみを行う。作り直す材料を持たないからである。

[0027](0027-delegated-provenance.md) §6 が「webui が IAP の検証済み JWT から
ユーザーを取り出してこのヘッダに載せればよい」と予告した実装であり、
[0002](0002-authn-authz.md) §4 が「必要になったら」としていた IAP JWT 検証を、
ochakai 本体ではなく webui 側に置くという整理をそのまま履行する。

## 2. 問題: プロキシが、自称を検証済みのように中継していた

serve-ui は「サービスとして」上流に認証する — `X-Serverless-Authorization` に
自分の ID トークンを載せる。しかし**受け取ったヘッダを削っていなかった**。

0027 で `X-Ochakai-On-Behalf-Of` が導入された結果、これは条件付きの
なりすまし経路になった。運用者が webui のサービスアカウントを
`OCHAKAI_DELEGATING_CALLERS` に載せた瞬間 — つまり 0027 §6 が想定する構成に
した瞬間 — **webui に到達できる誰でも、devtools から任意の identity を名乗って
書き込める**。ブラウザという「その主張をする資格が最も無い当事者」の自称を、
検証済みの委譲としてサーバーに渡してしまう。

既定(delegators 空)では 403 になるので現に穴が開いていたわけではない。
しかし「この機能を意図したとおりに設定すると穴が開く」という形は、
設定ミスではなく設計の欠落である。

`ochakai ui` も同じ形をしている。こちらはブラウザから来た `Authorization` を
明示的に捨てている(「プロキシの仕事は CLI ユーザーの identity に
置き換えることだ」)のに、委譲ヘッダだけが素通りしていた。同じ理由で
同じ扱いにする。

## 3. 世界観: identity を差し替える者は、identity の自称を運んではならない

両プロキシに共通する役割は「**呼び出し元が誰であるかを、上流に対して
言い直す**」ことである。その役割を持つコンポーネントが、言い直す対象で
あるはずの自称をそのまま横に添えて渡すのは、役割の裏切りである。

したがって規則は 1 行で書ける: **プロキシは、検証できる出所を持つときだけ
identity を主張し、それ以外のときは何も主張しない。** 削るのが既定であり、
載せるのは例外である。

## 4. 決定の詳細

### 4.1 検証は Google の検証器で行う

`google.golang.org/api/idtoken`(既存の直接依存)の `Validate` を使う。
IAP のアサーションは ES256 で、鍵は
`https://www.gstatic.com/iap/verify/public_key-jwk` から取る — この分岐と
鍵のキャッシュは idtoken が持っている。新しい依存は増やさない。
署名・audience・有効期限は idtoken が見る。

**`iss` は自分で確認する。** idtoken は issuer を見ないので、
`https://cloud.google.com/iap` であることを別途検査する。audience が
一致する Google 署名のトークンが他の経路から来る可能性を塞ぐ。

`OCHAKAI_IAP_AUDIENCE` は運用者が与える。推測しない — audience 文字列は
IAP のリソース種別で形が変わり、間違った既定値は「検証しているつもりで
検証していない」という最悪の状態を作る。

### 4.2 検証できないリクエストは拒否する

audience を設定したということは、運用者が「ブラウザの人を記録せよ」と
言ったということである。そこでアサーションが無い・壊れている場合に
サービスアカウント名義へ黙って落とすのは、0027 §5.2 が拒否した
**静かな降格**そのものになる。403 を返す。

これは IAP が実際には前に立っていない構成(あるいは IAP を迂回して
到達した呼び出し)を、運用者が気づける形にもする。

audience が**未設定**なら従来どおり: ヘッダは削るが作らず、書き込みは
サービスアカウント名義になる。IAP を使わない deployment のための正しい
挙動であり、起動ログにどちらのモードかを出す。

### 4.3 audience 不一致は、直し方が分かるエラーにする

検証に失敗したとき、ログには「設定された audience」と「トークンが
名乗った audience」を併記する。後者は**署名を検証せずに読んだ値**であり、
判断には一切使わない — 運用者が `OCHAKAI_IAP_AUDIENCE` に何を入れれば
よいかを知るためだけの表示である。コードにもそう書く。

### 4.4 サーバー側は変えない

ochakai 本体(`serve`)は 0027 のままである。delegators の許可リスト、
403、`via` 連鎖、すべて既存の機構をそのまま使う。本ドキュメントが足すのは
**プロキシがそのヘッダに何を入れるか**だけで、サーバーの信頼モデルは
1 行も動かない。0002 の「認可を持たない」も不変である。

## 5. 壊れるもの

- **IAP 構成で `OCHAKAI_IAP_AUDIENCE` を設定すると、webui のサービス
  アカウントを `OCHAKAI_DELEGATING_CALLERS` に載せる必要がある。**
  載せ忘れるとサーバーが 403 を返す(0027 の設計どおり、静かに落とさない)。
- 設定した後の書き込みは `human:<ユーザー>` via `agent:<webui の SA>` として
  記録される。既存エントリの provenance は変わらない。
- ブラウザから委譲ヘッダを送っていた利用者はいない(そんな用途は無い)。

## 6. 検討して採らなかった案

- **ヘッダを削るだけにする。** 穴は塞がるが、0027 §6 が予告した
  「webui の provenance がサービスアカウント 1 つに潰れる」問題
  (0002 §3)は残ったままになる。削る修正と作り直す修正は同じ場所の
  同じ 1 つの判断であり、分けると「なぜ削るのか」の理由が薄くなる。
- **ochakai 本体で IAP JWT を検証する。** 0002 §4 と 0027 §6 が既に
  「webui 側の実装として片づく」と判断している。本体に持たせると、
  IAP を使わない deployment にも IAP の設定項目が生える。
- **audience 未設定でも IAP ヘッダがあれば検証する。** 検証すべき
  audience を知らずに検証はできない。「あれば使う」は検証していない
  ものを検証したことにする典型である。
