# ochakai 設計ドキュメント 0117: 人が process として記録されるとき、そう言う

Status: Accepted(2026-08-22)。[0086](0086-a-second-way-to-say-who-is-calling.md) §4 の
「email が無い / verified が false — `sub` を、process として記録する」を改訂する
— **記録の仕方は一字も変えない**。変えるのは、それを黙って行わないことである。
[0065](0065-identity-and-provenance.md) §3 が委譲について決めた原則の、
二つ目の扉への適用である
Date: 2026-08-22

## 1. 何が起きたか

0086 §4 は、検証済みトークンから何を読むかを三つに分けた。verified な
email は人、verified でない email は使わない、そして **email が無ければ
`sub` を process として記録する**。三つ目に添えた理由は「機械のトークンは
この形をしている」であり、それは正しい。

**正しくなかったのは、人のトークンもこの形で届きうることである。**
[0116](0116-the-connector-price-changed-not-its-condition.md) の実験で
実際に踏んだ: ブラウザで認可を通った人の access token に email クレームが
無く、`identityFrom` は `sub` を返し、`Machine: true` が付いた。その人が
書いた concept の `created_by` は `process:` である。

**何も落ちない。** 401 も 403 も出ず、書き込みは成功し、応答は 200 で
ある。運用者が気づく契機は、数週間後に台帳を眺めることしかない。

email が ID トークンにしか載らないのは、発行者の側では普通の構成である
(access token に載せるには意図的なマッパーが要る)。**つまりこれは
珍しい設定ミスではなく、既定を踏み抜いた形である。**

## 2. 0065 §3 は、同じ形を既に断っている

委譲について、0065 §3 はこう書いた。

> 許可されていない呼び出し元がヘッダを送ったら **403 を返す。無視しない。**
> 黙って呼び出し元自身として記録すると、アプリは自分が利用者名義で書けて
> いると信じたまま動き続け、数か月後に全エントリが SA 名義だったと気づく。
> **静かな降格は、明示的な失敗より常に高くつく。**

OIDC 経路で起きているのは字義どおり同じことである — 全エントリが
`process:<sub>` 名義になる。**違うのは扉だけで、原則は同じ扉のために
書かれたのではない。**

そして 0086 §4 がこの綴りを決めたとき、この扉はまだ開いていなかった。
[0116](0116-the-connector-price-changed-not-its-condition.md) が開けた
のではなく、**開けられることが分かった**のがその実験である。

## 3. なぜ 403 ではないのか

0065 §3 が 403 にできたのは、そこに曖昧さが無いからである — 許可リストに
載っていない呼び出し元が他人の名を送った、という事実は一つしか読めない。

**こちらは曖昧である。** email を持たず `sub` だけのトークンは、人のもの
かもしれないし、機械のものかもしれない。ochakai には見分ける材料が無く、
**見分けられないものを拒めば、正当な機械のトークンを拒むことになる** —
0086 §4 が三つ目を置いた理由がそれである。

だから答えは拒否ではなく告知であり、**この記録が決めるのは「どこで言うか」
だけ**である。

## 4. 決定: プロセスに一度だけ言う

`OCHAKAI_OIDC_ISSUER` を設定したデプロイが、email を持たないトークンを
**そのプロセスで最初に受けたとき**、警告を一行出す。二度目以降は出さない。

```
level=WARN msg="a verified token carried no email; recording the caller as a process"
  issuer=https://issuer.example subject=<sub>
```

- **一度だけなのは、機械のトークンでも出るからである。** 見分けられない
  以上、正当な構成でも必ず一度は鳴る。毎回鳴る警報は何も知らせない
  ([docs/surface.md](../surface.md) が `DOC-LINES` の幅について書いた
  当の理由)。
- **設定を終えた直後に必ず目に入る。** 運用者が発行者を設定して最初の
  呼び出しを通したその瞬間が、マッパーを直せる唯一の安い時点である。
- **`sub` は出す。** 誰のことを言っているのか分からない警告は、直す手が
  かりを持たない。トークンそのものも鍵の素材も出さない(0086 §2 の
  エラーが守っている線と同じ)。

**記録される名前も、trust の段も、応答も、一つも変わらない。** 0086 §4 の
三つ目はそのまま生きている。

## 5. 言わない場所

- **要求ごとのログ。** 機械のトークンを使う正当なデプロイでは全リクエスト
  に付く。読まれない行が増えるだけである。
- **起動時。** そのときはまだ何のトークンも見ていない。0086 が起動時に
  断るのは片方だけの設定であって、トークンの中身は起動時に存在しない。
- **応答のヘッダや本文。** これを知る必要があるのは呼び出し元ではなく
  運用者であり、しかもヘッダ名は凍結の内側である
  ([0082](0082-what-the-freeze-holds-still.md) §2)。
- **Cloud Run 経路。** あちらは `actorFromIDToken` が読み、**email の無い
  トークンを降格させず、エラーにする**(「identity token has no email
  claim」)。二つの経路は最初から違う答えを持っていて、片方だけが黙って
  いた。**この記録は 0086 の経路にだけ効く。**

## 6. 面

**一つも動かない。** REST も MCP も CLI も Web UI も、ワイヤも語彙も
環境変数も同じである。増えるのは運用者のログに出る一行で、それは
[0067](0067-four-faces-and-what-they-decline.md) が数える面ではない。

`internal/restapi/requestlog.go` が「これはテレメトリではない — 行は
stdout に出て、Cloud Run ではそのデプロイ自身のログである」と書いている
のと同じ性質を持つ。**どこにも報告しない。**
