# ochakai 設計ドキュメント 0058: 誰も通らなかった二つのフィルタ

Status: Accepted(2026-07-30)。**BREAKING。**
`GET /api/v1/context` の `min_score` と `ochakai context --min-score` を
**廃す**([0004](0004-cli.md) §3 の表が載せている `--min-score` を改訂する)。
frontmatter フィルタ `fm.` を **MCP の 2 ツールから降ろす**
([0047](0047-fm-carries-okf-keys.md) §4 の「Web UI には載せない」を、
MCP も載せないに改訂する)— REST と CLI には残るので能力は落ちない。
[0015](0015-surface-consistency.md) §3 の「載せないもの」に 1 件足す。
[0051](0051-instance-metrics-and-search-misses.md) §3.1 がスコアの床を
採らなかった理由を、そのままこちらにも適用する
Date: 2026-07-30

## 1. 問題: 面に載っているが、誰も通っていない

0046・0055・0056 の畳み込みは、どれも**同じ能力の第二の住所を消す**もの
だった。消えたのは面であって能力ではない、と各ドキュメントが書いている
とおりである。その作業がほぼ終わったところで残るのは、**第二の住所では
なく、最初から誰も通らなかった入口**である。

二つある。

### 1.1 `min_score` — 較正しろ、としか言えないパラメータ

`GET /api/v1/context?min_score=` と `ochakai context --min-score` は、
スコアが床を下回るヒットを展開前に落とす。問題は**その床を誰も決められ
ない**ことである。

[0051](0051-instance-metrics-and-search-misses.md) §3.1 は検索ミスの定義
を決めるときに同じ壁に当たり、こう書いた —

> ochakai のスコアは**検索モードに依存して較正されていない** —
> レキシカルではフラグメント一致重み + boost、ハイブリッドでは
> RRF(~0.02 スケール)であり、片方で意味のある床はもう片方では
> 無意味である

0051 はその理由で閾値を**採らなかった**。同じ理由が既にあるパラメータに
及んでいなかっただけである。

実際に何が起きていたか:

- **MCP は最初から載せていない。** `contextIn` のコメントが「較正の要る
  パラメータをエージェントに渡してもエージェントは較正できない」と
  書いていた。
- **Web UI も使っていない。**
- **同梱の唯一の利用者が、既定で切っていた。**
  `examples/claude-code/hooks/ochakai-recall.sh` は
  `--min-score "${OCHAKAI_RECALL_MIN_SCORE:-0}"` を渡す — 既定値 0 は off
  である。`examples/claude-code/README.md` はその隣で「較正してから
  使え、普遍的な既定は無い、だからフックは床を切って出荷する」と
  説明していた。**製品が自分で「使うな」と書いている面**が、それでも
  三つの面に載っていた。
- ドキュメント([knowledge.md](../knowledge.md))も同じことを、
  「ordering であって measure ではない」という一文で書いていた。

つまり REST 面のパラメータ 1 本と CLI のフラグ 1 本、OpenAPI の 10 行、
フックの 1 行、README の 1 段落、`Service.Context` の 6 行が、**誰も
使っていない一つの機能の説明に費やされていた**。

### 1.2 `fm.` の MCP スキーマ — 1,888 文字で、通行量ゼロ

[0047](0047-fm-carries-okf-keys.md) が決めた `fm.<key>=<value>` は、OKF が
定義するキーのうち専用フィルタを持たない 11 個を引く。設計としては筋が
通っており、`EnvelopeKeys` から導出するので OKF がキーを増やせば自動的に
引けるようになる — **REST の面としては何も間違っていない。**

問題は MCP に載っていることの値段である。ツールスキーマの説明文は
**エージェントのコンテキスト窓から支払われる**([0015](0015-surface-consistency.md)
§3.1: だから MCP の既定は no)。実測すると:

| | 文字数 |
|---|---|
| MCP スキーマの説明文 合計(改訂前) | 13,099 |
| うち `fm` の説明(`search_concepts` と `get_context` に同文) | 944 × 2 = **1,888** |

**14%** である。接続するエージェントが毎回払う。

対して、この面を通った形跡は無い — Web UI は使わず、
[examples/demo](../../examples/demo) にも
[examples/claude-code](../../examples/claude-code) にも `fm` は現れず、
CLI ヘルプの worked example にも無い。

理由は 0047 §4 が Web UI を断ったときの理由とほぼ同じである。**`fm.` は
「どのキーで絞るかを既に知っている人」の語彙である。** 0047 は Web UI に
ついて「絞り込みの語彙を利用者が既に知っていることを前提にする」と書いた。
エージェントについても同じことが言える上に、エージェントの場合は
**その前提を満たさせるための説明が課金される** — 11 個の綴りと、
`fm.status` と `status=` がなぜ別の答えを返すのかを、毎回スキーマで
教えることになる。

## 2. 決定

### 2.1 `min_score` を廃す

REST・CLI・`Service.ContextRequest` から消す。**代替は置かない。**

応答を絞りたい呼び出し元が使うものは `budget` である。バイト数は較正を
要さず、モードに依存せず、入りきらなかったものは `outline` 行として名前が
返る([0033](0033-context-hits-are-a-ranking.md))— 「落とす」ではなく
「名前は返す」であり、呼び出し元は続きを取りに行ける。**床は捨てるが、
床が解こうとしていた問題は既に解けている。**

これは畳み込みではなく削除であり、**能力は落ちている**。落ちるのは
「較正した呼び出し元がスコアの床を置く」能力で、較正の手順を製品が説明
できず、同梱の唯一の利用者が既定で切っていたものである。

### 2.2 `fm.` を MCP から降ろす

`search_concepts` と `get_context` の入力から `fm` を外す。REST
(`?fm.<key>=`)と CLI(`--fm key=value`)は**そのまま残る** — 0047 の
決定はどこも覆さない。変わるのは載る面だけである。

エージェントが frontmatter のキーで絞りたくなったとき、道は二つある:
CLI を shell から呼ぶ(README が Claude Code に勧めている経路そのもの)
か、REST を直接叩く。**どちらも、そのエージェントが実際にそのキーを
知っているときにだけ払う。** スキーマは全員が毎回払う。

見直す条件: MCP クライアントが `fm` の無いことで詰まった実例が出たら、
`search_concepts` にだけ戻す。そのときの説明文は 11 個の綴りを列挙せず、
「引けるキーはエラーが教える」形にする — サーバは既に
`askableHint` でそれを返している。

## 3. 選ばなかった案

### 3.1 `min_score` を残して「較正済みの呼び出し元向け」と書き足す

今そうなっている。**説明を足しても通行量は増えない** — 三年後に読む人が
「これは何のためにあるのか」を調べ直すコストだけが残る。

### 3.2 スコアを較正して、床を意味のあるものにする

モード間で比較可能なスコアを作ることは、検索の設計をやり直すことである。
0051 が「モードによって意味の変わる閾値を、後から解釈できない履歴の中に
焼き込むことはしない」と書いた判断を、より大きな工事で覆すことになる。
**そこまでして買えるのは、誰も要求していない床である。**

### 3.3 `fm` の MCP スキーマ説明を短くする

944 文字を 200 文字に削る案は検討した。だが短い説明は
「`fm.status` と `status=` はなぜ違うのか」を答えられず、答えられない説明は
**間違った使い方を招く**(0047 §1.1 がまさにその混同を問題にしていた)。
説明の長さは `fm.` の性質から来ており、**縮められるのは説明ではなく載る
面である。**

### 3.4 `fm.` を REST からも消す

消さない。REST は唯一の契約(0015 §3.1)であり、**利用者が自分の Web
サービスに埋める小さな API** という条件(C6)は「自分のアプリが何を
引きたいか知っている」呼び出し元を想定している。`fm.` はその呼び出し元の
語彙である。0047 の導出は additive なクエリ面という目的も果たしており、
それを捨てる理由は無い。

## 4. サーフェス(0015)

| 面 | `min_score` | `fm.` |
|---|---|---|
| REST | **廃止** | 残す(変更なし) |
| CLI | **廃止**(`--min-score`) | 残す(`--fm`、変更なし) |
| MCP | 元から無し | **降ろす** |
| Web UI | 元から無し | 元から無し(0047 §4) |

`docs/surface.md` の PARAM が 19 → 18、上限も 19 → 18 に下がる
(「下げるのは日常」)。MCP のツール数は 8 のまま — **ツール数に出ない
ところでツールスキーマが 14% 減る**というのがこの改訂の形であり、
surface.md がまだ数えていない次元が一つ見えたということでもある。

## 5. 互換性

**BREAKING。** `min_score=` を送っていた呼び出し元は、そのパラメータが
無視される(未知のクエリパラメータは 400 にしない)。値が効かなくなる
ので、床に頼っていた挙動は変わる — 0.x に deprecation window は無い
([compatibility.md](../compatibility.md))。

MCP クライアントが `fm` を送ると、未知の引数としてスキーマ検証で拒否
される。上記のとおり、そのようなクライアントの存在は確認されていない。

保存されるものは何も変わらない。producer のキーは今までどおり保存され、
往復し、エクスポートに出る(0046 §2.2、SPEC §4.1)。
