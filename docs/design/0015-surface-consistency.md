# ochakai 設計ドキュメント 0015: サーフェス一貫性の方針

Status: Accepted(2026-07-18 の議論で決定)。§4 のサーフェス表は
[0046](0046-bundle-address-space.md) §3.14 が現在の姿(REST 8 面・MCP 5 ツール)に
言い直した — 役割分担と「意図して載せない」という方針そのものは不変。§4 の「verify は新 API を作らず PUT の糖衣として」は [0025](0025-closing-the-loop.md) §6 が覆した — 内容の変わらない PUT は何も書かないので糖衣では再検証を表現できず、`POST /api/v1/verify/{id}` を新設した(REST / CLI / Web UI に載り、MCP には載らない)。§3 の「載せないもの」に [0047](0047-fm-carries-okf-keys.md) §4 が 1 件足した — frontmatter キー(`fm.`)のフィルタは Web UI に載せない。§3.1 にも [0051](0051-instance-metrics-and-search-misses.md) §4 が 1 件足した — インスタンスの集計(`stats`)は MCP に載せない。同じく [0052](0052-producer-beside-the-actor.md) §3.3 が 1 件足した — producer の申告は Web UI に載せない(人が自分で書く編集面には名乗るソフトウェアが無い)
Date: 2026-07-18

## 1. 目的

ochakai には 4 つのサーフェスがある: REST(/api/v1)、MCP(/mcp)、
CLI、Web UI。機能を足すたびに「どのサーフェスに載せるか」を都度判断
していると、載せ忘れ(PR #71 で browse が CLI に入らなかった)や
文言の乖離(設計ドキュメント 0013 の添付一般化がヘルプに反映されな
かった)が繰り返される。本ドキュメントは各サーフェスの役割と、
**意図して実装しないもの**を明文化し、次の機能追加が参照する場所を
作る。

## 2. 各サーフェスの役割

- **REST は唯一の契約。** すべての機能はまず /api/v1 に載る(または
  どこにも載らない)。他の 3 サーフェスは全部そのクライアントである
  (設計ドキュメント 0007)。上限・enum・デフォルトなどの契約は
  サーバー側に一元化する。
- **MCP はエージェントの目的特化入口。** ツールスキーマはエージェント
  のコンテキストを消費するから、ツール数は予算である。REST の 1:1
  ミラーは目指さない。「エージェントのループが 1 コールで必要とする
  もの」だけを載せる(get_context がその極致)。
- **CLI は完全性のサーフェス。** /api/v1 の純クライアントとして REST
  の全操作をカバーする。シェルを持つエージェントと人間の両方が使う。
  バルク操作(OKF import)は CLI が既存 API を合成して実現する。
- **Web UI はループの人間側。** キュレーション面であって BI ツール
  ではない。検索・ブラウズ・レビュー(verify/reject)・履歴の閲覧
  まで。ページは認証を知らない(設計ドキュメント 0006)。

## 3. 実装しないもの(サーフェス別)

### 3.1 MCP に載せないもの

- **browse。** 設計ドキュメント 0014 §2.3 のとおり。木を歩くのは
  多ラウンドトリップ型の探索で、get_context の「1 コールで全部」と
  正反対。
- **revisions。** エージェントが必要とする信頼シグナル(created_by /
  verified_by / updated_at)はエントリ本体に載っている。全スナップ
  ショット付き履歴はトークン的に重く、監査は人間の仕事。
- **backlinks。** get_context がリンクを逆向きにも展開して同梱済み。
  単独ツールは機能重複になる。
- **添付の書き込み(attach / detach)。** base64 をツール引数に載せる
  のはトークンの浪費であり、思想にも反する: エージェントの書き戻しは
  検索可能なテキストであるべきで、「添付から学んだら本文に書け」と
  get_attachment の description が既に誘導している。
- **バルク(export / import / import-ossie)。** 応答サイズが読めず、
  tar.gz はツール結果に載らない。管理タスクは CLI / CI の領分。
- **人間が判断を下したエントリ(verified / rejected / deprecated)の
  上書き・削除。** update_knowledge / delete_knowledge は対象がこの
  いずれかなら拒否する(create、draft の更新、draft から verified への
  昇格はいずれも従来どおり)。

  これは認可ではない。0002 の「認可を持たない・verified 昇格を制限
  しない」は撤回しない — 誰が検証したかは記録され、信頼は provenance
  で判断される、という原則はそのまま。制限するのは**前提条件を
  表明できない面からの黙示的な置き換え**だけである。0030 の
  If-Match は REST の ETag に乗っており、MCP にはその通り道がない。
  つまり MCP の update は last-write-wins で、draft には許容できるが
  人間がキュレーションしたものには許容できない。

  非対称性の根拠は復旧可能性ではなく**可視性**にある。soft-delete は
  目に見えて、かつ create で復活する。verified なゴールデンクエリの
  本文が黙って置き換わった場合、誰かがそれを実行して間違った数字を
  得るまで誰も気づかない。

  エージェント側の正しい行動は 0025 が既に用意している: 誤りなら
  report_outcome failed(sort=failed の再検証フィードに乗る)、
  より良いものがあるなら新しい draft を create する。どちらも
  書き戻しループの正規の経路であり、この規則はむしろそこへ誘導する。

  **rejected は verified と同じかそれ以上に重要である。** Create は
  live なエントリがあれば ErrAlreadyExists を返す(rejected を含む)
  ので、rejected に阻まれたエージェントには delete → create という
  2 手の迂回路がある。soft-delete 済みエントリは Create が draft として
  復活させるので、却下の理由(status_note)ごと消える。README が
  memory layer との差別化の筆頭に挙げ、配布する指示がエージェントに
  「再提案の前に --status rejected を見ろ」と言っている当のものが、
  2 コールで消せる。しかも verified の消失と違い、rejected の消失は
  誰も使っていなかったので誰も気づかない。

  **create による復活も塞ぐ(2026-07-25 追記)。** delete を塞いだだけ
  では足りなかった。Create は soft-delete 済みの行を
  `ON CONFLICT ... WHERE deleted_at IS NOT NULL` でその場で復活させ、
  status と status_note を入力で上書きする。つまり**すでに存在する
  墓標**——このルール以前に消されたもの、あるいは人間が REST/CLI で
  整理として消したもの(rejected を消すのは正当な運用である)——は、
  create 1 コールで「一度も判断されていない draft」として戻せる。
  update / delete のガードはこれを見られない。読む行が live ではない
  からである。

  そこで create も、対象 id が verified / rejected / deprecated の墓標
  なら拒否する(`RefuseIfRevivingCurated`)。draft の墓標は従来どおり
  復活できる — 誰も判断を下していないし、放棄された draft の id を
  再利用するのは create の想定どおりの使い方である。人間の面(REST /
  CLI / Web UI)は従来どおり復活でき、id を完全に解放したければ purge
  がある(0031)。

  **状態遷移も同じ扱いにする。** verified → deprecated も MCP からは
  できない。廃止は「正しかったが今は推奨しない」という判断であって、
  エージェントの観測ではない。観測の通り道は report_outcome であり、
  判断は人間の面で行う。

  **TOCTOU。** チェックと書き込みの間に別の書き込みが挟まりうる。
  update はチェック時に読んだ updated_at を If-Match として渡すことで
  構造的に閉じてある(0030 の機構をそのまま使う)ので、窓の中で
  キュレーションされた場合は上書きではなく衝突になる。delete には
  ストア側に precondition の通り道が無く、窓は 1 往復ぶん残る —
  delete は復活可能なので許容している。

- **purge。** 履歴の破壊は人間の判断である(0031 §3.4)。上の墓標
  ガードの裏面: エージェントから塞いだ結果として必要になった逃げ道は、
  塞いだ相手ではなく人間の面に置く。
- **reembed。** 埋め込みモデルを入れ替えた後にコーパスを埋め直す運用
  タスクで、エージェントの仕事ではない。バルクと同じく CLI / CI の領分。

### 3.2 REST に載せないもの

- **SQL 実行。** ochakai はウェアハウス資格情報を持たない。コンパイル
  まで、実行はクライアント。
- **LLM を使う機能(要約・チャット・自動検証)。** LLM を使わない
  ことが決定的コンパイルと人間検証への信頼の根拠。
- **認証・ユーザー管理。** 認証は Cloud Run IAM の仕事(設計
  ドキュメント 0002)。ユーザー DB を持った瞬間 secrets ゼロ運用が
  壊れる。
- **Web UI の配信。** ページを持たないサーバー(設計ドキュメント
  0006)。認証境界をプロキシに置く前提。
- **バルク OKF import(POST /import/okf)。** import は CLI が
  create / update / attach を 1 件ずつ叩いて合成する。件別の
  created / updated / unchanged レポート・dry-run・部分失敗の位置
  特定・actor 記録がすべて既存 API の意味論に乗り、サーバー側バルク
  という「同じ成果物への 2 経路目」(0007 §2.1 の drift の温床)を
  作らずに済む。見直す条件は、CLI を持たないクライアントが import を
  実際に必要としたとき、だけ。

  この判断は 2026-07-25 に再検討し、維持した。埋め込みホストからの
  要望として上がったが、REST bulk import があっても**できることは
  増えない** — POST /api/v1/knowledge を N 回と添付の PUT で完結し、
  `ochakai import` がやっているのはまさにそれである。増えるのは
  利便性だけで、移行は一度きりのオペレータ作業、CI からの継続同期も
  ochakai バイナリ(または公開コンテナイメージ)を実行できる。加えて
  現在のリクエスト本文上限は 4MiB で実バンドルはこれを超えるため、
  ストリーミング受信と Cloud Run のリクエストタイムアウトという別の
  設計が要る。

  ただし代償は認めておく。README は CLI を「a thin client of the same
  REST API」と説明しており、**import はその主張の唯一の例外**である。
  バンドルの解析・添付の帰属解決・skip レポートの生成という、本来
  サーバー側に属するセマンティクスがクライアントに住んでいる。帰結は
  2 つ: (1)「どの生成者の OKF バンドルでも読める」という相互運用の
  売りを、Go バイナリ以外から享受できない。(2) export/import の往復
  セマンティクスをクライアントのバージョンが決める — データを所有して
  いるのはサーバーなのに。

  そこで、作らない代わりに**何を実装すれば同じことができるか**を
  openapi と README に明記する(§3.2 の判断が相互運用の障壁になら
  ないように)。実装に踏み切るトリガも決めておく:
  **バイナリを持ち込めない環境からのリストア要求が実際に来たとき。**

### 3.3 CLI に載せないもの

- **DB 直結コマンド。** `serve` のみ(設計ドキュメント 0007 で決着)。
- **レビューキューのヒューリスティック再実装。** Web UI の stale 判定
  (14 日)や weak-score 閾値は表示層のヒューリスティックであり、
  複製すると二重実装 drift が始まる。CLI は素材の提供
  (`search --sort usage --status draft`)まで。
- **TUI・対話モード。** パイプで合成できる行指向出力が CLI の価値。
  対話が欲しければ `ochakai ui` が立つ。
- **ローカルキャッシュ・オフラインモード。** スナップショットは
  export が担う。キャッシュは鮮度と provenance の問題を持ち込む。

### 3.4 Web UI に載せないもの

- **report_outcome(worked / failed ボタン)。** outcome は「知識に
  基づいて SQL を実行した結果」の証跡であり、SQL を実行しない UI に
  ボタンを置くと行動の裏付けのない worked / failed が混入して再検証
  フラグの信号が汚染される。表示のみが正しい。人間の判断は verify /
  reject という別の語彙で記録される。
- **context ビュー。** エージェント向けのパッキング面。UI に置くと
  「質問を入れる箱」になり、チャット / BI への滑り坂。デバッグは
  CLI で足りる。
- **SQL 実行・チャート・チャット。** README の宣言どおり、エージェント
  に食わせる側に徹する。
- **OKF import アップロード。** バルク REST を作らない判断(§3.2)の
  帰結。複数ファイル・dry-run・件別レポートはブラウザのアップロード
  1 発と相性が悪い。
- **ログインフォーム。** 認証はプロキシの仕事。ページが認証を知らない
  から同じ 1 枚が 2 通りに配布できる(設計ドキュメント 0006)。
- **purge。** 削除ボタンの隣に不可逆な破棄を置くと、delete → purge を
  二段階にした意味が薄れる(0031 §3.4)。CLI から行う。
- **reembed。** 運用タスクであって閲覧・キュレーションの操作ではない。

## 4. 境界上の判断(現状維持、見直し条件つき)

- **CLI の verify / reject 糖衣コマンド。** status 遷移は update の
  一形態であり、専用動詞は同じ成果物への 2 経路目になるから作らない。
  ターミナルからのレビューが実運用で頻発するなら、**新 API を作らず
  PUT の糖衣として**足すのは許容する。
- **バルク OKF import。** §3.2 のとおり。
- 新しいエンドポイントを /api/v1 に足すときは、本ドキュメントに
  照らして「CLI に載せる(原則 yes)/ MCP に載せる(原則 no、
  エージェントのループが 1 コールで必要とする場合のみ yes)/
  Web UI に載せる(人間のキュレーションに要るなら yes)」を PR で
  明示する。
