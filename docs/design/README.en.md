# Design records, in English

The decision records in this directory are Japanese, immutable, and
authoritative. This file is neither immutable nor authoritative: it is a
reading aid for people who cannot read them, so that the citations to
"design doc NNNN" scattered through the README, the architecture doc and
`api/openapi.yaml` lead somewhere. Where a row here and its record
disagree, **the record is right** — say so in an issue and this file
gets fixed.

One row per record: the record it links to, its status, and the decision
in a sentence or two. The grouping follows [the index](README.md) — start
with the table at the top of it for which record still describes an area
today. Numbers have gaps: proposals that never landed stay in their pull
requests.

A record that has been superseded gets a one-line pointer to whatever
replaced it instead of a summary — that is enough to follow the trail and
is all the maintenance it earns (design record
[0048](0048-decision-records-for-wire-contracts.md) §2.5).
`TestEnglishDesignIndexCoversEveryRecord` holds every record to at least a
row, and `TestEnglishIndexSummarizesOnlyWhatIsCurrent` holds a superseded
one to the pointer and nothing more.

For the shape of the system rather than the history of it, read
[docs/architecture.md](../architecture.md) (Japanese) first.

| [0080 What search fuses, and how a deployment embeds](0080-search-and-how-a-deployment-embeds.md) | Accepted; the current record for search and embeddings (carries 0020, 0053, 0073, 0078) | On Google Cloud the project **and the region** are discovered from the metadata server and semantic search is on by default; IAM decides whether it works, not configuration, and a discovered default degrades to lexical while a named one refuses to start. **Text is embedded in the region the deployment runs in** — a deployment in asia-northeast1 does not send concept bodies and search queries to another continent to be embedded, and where the region cannot be read ochakai embeds nowhere rather than picking a region nobody chose. No fixed default is right: us-central1 exports a Japanese deployment's text, and asia-northeast1 is the same mistake mirrored. One variable says how a deployment embeds: `OCHAKAI_EMBEDDINGS` takes unset/`on`, `off`, or a Vertex AI model resource name — the one string that already carries project, location and model together — and anything else is a startup error naming the three forms. Search fuses three lists: lexical (filenames included), concept vectors and file vectors, with a file's hit mapped onto the concept that owns it. Files never come back on their own, and ochakai never interprets them. Consolidates four records; no decision changes, except that 0073 §6's claim of a write-side media-type allowlist is corrected — there is none, and the five embeddable types decide only what is worth an embedder call. |
| [0089 A half-embedded concept says so](0089-a-half-embedded-concept-says-so.md) | Accepted; amends [0080](0080-search-and-how-a-deployment-embeds.md) §3 and §7 | A concept longer than the embedding model's input window is embedded from its front and the rest is dropped — and nothing about the result looks wrong: it has a vector, it ranks, it comes back, and it is simply unfindable by anything said in its second half. The longer and more valuable the document, the more of it is gone. The flag lives on the vector row rather than on the concept, because the same concept is truncated under one model and whole under another; it is derived like the vector beside it, so existing rows read false ("not known to be truncated", which is what an un-reembedded row honestly is) until the next write or `ochakai reembed`. `GET /api/v1/stats` answers `embedding` with `enabled`, `vectors` and `truncated` — `enabled` because `vectors: 0` otherwise conflates a deployment without semantic search with one whose corpus is entirely unembedded, and the other two read as a pair: three in four is the shape of the corpus and wants a wider model, three in four hundred is one long runbook and wants splitting. CLI prints the pair (`-` with no embedder, as with misses); the web UI draws it only when it is not zero, as it does for dropped observations; MCP does not carry it. **Chunking is declined**: nobody can yet name who got stuck, because until now no surface said this was happening at all; the one-concept-one-vector assumption is load-bearing in the primary key, the search SQL, the reembed cursor and the stats count, and how chunks fold back into a concept is a ranking decision no record has made; and a document over the window is more often two concepts than one long one. §4 states the condition for reopening it. Files are not counted — a second table, a second number, and a file stays findable by name whatever happens to its bytes. |
| [0091 A file vector is keyed by its path](0091-a-file-vector-is-keyed-by-its-path.md) | Accepted; amends [0080](0080-search-and-how-a-deployment-embeds.md) §5 | A file's vector was keyed by `(concept id, filename)` — the shape from when a file was something a concept *had*, addressable only at `<id>/<name>`. Once [0046](0046-bundle-address-space.md) and [0075](0075-the-bundle-is-the-address-space.md) made a file an object of the bundle attributed by any body that links it, the name became the path's last segment, and **a concept whose body showed `charts/q1.png` and `tables/q1.png` wrote both to one row**: the second vector overwrote the first and one of the two files silently left semantic search. Silently is the word — the file is still stored, served, exported and found by name; what is missing is only the vector half, which is the "ask it another way" path that embeddings exist for. The key is the path now, and **which concept a hit belongs to is read at search time from the bundle**, through the same attribution predicate the listings, backlinks and export already go through. Three things become true with it: a file the body links today ranks that concept today with nothing re-embedded, a file the body stops linking stops ranking it at once, and one file two concepts show ranks both from a single vector. Same reason, a file no concept names is embedded when it lands rather than waiting for a `reembed` to find an owner. The old rows are **dropped, not migrated**: a vector is derived and refilling is `reembed`'s job (0080 §3), and here the overwritten side no longer exists and a surviving row cannot say which file it described — guessing is worse than rebuilding. So an upgrade adds one step for the operator, `ochakai reembed`, and until it runs files are found by name, where a deployment without embeddings already is. The pending queue becomes a queue of files rather than (concept, file) pairs, holding only the media types this deployment's model can take: a zip in the old queue could never leave it, so `ochakai reembed` ended non-zero on every pass saying work was outstanding and pointing at a server log that said nothing. No surface changes. |
