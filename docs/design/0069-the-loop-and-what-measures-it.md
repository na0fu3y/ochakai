## 1. ループは三つの部品で締まる

中核仮説は「エージェントが下書きし、人が検証する」双方向ループである
([0001](0001-architecture.md))。締まるには三つが要る。

1. **利用が測られている** — どの concept が実際に使われたか。
2. **検証が時効を持ち、古くなると浮上する** — verified はスキーマ変更で腐る。
3. **再検証が証拠で優先され、人が回すワークフローの中で拾われる。**

3 のために、**時間にもとづく陳腐化に、証拠にもとづく陳腐化を足す。**
`verified_at` の古さは「腐っているかもしれない」を、失敗報告は「腐っていると
報告された」を拾う。両者は補完的で、後者が無いと、あるエージェントが golden
query を実行して誤った数字を得て報告しても、**次のエージェントは同じ concept を
同じ信頼度で引いてしまう。**

## 2. 三つのキューと、キューではない一つのフィード

| キュー | 一覧 | 空になる条件 |
|---|---|---|
| 下書きレビュー | `ochakai list usage --status draft` | 公開する編集 / 却下 |
| 誤りと報告されたもの | `ochakai list failed` | 最後の失敗報告より後の verify |
| 宣言した期限切れ | `ochakai list stale_after` | 書き手が期限を宣言し直す編集 |

**三本とも空にできる。** 空にできないキューは読まれなくなるからで、これが
検証を独立した操作にした理由そのものである — 内容の変わらない書き込みは
何も書かないので、「読み直したが、まだ正しい」を表現する手段が他に無かった。
裁定の面は 0068 §4 が持つ(`POST /api/v1/review/{id}`)。

**`sort=verified_at` は数えない。** これはランキングであってキューではない。
対象は検証済み concept 全部で、件数はナレッジベースの大きさそのものであり、
**誰にも 0 にできない。** 0 にできない数を「待っている仕事」として並べれば、
他の三つの数の意味まで薄まる。カナリア運用はフィードを上から N 件取る運用で
あって、残件を数える運用ではない。

### 2.1 `failed` — 証拠にもとづく再検証

対象は `failed > 0` かつ**未処理のもの**(`verified_at IS NULL` または
`last_failed_at > verified_at`)。最後の失敗報告より後に検証された concept は
落ちる。並びは `failed DESC, worked ASC, verified_at ASC NULLS LAST, id` —
最も多く誤りと報告されたものが先頭、同数なら裏付けの worked が少ないもの
(信号対雑音が最悪)を上に、さらに同数なら検証が古いものを上に。
**未検証の draft は最後**である: 認証されていない下書きの失敗より、認証済み
concept の失敗のほうが緊急である。

**在否が「未処理か」を、並びが「どれだけ悪かったか」を表す。** 厳密な件数
(検証後に何回失敗したか)は生イベントが 180 日で刈られるので復元できず、
並びは累計のままにしてある。

### 2.2 `stale_after` — 宣言した期限は、verify では空にならない

`stale_after` が**今日以前**の concept だけを、超過の大きい順に返す。未来の
期限は入れない — まだ切れていない宣言は作業ではない。

**「今日」は UTC で、明示的にそう書く。** `current_date` はデータベース
セッションの `TimeZone` に従うので、そのまま使うと**同じ concept が、ある
環境では期限切れで別の環境ではそうでない**ことが起こる(実装中に実際に
踏んだ: JST の開発機と UTC の DB で一日ずれた)。
`(now() AT TIME ZONE 'UTC')::date` と綴って固定する。

**このフィードは他の二本と空き方が違う。** `stale_after` は書き手の宣言で
あってサーバーが観測した事実ではないので、**verify しても動かない** —
動かしたら、サーバーが書き手の宣言を書き換えたことになる。解消する正しい
操作は「再確認したうえで期限を引き直す」、つまり編集である。典型的な運用は
verify(確認した事実を記録)+ 編集(期限を引き直す)の二手になる。verify に
自動延長させる案は採らない — **何日延ばすかはサーバーが知らないし、知る
べきでもない。**

### 2.3 引用元からの逆引き

`source` フィルタは source の `resource`(引用先の URI / パス)**完全一致**
である。引用元が改訂されたとき — 会計方針が変わった、スキーマドキュメントが
更新された — 影響範囲を出すための面である。

- **フィルタであってフィードではない。** クエリとも `sort` とも組み合わせ
  られる(「この資料を引用していて、かつ期限切れのもの」が一回で引ける)。
  `source` だけを渡したときは順位づけの根拠になるテキストが無いので、
  住所順の一覧になる(`ochakai list --source <uri>`)。
- **`resource` だけで照合し、`id` では引かない。** `sources[].id` は本文の
  footnote から参照するためのその文書内のキーであって、concept をまたいで
  同じものを指す保証がない。
- **前方一致・部分一致・繰り返しはしない。** containment(`@>`)なら GIN
  index がそのまま効き、選言に落とすと効かなくなる。「この URL が変わった」
  という問いに部分一致は誤検出を増やすだけである。

## 3. 利用測定は読み取りパスに触れない

利用イベント(`search_hit` / `fetched`)は**メモリにバッファし、背景ループが
5 秒ごとにフラッシュする。**

**芯は、利用測定が best-effort であることである。** 利用統計は失われてよい。
失われてはいけないのはナレッジ本体であり、「このエントリは何回引かれたか」の
端数ではない。この非対称を明示的に選ぶことで、以下がすべて素直に決まる —
バッファ上限は 20,000 イベントで超過分は捨て(捨てたことは呼び出し元に返り
ログに残る。**静かに減るのではなく、減ったと分かる形にする**)、フラッシュの
失敗はバッチごと失われ、再試行キューは持たない。

**`report_outcome` はこの扱いに含めない。** 結果報告は読み取りの副作用では
なく意図的な書き込みであり、再検証ループがそれに依存している。同期的に書き、
失敗は面に返る。

`Close` はもう一度ドレインしてから終わるので、**順序が意味を持つ** — HTTP
サーバーがドレインを終えてから store を閉じる。逆順にすると、最後の数秒に
処理していたリクエストのイベントが最終フラッシュの後に積まれ、失われる。
SIGTERM 後の猶予は 5 秒である(Cloud Run が与えるのは 10 秒で、全部を
ドレインに使うと最終フラッシュが書き込み途中で殺される)。

生行は **180 日で刈る**。running total は残るので、刈っても利用数は正確な
ままである。

## 4. 答えられなかった問いも記録する

**ミスとは「ヒット 0 の検索」である。** クエリ文字列・呼び出し元・時刻を
一行として残す。キュレーションされたナレッジベースにとって*誰かが求めて、
無かったもの*は最も価値のある信号 — 次に何を書くべきかを教える唯一のリスト
であり、それだけが捨てられていた。**成功だけが数えられていた。**

**スコア閾値は採らない。** ochakai のスコアは検索モードに依存して較正されて
おらず、片方で意味のある床はもう片方では無意味である。モードによって意味の
変わる閾値を、後から解釈できない履歴の中に焼き込むことはしない。
**0 件はモードに依存しない。**

記録はサービス層の検索一か所で行うので、どの面から来た問いも同じ一か所で
数えられる。フィードは数えない — あれは問いではなく列挙である。

**これは ochakai が初めて保存する「利用者が打った文字列」である。**

- provenance は利用イベントと同じで、委譲が効いていれば委譲先が記録される。
  認可は無いので**読める者は全員読める** — ミスの一覧はキュレーションの
  材料であって、監査ログではない。
- 保持は 180 日。ただし利用イベントと違い**ミスには累計が無いので、刈られた
  期間は完全に消える。**
- 保存するのは先頭 500 バイトまで。それを超える文字列は問いではなく
  ペイロードである。
- **打たれたそのままの文字列でグルーピングする。** case も空白も畳まない。
  畳めば「サーバーが理解している」ように読めるが、ochakai はこの文字列に
  ついて何も理解していない — 答えを持っていなかったことだけを知っている。

**`OCHAKAI_RECORD_MISSES=false` で止まる。** 既定 on の唯一の boolean で、
既定を on にするのは**誰も有効にしない測定は存在しない測定**だからである。
**公開デプロイ([0066](0066-four-postures-one-word.md) §3)は記録しない** —
identity を読まないと決めたデプロイが、見知らぬ相手の打った文字列を別の
見知らぬ相手が読める場所に貯めるのは筋が通らない。**read-only では記録する**
(サーバー自身の観測であって呼び出し元が書いた内容ではない)。

## 5. インスタンスを一回で答える — `GET /api/v1/stats`

「何回引かれたか」はエントリの属性、**「答えられたか」はインスタンスの属性**
である。前者は per-entry の数で十分に測られていて、後者には器が無かった。

窓 `days`(既定 30)を取り、**「いまの姿」と「窓の中で起きたこと」**を
明示して返す。

| いまの姿(state) | 窓の中(flow) |
|---|---|
| `concepts.total` / `.status` / `.trust` / `.rejected` | `concepts.created` |
| `queues.drafts` / `queues.failed` / `queues.stale_after` | `review.verifications` |
| `misses.recording` | `outcomes.worked` / `.failed` / `misses.count` / `.queries` |

- **キューの述語はフィード自身のものを共有する。** 一致を**構造で**保証する
  のがこの面の負担である — **開いたら件数が違うキューは、件数が無いより
  悪い。** 同じキューを二回数えれば、食い違う機会が二つできる。
- **`status` と `trust` は語彙の全値を 0 込みで返す。**「無い」と「報告されて
  いない」を読み手が区別できるようにするためで、status を書いていない文書は
  OKF の既定として数える — 他のどの面もそう読ませているので、集計だけが別の
  読み方をしてはいけない。
- **`review.verifications` は台帳の行を数える。**「先週どれだけレビューが
  回ったか」に答えるのはこの数で、**キューの深さでは答えられない** — 深さは
  残量であって通過量ではない。
- **`misses.recording` が false のとき、`count` と `queries` は 0 ではなく
  無意味である。** 面はそれを 0 として描いてはならない(CLI は `-`)。
  `queries` は最大 10 件 — 人が「次に何を書くか」を決めるためのリストであり、
  一度に読んで動ける量を超えて返す意味がない。
- **ロールアップを持たない。** 専用の集計テーブルも日次バッチもスケジューラも
  足さず、すべてオンデマンドで計算する。**ロールアップはテーブルが既に
  持っている数の二つめの写しであり、写しは間違いうる。** 代償として、生イベント
  が刈られる前の期間には誰も答えられないので、窓は 180 日を上限とし、それを
  超える `days` は **400 で拒否する** — 一年を求めて半年ぶんが黙って返るなら、
  呼び出し元はそれを一年と読んでしまう。**足りない答えを黙って返すより、
  答えないほうがよい。**

### 5.1 `prefix` は、ミス以外のすべてを絞る

一つのデプロイを共有するチームが**自分のキューを数えて自分の知識を数え
られない**のは、分業ではなく欠落である。エントリに紐づく数はすべて絞られる。
outcome は台帳の id で絞る — concept を join すると、prefix を渡した瞬間に
削除済み concept への報告が黙って落ちるからである。

**`misses` は絞られない。絞れない。** ミスとは「ヒット 0 の検索」であり、
**0 件だったということは、それが属する id が無いということである。**
記録に残るのは打たれた文字列と時刻だけで、部分木に結びつける手がかりが
存在しない。これは仕方なく残した歪みではなく、**ミスがエントリの属性では
ない**という §4 の主張そのものである。

### 5.2 キューは、それを一覧する sort の名で呼ぶ

`failed` と `stale_after` は、それを一覧する `sort` の名である。この向きな
のは、**sort の名前が既にある語を使い回しており、キューの名前が発明語だった**
からである — `failed` は呼び出し元が報告する outcome の値であり、
`stale_after` は OKF SPEC §5 の frontmatter キーそのものである。

**`drafts` だけが自分の名前を持つ。** 単一の sort ではない
(`sort=usage` + `status=draft`)ので、名前を持たないものに sort の名を
着せることはできない。**規則が当てはまらない一件を、規則の形に合わせて
曲げない。**

`docs/surface.md` の VOCAB は、sort 名を着たキューを **1 と数える** —
`stats` が数える集合と `sort=` が並べる集合は同じ一つだから、キューは自分の
語を持たない。実装は `QueueCounts` の json キーのうち `domain.ListSorts` に
無いものだけを数えるので、**キューが sort でない名前をまた持ったら、その
瞬間に語として数に出る。**

## 6. 押すのは数であって、通知ではない

ochakai は LLM もスケジューラも持たず、secret を持たないので宛先・トークン・
SMTP・Webhook URL のいずれも置けない。したがって「人に届ける」機構を製品の
中に作る道は最初から閉じている。

閉じていない道が一つある。**すでに運用者が持っている通知経路に、ochakai が
乗せられる形の答えを一つ返すこと**である。`ochakai stats --exit-code` は
どれか一本でも空でない間 **2** で終了し、三本とも空なら 0 で終了する。
**2 なのは、1 が「コマンドが失敗した」だからである** —「サーバーに届か
なかった」が「やることは無い」と読まれてはならない。届けるのは運用者の
cron / CI で、ochakai は数を持つ。

`ochakai stats` の各行は**次に打つコマンドを持つ**。キーと数は第一・第二
フィールドのままなので、`cut -f2` も grep も効く。

## 7. やらないこと

- **自動 demote と status ゲート。** failed が閾値を超えても verified を
  自動で draft に落とさない。フィードは*浮上させる*だけで、直すか否かは人か
  エージェントの判断である。期限切れを自動で落とすことも、報告の多いものを
  自動で deprecated にすることもしない。
- **通常の検索順位に failed を混ぜること。** 期限切れも同じで、期限切れは
  「再確認が必要」であって「間違い」ではない。フィードで浮上させるだけである。
- **配送とスケジューラ。** メール・チャット・Webhook・宛先リスト・購読設定を
  持たない。サーバーは自分で目を覚まさない。
- **閾値と抑制。**「10 件を超えたら赤」「金曜は黙る」の類は入れない。空か
  空でないかは ochakai が正直に言える唯一の線で、そこから先の政策は運用者の
  cron 側にある。
- **時系列 API とダッシュボード。** 返すのは一つの窓のスナップショットだけで、
  系列が要るなら `stats` を cron で回して外に貯める。
- **`sort=gaps` というフィード。** フィードが返すのはナレッジであり、問いは
  ナレッジではない。
- **ミスの検索・エクスポート・per-actor の内訳。**「誰が何を探していたか」を
  引ける面は、キュレーションの道具ではなく監視の道具である。記録は actor を
  持つが、面はそれを返さない。
- **ミスからの自動生成・クエリのクラスタリング・言い換えの名寄せ。** どれも
  LLM を要求する。10 件の生の文字列を人が読むほうが速い。
