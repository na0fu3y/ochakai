# ochakai 設計ドキュメント 0128: 番号は領域の決定に与え、その内側の規則には与えない

Status: Accepted(2026-08-23)。[0048](0048-decision-records-for-wire-contracts.md)
§2.1 / §2.2 を改訂する — 番号の基準に、**観測できるか**に加えて**粒**を足す。
§2.4 の早見表に、一行が挙げてよい記録の数の天井を置く。既存の記録は
1 行も書き換えない。0048 §3 が「プロセスについての決定は、この規則を
変えるときにだけ書く」と置いた、その場合である。
Date: 2026-08-23

## 1. 問題: 0048 は領域を選んだが、粒を選ばなかった

0048 は「記録が、記録される対象より速く育っている」と数えて、番号を
利用者が観測できる変化に絞った。四週間後に同じ数え方をする。

| | 0048 のとき | 今 |
|---|---|---|
| 番号付き記録 | 47 本 / 7,994 行 | 121 本(うち Superseded 56)/ 10,633 行 |
| 本番 Go コード | 14,809 行 | 24,758 行 |
| 記録の着地 | 2 週間で 47 本 | 毎週 14〜19 本、四週間ずっと |

行数は墓石の規則([CONTRIBUTING](../../CONTRIBUTING.md) "What a superseded
record keeps")がコードの下に押さえている。**速さは変わっていない。**
2026-08-02 に 18 本を 6 本へ、15 本を 3 本へ畳んで 78 本 / 5,121 行まで
戻した corpus は、16 日で倍になった。畳む速さは書く速さに勝てない。

どこで育っているかは、0048 §2.4 が置いた早見表が示している。表は
「改訂の履歴を追わずに現在の姿にたどり着く」ための一行のはずだったが、
今日その一行は:

| 行 | 挙げている記録 |
|---|---|
| サーフェスの配分 | 10 本 |
| 認証と identity | 9 本 |
| 検索と埋め込み | 9 本 |
| REST の安定性契約 | 8 本 |

認証の一行は 0109 と、その §2 か §3 を一つずつ改訂する五本
(0120 / 0122 / 0123 / 0124 / 0127)を並べている。「最初の一行を置けるのは
管理者だけ」「`stats` は範囲を持つ呼び出し元にも答える」「prefix に
自分の管理者を置ける」— どれも利用者が観測でき、どれも 0048 §2.1 の
表の「identity と provenance の意味」に入る。**基準は満たされていて、
それが問題である。** 観測できるかは、どの領域が記録を要するかを選ぶ
基準であって、一つの領域を何本に切るかを選ぶ基準ではない。

`design-doc` skill の手順 7 は既に「同じ記録への二つ目の部分改訂は、
差分を足さず全体を書き直す」と言っている。skill に書かれ、何も検査
せず、0109 は五つ目の改訂を受けた。**検査されない手順は、0048 §1 が
記録について言ったのと同じ理由で、口頭の手順と同じである。**

## 2. 決定

### 2.1 番号は領域の決定に与える

記録が答える問いは「**なぜこの領域はこうなっているか**」である。
「この領域の規則の一つがどう働くか」— 誰が最初の行を書けるか、範囲を
持つ呼び出し元に数が何を含むか、prefix が自分の管理者を持てるか — は、
その決定の**内側の規則**であり、番号を取らない。置き場は PR の説明と
[CHANGELOG](../../CHANGELOG.md)、面が動くなら
[docs/surface.md](../surface.md) である。0048 §2.2 の「既存の決定の内側
での追加」を、型の綴りやエラー文言だけでなく、規則そのものにまで広げる。

判定は 0048 §2.2 の問いをそのまま使う: 三か月後に問い直す人は、**親の
記録と CHANGELOG を読めば答えに着くか。** 着くなら番号は要らない。
着かない — 親の文面がその規則と矛盾する — なら、それは改訂であり、
§2.2 へ進む。

### 2.2 改訂は、親が未リリースなら差し替え、リリース済みなら一本に畳む

親がまだリリースに乗っていなければ、0048 §2.3 のとおり親を書き替える。
番号は増えない。

親がリリース済みで文面と矛盾するときだけ、新しい番号を取る。ただし
その記録は**差分ではなく、領域の現在の姿を丸ごと述べる**: 親と、親に
積まれていた改訂のすべてを Superseded にして吸収する。一つの領域に
現行の記録は世代ごとに一本で、早見表の一行は原則一本を指す。

これは skill の手順 7 を規則にしたものである。書く側の費用は差分より
大きく、それは意図したものだ — 小さな改訂を書くのが高く、現在の姿を
読むのが安い向きに、費用を置き直している。2026-08-02 の畳み込みは
同じ費用を後から利子つきで払った。

### 2.3 早見表の一行が挙げてよい記録の数に天井を置く

[CONTRIBUTING](../../CONTRIBUTING.md) が `INDEX-ROW-RECORDS` を宣言し、
`cmd/ochakai/designdocs_test.go` が読み返す: 早見表のどの行も、それより
多くの記録を挙げない。**向きは下だけである** — 宣言は今日の最大
(10)から始まり、行を畳む PR がその都度下げ、目標の 3 に着いたら
止まる。上げる PR は、この記録を改訂する PR である。

3 は「親・その改訂・もう一つ」の幅で、§2.2 の「二つ目の改訂は畳む」と
同じ線を表の側から引いたものである。四本目を挙げようとする PR は、
代わりに畳む記録を書く。

### 2.4 今日の四行は、広い行から順に畳む

§2.3 の天井は宣言を今の最大に置くので、この記録が着地した日には何も
落ちない。畳むのは別の PR で、一行ずつ、広い順に — サーフェスの配分、
認証と identity、検索と埋め込み、REST の安定性契約。それぞれが §2.2 の
形の記録を一本書き、挙げていた記録を Superseded にし、宣言を下げる。
0048 §4 が「既存 47 本を今回まとめて整理する」を採らなかった理由は
ここでも同じで、畳む費用は畳むときに払う。

## 3. 本ドキュメント自身について

0048 §3 と同じく、§2.1 の基準ではこの記録は番号を要しない。番号を
取るのは、0048 が「書くとすれば、それはこの規則を変えるときである」と
置いた当の場合だからである。

## 4. 選ばなかった案

- **リリース済みの記録に、日付つきの節を追記できるようにする。** 採ら
  ない。元の文面と選択肢は残るので 0048 §4 の反対理由の半分は当たら
  ないが、残りの半分は当たる: 読者が開いた tag によって同じ番号が違う
  ことを言い、「設計ドキュメント NNNN」という引用が指す先が動く。
  不変性は引用のためにある。
- **基準を変えず、畳み込みを定期作業にする。** 採らない。2026-08-02 に
  やり、16 日で戻った(§1)。書く側の規則を変えずに読む側の掃除を
  続けるのは、蛇口を開けたまま床を拭くことである。
- **リリースの頻度を下げて、0048 §2.3 の「未リリースなら差し替え」の
  窓を広げる。** この記録は前提にしない。毎日のリリースのもとで §2.3 の
  窓は一日しか無く、それが改訂鎖の一因ではあるが、リリースの頻度は
  利用者に届く速さの決定であって、記録の都合で決めるものではない。
  頻度が変われば §2.3 は勝手に効きはじめ、この記録と両立する。
- **早見表の行を増やして一行あたりを減らす。** 採らない。行は領域で、
  領域を細かく切ることは §2.1 の粒の問題を表の側で再演することである。
  天井は行ではなく、行が挙げる記録に置く。

## 5. サーフェス(0015)

**該当なし。** REST / MCP / CLI / Web UI のいずれも変わらない。

## 6. 互換性

**破壊的変更は無い。** 既存の記録と、それへの引用は生きたまま残る。
変わるのは [CLAUDE.md](../../CLAUDE.md)、`design-doc` skill、
[CONTRIBUTING](../../CONTRIBUTING.md) の "Design docs"、index の冒頭、
そして `designdocs_test.go` が読む一行である。0048 §2.1 の表は
そのまま残り、この記録はその上に粒の基準を重ねる。
