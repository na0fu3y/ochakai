## 1. 一枚のページ、二つの配信経路

バンドルされた Web UI は**自己完結の `index.html` 一枚**である — ビルド
ステップなし、フレームワークなし、CDN なし。**ページは認証を知らない**。
自オリジンの相対パス(`/api/v1`)を叩くだけで、資格情報の付与は手前に立つ
プロキシの仕事である。この分離があるから、同じ一枚を二通りに配れる。

| | `ochakai ui`(クライアント) | `ochakai serve-ui`(サーバー) |
|---|---|---|
| 想定用途 | 個人利用。デプロイ不要 | チーム共有の常設 URL(Cloud Run) |
| トークンの出所 | 利用者の ADC / gcloud | サービスのメタデータサーバー |
| ヘッダ | `Authorization` | `X-Serverless-Authorization` |
| 記録される identity | `human:<本人>` | `process:<サービスの SA>`、IAP があれば本人(0065 §5) |
| 待受 | 127.0.0.1 のみ | `:$PORT`(保護は Cloud Run IAM / IAP) |

両者は同一バイナリ・同一コンテナイメージに同居する。デプロイは `serve` と
同じイメージに `--args=serve-ui` を渡すだけで、**UI とサーバーのバージョンは
常に一致する**。

サーバー同梱型(単一バイナリのサーバーが UI も配信する形)は採らない。
Cloud Run IAM の背後ではブラウザが ID トークンを付けられず、認証モデルと
衝突する。採ったのは「CLI が資格情報を貸してローカルに UI を立てる」形で、
`kubectl proxy` + Dashboard や `go tool pprof -http` と同型である。
**`ochakai serve` は UI を配信しない。**

### 1.1 `ochakai ui` は利用者のトークンで書けるプロキシである

だから三つを守る。

- **127.0.0.1 固定バインド**(可変なのはポートだけ)。LAN 共有の要件は
  `serve-ui` が担う。
- **Host ヘッダ検証** — loopback 名以外は 403。攻撃ページが自ドメインを
  127.0.0.1 に解決させて same-origin でプロキシを叩く DNS リバインディング
  への防御である。
- **ブラウザ由来の `Authorization` は転送前に必ず破棄**し、CLI が解決した
  トークンで置き換える(委譲ヘッダについても同じ規則が効く — 0065 §5)。

`/mcp` もプロキシするので、proxy プロセス無しで MCP クライアントを本人の
identity で繋げられる副効果がある。

### 1.2 コマンドを二つに分けるのは、危険な組み合わせを書けなくするため

一つのコマンドのフラグ(`ui --public` の類)にはしない。二つのモードは
バインド先・identity の出所・ヘッダ・ブラウザガードの要否が**すべて反転**
しており、共有されるのは静的ページとプロキシの骨組みだけである。分けると:

- `ui` は決して loopback 以外にバインドしない — **本人のトークンで書ける
  プロキシを LAN に晒す事故が、構造的に起きない。**
- `serve-ui` は決して個人の資格情報を使わない。

## 2. UI のスコープ

UI は `/api/v1` の薄いクライアントに留める — **UI にできることはすべて
エージェントにもできる。** サーバー側状態や LLM を要する機能は UI ではなく
エージェント側に属する。

**一ファイル・ビルド無しの構造は意図的な制約である** — 読める、フォーク
できる、リブランドできるために維持する。API の全機能を UI が追随する義務は
なく、キュレーションに要るかどうかで都度判断する
([0067](0067-four-faces-and-what-they-decline.md) §5.4 が載せないものを
数えている)。

## 3. 編集は正準 OKF 文書のテキスト編集である

詳細画面は投影で描き、**編集画面は文書をそのまま渡す。** `sources` と
`parameters` の行エディタ、型に応じた契約セクションの出し分けは持たない。

書き出しだけならフォームでも解ける(全値を JSON で書けば、JSON は YAML の
部分集合なのでクォート規則にも日付の誤読にもぶつからない)。**解けないのは
読み取り側である** — フォームに値を入れるにはサーバが正準化した本物の YAML を
パースする必要があり、ブラウザにその能力は無い。

残る道は二つあり、どちらも採らなかった。

**ブラウザに YAML の部分集合パーサを書く。** 文法は限定的だ — UI が読むのは
常に ochakai 自身の正準出力だから — が、「限定的な入力しか来ないはずの
パーサ」は想定外の値で壊れる典型であり、しかも壊れ方が**フォームが黙って値を
落とす**形になる。拡張キーを保存すると決めた直後に、ブラウザ側へ同じ失敗の
種を植えることになる。

**読み取り応答に封筒の構造を併走させる。** パーサは要らずフォームも動くが、
採らない理由はこちらのほうが重い — **キュレーション面が、形式と違う形を
教えてしまう。** ochakai の知識は OKF 文書であり、CLI も MCP もエクスポートも
Git のバンドルもその形で扱う。人が触る唯一の面だけが「フィールドの集まり」に
見えると、書き手はその面でしか通じない心象を持つ — 未知キーはどこへ行ったのか、
`# Computation` の fence は何なのかが説明できなくなる。**文書を見せることは、
機能の削減であると同時に形式を教えることでもある。**

### 3.1 失うものは、値引きではなく支払いである

**行エディタは実際に便利だった。** `sources` に一行足す、`parameters` の
`required` にチェックを入れる、といった操作は、YAML のインデントを人が
数えるより速くて安全である。

緩和は最小限に留める。編集画面は**保存前にパースを通し**(サーバは唯一の
判定者であり続けるが、往復が一回減る)、新規作成は**テンプレート文書**から
始める(空の textarea に `---` から書かせない)。詳細画面は投影と、文書から
切り出した本文で描く — 切り出しは終端の `---` で切るだけで、パースではない。
frontmatter は「Document」タブに生のまま置く。**引用や契約を読むための専用
タブは作らない** — それぞれが frontmatter の一部を別の形に描き直すもので
あり、形式を一つにするというこの節の理由づけと衝突する。

**戻す条件を書いておく。** 行エディタの需要が実運用で戻ってきたら、
読み取りの既定形を二重にするのではなく、**サーバ側に「文書 → 構造」の面を
足す**。そのほうが後戻りが小さい。条件が満たされたらこの記録を改訂する。

## 4. やらないこと

- **UI のための新しい認証機構。** ブラウザの per-user identity は IAP の
  領域である(0065 §5)。
- **`ochakai serve` から UI を配信すること**(§1)。
- **文書のシンタックスハイライト。** 依存を増やす。textarea と等幅フォントで
  足りる。
- **サーバ側の「文書 → 構造」面** — §3.1 の条件が満たされるまで作らない。
- **エクスポート形の編集。** 編集画面が渡すのは正準形(サーバ所有キーなし)
  である。`generated` や `verified` を人が書き換えられる欄にすることは、
  provenance を観測記録とする [0009](0009-provenance-portability.md) に
  正面から反する。
