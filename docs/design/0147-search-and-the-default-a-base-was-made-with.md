## 0. この記録が決めたこと

**何も名指さないデプロイの既定の埋め込みを、新しく作るベースに限って
`gemini-embedding-2`(`global`)にする。** 既にあるベースは
`gemini-embedding-001` を、動いているリージョンで使い続ける。

0080 は二つのことを言っていた。§1.2「埋め込むのはデプロイされたリージョン
である」と、§5「既定のモデルは変えない」。どちらも理由は正しく、どちらも
**既に動いているデプロイ**についての約束である — 保存済みのベクトルを別空間
の遺物にしない、テキストを誰も選んでいない場所へ出さない。その約束は
守ったまま、**これから作られるベースには、いま最良のものを既定で渡す**。
それを分けるのが §1.2 の「ベースが生まれたときを覚える」である。

`gemini-embedding-2` を既定にする理由は三つある。画像と PDF を検索に載せる
(§5。001 ではファイル名でしか見つからない)、入力窓が 001 の四倍で
([0089](0089-a-half-embedded-concept-says-so.md) の「半分しか埋め込まれて
いない concept」が減る)、そして Google が次に手を入れるのはこちらである。
代わりに**居場所が `global`(と `us`/`eu`)しか無い**(2026-09-25、
`ochakai-example` で asia-northeast1・us-central1・europe-west1 の
リージョン窓口がいずれも 404、`global` が 200)。既定を移すことは、新しい
ベースのテキストが `global` で処理されることを製品が選ぶことである。
本書はそれを隠さずに選ぶ(§1.2)。

幅は動かさない(§3)。二つの既定は同じ 768 で、どちらの既定で生まれた
ベースもベクトルのテーブルを作り直さない。

## 1. Google Cloud の上では、埋め込みが既定である

**この製品でいちばん効く機能が、いちばん奥に置いてあった。** 日本語の
字句検索は trigram 索引が二文字のパターンを引けないためスキャンで答える
ことになり、答えは「埋め込みを有効にすること」だった。そこへ至るには
API を有効にし、IAM ロールを付け、環境変数を置き、`reembed` を打つ必要が
あった。**中核の想定利用者(日本語で書かれた知識ベースを持つチーム)に
とって、既定の検索は最良の検索ではなかった。**

### 1.1 プロジェクトは、設定ではなく発見する

何も名指されていないとき、メタデータサーバに自分が**どのプロジェクトの
どのリージョンで**動いているかを訊き、その答えで埋め込みを有効にする。
Cloud SQL IAM 認証が短命トークンを取っているのと同じ出所であり、
**新しく持つものは何も無い**。メタデータサーバが無い環境 — 手元の開発機、
CI、Google Cloud の外 — は何も変わらない。ADC の資格情報からプロジェクトを
取る案は採らない: 手元の `gcloud auth application-default login` まで
拾って、開発機が黙って課金を始める。

### 1.2 テキストがどこへ行くかは、ベースが生まれたときに決まる

**どこで埋め込むかは、データ所在地の決定である。** 0080 はそれを製品の
定数から外し、デプロイのリージョンに置いた — 東京に立てれば東京で埋め込む。
既にあるベースについて、その約束は動かさない。

**ベースは自分が生まれたときを覚える。** 起動のたびに、`schema_migrations`
が空だったか — このプロセスがベースを無から作ったか — を一度だけ見て、
その答えを一行に書き残す(migration 0053、`base_birth`)。

| ベース | 何も名指さないときの埋め込み |
|---|---|
| 本書より前からある | `gemini-embedding-001`、**動いているリージョンで**(0080 のまま) |
| 本書以後に作られた | `gemini-embedding-2`、**`global` で** |

**見分けるのはベースであって、中身ではない。** 保存済みのベクトルの有無で
決める案は採らない。いま字句検索だけで動いている既存のデプロイ — 001 の
居ないリージョン(asia-northeast2)に立てたもの、`off` にしていたもの —
が、次の起動で黙って `global` へテキストを送り始める。それは 0080 §6 が
「意図した取引」と書いたものを、利用者の知らないうちに裏返すことである。
0053 が既存のベースに書くのは古い側の答えで、新しい側に書き換えるのは
全 migration が commit した後だけである。途中で落ちた起動は古い側に倒れる
— 何も変えない側である。

**新しいベースは `global` へ行くことを、製品が選ぶ。** 0080 は
「どの一つの綴りも、それを選ばなかったデプロイにとっては間違いである」と
書いて固定のリージョンを退けた。`global` はそれと同じ種類の選択であり、
本書はそれを承知で採る。違いは二つある。**選んでいるのはモデルであって
リージョンではない** — `gemini-embedding-2` は `global`/`us`/`eu` にしか
居らず、このモデルを既定にすることが場所を決めてしまう。そして**まだ誰の
テキストも出ていない** — 新しいベースを作る運用者は、それを作る前にこの
既定を読める。所在地を固定したい運用者には resource name がある
(`…/locations/asia-northeast1/…/models/gemini-embedding-001`)。それは
0080 と同じく「テキストはここへ行く」と書いてある綴りそのものである。

**export して別の DB に import し直したベースは、新しいベースである。**
ベースの生まれは DB の性質で、バンドルは運ばない(運べばバンドルが
デプロイの設定を持つことになる)。移し替えで所在地を保ちたいなら名指す。

古いベースのリージョンが読めなかったときは、**埋め込みを有効にしない**
(字句検索で動き、ログが resource name の書き方を名指す)。ここで既定に
落ちれば、落ちた先は必ず誰も選んでいない場所である。新しいベースは
リージョンを要らないので、この分岐に来ない。

### 1.3 使えるかどうかを決めるのは IAM であって、設定ではない

**ochakai は要求し、IAM が答える。** サービス ID に `roles/aiplatform.user`
が無ければ Vertex AI は答えず、そのデプロイに埋め込みは無い。
[0065](0065-identity-and-provenance.md) §1 の「認可を持たない」と同じ
考え方である。答えは**起動時に一度だけ、一語の埋め込みで**訊き、10 秒で
打ち切る。訊かずに走ると、権限の無いデプロイは書き込みのたびに失敗を記録し
続ける。

### 1.4 発見された既定は落ちてよい。名指しされた設定は落ちない

| 埋め込みの出所 | Vertex AI / pgvector が使えないとき |
|---|---|
| 発見(未設定・`on`) | 警告を一行出し、**字句検索だけで動く** |
| resource name(名指し) | **起動しない** |

名指しした利用者は意味的検索を頼んでおり、黙って劣化した検索を返されるより
なぜ無いのかを知りたい。発見された既定は頼まれたものではないので、知識を
配ることを止める理由にはならない。同じ区別が pgvector にも及ぶ。

## 2. 一つの変数が、このデプロイはどう埋め込むかを言う

`OCHAKAI_EMBEDDINGS` 一語で言う:

```
未設定・on   メタデータサーバが答えたプロジェクトで、ベースの生まれに
             応じた製品既定のモデルと場所で埋め込む(§1.1・§1.2)
off          埋め込まない。Vertex AI を一度も呼ばない
resource     そのプロジェクト・場所・モデルで埋め込む
             projects/<project>/locations/<location>/publishers/google/models/<model>
```

resource name は Vertex AI が呼び出し先の URL に書く綴りそのもので、
project・location・model を**一つの文字列で**運ぶ。モデルは場所に、場所は
プロジェクトに依存するので、三つを独立に置けることは自由ではなく、**合わ
ない三つ組を書ける余地**である。

**三つのどれでもない綴りは、起動エラーである。** `=true` も
`=my-project` も `=gemini-embedding-2` も起動を拒否し、三つの形を名指す。
既定に落とさない理由は外し方が二方向あることで — off のつもりで `false`
と書いたデプロイは頼んでいない課金を払い、モデルを名指したつもりで綴りを
外したデプロイは既定のモデルで埋め込み続ける。後者に気づくのはログでは
なく、順位が悪くなった検索のほうである。

**名指すことは、要求することである。** resource name を書いたデプロイは
§1.4 の「名指し」側に立つ。Terraform 側はモジュールの変数一つ
(`embedding_model`)で同じことを言う。

本書は変数を一つも足さない。**既存のベースを新しい既定に移す**のも、
新しいベースを**リージョンに留める**のも、この resource name で言える。

## 3. 幅はモデルのものであって、デプロイのものではない

**すべてのベクトルは、それが指すオブジェクトから再計算できる。** だから
ベクトルのテーブルは番号付き migration の外にあり、`reembed` が存在する。
保存されている列の幅がモデルの幅と違うとき、ochakai はベクトルのテーブルを
作り直し、ログの一行が `ochakai reembed` を名指す。**詰め直しは自動で
やらない** — 埋めることは利用者の口座から支払うことである。その間も答えは
返る。幅が同じでモデルだけ変わった場合、古い行は消さない(検索はモデルで
絞るので、新しいモデルのクエリからは見えないだけである)。

**幅は設定ではない。** モデルごとの定数としてコードにあり、
`gemini-embedding-001` も `gemini-embedding-2` も 768 である。Gemini の
埋め込みは Matryoshka 表現学習なので短い出力は長い出力の接頭辞であり、一つの
幅が両方に効く。**本書は幅を広げない。** 既定を移す今なら新しいベースに
限って費用なしに広げられるが、2 の幅を変えれば既に 2 を名指している
デプロイのテーブルが作り直されて空で戻る —
「既存のデプロイを困らせない」という本書の条件そのものに反する。それに
pgvector の `vector` 型は 2000 次元を超えると HNSW を張れない。広げて得る
ものは、測れる形でまだ誰も示していない。

### 3.1 知らないモデルは、起動エラーにする

**知らないモデルの幅は、推測である。** 外せば書き込みごとに幅違いで拒否
され、検索は字句だけになり、ログの外からは「埋め込みが効いていない」としか
見えない。エラーは知っているモデルを名指す。型は利用者が書いて ochakai が
往復させる値なので知らない綴りを拒む理由が無い
([0071](0071-the-recommended-type-vocabulary.md))が、モデルは ochakai が
呼び出し、その答えの幅で**列を作る**値である。代償は、新しい埋め込み
モデルに ochakai のリリースを待たずに移れないことで、待つのは表の一行である。

## 4. 検索は三本のリストを融合する

- **字句** — 問い合わせを断片に割り、`search_text` がそれをいくつ含むかで
  点を付ける。**ファイル名もこのハイスタックに入る**。埋め込みの無い
  デプロイにもそのまま効く。
- **concept のベクトル。**
- **ファイルのベクトル** — 書き込み時に埋め込み、検索では concept ごとに
  最良の一件を取って concept のヒットに写像する。

三本を RRF で融合する。本文でもファイルでも当たる concept は両方のリスト
から寄与を得て上がる。**変えない原則が二つある。**

1. **ファイルは独立して返らない。** 検索がヒットするのは所有する concept で
   あり、ファイルはその中のメタデータとして現れる。
2. **ochakai はファイルを解釈しない。** OCR もキャプションもパースもしない。
   **埋め込みは決定的なエンコーダであって解釈ではない**ので、この線は越えて
   いない。

## 5. ファイルが載るかはモデルが決め、既定のモデルはベースが決める

画像と PDF のベクトルを持てるかは埋め込みモデルによる。ファイル入力を取れる
モデル(`gemini-embedding-2` 系)ではバイト列を埋め込み、取れないモデルでは
静かにスキップして**ファイル名の字句一致だけで見つかる**。テキストファイルは
どのモデルでも本文を埋め込む。

0080 はここで「既定のモデルは変えない」と書いた。ベクトルはクエリと同じ
空間になければ比較できず、既定を切り替えれば既存デプロイの保存済み
ベクトルが全て遺物になるからである。**その理由は既存のベースについてだけ
正しい**。本書は §1.2 で既存のベースの既定を動かさず、新しいベースの既定を
2 にする。既存のベースを移すかは運用者が決め、移すときは resource name を
書いて `ochakai reembed` を打つ。

**既存ファイルのバックフィルはしない。** 埋め込みは書き込み時のみで、
詰め直したければ `reembed` がある。字句のファイル名検索は即座に全件に効く。

## 6. 何を差し出しているか

- **既定パスが Vertex AI に依存する。** [0003](0003-gcp-only.md) が守って
  いるのは secret-zero であって依存の数ではなく、Vertex AI の認証も ADC
  なので**持つ秘密は増えない**。
- **書き込みが支出になる。** 逃げ道は二つあり、どちらも明示的である —
  ロールを与えない、または `OCHAKAI_EMBEDDINGS=off`。
- **cold start が一回の Vertex AI 呼び出しぶん伸びる。**
- **新しいベースのテキストは `global` で処理される。** 何も名指さずに
  asia-northeast1 に立てた新しいデプロイの本文と検索クエリは、国内の窓口
  ではなく Google の `global` へ行く。取り返す道は名指しで、001 を
  自分のリージョンで使う(画像と PDF はファイル名でしか見つからなくなる)。
- **同じイメージの二つのデプロイが、生まれで違う既定を持つ。** ログの
  `semantic search enabled` の行が model と location を名指すので、どちら
  なのかは起動のたびに読める。
- **古いベースの、001 の居ないリージョンのデプロイは、意味的検索を失った
  ままである。** 0080 §6 の取引をそのまま受ける — 取り返す道は名指しで
  ある。

## 7. やらないこと

- **PDF のテキスト抽出・OCR**、**どのファイルが当たったかの帰属表示**、
  **ファイル本文の DB への複製**(§4)。
- **受け取る形式を埋め込みの都合で狭めること。** 書き込み側に許可リストは
  無い([0075](0075-the-bundle-is-the-address-space.md))。五形式が決めて
  いるのは**埋め込み呼び出しに値するのはどれか**だけである。
- **モデルごとの幅を設定可能にすること**、**未知のモデルを既定の幅で
  受け入れること**、**幅を 768 から広げること**(§3)。
- **リージョンとモデルの組み合わせの検証。** 居ない場所を指せば Vertex AI
  がそう答え、起動時の probe(§1.3)がそれを一度で受ける。
- **古いベースのリージョンが読めないときに、どこかで埋め込むこと**(§1.2)。
- **既存のベースを新しい既定へ自動で移すこと。** 移せば保存済みの
  ベクトルが全て遺物になり、テキストがこれまで行かなかった場所へ行く。
  どちらも運用者が名指して決めることである(§5)。
- **ベースの生まれをバンドルに載せること**(§1.2)。
- **リージョンや世代を言う変数を足すこと。** 言いたいデプロイには resource
  name があり、それは**場所とモデルを一度に運ぶ綴り**である(§2)。
- **モデル切り替え時の自動再インデックス**、および**次元変更後の自動
  reembed**(§3)。支払いは頼まれてから行う。
- **`references/` という慣習を ochakai が解釈すること**、**幅ごとに
  ベクトルのテーブルを残すこと**(purge の「消したものは消える」と両立
  しない)。
