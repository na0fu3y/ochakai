# ochakai 設計ドキュメント 0051: 答えられなかった問いを記録し、ループをインスタンスで測る

Status: Accepted(2026-07-29、同日改訂)。[0049](0049-queue-counts.md) §3.1 が
「#293 の instance metric は `queues` の応答に兄弟キーとして入るべき」
として空けた場所を埋める — キューの深さは 0049 と同じ問い合わせで
数え、本ドキュメントは足さない(§3.5)。**改訂(リリース前)**: その
結果 `GET /api/v1/queues` は同じキーへの二つ目の住所になったので、
面はこの 1 つになり、`prefix` がここに移った(§3.5、§3.7、0049 §3.1)。
[0029](0029-usage-recording-off-the-read-path.md) の best-effort バッファと
180 日の刈り取りを、エントリに紐づかない「検索ミス」に広げる(§3.2、§3.3)。
[0040](0040-read-only-mode.md) §2.2 の「read-only でも利用測定は記録する」は
維持し、[0042](0042-public-read-only.md) の公開デプロイにだけ例外を足す —
identity を読まないデプロイは、呼び出し元が打った文字列も残さない(§3.4)。
[0015](0015-surface-consistency.md) §3.1 の「MCP に載せないもの」に 1 件
足す(§4)。REST に 1 面(`GET /api/v1/stats`)、CLI に 1 コマンド
(`ochakai stats`)が増える。
Date: 2026-07-29

## 1. 問題: 測っているのはエントリだけで、しかも成功しか数えていない

ochakai の中核仮説は「エージェントが下書きし、人が検証する」ループで
あり(0001)、**そのループを回すための指標が測られていること**が前提に
ある。いま測られているのは per-entry の 5 つの数
(`search_hits` / `fetches` / `worked` / `failed` / `last_used_at`)と、
それを並べ替えた 3 つのフィードである。

ここには 2 つの穴がある。

### 1.1 インスタンス全体を答える面が無い

「検証済みの割合は増えているか」「先週いくつ検証されたか」「失敗報告は
減っているか」に答える面が、どのサーフェスにも無い。ループに必要なのは
**傾向**で、あるのは**カウンタ**である。しかも生イベントは 180 日で
刈られる(0029 §3.4)ので、集計しないまま過ぎた期間は後から再構成
できない。

[0049](0049-queue-counts.md) がこの穴の一部を先に埋めた —
`GET /api/v1/queues` が 3 本のキューの**長さ**を返す。だがキューの長さは
**残っている量**であって、**通った量**ではない。「先週 7 件検証された」は
どのキューの深さからも復元できず、「検証済みの割合が増えているか」も
同様である。0049 §4 自身が推移を対象外と書き、§3.1 でその置き場所だけを
空けてある。本ドキュメントはそこを埋める。

### 1.2 見つからなかった問いは捨てられている

`recordUsage` は `len(ids) == 0` で即座に戻る。つまり**ヒット 0 の検索は
何も残さない**。キュレーションされたナレッジベースにとって、
*誰かが求めて、無かったもの* は最も価値のある信号である —— 次に何を
書くべきかを教える唯一のリストであり、それだけが捨てられていた。
成功だけが数えられていたことになる。

この非対称は測定の設計に由来する。`knowledge_event` も
`knowledge_usage` も `knowledge_id` が主キーの一部であり、**当たらな
かった検索には紐づけるエントリが無い**。だから記録する場所が無かった。

## 2. 世界観: 「何回引かれたか」はエントリの属性、「答えられたか」はインスタンスの属性

エントリに属する事実(このエントリは 412 回ヒットした)と、インスタンスに
属する事実(先週 7 件検証された、11 件の問いに答えられなかった)は別種で
ある。前者は既に十分に測られていて、後者には器が無い。

本ドキュメントは器を 2 つ足す: **ミスという行**と、**インスタンスを 1 回で
答える面**。どちらも LLM を持ち込まず、スケジューラも足さない。

## 3. 決定

### 3.1 ミスとは「ヒット 0 の検索」である

記録する事実を一つに定義する: **検索がエントリを 1 件も返さなかったこと**。
クエリ文字列・呼び出し元・時刻を 1 行として `search_miss` に残す。

**スコア閾値は採らない。** 「ヒットは返ったが全部スコアが低い検索」も
ミスだ、という定義はもっともらしいが、ochakai のスコアは**検索モードに
依存して較正されていない** — レキシカルではフラグメント一致重み + boost、
ハイブリッドでは RRF(~0.02 スケール)であり、片方で意味のある床は
もう片方では無意味である(`Service.Context` の `MinScore` の説明が
既にそう書いている)。モードによって意味の変わる閾値を、後から解釈
できない履歴の中に焼き込むことはしない。**0 件はモードに依存しない。**

記録はサービス層の `Search` 1 か所で行う。`get_context` も同じ関数を
通るので、**どのサーフェスから来た問いも同じ 1 か所で数えられる**
(0015 の「REST が唯一の契約、他はそのクライアント」の帰結)。フィード
(`sort=`)は数えない — あれは問いではなく列挙である。

フィルタで絞った結果の 0 件も記録する。「聞いて、無かった」ことに
変わりはないからである。ただし**フィルタそのものは記録しない**ので、
`prefix` で自分のサブツリーに絞ったための 0 件と、ベース全体に無い
0 件は、この行の上では区別できない。区別が必要になるまで足さない。

### 3.2 書き込みは 0029 の形をそのまま使う

ミスの記録は**読み取りパスに触れない**。0029 の決定をそのまま適用する:
メモリにバッファし、5 秒ごとの同じフラッシュループが同じ `FlushUsage` で
書く。上限を超えたぶんは捨て、フラッシュの失敗はバッチごと失われ、
再試行キューは持たない。**利用統計と同じく、ミスは失われてよい** ——
失われてはいけないのはナレッジ本体である(0029 §3.1)。

`Close` のドレインも共通なので、シャットダウンの順序に関する 0029 §3.3 の
制約はそのまま効く。

### 3.3 クエリ文字列は誰のもので、いつまで残るか

**これは ochakai が初めて保存する「利用者が打った文字列」である。**
キュレーションされた成果物ではないので、扱いを明示する。

- **provenance は利用イベントと同じ。** 呼び出し元の actor をそのまま
  記録する。委譲(0027)が効いているデプロイでは、委譲されたエンド
  ユーザーが記録される。認可は無い(0002)ので、**読める者は全員読める** ——
  ミスの一覧はキュレーションの材料であって、監査ログではない。
- **保持は 180 日**。生イベントと同じ刈り取り(0029 §3.4)に相乗りする。
  ただし違いが一つある: 利用イベントは刈られても running total が残るが、
  **ミスには累計が無いので、刈られた期間は完全に消える**。集計面の窓を
  180 日で打ち切るのはこのためである(§3.5)。
- **保存するのは先頭 500 バイトまで**。それを超える文字列は問いでは
  なくペイロードであり、全部を持つ理由が無い。
- **クエリのグルーピングは打たれたそのままの文字列で行う。** case も
  空白も畳まない。畳めば「サーバーが理解している」ように読めるが、
  ochakai はこの文字列について何も理解していない — 答えを持って
  いなかったことだけを知っている。

### 3.4 記録しないデプロイがある

- **`OCHAKAI_RECORD_MISSES=false` で止まる。** ochakai の設定で唯一の
  既定 on の boolean なので、唯一「`false` 以外はすべて true」として
  読む。既定を on にするのは、**誰も有効にしない測定は存在しない測定**
  だからである。
- **公開デプロイ(0042)は記録しない。** `OCHAKAI_PUBLIC_READ_ONLY` が
  `OCHAKAI_READ_ONLY` を含意するのと同じ形で `RecordMisses=false` を
  含意し、同時に `true` を書いても戻らない。理由も同型である:
  **identity を読まないと決めたデプロイが、見知らぬ相手の打った文字列を、
  別の見知らぬ相手が読める場所に貯めるのは筋が通らない。**
- **read-only(0040)では記録する。** 0040 §2.2 が「利用測定はサーバー
  自身の観測であって呼び出し元が書いた内容ではない」としてテレメトリを
  凍結の外に置いた判断は、ミスにもそのまま当てはまる。参照専用インスタンスで
  「何が求められて無かったか」が分かることには意味がある。

### 3.5 集計面は `GET /api/v1/stats` 1 つ、キューの深さは 0049 から借りる

窓 `days`(既定 30)を取り、次を 1 回で返す。**「いまの姿」と「窓の中で
起きたこと」の 2 種類**が混ざるので、フィールドごとにどちらかを明記する。

| いまの姿(state) | 窓の中(flow) |
|---|---|
| `entries.total` / `entries.status` / `entries.trust` / `entries.rejected` | `entries.created` |
| `queues.drafts` / `queues.reported_wrong` / `queues.past_expiry` | `review.verifications` |
| — | `outcomes.worked` / `outcomes.failed` |
| `misses.recording` | `misses.count` / `misses.queries` |

- **`queues` は 0049 の応答をそのまま運ぶ。** 同じキー、同じ 3 つの数、
  同じ `Store.QueueCounts` の 1 クエリ。0049 §3.1 が「#293 の instance
  metric はこの応答に兄弟キーを足す形で入るべき」と書いて空けた場所は、
  ここで**キーの並びとして**満たされる。**同じキューを 2 回数えれば、
  食い違う機会が 2 つできる。**
- **そして面は 1 つになった(2026-07-29 改訂、リリース前)。** 当初の
  この節は面を 2 つ持つと決め、「URL まで 1 つにすべきだと後で決まった
  なら、`/stats` が `/queues` を吸収するのが自然な形になる — どちらの
  数もすでに同じ関数から出ている」と書いていた。そう決まった。
  `/queues` が `/stats` に対して持っていた能力は `prefix` だけで、
  それは面を保つ理由ではなく**パラメータを移す理由**だったからである
  (§3.7)。呼び出し頻度の違いは残るが、それは実装の性質であって契約の
  性質ではない — 安く聞きたい cron が打つのは `ochakai queues` であり、
  そのコマンドは 0049 §3.5 のとおり残っている。
- **`entries.status` と `entries.trust` は語彙の全値を 0 込みで返す。**
  「無い」と「報告されていない」を読み手が区別できるようにするためで、
  値は `domain.Statuses` / `domain.Trusts` から描く。status を書いていない
  文書は SPEC §5.4 の既定(`stable`)として数える —— 他のどの面もそう
  読ませているので、集計だけが別の読み方をしてはいけない。
- **`review.verifications` は台帳の行を数える**(0043 §3.2)。再検証は
  そのつど 1 行なので、「先週どれだけレビューが回ったか」に答えるのは
  この数である。**キューの深さでは答えられない** —— 深さは残量であって
  通過量ではない。draft→stable の遷移数でもない(検証と lifecycle は
  独立である)。
- **キューの述語はフィード自身のものを共有する。** `sort=failed` と
  `sort=stale_after` の WHERE を共有の SQL 断片(`unansweredFailure` /
  `pastExpiry`)に括り出し、0049 の `QueueCounts` もフィードもそこを読む。
  0049 §3.1 は「各値はフィードが返す件数と一致する」と約束しており、
  一致を**構造で**保証するのが本ドキュメントの側の負担である。
  **開いたら件数が違うキューは、件数が無いより悪い。**
- **`misses.recording` が false のとき、`count` と `queries` は 0 ではなく
  無意味である。** サーフェスはそれを 0 として描いてはならない
  (CLI は `-`、Web UI は `–`)。
- `misses.queries` は最大 10 件。人が「次に何を書くか」を決めるための
  リストであり、一度に読んで動ける量を超えて返す意味がない。

### 3.6 ロールアップを持たない

すべてオンデマンドで計算する。専用の集計テーブルも、日次バッチも、
スケジューラも足さない。

- キュレーションされたナレッジベースが到達する規模では、いずれも索引付き
  カラムの count か、エントリ全体の 1 スキャンで足りる。
- **ロールアップは、テーブルが既に持っている数の 2 つめの写しである** ——
  そして写しは間違いうる。0029 が「集計は 1 文で行う」を選んだのと
  同じ姿勢である。
- 代償は、**生イベントが刈られる前の期間には誰も答えられない**こと。
  だから窓は 180 日を上限とし、それを超える `days` は 400 で拒否する
  —— 1 年を求めて半年ぶんが黙って返るなら、呼び出し元はそれを 1 年と
  読んでしまう。**足りない答えを黙って返すより、答えないほうがよい。**

### 3.7 `prefix` で部分木に絞る — ミスだけは絞れない

`GET /api/v1/stats` は `prefix` を取る(0041 の segment 境界一致、
繰り返し可・OR)。当初この面は scope を取らず、「これはインスタンスの
姿であり、チームの姿ではない」と書いていた。それは `/queues` が
`prefix` を持っていたから成り立っていた分業で、面が 1 つになった以上
成り立たない — **1 つのデプロイを共有するチームが自分のキューを数えて
自分の知識を数えられないのは、分業ではなく欠落である。**

**エントリに紐づく数はすべて絞られる。** `entries.*`(何があるか)、
`queues.*`(何が待っているか)、`review.verifications`(誰が何を
確認したか)、`outcomes.*`(何が返ってきたか)。outcome は
`knowledge_event` の id で絞る — エントリを join すると、prefix を
渡した瞬間に削除済みエントリへの報告が黙って落ちる。§3.5 の
「報告は起きた事実として数える」が prefix の有無で変わってはならない。

**`misses` は絞られない。絞れない。** ミスとは「ヒット 0 の検索」で
あり(§3.1)、**0 件だったということは、それが属する id が無いという
ことである**。記録に残るのは打たれた文字列と時刻だけで、部分木に
結びつける手がかりが存在しない。したがって `prefix` を渡しても
`misses` はインスタンス全体の答えを返す。

これは仕方なく残した歪みではなく、**ミスがエントリの属性ではない**と
いう §2 の主張そのものである。「何回引かれたか」はエントリのもの、
「答えられたか」はインスタンスのもの — 部分木に切れるのは前者だけで
ある。呼び出し元がこの非対称を読み違えないように、openapi はこの 1 点
だけ太字で書く。

## 4. 各サーフェス(0015 §4)

- **REST = yes。** `GET /api/v1/stats`。唯一の契約であり、
  `api/openapi.yaml` に載る。統合テストがあるので、0035 の contract
  テストの対象にもなる。
- **CLI = yes。** `ochakai stats`。完全性のサーフェスであり、1 行 1 数値の
  タブ区切りなので、定期実行して diff する / 1 行だけ grep する、が素直に
  できる。ミスの行は `gap<TAB>件数<TAB>クエリ`。
  **`ochakai queues` を置き換えない** — あちらは各行に次に打つコマンドを
  持ち、`--exit-code` で CI を赤くする「nudge」であり(0049 §3.4)、
  こちらは全体像である。3 つのキューの数は両方に出るが、出し方が違う。
- **Web UI = yes。** Review 画面の上に 4 つのタイルと、「Asked for, not
  found」の折りたたみ。0049 が同じ画面に置いたキューの帯の隣に並ぶ —
  帯が「何が待っているか」を、タイルが「どう進んでいるか」を言う。
  ループの人間側が既に開いている画面に置く。
  ダッシュボードではない —— 今朝手を動かせることだけを出し、それ以上は
  出さない(0015 §2 の「BI ツールではない」)。ギャップをクリックすると
  その問いをもう一度検索する: 無いものを書く前に、あるものを見るため。
- **MCP = no。** ツール数は予算である(0015 §2)。「このナレッジベース
  には何が無いか」はエージェントにとって面白い問いだが、**エージェントは
  検索して 0 件を得た時点で既にそれを知っている** —— そしてその 0 件は、
  この決定によって記録される。見直す条件は、下書きの生成をギャップから
  駆動するエージェント(「答えの無い問いから書き始める」)が実際に
  現れたとき。

## 5. 壊れるもの

追加のみ、ただし 1 つだけ引き算がある(最後の行)。

- マイグレーション `0031_search_miss.sql`(新テーブル 1 つ)。既存の
  データには触れない。
- `GET /api/v1/stats` が増える。旧クライアントには影響しない。
- CLI に `stats` が増え、補完スクリプト 3 種とヘルプが増える。
- 環境変数 `OCHAKAI_RECORD_MISSES` が増える(既定 on)。
- **公開デプロイの挙動が変わる**: `OCHAKAI_PUBLIC_READ_ONLY` は
  ミスを記録しない。既に公開している運用者にとっては、記録が始まらない
  という形でしか観測されない。
- **`GET /api/v1/queues` は無くなる**(改訂前はここに「変わらない」と
  書いていた)。3 つの数はこの応答の `queues` キーに同じ問い合わせから
  入り、唯一できたことだった部分木への絞り込みは `prefix` として
  `stats` に移った(§3.5、§3.7、[0049](0049-queue-counts.md) §3.1)。
  **CLI の `ochakai queues` は残る** — `--prefix` も `--exit-code` も
  そのままで、読む先が `stats` になるだけである。REST を直接叩いて
  いるクライアントだけが 1 行書き換える。

## 6. やらないこと

- **時系列 API とダッシュボード。** 返すのは 1 つの窓のスナップショット
  だけで、日次の系列は返さない。系列が要るなら `stats` を cron で
  回して外に貯める —— それは ochakai の仕事ではない(0015 §3.4、
  ROADMAP の「チャートもダッシュボードも作らない」)。
- **スコアの低いヒットをミスとして数えること**(§3.1)。
- **ミスからのエントリ自動生成・クエリのクラスタリング・言い換えの
  名寄せ。** どれも LLM を要求する(0001)。10 件の生の文字列を人が
  読むほうが速い。
- **`sort=gaps` というフィード。** フィードが返すのはナレッジであり、
  問いはナレッジではない。同じ `hits` の形に無理に載せるより、
  `stats` の中の 10 件で足りる。
- **ミスの検索・エクスポート・per-actor の内訳。** 「誰が何を探して
  いたか」を引ける面は、キュレーションの道具ではなく監視の道具である。
  記録は actor を持つが、面はそれを返さない。
- **通知と配送。** #299 が求める「人を呼ぶ仕組み」は
  [0049](0049-queue-counts.md) が決めた — 数と終了コードを返し、押すのは
  運用者の cron である。本ドキュメントはそれを繰り返さないし、緩めない。
- **キューの深さをもう一度数えること。** 0049 の面と同じ数を別の
  クエリで出すことはしない(§3.5)。
