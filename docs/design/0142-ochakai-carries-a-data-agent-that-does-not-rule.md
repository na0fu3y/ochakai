# ochakai 設計ドキュメント 0142: ochakai は裁定しないデータエージェントを持つ

Status: Accepted(2026-09-23)。**全体アーキテクチャの現行ドキュメント。**
[0081](0081-what-ochakai-is-and-what-it-refuses-to-hold.md) を Superseded に
する。0081 の決定のうち動かないもの(一つのバイナリ、PostgreSQL だけ、配布、
却下の記憶)は §8 に再掲する。面の配分が動く部分は
[0143](0143-four-faces-and-an-agent-that-answers-behind-one.md) が持つ(§7)。
受理の前に確かめた三つは §10
Date: 2026-09-23

## 0. この記録が決めたこと

1. **ochakai はデータエージェントを持つ。** Web UI で問いを受け、
   ナレッジを読み、利用者本人の身元で SQL を走らせ、どの concept から
   来たかを添えて答える。**既定は off** で、運用者が一語で入れる(§5)。
2. **LLM は製品の中に入るが、裁定しない。** 答えと提案(draft、裁定用の
   一枚)を作るだけで、verify も却下も、裁定済みの concept の書き換えも
   しない。**配るナレッジが人の裁定でしか変わらないこと**は動かない(§3)。
3. **サーバーは SQL を実行しない。** ウェアハウスの資格情報を持たない
   ことは動かず、実行するのは常に利用者本人の身元である(§4)。
4. **エージェントの軌跡と、人がその答えに下した判定が、検証ループの
   入力になる**(§1)。これが、この製品がエージェントを持つ理由である。

## 1. なぜ持つのか

0081 は「LLM を持たないことが、人の検証への信頼の根拠である」と書いた。
**守っていたのは手段ではなく性質のほう**である — 配られるナレッジを
変えられるのは人の裁定だけで、誰が書いたかは台帳が言う。LLM を持たない
ことはその性質を構造で保証する一つの手段だった。この記録は手段を替え、
性質を残す。

替える理由は三つあり、どれも想像ではなく起きたことである。

- **流量が人を超えた。** 運用者が、入ってくるナレッジの量が裁定する
  人の手を超えたと言った(2026-09-23)。棚卸しの手順
  (`examples/claude-code/bundle/skills/ochakai-triage`、#867)は有効
  だったが、回せるのは Claude Code を持つ人だけで、Web UI で裁定する人の
  前には来ない。C4(No FDE)が、その人に手順を回させることを求める。
- **データエージェントとして使いたい人が現れた。** Claude Code も gcloud
  も持たない人が、ochakai に直接問いたいと言っている。
- **ループに足りない入力がある。** いま ochakai が見るのは検索(ミス)と、
  エージェントの自己申告の結果報告だけである。意味層を自動で育てる研究
  EvoOntology([arXiv:2609.15779](https://arxiv.org/abs/2609.15779))が
  診断の材料にしたのは**軌跡** — 何を読み、何を書き、どこで外したか —
  で、ループで最も効いた部品(親と候補の比較、外すと −11.2)は**正解の
  付いた検証セット**を前提にしていた。ochakai の比較(`questions.txt`)は
  正解を持たない。

自分のエージェントを持てば、三つが同時に手に入る。**人の判定の付いた
結果報告**(答えに付けた 👍 / 👎 と一言)、**正解の付いた問い**(人が
合っていると言った問いと、そのとき読まれた concept の組)、**根拠の付いた
下書き**(通った SQL と、それが返したものの形)。使われるほどナレッジが
育ち、育つほど答えが良くなる。

**答えはナレッジにしない。** 同じ研究で、過去の軌跡を丸ごと取り出して
前置する記憶(+6.3)は、型を持つ層(+20.0)に遠く及ばなかった。会話は
ループの入力であり、ナレッジになるのは、そこから人が裁定した concept
だけである。

## 2. ochakai とは

データエージェントに「メトリクスの定義」だけでなく「その値をどう見るか」
までを渡す **Context Provider** であり、**その上で問いに答えるデータ
エージェントを一つ持つ**。メトリクス定義、検証済みのクエリ、解釈の
ナレッジ、用語、テーブルカタログを一つのベースに集め、どのエージェントにも
同じ契約で配る — 自分のエージェントも、その契約の読み手の一人にすぎない。

**キュレーテッドなナレッジベースであってカタログではない。** コネクタで
自動収集しない(0081 §1 のまま)。エージェントがウェアハウスに触れるのは
利用者の問いに答えるときだけで、スキーマを刈り取って concept にする経路は
作らない — 空のベースを埋めるのは [0085](0085-the-empty-base-and-what-fills-it.md)
の `seed` のままである。

## 3. LLM が入る場所と、入らない場所

**入る場所は三つ。**

- **答える。** 読みは他のクライアントと同じ search → get で、特権的な
  近道を持たない。答えには、使った concept の id と、それが人に確認された
  ものかどうかを添える(`examples/claude-code/CLAUDE.md` がエージェントに
  求めている引用と同じ規則)。確認されていないものは、そう言う。
- **提案する。** 学んだことを draft として書く。記録は
  `process:<エージェント> via human:<問うた人>`
  ([0065](0065-identity-and-provenance.md) の代理の形)で、人の書いた
  ものと取り違えられない。
- **棚卸しを回す。** 手順は `type: Skill` の concept として
  ベースにあるものを読み、**human-reviewed のときだけ従う**。結果は裁定の
  一枚として、Web UI のレビューの前に置く。

**入らない場所。**

- **裁定。** verify・却下・deprecate をしない。裁定済みの concept を
  書き換えない(MCP に課している制限を、自分のエージェントにも同じく
  課す — 0143 §6)。`type: Skill` を
  書かない。
- **検索と読みの面。** REST と MCP の search・get は、エージェントを
  入れたデプロイでも一バイトも変わらない。順位に LLM を入れない — 順位は
  すべてのクライアントが同じものを受け取る契約で(C5・C6)、決定的で
  なければ比べられない。
- **👍 は検証ではない。** 答えへの判定は、その答えが使った concept への
  結果報告(`report_outcome`、人の名で、一言を添えて)になる。tier は
  動かさない。0067 §5.4(いまは 0143 §5.4)が Web UI に結果報告のボタンを置かなかった理由は
  「実行しない UI に置くと裏付けの無い報告になる」だった — エージェントを
  入れた UI は実行するので、その理由がここで外れる。

## 4. SQL を実行するのは誰か

**サーバーではない。** ochakai のサーバーはウェアハウスの資格情報を
持たず、ウェアハウスのクライアントも持たない。

- **共有の Web UI では、ブラウザが本人の身元で実行する。** ページは
  Google のサインインから**本人の短命なアクセストークン**を受け取り、
  BigQuery の API を直接呼ぶ。トークンはページのメモリにだけあり、
  サーバーには送らず、どこにも保存しない。要るのは OAuth のクライアント
  ID で、これは公開の識別子であって secret ではない(C2)。
- **手元の `ochakai ui` では、プロキシが本人として実行してよい。** あの
  プロキシは既に利用者自身の身元で API を呼んでいる(0065 §5)。実行する
  のは利用者のマシンの利用者であって、デプロイではない。
- **流れは一方向に閉じる。** LLM が走らせたい SQL をサーバーが返し、
  ページが実行し、結果をサーバーに返し、LLM が続きを考える。**結果は
  サーバーと、デプロイのリージョンのモデルを通る** — データエージェントで
  ある以上避けられず、運用者がエージェントを入れることは、それを選ぶ
  ことである。結果はナレッジにも会話の記録にも残さない(§6)。
- **止めるのはウェアハウスである。** 何を読めるかは本人の権限が、
  いくら走らせてよいかはページが付ける課金上限(`maximumBytesBilled`)が
  決める。ochakai は SQL を検閲しない — 検閲する側に立つと、資格情報を
  持たない理由(攻撃面を持たない)と同じ理由で、持たなくてよい責任を持つ。
- **始めは BigQuery だけ。** [0003](0003-gcp-only.md) の足場の上で、
  本人の Google の身元がそのまま通るのがそこだけだからである。

## 5. 既定と、デプロイが払うもの

- **既定は off。** 入れない運用者の ochakai は、今日の ochakai と
  一バイトも違わない。入れるのは一語で(モデルを名指す変数)、SQL の実行に
  もう一語(OAuth のクライアント ID)が要る。後者が無ければエージェントは
  読むだけで答え、SQL は書いて見せるだけになる。
- **モデルはデプロイのリージョンで走る。** 埋め込みと同じ規則
  ([0080](0080-search-and-how-a-deployment-embeds.md) §1.2)で、名指した
  モデルがそのリージョンに無ければ、黙って他所へ送らずに起動を止める(C8)。
- **呼ぶのは IAM で。** Cloud Run のサービスアカウントが Vertex AI を呼ぶ。
  API キーは読まない(C2)。
- **姿勢ごとに。** `public` と `sandbox` では入らない(匿名の呼び出しに
  運用者の課金を開かない)。`read-only` では答えるが書かない。
- **新しい Google Cloud への依存**は Vertex AI の生成モデルである。
  実行時の依存は PostgreSQL のままで、埋め込みと同じく、無ければその機能が
  無いだけでサーバーは動く。

## 6. 会話の記録

軌跡はループの入力なので残す。ただし**残すのは形であって中身ではない**。

- 残すもの: 問いの文、読んだ concept の id、書いた SQL の文、判定と一言、
  書いた draft の id。**SQL の結果は残さない。**
- 保持は利用イベントと同じ 180 日(0141 §3)。読めるのは問うた本人と
  管理者で、範囲を持つ呼び出し元には自分の範囲の分だけ(0109)。
- 人が 👍 を付けた問いと、そのとき読まれた concept の組は、比較に使う
  問いのセットの候補になる。候補が問いのセットに入るのは人が選んだとき
  だけである。
- **問いのセットはナレッジベースの外、同じ PostgreSQL に置き、export に
  載せない。** ベースの中に concept として置けないのは、置いた瞬間に二つが
  壊れるからである — 問いの文そのものが検索に当たって本物の concept より
  上に来ること、そして答えられなかった問いを集めた concept が在るだけで、
  その問いがミス([0141](0141-a-miss-is-read-off-the-words.md) §4)として
  数えられなくなること。外に置くなら、会話の記録や利用イベントと同じ
  **ループの測定**であって、C1 が「丸ごと出て丸ごと戻る」と約束している
  ナレッジではない — 利用イベントもミスも export に載らないのと同じ線で
  ある。

## 7. 面への影響

決めるのは向きまでで、形はそれぞれの面の記録が持つ。

- **REST** に対話の操作が一本入る — REST は唯一の契約で、Web UI はその
  クライアントである(0143 §1)。
- **Web UI** に問いの欄と答えの画面、👍 / 👎 が入る。0067 §1 の「BI
  ツールではない」は、チャートとダッシュボードを持たないという意味で残る。
- **MCP には載せない。** MCP の向こうはすでにエージェントで、エージェントに
  エージェントを渡すのはツールの予算の浪費である。
- **CLI** には、いまは載せない。CLI を使う人はたいてい自分のエージェントを
  持ち、能力は REST に残るので完全性は欠けない(0143 §5.3)。

0067 のうち、これと矛盾する文面(§1 の Web UI、§5.2 の「LLM を使う
機能」「SQL 実行」、§5.4 の「結果報告のボタン」「SQL 実行・チャット」)は、
面が動く最初の PR で、0143 が領域ごと置き換えた。**0130 は
置き換えない。** Web UI は REST の応答を描くだけで、LLM はページではなく
REST の後ろにいるので、0130 §2 の「UI にできることはすべてエージェントにも
できる」「LLM を要する機能は UI ではなくエージェント側に属する」はその
まま成り立つ — 画面の棚卸しも、REST を叩く誰にでもできる一本である。

## 8. 動かないもの

0081 が決めたことのうち、以下はそのまま引き継ぐ。

- **Go の単一バイナリ**で MCP と REST を同一ポートに出す。エージェントも
  同じバイナリの中にある — デプロイを二つにすると、自分で立てられること
  (C4)の代金が倍になる。
- **実行時の依存は PostgreSQL だけ。** Redis も別のベクトル DB も検索
  クラスタも持たない。会話の記録も同じ PostgreSQL に置く。
- **配布とサプライチェーン**(GHCR のマルチアーキイメージ、静的バイナリ、
  distroless、SBOM・SLSA provenance・keyless 署名、SHA 固定の Actions)。
- **却下の記憶** — 却下は削除で、理由は OKF §9 の `log.md` が運ぶ
  ([0135](0135-a-rejection-is-a-deletion.md))。エージェントは提案の前に
  それを読む。
- **コネクタによる自動収集をしない。**
- MCP のツール名は `動詞_対象`、何本で線を引くかは
  0143 §1・§5.1 と [0096](0096-a-listing-is-not-a-search-here-either.md)。

## 9. 退けた案

- **別のサービスにし、REST の上に載せる。** ochakai 本体は LLM も SQL も
  持たないまま、REST の最初の組み込み先になる案で、0081 の文面を最も
  保つ。退けたのはデプロイが二つになるからである — C4 の「自分で
  立てられる」を二度払わせ、軌跡と裁定のキューを別々の場所に置く。
- **サーバーがチームのサービスアカウントで SQL を実行する。** secret は
  要らないが、見える範囲がサービスアカウントの権限になり、本人の権限と
  行レベルの制御が失われる。
- **本人の同意を得て、サーバーがリフレッシュトークンを持つ。** 本人の
  権限で共有サービスにできるが、トークンの保管は secret であり C2 を崩す。
- **既存のエージェントと MCP の組み合わせを手順として出すだけにする。**
  作るものはほぼ無いが、軌跡も人の判定も ochakai に戻らず、§1 の三つが
  一つも手に入らない。
- **検索の順位付けに LLM を使う。** §3。
- **👍 を検証にする。** 答えが合っていたことは、その答えが読んだ concept
  が正しいことを意味しない。検証は concept を読んだ人の裁定である。

## 10. 受理の前に確かめたこと

1. **ブラウザから BigQuery を本人の身元で呼べる**(2026-09-23)。Google
   Identity Services のトークンクライアントで `bigquery.readonly` の
   スコープを受け、`jobs.query` をページから直接呼んで 200 と行が返った。
   `bigquery.readonly` で足りるので、ページが求めるのは読むだけの権限で
   ある。ページのポリシー([0094](0094-the-page-runs-under-a-policy.md))に
   Google のサインインと BigQuery の接続先を足すのは、SQL を載せる段の
   PR である。
2. **日本のリージョンで答えるモデルはある — ただし世代が一つ古い**
   (2026-09-23)。asia-northeast1 では `gemini-2.5-flash` が答え、
   `gemini-3.x` 系は `global` にしか無かった。§5 の規則はそのまま効く:
   モデル id だけを書いたデプロイは自分のリージョンで確かめ、無ければ
   起動を止める。新しい世代を使いたい運用者は `locations/global` を
   resource name で名指す — テキストがどこで処理されるかを、運用者自身が
   選んだことになる。埋め込みの `gemini-embedding-2` と同じ形である
   ([0080](0080-search-and-how-a-deployment-embeds.md) §1.2)。
3. **問いのセットの置き場所** — ベースの外に置き、export に載せない(§6)。
