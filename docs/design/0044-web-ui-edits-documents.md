# ochakai 設計ドキュメント 0044: Web UI は文書を編集する — フォーム糖衣の撤去

Status: Accepted(2026-07-28)。[0043](0043-document-first.md) §3.11 の
Web UI の項(「編集は文書エディタと、既知キーのフォーム糖衣の二本立て」)を
改訂する。[0036](0036-okf-schema-first.md) §3.15 の「行エディタで sources と
parameters を編集し、契約は type に応じて出し分ける」は対象消滅。
[0006](0006-web-ui-serving.md) の「Web UI はキュレーション面である」は維持
Date: 2026-07-28

## 1. 目的

0043 §3.11 は Web UI について「編集は文書エディタと、既知キーのフォーム糖衣の
二本立て。糖衣は文書の read-modify-write として実装し、未知キーを保存する」と
書いた。**書き出し側は解決したが、読み取り側の手当てが無い。**

書き出しは 0043 の実装(#252)で片付いた。フォームの値を YAML として書くとき、
全値を JSON で出せばよい — JSON は YAML の部分集合なので、独自のクォート規則も
日付との誤読も無く、コロンだらけの本文も安全に通る。

読み取りは同じ手が使えない。フォームに値を入れるには、サーバが正準化した
**本物の YAML をパースする**必要があり、ブラウザにその能力は無い。残る道は
3 つだった:

- **(a)** 単体読み取りの `summary` を厚くし、封筒の構造をワイヤに併走させる
- **(b)** JS に YAML 部分集合パーサを書く
- **(c)** フォーム糖衣をやめ、文書エディタ一本にする

## 2. 決定: (c) フォーム糖衣を撤去する

**Web UI の編集は、正準 OKF 文書のテキスト編集である。** 詳細画面は投影
(§3.5 の `summary`)で描き、編集画面は文書をそのまま渡す。`sources` と
`parameters` の行エディタ、type に応じた契約セクションの出し分けは撤去する。

### 2.1 (b) を採らない理由

手書きの YAML パーサを 1 つ抱えることになる。文法は限定的だ — UI が読むのは
常に ochakai 自身の正準出力だから — が、「限定的な入力しか来ないはずのパーサ」は
想定外の値で壊れる典型であり、壊れ方が**フォームが黙って値を落とす**形になる。
0043 §3.6 が「取り込み時に捨てたキーは後のリリースで取り返せない」として
拡張キーの保存を決めたばかりで、その舌の根も乾かぬうちにブラウザ側に同じ
失敗の種を植えることになる。

### 2.2 (a) を採らない理由

`summary` に封筒の構造を持たせれば パーサは要らず、フォームもそのまま動く。
0043 §3.1 の「索引は文書からの導出、矛盾したら文書が正」と同じ関係をワイヤに
写すだけなので、筋も通っている。

採らないのは、**キュレーション面が形式と違う形を教えてしまう**からである。
ochakai の知識は OKF 文書であり、CLI も MCP もエクスポートも Git のバンドルも
その形で扱う。人間が触る唯一の面だけが「フィールドの集まり」に見えると、
書き手はその面でしか通じない心象を持つ — 未知キーはどこへ行ったのか、
`# Computation` の fence は何なのか、が説明できなくなる。文書を見せることは
機能の削減であると同時に、**形式を教えること**でもある。

もう一つ、二重に運ぶ形はいずれ乖離する。0036 §2.3 が封筒フィールドを増やした
のは「4 サーフェスが同じ形を語れること」のためだったが、0043 はその答えを
「形は文書ひとつ」に置き換えた。厚い `summary` は、置き換えたはずの二重表現を
読み取り側に残す。

### 2.3 失うもの

**行エディタは実際に便利だった。** `sources` に 1 行足す、`parameters` の
`required` にチェックを入れる、といった操作は、YAML のインデントを人間が
数えるより速くて安全である。これを失うのは値引きではなく、支払いである。

緩和は最小限に留める:

- 編集画面は**保存前にパースを通す**。壊れた YAML は 400 を待たずにその場で
  言う(サーバは唯一の判定者であり続けるが、往復を 1 回減らす)。
- 新規作成は**テンプレート文書**から始める。空の textarea に `---` から
  書かせない。型ごとの雛形は推奨語彙(0038)の分だけ用意する。
- 詳細画面は投影(見出し・バッジ・タグ・リンク)と、文書から切り出した
  本文で描く。本文の切り出しは終端の `---` で切るだけで、パースではない。
  frontmatter そのものは「Document」タブに生のまま置く — 引用や契約を読む
  ための専用タブは、それぞれが frontmatter の一部を別の形に描き直すもので
  あり、**形式をひとつにするという本ドキュメントの理由づけと衝突する**。

行エディタの需要が実運用で戻ってきたら、そのときは (a) ではなく **(b) を
サーバ側で**やる — 「この文書を構造にして返す」面を足すほうが、読み取りの
既定形を二重にするより後戻りが小さい。この条件を満たしたら本ドキュメントを
改訂する。

## 3. 各サーフェス(0015 §4)

- **REST = 変更なし。** 本ドキュメントは既存の面の使い方の決定であって、
  面を足さない。
- **CLI = 変更なし。** `ochakai get` は最初から文書を出し `update` は文書を
  受ける。むしろ Web UI が CLI に揃う。
- **MCP = 変更なし。**
- **Web UI = 本ドキュメントの主題。** 詳細は投影、編集は文書。

## 4. やらないこと

- **文書のシンタックスハイライト。** 依存を増やす(0001 の軽さ)。textarea と
  等幅フォントで足りる。
- **サーバ側の「文書 → 構造」面。** §2.3 の条件が満たされるまで作らない。
- **エクスポート形の編集。** 編集画面が渡すのは正準形(サーバ所有キーなし)で
  ある。`generated` や `verified` を人間が書き換えられる欄にすることは、
  provenance を観測記録とする 0009 に正面から反する。
