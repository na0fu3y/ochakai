# ochakai 設計ドキュメント 0030: If-Match による楽観ロック(opt-in)

Status: Accepted(2026-07-26)
Date: 2026-07-26

## 1. 背景: 決定はランドしていたが、記録されていなかった

条件付き更新(ETag / If-Match)は 2026-07-21 の PR #108 でランドし、
[0015](0015-surface-consistency.md) §3.1 の MCP キュレーション保護は
その機構に依存している。しかしこの決定は設計ドキュメントに書かれない
ままコードだけがランドし、コメントは存在しない節(「0025 §11」)を
引いていた。本ドキュメントはその決定を事後に記録し、宙に浮いた参照の
宛先を与える。決定自体は変更しない。

## 2. 問題: read-modify-write が黙って上書きする

update は全置換である(0016)。したがって編集は必ず read-modify-write に
なる — エントリを読み、一部を書き換え、全体を書き戻す。

2 者がこれを重ねると、後から書いた側が前の変更を**黙って**消す。
ochakai は人間とエージェントが同じエントリを共同所有する前提
(0001)なので、この窓は理論上のものではない: 人が Web UI で本文を
直している最中にエージェントが `update_knowledge` を投げる、という形で
日常的に起きうる。

失われたのが「編集」だと分かる手段が無いのが問題である。リビジョン履歴には
両方の書き込みが残るが、**後の書き込みは前の内容を読んでいない**という事実は
どこにも記録されない。

## 3. 決定

**opt-in の楽観ロックを入れる。** 既定の挙動(last-write-wins)は変えない。

### 3.1 バージョンは `updated_at` そのもの

新しい版番号カラムは足さない。エントリの版は `updated_at` である。

- **ETag** = `updated_at` を RFC3339Nano で表し、引用符で囲んだもの。
  GET / PUT / verify のレスポンスヘッダに載る。
- **If-Match** = その値。PUT のリクエストヘッダで送ると、
  「読んだときのまま」でなければ書かない。

JSON 本文の `updated_at` フィールドと同じ値なので、ETag ヘッダを見ない
クライアントでも版を取り出せる。

### 3.2 精度の不変条件

これが実装上の要である。**メモリ上の `updated_at` は、DB に往復した値と
常に一致していなければならない。** PostgreSQL の `timestamptz` はマイクロ秒
精度なので、`time.Now()` のナノ秒はストア時に切り捨てられる。ナノ秒分解能の
クロック(Linux)では、書き込みが返した値と保存された値が食い違い、
クライアントの次の条件付き更新が必ず 412 になる。

したがってエンティティのタイムスタンプは `nowStored()`
(`time.Now().UTC().Truncate(time.Microsecond)`)からのみ設定する。

### 3.3 判定はトランザクションの中で行う

サービス層の事前チェックではなく、`Store.Update` の条件付き UPDATE
そのものが判定する — `WHERE ... AND updated_at = $ifMatch`。0 行更新は、
エントリが存在しないのか(`ErrNotFound`)版が違うのか(`ErrConflict`)を
判別してから返す。チェックと書き込みの間に窓は無い。

### 3.4 サーフェスごとの扱い

- **REST**: `If-Match` ヘッダ。不在または `*` は precondition 無し。
  不一致は **412 Precondition Failed** で、何も書かれない。値が
  RFC3339Nano でも `*` でもなければ 400。
- **CLI / apiclient**: REST の薄いクライアントとして If-Match を通す
  (0004)。
- **MCP**: エージェントに版を持ち回らせる通り道は作らない。ツールスキーマに
  版フィールドを足せば、エージェントは埋めるべき値を知らないまま何かを
  埋める。代わりに **MCP はこの機構を内部で使う** — 0015 §3.1 の
  キュレーション保護が、チェック時に読んだ版をそのまま If-Match として
  渡すことで、チェックと書き込みの間の TOCTOU 窓を構造的に閉じる。
- **Web UI**: 現時点では送らない(0015 §3.4 の意味での意図的な省略)。

### 3.5 なぜ opt-in か

必須にすると、単発の CLI 編集やスクリプトが常に 2 往復を強いられる。
ochakai の書き込み頻度でその税を全員に課す理由は無い。競合を気にする
クライアントだけが払えばよい。

## 4. 壊れるもの

- 何も壊れない。If-Match を送らないクライアントの挙動は従来どおりである。
- ただし **412 は新しいエラーである**: If-Match を送るクライアントは、
  読み直して編集をやり直し再試行する経路を持つ必要がある。
