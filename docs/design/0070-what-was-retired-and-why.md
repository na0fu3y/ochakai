## 0. この記録が決めたこと

**三つの記録が一つの絵であること。** issue
[#471](https://github.com/na0fu3y/ochakai/issues/471) が始めた統合の三回目
である。決定は一つも動かない。

三つは同じ形をしていた。0028 自身が「0012 と同じ形をしている」と書いて
おり、0018 の生き残った決定は 0028 の前提そのものである。**基準を一度書けば、
三つは基準の適用例として読める** — 分かれていた間、その基準はどこにも
書かれていなかった。

0018 は特にそうである。233 行のうち生きているのは**一文**で、残りは
compile_sql が存在した世界の話(`attrs.spec` の書き込み時検証、モデル解決、
派生エントリの規約)である。0028 がその世界ごと撤去したので、0018 の本文は
**撤去されたものの仕様書**として残っていた。

## 1. 基準: 技術判断ではなく、費用対効果の前提が覆る

三つとも、**設計が間違っていたから撤去したのではない**。0010 の CIMD による
最小 OAuth AS も、`internal/compiler` の決定的な SQL 生成も、設計としても
実装としても健全だった。覆ったのは前提のほうである。

撤去を正当化した観測は、三つで共通していた。

- **利用がない。** 想定した利用者が具体化しないまま時間が経った。
- **ドキュメントが自分で降格させていた。** README は compile_sql をツール表の
  外に置き「optional、埋め込みホストは外してよい」と書いていた。**使わない
  前提で説明が書かれているものを、コードだけが第一級で持ち続けている**状態
  だった。
- **保守面積と、その面が引き受け続ける債務。** コネクタは ~1,700 行、
  compiler は ~1,300 行と六つの面。どちらも利用ゼロのまま、セキュリティ
  レビューの主対象であり続けるか、外部仕様への追従を抱え続けるかだった。
- **ツールスキーマはエージェントのコンテキストである。** `compile_sql` は
  この製品で最大のスキーマを持っていた。**使わないツールの定義が、全リクエスト
  のコンテキストを食っていた**([0067](0067-four-faces-and-what-they-decline.md)
  §1)。

**撤去は保守であって失敗ではない。** 面がその場所に値しなくなったときに
降ろせることが、既定の答えを no に保てる条件である。

## 2. MCP OAuth コネクタ

claude.ai / ChatGPT のリモートコネクタ向けに置いた**公開の第二サービス**を
撤去した。[0065](0065-identity-and-provenance.md) §1 の「必要になったら」に
戻る。

撤去が買ったものは、面の数ではなく**姿勢の回復**である。コネクタは一つで
デプロイ全体の性質を四つ変えていた — 唯一の secret(Google OAuth client
secret)、唯一の `allUsers` サービス、唯一の Domain Restricted Sharing 例外、
そして公開 AS 固有の攻撃面(SSRF・token 総当たり・redirect 偽装)。撤去して
**デプロイ全体が secret-zero・全サービス非公開・組織ポリシー例外なしに
戻った**。

到達の需要そのものは消えていない。埋めたのは公開サービスではなく CLI の
`ochakai mcp-stdio` で、これは利用者の機械の中のプロセスであり listen する
ポートを持たない(0067 §3)。

**この撤去だけは起動拒否ガードを置いた。** 稼働中のコネクタは
`--allow-unauthenticated` で公開されており、撤去後のバイナリが
`OCHAKAI_CONNECTOR_PUBLIC_URL` を黙って無視すると、**公開のまま本体モードで
起動する** — 即座になりすまし可能な構成になる。正しい撤去手順はアップグレード
ではなくサービスごとの削除であり、その一点だけを起動時に強制した。他の二つに
ガードは要らない(消えるのは面とコマンドで、叩けば即座に分かる)。

## 3. 決定的な SQL コンパイルと、セマンティックモデルの専用機構

**セマンティックモデルは専用機構を持たない。** 専用テーブルも専用インポート
経路も持たず、**他のすべての知識と同じ**書き込み・検索・エクスポート・
リビジョン・provenance の下に置かれる通常の concept である。真実が二重に
なること、エクスポートに乗らないこと、リビジョンも provenance も付かない
ことが、専用機構の代金だった。

**そして決定的な SQL コンパイル自体も撤去した。**
`POST /api/v1/compile`・MCP の `compile_sql`・`ochakai compile`・Web UI の
Compile タブ・書き込み時のモデル検証・`internal/compiler` の一式。

**答えは `get_context` 側にある。** エージェントが必要とするのは検証済みの
クエリとその注意点であり、両方そこから来る。compile が答えるのは「誰も
聞いたことのないメトリクス × 粒度 × フィルタの組み合わせ」だけで、これは
実在するが、聞こえるほど広くはなかった。

サーバーに残る保証は provenance・リビジョン・検証ワークフローになる。
0067 §1 の役割分担(解釈と生成はクライアント、記録はサーバー)の線を、
**「決定的な生成」も含めてクライアント側に引き直した**ということである。

## 4. 撤去しても、利用者のナレッジは消さない

**`Semantic Model` と `Metric` の concept は一件も動かさない。** 型は
[0038](0038-type-vocabulary-realignment.md) §3.1 が推奨語彙から外したが、
**自由型として無傷**である — 型は閉じた集合ではなく、退役した綴りは書ける
まま残る。失われたのは書き込み時検証だけで、読まれない `attrs` が黙って
通るようになっただけである。メトリクスの定義は、コンパイルされなくても
散文の知識として意味がある。

**`compiled` の利用イベント行も消さない。** 集計側の絞り込みが消えるだけで、
行は残る — **履歴は履歴として残す**。再実装したくなったときに、過去の使用
実績が失われていない。

どちらも同じ一つの理由による: **利用者のナレッジであって、サーバーの都合で
消してよいものではない**([0009](0009-provenance-portability.md))。

## 5. 再実装の条件

三つとも設計は残っているので、戻すときは revert が出発点になる。戻す条件を
先に書いておく。

- **コネクタ** — claude.ai / ChatGPT の Web コネクタから組織ナレッジを引き
  たい利用者、または proxy なし直結が必須の MCP クライアント要件が具体化
  したとき。そのときも 0065 §1 の原則(到達 = 読み書き、認可なし、OAuth は
  到達制御と provenance のみ)は維持する。
- **compile** — 「聞かれたことのない組み合わせ」を SQL にする要求が、検証済み
  クエリの検索では足りないと確認できたとき。**その時点で外部仕様への追従を
  引き受ける用意があること**も条件である。戻すときもモデルは通常の concept
  のまま(専用インポート経路は作らない)。

## 6. やらないこと

- **段階的な deprecation 期間。** 消える面は叩けば即座に分かり、0.x に
  deprecation window は無い([compatibility.md](../compatibility.md))。
- **サーバー側の派生フック。** モデルの書き込み時に metrics / tables の
  concept を自動生成することはしない — 撤去した importer の同期ロジックが
  場所を変えて生き残るだけで、片方向導出の問題が戻ってくる。埋めるのは
  クライアントである。
- **YAML 専用の投入経路。** 汎用の書き込みで足りる。
- **撤去した面の互換シム。** 404 と usage エラーがその面の墓標である。
