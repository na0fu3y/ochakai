# ochakai 設計ドキュメント 0096: MCP でも、一覧は検索ではない

Status: Accepted(2026-08-10)。[0068](0068-how-a-face-is-added-and-removed.md)
§1・§2 を改訂する — 「能力が二つならコマンドも二つ」の適用先に MCP を
加え、§2 の「ワイヤは一本のままである」がこの面には及ばないことを決める。
0068 が決めた規則は一つも動かない。**破壊的変更**
([#539](https://github.com/na0fu3y/ochakai/issues/539) の束)。
Date: 2026-08-10

## 0. この記録が決めたこと

1. **`search_concepts` から `list_concepts` を割る。** MCP のツールは
   6 本から 7 本になる(§1)。**破壊的** — `search_concepts` は
   `sort` も `cursor` も受け取らなくなる(§4)。
2. **能力は一つも増えていない。** 割ったのは、一つのスキーマが自分の
   制約を言えなかったからである(§1)。
3. **`MCP-BYTES` を 12,000 から 13,500 に上げる。** 常駐 11,829 →
   13,433 バイト。**この面で天井が上がるのは初めてである**(§2)。
4. **`get_context` の毎回のヒントは残す**(§3)。

## 1. スキーマが言えなかった三つ

0068 §1 は「能力が二つならコマンドも二つ」と決め、§2 は同じ節で
**ワイヤは一本のままだ**と書いた。REST で一覧と順位が同じ操作なのは、
フィルタが完全に共通で応答の形も同じだからである。MCP はどちらに従うのか
が、書かれていなかった。

一本のままだった `search_concepts` のスキーマは、三つの規則を**散文でしか
言えなかった**:

| 規則 | JSON Schema で言えるか |
|---|---|
| `query` は `sort` が無いとき必須 | 言えない |
| `cursor` は一覧のときだけ、検索では 400 | 言えない |
| `limit` の既定と上限が 10/50 と 100/1000 の二通り | 言えない(説明文に両方書く) |

**散文の制約は、守られなかったときに初めて分かる。** 誤った組み合わせは
エージェントのターンを一つ使って初めてエラーになる。割ったあとは、
`sort` を `search_concepts` に送った時点で**スキーマ検証が落とす** —
ハンドラに届く前に、間違いの名前が付いた形で。

これは 0068 §1 の後半そのものである:「一本に押し込むと、消えるのは
コマンド数だけで、利用者が覚える規則は消えない — フラグのヘルプに移る
だけである」。MCP ではその「ヘルプ」がスキーマの説明文であり、それを
読むのは人ではなくモデルである。

そして **MCP は人の記憶ではなくワイヤに近い**、という反論のほうを退けた
のがこの記録である。近いのは費用の払い方だけで(§2)、**払っているのは
理解ではない** — スキーマは会話ごとに読み直され、読み違えは毎回起こる。
人は一度覚えれば覚えたままだが、モデルは毎回同じ散文を同じ確率で読み
違える。だから「一度覚えれば済む」という一覧側の言い分が、この面には
無い。

## 2. 代金は 1,604 バイトで、隠す場所が無い

フィルタ七つ(`types` / `statuses` / `trusts` / `rejected` / `tags` /
`source` / `prefixes`)は**両方のツールに要る**。一覧を型で絞れないなら
それは一覧ではない。だからスキーマは二重になる:

```
常駐バイト   11,829 → 13,433 (+1,604, +13.6%)
             search_concepts 2,987 → 2,083、list_concepts 2,508 が増える
```

[surface.md](../surface.md) の `MCP-BYTES` は、**この面で数えるのが本数
ではなくバイトである**ことを言うために在る。ならば上げるときも同じ場所で
言う: 12,000 → 13,500。

**それでも割ったのは、バイトが目的ではないからである。** この面の既定が
no であるのは、エージェントのコンテキストが有限だからであって、数字が
小さいことが良いからではない。1,604 バイト(約 400 トークン)は毎ターン
払われる — 対して、誤用が一回起きればターンが一つ消える。どちらが高いか
は使い方で変わり、**片方だけが測れる**。測れるほうを上げて、測れない
ほうを消した。

天井が上がった記録が残ること自体が、この判断の一部である。次に誰かが
「ツールを一本足したい」と言うとき、読むべきなのは 7 という数ではなく、
**7 本目が何と引き換えだったか**である。

## 3. `get_context` の毎回のヒントは残す

[#530](https://github.com/na0fu3y/ochakai/issues/530) はこれも外す候補に
挙げていた。外さない。

- **常駐ではない。** 応答ごとの約 340 バイトであって、ツール一覧のように
  会話中ずっと保持されるものではない。この記録が数えている費用と種類が
  違う。
- **[0069](0069-the-loop-and-what-measures-it.md) がここに置いた機構で
  ある。** instructions を落とすホストは実在し、そのとき書き戻しの習慣を
  運ぶのはこの一文だけになる。ループはこの製品の中心であり、その最後の
  辺を、測っていない節約のために外さない。

## 4. 破壊で、猶予は無い

`search_concepts` に `sort` や `cursor` を送っていた呼び出し元は**エラーに
なる**。[0088](0088-a-retired-name-answers-for-one-release.md) の一リリース
の窓は**名前**の改名に対する仕組みで、ここで変わったのは名前ではなく
引数である — 転送先で同じ引数が同じように拒まれる以上、運べるものが無い。

0.x の互換方針(minor で破壊可、最新のみサポート)のうちに払う、という
のが #539 の束の考え方であり、これはその一つ目である。

## 5. やらないこと

- **`get_concept` / `get_file` を割ること。** どちらも能力は一つである。
- **一覧に `query` を戻すこと。** それが割った当のものである。
- **`sort` を必須にすること。** `source` だけの逆引き(0037 §2.3)は
  フィードの名前を持たない一覧であり、必須にすると住所が消える。
  無いときだけハンドラがどちらかを求める。
- **ツールをもう一本足すこと**を、この記録が容易にすること。天井は
  上がったが、7 本目は**能力を一つも増やしていない**という条件で
  通っている。
