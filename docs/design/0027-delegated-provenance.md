# ochakai 設計ドキュメント 0027: 呼び出し元によるエンドユーザー identity の委譲

Status: Accepted(2026-07-25)
Date: 2026-07-25

## 1. 問題

ochakai を自社のデータ分析 LLM ウェブアプリに組み込む、という利用形態で
provenance が壊れる。アプリは自分のサービスアカウントで Cloud Run IAM を
通過するので、**そのアプリの利用者が何人いようと、書き込まれるナレッジの
`created_by` はすべて 1 つの SA に潰れる**。

これは新しい発見ではない。[0002](0002-authn-authz.md) §3 の表が sample webui
について「全利用者が集約される。per-user が必要になったら IAP 検証を将来検討」と
自認しており、§4 の「将来の選択肢」にも IAP JWT 検証が挙がっている。埋め込み
利用が現実になったことで、この既知の穴が主要ユースケース全体に広がった。

provenance が潰れると ochakai のコア価値が消える。「誰が書いたか・誰が
検証したかを記録し、参照側が provenance を見て信頼を判断する」——認可を
持たない代わりに記録で担保する、という 0002 の設計全体がこれに依存している。
書き手が全員 `agent:insightflow-sa` なら、判断材料は何も残らない。

## 2. 0009 との関係(先に片付ける)

[0009](0009-provenance-portability.md) は「ペイロードから provenance を
受け取る」案 A を**不採用**とし、provenance は認証から来る、と決定している。
委譲ヘッダはこの決定に触れるので、射程を明示的に切り直す。

区別すべきは 2 つの状況である。

- **0009 が拒否したもの**: バンドルが運ぶ自称 provenance。エクスポートされた
  ファイルに書かれた `created_by` には、それを裏づける認証が一切ない。
  インスタンスをまたいだ時点で、その名前は単なる文字列になる。
- **本ドキュメントが認めるもの**: 認証済みの呼び出し元が、自分の identity を
  証明したうえで、追加でエンドユーザーの identity を申告する。呼び出し元が
  誰かは Google が検証済みで、その呼び出し元が委譲を許されているかは設定で
  決まり、**そして呼び出し元の identity は記録から消えない**(§3)。

前者は「誰の主張かも分からない名前」、後者は「誰の主張かが分かる名前」で、
provenance の忠実性という観点では正反対の性質を持つ。0009 の決定は前者に
ついてのものであり、維持する。

## 3. 決定: 置き換えではなく合成

**委譲された identity は actor になり、呼び出し元は `via` として残る。**

```
created_by: human:tanaka@example.co.jp via agent:insightflow@proj.iam.gserviceaccount.com
```

`created_by` を `human:tanaka@example.co.jp` で単純に置き換えてはならない。
置き換えると、tanaka が gcloud で直接書いたエントリと、InsightFlow 経由で
書かれたエントリが**記録上まったく区別できなくなる**。区別できない委譲は
偽装と同義であり、provenance の忠実性を回復するはずの機構が、逆にそれを
破壊することになる。

合成で記録することには実務上の効果もある。参照側は「これは人間が自分の
資格情報で書いたのか、アプリ経由なのか」を見て信頼を判断できる。これは
0002 の「信頼は provenance を見て判断する」という原則の、そのままの延長で
ある。

## 4. これは認可ではない

作らないものを明示する。role もスコープもトークン発行/失効も作らない
(0002 §1)。

`OCHAKAI_DELEGATING_CALLERS` が決めるのは「**誰の identity 主張を記録するか**」
であって「誰が何をしてよいか」ではない。ochakai に到達できる呼び出し元は
今までどおり全部を読み書きできる。この設定を空にしても誰の権限も増減せず、
記録される名前が変わるだけである。

## 5. 仕様

### 5.1 ヘッダ

```
X-Ochakai-On-Behalf-Of: human:tanaka@example.co.jp
```

- 形式は `<kind>:<identity>`。kind は `human` か `agent`。
- **kind は推測しない。** 呼び出し元は人間を代理しているのか別のエージェントを
  代理しているのかを知っている。名前の見た目から推測すると、想定した形に
  ならない identity を静かに誤ラベルする。
- 空白を含む identity、320 バイト超、未知の kind は 400。

### 5.2 許可

`OCHAKAI_DELEGATING_CALLERS` にカンマ区切りで、委譲を許す呼び出し元の
identity(SA のメールアドレス)を列挙する。`*` は認証済みの全呼び出し元。
**既定は空、つまり委譲は無効。**

許可されていない呼び出し元がヘッダを送った場合は **403 を返す。無視しない。**
黙って呼び出し元自身として記録すると、アプリは「自分は利用者として書いて
いる」と信じたまま動き続け、数か月後に全エントリが SA 名義だったと気づく。
静かな降格は、明示的な失敗より常に高くつく。

### 5.3 記録範囲

| テーブル | 列 |
|---|---|
| `knowledge` | `created_by_via` / `verified_by_via` / `rejected_by_via` |
| `knowledge_revision` | `changed_by_via` |
| `knowledge_event` | **足さない** |

`knowledge_event` の actor は書き込み専用のテレメトリで、180 日で刈られ、
どのサーフェスも読み戻さない。読まれない値に `via` を添えても情報は増えない。

`via` は NOT NULL DEFAULT ''。委譲が無いことと空であることは同じ状態なので、
NULL を分ける意味がない。

## 6. 波及

- **sample webui の集約問題(0002 §3)も同じ機構で解ける。** webui が IAP の
  検証済み JWT からユーザーを取り出してこのヘッダに載せればよい。0002 §4 の
  「IAP JWT 検証」は、ochakai 側の新機構ではなく webui 側の実装として片づく。
- **`create_knowledge` でエージェントが `status: verified` を直接作れる**という
  別の懸念([0015](0015-surface-consistency.md) §3.1 の verified 保護でも
  塞がらない部分)は、これで記録により担保される。`via agent:...` が残るので、
  参照側は「人間の検証ではない」と判断できる。
- 表示は全サーフェスで `Actor.String()` に集約した。OKF フロントマター、
  CLI の provenance 行、リビジョン一覧のいずれにも `via` が出る。
  フロントマターの `created_by` はインポート時に読み戻されない
  (0005 §3.3 のサーバー所有キー)ので、表記の変更は往復に影響しない。

## 7. 検討して採らなかった案

- **actor 名に埋め込む**(`"tanaka@example.co.jp via insightflow"` を `name` に
  入れる)。列を増やさずに済むが、検索も集計もできなくなる。provenance は
  ochakai の商品であって、ログの飾りではない。
- **allowlist を持たず、全呼び出し元に委譲を許す。** 合成記録があるので偽装は
  可視であり、これでも 0002 の原則は機能する。それでも allowlist を入れたのは、
  数十行で済み、既定を「無効」にできるため。運用者が意図して有効化する形が、
  この種の機能の既定として妥当と判断した。
- **委譲された identity のドメイン検証。** `human:` の後ろを社内ドメインに
  限定する案。呼び出し元を信頼して委譲を許した以上、その先の値まで疑うのは
  一貫しない。必要になれば allowlist と同じ形で足せる。
