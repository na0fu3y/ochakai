# ochakai 設計ドキュメント 0097: 書き込みは、自分が何をしたかを本文で言う

Status: Accepted(2026-08-10)。[0074](0074-the-document-and-the-vocabulary-that-asks-it.md)
§5 を改訂する — `Ochakai-Plan` が運んでいた語を**応答本文にも**載せる。
0074 が決めたこと(dry run の意味、三つの語、ヘッダを二本に割らないこと、
plan が書き込み経路と同じ判断から出ること)は一つも動かない。
[0082](0082-what-the-freeze-holds-still.md) §2 の下での**追加**であって、
ヘッダの移設ではない(§2)。
Date: 2026-08-10

## 0. この記録が決めたこと

1. **concept の書き込みの応答に `plan` が乗る** — `created` /
   `updated` / `unchanged` の一語。REST(本文)と MCP(`knowledge.plan`)
   の両方(§1)。
2. **ヘッダは残る。** `Ochakai-Plan` と `Ochakai-Unchanged` は凍結の内側に
   あり、外すことは 1.0 まで available ではない(§2)。
3. **三語は `internal/domain` に移る。** そして移したとたん
   `VOCAB` が 46 → 49 になった(§3)。
4. **ファイルの書き込みには乗せない**(§4)。

## 1. ヘッダは、応答のうち誰も見ない部分である

改善計画の W5 はこう書いていた — 「ヘッダは curl や生成クライアントから
見えにくい」。実際にそうである:

```
$ curl -X PUT --data-binary @revenue.md .../api/v1/metrics/revenue.md
{"id":"metrics/revenue","document":"---\ntype: Metric\n…
```

**何が起きたのかは、この出力のどこにも無い。** 作られたのか、置き換え
られたのか、同じ内容だったので何も書かれなかったのか。`-i` を付けるか、
201 と 200 を見分けるか、`Ochakai-Unchanged` を知っているかのどれかが要る。
`jq` に通せばヘッダは消える。

そして **MCP にはヘッダが無い**。書き戻したエージェントは、いままで
「それで何か変わったのか」を知る手立てを持っていなかった — もう一度読む
以外に。ループの書き手側が、自分の書き込みの結果を読めない面である。

だから語は本文に乗る。**同じ語**である(§3)。

## 2. 移設ではなく追加である — 凍結がそう決めている

issue は「ヘッダから body へ**移設**」と書いていたが、その半分は取れない。
0082 §2 が凍結の対象をこう定めている:

> **住所** — 操作、`operationId`、パス、メディアタイプ、ステータスコード、
> **ヘッダ名**。

`Ochakai-Plan` と `Ochakai-Unchanged` を応答から外すのは、この住所を消す
ことである。0064 §11 が「凍結を破ってよい唯一の理由はセキュリティ上の
欠陥」と書いており、これはそれではない。

**足すほうは、そもそも凍結が止めているものではない**(0082)。`View` は
応答専用スキーマであり(リクエスト本文は markdown か bytes で、JSON は
415)、知らないキーはデコーダが無視する。

つまり結論は「二箇所が同じことを言う」である。0074 §5 は
**ヘッダを二本に割らない**ことを決めていた — 「重なることを言う二つの
ヘッダは、クライアントが片方しか読まない形である」。ここで増えるのは
二本目のヘッダではなく、**同じ答えの読める置き場所**であり、片方は
1.0 で消える側だと分かっている。それを書いておくのがこの記録の仕事で
ある。

## 3. 語は一つの家を持つ

`created` / `updated` / `unchanged` は、`internal/restapi` の非公開定数と
`internal/apiclient` の公開定数として**二箇所に書かれていた**。本文が
同じ語を言うようになる以上、三箇所目を作るのではなく `internal/domain`
に移す — 各面がそこから語彙を取る、という既にある形
([0038](0038-type-vocabulary-realignment.md) の `TypesGuide` と同じ)。

**移したとたん、[surface.md](../surface.md) の `VOCAB` が 46 → 49 に
なった。** これは新しい語ではない — `Ochakai-Plan` の enum は凍結された
契約に書いてあり、`ochakai import` は三語を印字していた。**数えられて
いなかっただけ**で、数えられていなかった理由は、その節が読む場所に値が
無かったことである。

`error.*` 12 語が [0083](0083-an-error-carries-a-code.md) で数に出たのと
同じ形である: 書き直せる文言でいるあいだは覚える語ではなく、
**クライアントが分岐する値になった瞬間に**そうなる。

## 4. やらないこと

- **ヘッダを外すこと**(§2)。1.0 の仕事である。
- **ファイルの書き込みに `plan` を乗せること。** 本当の書き込みは
  受け取ったバイト列を既にあるバイト列と比べない — つまり `unchanged`
  を言えない。二つの経路のうち片方にしか無いフィールドは、ヘッダより
  悪い。dry run のヘッダはそのままである。
- **`move` と `review` の応答に乗せること。** 移動も裁定も、
  created / updated / unchanged のどれでもない。三語の族に四語目を
  足すのは、族を壊すことである。
- **`Ochakai-Note` を本文に移すこと。** 同じ形の問題であり(MCP は既に
  本文で返している)、同じ答えになるはずだが、これは `plan` の決定では
  ない。別の記録で決める。
- **`plan` を読んで分岐することを CLI に求めること。** `ochakai` 自身の
  クライアントはヘッダを読み続ける — dry run で**ヘッダが無いこと**が
  「サーバが `dry_run` を知らずに書いた」の検出器であり
  (0074 §5 —「不在は『きれいだった』ではなく『書いてしまったかもしれない』
  を意味する」)、その検出器は本文では作れない。
