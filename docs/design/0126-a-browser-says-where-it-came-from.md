# ochakai 設計ドキュメント 0126: ブラウザは、どこから来たかを言う

Status: Accepted(2026-08-23)。[0072](0072-the-web-ui-serves-and-edits-documents.md)
§1.1・§1.2 の「ブラウザガードは `ochakai ui` 側の要件」を改訂する —
**クロスサイトの書き込みを断る規則は二つの配信経路の両方に掛かる**。
DNS リバインディング防御が `ui` 固有であることは変わらない(§4)。
[0094](0094-the-page-runs-under-a-policy.md) はページが何をできるかを
決め、これは**要求がどこから来たか**を決める。認証も identity も
provenance も動かない([0065](0065-identity-and-provenance.md))
Date: 2026-08-23

## 0. この記録が決めたこと

1. **安全でないメソッドのクロスサイト要求は 403 になる** —
   `ochakai ui` と `ochakai serve-ui` の両方で(§2)。
2. **ヘッダを一つも送らない呼び出し元は、今までどおり通る**。CLI、
   MCP を話すエージェント、curl は何も変わらない(§3)。
3. **`ochakai serve` には置かない**。理由は §5。

## 1. 二つの経路のうち、片方だけが断っていた

`ochakai ui` は書かれた日からクロスサイトの要求を断っている
(`Origin` が loopback でなければ 403)。`ochakai serve-ui` には**その
検査が無い**。

0072 §1.1 が `ui` の三つの防御を数え、§1.2 が「二つのモードは……
ブラウザガードの要否が**すべて反転**している」と書いている。前半は
正しく、**後半がここで外れた** — 反転しているのはバインド先と identity
の出所であって、「ブラウザから来た書き込みを信じてよいか」ではない。

そして `serve-ui` のほうが、条件が揃っている側である。

- **IAP を前置したデプロイでは、ブラウザが資格情報を持っている。**
  0065 §5 のとおり、ページを開いている人は IAP が認証しており、
  `serve-ui` はその署名付き assertion から書き込みの帰属を決める。
  他人のサイトのページがそのブラウザに書かせられるなら、**その人が
  頼んでいない書き込みが、その人の名前で台帳に載る**。
- **preflight は止めてくれない。** `readJSON` は `Content-Type` を
  見ない([0125](0125-a-body-names-each-field-once.md) が触ったのは
  中身であって、この検査ではない)。だから
  `enctype="text/plain"` のフォームで JSON をそのまま本文にできて、
  フォーム送信は "simple request" なので CORS の事前検査が起きない。
  CORS ヘッダを一つも返していないことは、**読みを防ぐだけで書きを
  防がない**。
- **届く先は四つある。** `POST /api/v1/review/{id}`(裁定)、
  `POST /api/v1/usage/{id}`、`POST /api/v1/move`、
  `POST /api/v1/reembed`。`PUT` と `DELETE` はフォームから出せないので
  この経路には乗らない。

**踏めることまでは確かめていない。** 成立するかどうかは IAP の
セッション cookie がクロスサイトの POST に付くかどうかで、それは
Google 側の属性であり ochakai からは動かせないし、確かめてもいない。
だからこの記録は「穴を塞ぐ」とは言わない。言うのは、**手元の経路で
断っていることを、デプロイする経路で断っていない**という非対称が
説明のつかないものだ、ということである。

## 2. 決定: 規則は両方の経路に掛かる

安全でないメソッド(GET・HEAD・OPTIONS 以外)の要求は、ブラウザが
別のサイトから来たと言っている場合、**プロキシが署名して転送する前に**
403 になる。`ui` と `serve-ui` は同じ一つの実装からこれを受け取る。

**読みは断らない。** GET は通る。断れば `serve-ui` の `/health` と
ページそのものが道連れになるし、読みを止めているのは CORS ヘッダを
一つも返していないこと(ブラウザ側)であって、ここではない。

## 3. 機構: 標準ライブラリの検査

Go 1.25 の `net/http.CrossOriginProtection` である。`Sec-Fetch-Site` を
読み、無ければ `Origin` のホストを `Host` と突き合わせる。

**ここで買っているのは、この検査が何を*しない*かである。**

- **どちらのヘッダも無い要求は通す。** ブラウザだけがこれらを送るので、
  CLI・エージェント・curl・生成クライアントは**一行も変わらない**。
  トークンも、隠しフィールドも、覚える綴りも増えない。
- **表面はどの次元も動かない。** エンドポイントもパラメータもヘッダも
  環境変数もフラグも語彙も、[surface.md](../surface.md) の九つの節の
  数はそのままである。契約(`api/openapi.yaml`)にも足さない — これは
  `/api/v1` を提供するサーバの規則ではなく、**その手前に立つ二つの
  UI コマンドの規則**だからである。
- **状態を持たない。** トークンを発行して照合する形の CSRF 対策とは
  違い、覚えるものが無い。secret-zero(0003・0065)に対して中立という
  より、**そもそも渡すものが無い**。

拒否は 403 の平文である。JSON のエラー本文
([0083](0083-an-error-carries-a-code.md))にしないのは、同じ層の既存の
拒否 — リバインディングの 403、静的資産の 405 — が平文だからであり、
**この 403 を読むのはページではない**からでもある。ページは自オリジン
からしか喋らないので、これを受け取ることがない。

## 4. リバインディング防御は残る

`ochakai ui` の `Host` 検査は畳まない。**クロスオリジンの検査が原理的に
見えない攻撃がそれだからである**: attacker.example を 127.0.0.1 に解決
させたページは、自分のドメインの `Origin` を送り、自分のドメインの
`Host` に届く。二つは一致し、`Sec-Fetch-Site` は same-origin と言う。
**検査は通る。** 通らないのは `Host` が loopback 名でないことのほうで、
だから `ui` ではその検査が先に走る。

0072 §1.1 の三つのうち、この記録が触るのは二番目の説明だけである —
`Host` 検査は「DNS リバインディングへの防御」であって、クロスサイト
一般への防御ではなかった。

## 5. `ochakai serve` には置かない

**ブラウザが資格情報を持って ochakai に届く経路は、二つの UI コマンド
だけである。**

- Cloud Run IAM の後ろ(既定)では、ブラウザは Bearer トークンを持って
  いないので届かない。
- 自分で検証するデプロイ([0086](0086-a-second-way-to-say-who-is-calling.md)・
  [0121](0121-each-path-reads-its-own-header.md))が読むのは
  `Authorization` であり、**ブラウザが勝手に付ける資格情報ではない**。
  他人のサイトのページはそれを付けられない。
- `dev` は手元、`public` は read-only、`sandbox`
  ([0087](0087-a-sandbox-says-it-is-one.md))は匿名で誰でも書ける —
  借りられる identity が無い。

つまり `serve` に同じ検査を置いても、**発火しうる構成が今日は一つも
無い**。発火しない検査を足さないのは 0035 §3.1 が linter について書いた
規則と同じ理由による。この判断が変わる条件は書ける: `serve` の前に
ブラウザのセッションを持つ何か(IAP を含む)を直接置く構成を
ochakai 自身が案内したときである。

## 6. 畳んだもの

`ochakai ui` の `Origin` 判定と `isLoopbackOrigin` は消える。手で書いた
比較であり、標準の検査はそれを**より広く**行う — `Sec-Fetch-Site` も
読み、`Origin` を「何らかの loopback 名か」ではなく「いま届いている
`Host` そのものか」で見る。

そこに一つだけ、今日より厳しくなる組み合わせがある:
`Host: 127.0.0.1:8098` に `Origin: http://localhost:8098` は、今まで
通り、これからは 403 になる。**ブラウザはこの対を作らない** — ページを
配ったホストにしか要求を出さない — ので、失われるのは誰も到達できない
寛容さである。
