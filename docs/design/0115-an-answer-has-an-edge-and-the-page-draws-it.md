# ochakai 設計ドキュメント 0115: 答えには縁があり、ページはそれを描く

Status: Accepted(2026-08-18)。
[0067](0067-four-faces-and-what-they-decline.md) §1 の「上限・enum・既定値は
サーバー側に一元化する」を、それを守っていなかった一つの面 — Web UI の
検索 — に当てる。0067 の決定は一つも動かず、§5.4 が Web UI に載せないと
決めたものも一つも載らない。[0050](0050-listings-page-rankings-do-not.md)
§2.2 の「検索はページングしない」と
[0110](0110-the-first-column-is-the-key-you-asked-for.md) の「較正できない
数は読み手に見せない」を前提にしている。
Date: 2026-08-18

## 0. この記録が決めたこと

1. **Web UI の検索は `limit` を名乗らない**(§2)。答えの大きさは
   サーバーの決定であり、ページはそれを数えるだけである。
2. **縁を描く**(§2.2)。読み手が明示に「もっと見る」と言った一回だけ
   契約の最大(50)を訊き、**サーバーの答えが終わった位置に線を引く**。
3. **畳み込みは「誰も見ない」を意味しない**(§3)。弱い一致として畳んだ
   ヒットのうち、エージェントにも届く件数を要約が言う。
4. **エージェント用のモードは作らない**(§5)。既定が正しければモードは
   要らない。

## 1. 同じ問いに、二つの答えが返っていた

[最初のひと月](../guides/onboarding.md) §3 は、このプロダクトが「飛ばすな」
と書いている唯一の手順である —— 書いたものを、それに当たるはずの問いで
撃ち、呼ばれることを確かめる。そこに書いてある確かめ方は CLI である:

```sh
ochakai search "$q" --limit 3
```

そして「**ここで返るものが、エージェントが見るものである**」と続く。
それは正しい。`ochakai search` は既定で 10 件を返し、`search_concepts` も
`GET /api/v1/search` も同じ 10 件を返す — 一箇所
(`internal/service/search.go` の `checkedLimit(limit, 10, 50)`)が
四つの面ぜんぶの答えを決めているからである。

**Web UI だけが違った。** ページは `limit=50` を送り、返ってきた 50 件から
スコアが 0.15 未満のものを `<details>` に畳んで表示していた。つまり
キュレーターは、**誰も受け取らない答え**を見ながら「エージェントは
見つけられるか」を判断していた。

代金は二方向にあり、どちらも静かである。

- **14 番目に出た concept を「見つかる」と読む。** 画面には出ている。
  エージェントには渡らない。書き手はそこで手を止める。
- **畳まれた concept を「誰も見ない」と読む。** 畳んだのはページであって
  サーバーではない。エージェントは同じ順で受け取っている。

どちらも「失敗が成功と同じ顔をしている」
([0114](0114-a-degraded-ranking-says-so.md) §1、
[0089](0089-a-half-embedded-concept-says-so.md) §1)の同じ形である。ここで
違うのは、退化したのが検索ではなく**検索の見え方**だったことだけである。

C7(人間の改善ループが測れる)がこの記録の条件である。ループの人間側は
「答えの無かった問い」を読み、答えになる concept を書き、**もう一度訊いて
確かめる**(`review.js` の gap 行がクリックで検索窓に戻すのはそのため
である)。その最後の一歩が別の答えを返していたなら、測っているのは
ループではない。

## 2. 決定

### 2.1 検索は limit を名乗らない

クエリのある検索は `limit` を送らない。返ってきた件数が、そのまま
**エージェントが受け取る答え**である。

一覧(フィードと着地画面)は従来どおり 100 件ずつ読み、カーソルで歩く
(0050 §2.1)—— そこはページの大きさであって答えの大きさではない。

### 2.2 縁は、数えて描く

「もっと見る(最大 50 件)」は明示の一回で、そのとき初めてページは数を
綴る。50 は**契約の最大**であり、既定ではない — 壁は読み手がぶつかるもの
なので、ページが知っていてよい。

線を引く位置は、直前の既定の応答が**何件だったか**である。ページは
10 を知らないまま、10 番目に線を引く。これが 0067 §1 の要求そのもので
ある: 二つの実装が同じ既定を持てば、いつか必ず片方だけが直る。

線が言うのは順位ではなく**終わり**である。順位は行の並びが既に持っている
—— 0110 §5 が CLI で順位の列を断ったのはそれが理由だった。並びが持って
いないのは「どこで終わるか」だけで、それがこの線である。

## 3. 畳み込みは「誰も見ない」ではない

弱い一致の畳み込み(スコア 0.15 未満、レキシカルのときだけ)は残る。
ノイズが一致として描かれるのを止める価値は変わらない。

変わるのは要約の一行で、畳んだもののうち**エージェントの答えの中に
あった件数**を言う。畳むこと自体は表示の判断だが、「これは誰も見ない」と
読ませるのは事実でない。

## 4. 面

- **REST** — 変更なし。既定 10・最大 50 は `api/openapi.yaml` の
  `limit` が前から宣言している。
- **MCP** — 変更なし。`search_concepts` の既定は同じ一箇所から出ている。
- **CLI** — 変更なし。`ochakai search` は既に既定を送っており、
  **この記録は CLI が最初から正しかったことの記録でもある**。
- **Web UI** — 上の 2.1〜3。人の curation に要るのは「エージェントが
  受け取るもの」であって、検索窓の下に並べられるだけ並べたものではない。

`docs/surface.md` の九つの数はどれも動かない。エンドポイントもパラメータも
コマンドもフラグも語彙も増えていない — Web UI は自分のアドレス空間を
持たない面だからである(「数えていないもの」)。

## 5. 採らなかった案

**50 件のまま、10 番目に線を引く。** 縁は見えるようになるが、**既定の
見え方は「誰も受け取らない答え」のまま**であり、しかも線を引くために
ページが 10 を綴ることになる(0067 §1)。既定を直せば線は縁の確認に
なり、既定を直さなければ線は言い訳になる。

**「エージェントの見え方」モード(トグル)。** 一つの画面が二つの姿勢を
持つことになり、[0062](0062-a-listing-is-not-a-search.md) が
`ochakai search` について書いたのと同じ形の分岐が生まれる。そして
**既定が正しければモードは要らない** — 要るのは逆向き(縁の外を見る)
だけで、それが「もっと見る」である。

**順位の重みを調整する・二つの順位を並べて比べる。** 0067 §5.4 が
Web UI に載せないと決めているもの(BI ツールではない)で、そもそも
較正できない数を読み手のつまみにする話である
([0080](0080-search-and-how-a-deployment-embeds.md) §3、0110 §2)。

**別の利用者の権限で見えるものを再現する。** ページは認証を知らない
([0006](0006-web-ui-serving.md))ので、他人の scope を騙ることになる。
[0109](0109-a-directory-has-readers-and-writers.md) の付与は
サーバーが呼び出し元を見て効かせるものであって、ページが選ぶものではない。

**何もしない。** これが既定の答えだった。覆したのは、この差が
**プロダクト自身が「飛ばすな」と書いた手順**(§1)に乗っていたからで
ある。

## 6. 見直す条件

サーバーの既定が「一つの数」でなくなったとき — 例えば答えの大きさが
クエリによって変わるようになったとき — ページの数え方は変わらないが、
線の文言(「上位 N 件」)は変わる。ページが数えているのは
**その一回の答えの大きさ**なので、機構としてはそのまま動く。
