# ochakai 設計ドキュメント 0139: ochakai は綴りを選ばない

Status: Accepted(2026-09-05)。**OKF の瞬間を ochakai がどう綴るかの現行
ドキュメント。**
[0133](0133-an-okf-moment-is-an-instant.md) を Superseded にする — 入りの
決定(二つの綴りを取る)はそのまま引き継ぎ、**出口の決定を裏返す**。
0133 が古くした [0069](0069-the-loop-and-what-measures-it.md) §2.2 と
[0074](0074-the-document-and-the-vocabulary-that-asks-it.md) §4.1 の
扱いも引き継ぐ(§7)。凍結された契約の一行を動かす口は
[0102](0102-one-history-in-one-spelling.md) §3 である(§5)
Date: 2026-09-05

## 1. 問題: 版が動かないまま、規格の側が動いた

0133 は 2026-08-28 に、`stale_after`・`sources[].last_modified`・
`usage_window` について**二つの綴りを取る**と決めた。RFC 3339 の datetime
と、`YYYY-MM-DD` の日付である。**その決定は正しく、いまも正しい。**

裏返すのは出口のほうである。0133 §3.1 は「戻すときは来た綴りで戻す。
ただし UTC の真夜中は日付として戻る」と書いた。**畳んだ先の綴りを、
規格が timestamp として定義しなくなった。**

### 1.1 v0.2 は公開後に normative を変え、版番号を動かさなかった

- **2026-07-24 に公開された v0.2** の §5.5 は `stale_after` を
  「An absolute date (`YYYY-MM-DD`)」と定義し、比較を `today >= stale_after`
  と書いていた。`sources[].last_modified` も `usage_window` も日付だった。
- **2026-08-21**(`open-knowledge-format` の `0b87c52`、`knowledge-catalog`
  の #323 と同じ変更)、§5 の冒頭は
  「Every timestamp-valued key in OKF is an ISO 8601 datetime with an
  explicit UTC offset」になった。見出しは**両方とも今も「Version 0.2」**
  である。
- SPEC §12 は minor を「後方互換な追加」、major を「破壊的変更」と定める。
  **この変更はどちらでもない** — 妥当だった値が妥当でなくなった。

**だから 0133 §1 の事実認識には誤りが一つある。** あの記録は、日付だけを
受けていた古いコードを「SPEC がそう言っていると書いてあったが、SPEC は
そう言っていない」と読んだ。そう言っていなかったのは**書かれた時点の**
SPEC であって、古いコードが書かれた時点の SPEC は**まさにそう言っていた**。
あれは誤読ではなく、七日前まで規格そのものだった。0133 の**決定**は
この訂正で弱らない — 二つの状態の「v0.2」で書かれたバンドルを両方読める
規則は、二つの綴りを取ることだけである。

### 1.2 代金は出口に移り、そこで実測できる

`FormatInstant` は UTC の真夜中を日付に畳んで書いていた。**規格自身の
worked example の四つの瞬間は、全部が UTC の真夜中である** — Appendix A を
ochakai に通すと、四つとも規格が定義しない綴りで返ってきた:

| 文書が書いた値 | 0133 の ochakai が返す値 |
|---|---|
| `stale_after: 2026-12-31T00:00:00Z` | `2026-12-31` |
| `sources[].last_modified: 2026-04-02T00:00:00Z` | `2026-04-02` |
| `usage_window: {from: 2026-06-01T00:00:00Z, …}` | `2026-06-01` |

0133 §1 は「SPEC 自身の worked example が読めないこと」を代金と呼んだ。
**読めるようにした先で、同じ例を書き換えて返していた。**

**受け手は黙って落とす。** OKF の参照エージェントの `is_stale()` は
`"T" not in raw` で `False` を返す — docstring が
「it is ignored rather than guessed at」と明言している。**これは仮定では
なく、出荷しているバンドルの話だった**:
`examples/demo/queries/sales/revenue-by-traffic-source.md` の
`stale_after` は `2026-08-01` で、ochakai の期限切れフィードは正しく上げ、
OKF 適合の消費者は同じファイルを「期限切れでない」と読んだ。

0133 §2 が「この製品が名指しで断ってきた形」と呼んだ**黙って値を落とす**
が、読む面から出口の面へ移っただけで残っていた。

## 2. 誰の綴りか、を先に決める

0133 の出口の規則は「来た綴りで戻す」だった。**それが守ろうとしたものは
正しい** — 書いた人の綴りを書き換えないことである。壊れていたのは実装で
あって、意図ではない: 真夜中を畳むのは「来た綴りで戻す」ではなく、
**来た綴りを捨てて ochakai が選び直す**ことだった。

そこで、値ごとに**ochakai の手元に何が残っているか**で分ける。

- **文書のバイト列**は書いた人のもので、読まずに保つ
  ([0043](0043-document-first.md) §3.1)。
- **`fm.` の索引**は文書が何と言っているかであり、文書と一致していなければ
  索引ではない([0047](0047-fm-carries-okf-keys.md)・
  0074 §4.1)。
- **`stale_after` の列**だけは瞬間で持っている(0133 §3.2、マイグレーション
  0046)。**テキストはもう手元に無い。** ここでは ochakai が綴りを選ぶ
  ほかなく、選べるのは一つしかない。

## 3. 決定

### 3.1 入りは変えない

`stale_after`・`sources[].last_modified`・`usage_window` の `from`/`to` は
**RFC 3339 の datetime**か **`YYYY-MM-DD` の日付**を取る。日付は**それが
開く UTC の真夜中**である。offset の無い datetime は取らない。0133 §3.1 の
前半をそのまま引き継ぐ。

**理由は 0133 の時より強い。** SPEC §11 は消費者に「バンドルを拒むな」と
言い、いま**二つの normative な状態の v0.2 で書かれたバンドルが世に
ある**。日付を読める規則は、その両方を読める唯一の規則である。

### 3.2 ochakai は綴りを選ばない。選ぶ一つは RFC 3339 で綴る

**手元にテキストがあるなら、そのテキストを返す。** YAML は引用符の無い
日付・日時を `time.Time` に解決してしまい、それはもうどちらの綴りで来たかを
言わない。だから frontmatter を読む経路は**decode の前にタイムスタンプの
ノードを文字列に retag する**(`okf.frontmatterMap` → `keepTimestampText`)。
この手当ては 0075 §3.1 の claim の経路と
[0130](0130-the-web-ui-and-the-fields-of-a-document.md) のフィールド編集の
経路には既にあり、**残りの二つ — 本体の parse と `fm.` の索引 — に無かった**。

**手元に瞬間しか無い一つ、`stale_after` の列は RFC 3339 で綴る**
(`domain.FormatInstant`)。真夜中を畳まない。畳んだ先は SPEC §5 が
timestamp として定義しない綴りだからである。

**文書は動かない。** 日付を書いた人は、自分の文書の中でも
`fm.stale_after` の照合でも、その日付を読み続ける。動くのは
**ochakai が自分の言葉で答える封筒**だけである。

### 3.3 自分のバンドルは規格の綴りで書く

`examples/demo`・`examples/bigquery-catalog`・`docs/architecture.md` の
worked example にあった 10 の日付を RFC 3339 にする。**値は一つも動かない**
— 日付は開く真夜中だったので、`2026-08-01` は `2026-08-01T00:00:00Z` で
ある。ochakai が**書き手として**出す文書は、規格が定めた綴りで書く。

### 3.4 他人の文書は正規化しない

インポートされた文書が日付を持っていれば、export はその日付を返す。
**ochakai は他人の文書を洗わない** — バイト列が持ち主のものであることが
C1 であり、規格は既に一度、版を動かさずに normative を変えている。洗う
決定をすれば、次に動いたときも洗い直すことになる。

**残る代金を正直に書く**: 日付で書かれた文書を取り込んだベースを export
すると、その三つの鍵は厳格な消費者に読まれない。直す口は書き手の側に
ある(`POST /api/v1/frontmatter`、0130)。

## 4. 面

**数はどれも動かない。新しい名前を一つも発明していない。**

| 面 | 現れ方 |
|---|---|
| REST | `Summary.stale_after` が常に RFC 3339 で返る。**操作もパラメータもヘッダも符号も増えない** |
| CLI | `ochakai list stale_after` の列と `ochakai get` の表示が RFC 3339 になる。フラグは動かない |
| MCP | `put_concept` のスキーマは**変わらない** — 入りの規則は動いていない |
| Web UI | フォームは文書の綴りを見せるまま(0130 の経路は元から retag していた)。`<input type="date">` が読めない値は text box に落ちる |

## 5. 凍結との関係

`stale_after` は bundle の往復に載るので
[0107](0107-the-freeze-holds-the-okf-core.md) のコアの中にある。口は
**0102 §3 の三つ目 — 規格が綴りを定めているものの、二つ目の綴りを畳む**
であり、三条件を全部満たす:

1. **SPEC が綴りを定めている**: §5「an ISO 8601 datetime with an explicit
   UTC offset」。
2. **ochakai の面に二つ目の綴りがある**: 同じ瞬間を `2026-12-31` とも綴る。
3. **畳むのは ochakai 側の綴り**: 落ちるのは日付、残るのは規格の側である。

0102 §3 の歯止め — **畳めるのは表現であって住所ではない** — にも当たる。
`2026-12-31` を読んでいたクライアントが受け取るのは 404 ではなく、
**同じ瞬間の別の形**である。

**向きは 0133 と逆で、そこは正直に書く。** 0133 の動きは広がる側だけ
だった。こちらは、日付だけを読むパーサを持つクライアントが読めなくなる。
それを引き受ける理由は、**畳まなければ ochakai が規格の外の値を出し続け、
適合する受け手には黙って落とされる**ことである。落ちるほうが黙っている。

## 6. 検査する不変条件([0035](0035-verifiability.md))

- SPEC Appendix A の四つの瞬間が、**書かれたとおりの綴りで**返ること
  (`TestSpecAppendixASurvivesTheRoundTrip`)。
- 二つの綴りがどちらも入り、どちらも RFC 3339 で出ること
  (`TestFormatInstantSpellsEveryMomentTheWaySpec5Does`)。
- **`fm.` の索引が、文書の書いた綴りを持つこと** — 日付も、真夜中の
  datetime も(`TestFrontmatterIndexesTheSpellingTheDocumentWrote`)。
- offset の無い datetime が、`soon` と同じように落ちること。
- 同じ日の一時間前と一時間後に期限を宣言した二件のうち、前者だけが
  フィードに載ること(0133 から引き継ぐ)。

## 7. 0069 と 0074 を Superseded にしないのは、0133 と同じ理由

[0128](0128-a-number-is-for-an-area-not-a-rule-inside-it.md) §2.1 の判定は
0133 §6 が書いたとおりで、この記録でも変わらない。0069 §2.2 が決めた
「今日は UTC であって、セッションの TimeZone に従わせない」も、0074 §4.1 が
決めた「列を持つ鍵は列が答え、`fm.` は別の問いだ」も、**決定は動かない**。
§3.2 は 0074 §4.1 の対比を**むしろ鮮明にする** — 列の答えと `fm.` の答えが
綴りまで別々になり、どちらが何の問いかが値を見て分かる。

## 8. 採らなかった案

- **何もしない。** 出荷しているバンドルが適合する受け手に黙って落とされ、
  それを実測してある以上、記録の無い放置は選択肢ではない。
- **日付を拒む。** SPEC §11 が消費者に禁じている。二つの状態の v0.2 が
  世にある以上、実害も大きい。
- **綴りをテキスト列で持つ。** 0133 §8 が断ったものを、まだ断る — 同じ鍵に
  ついて「何と書いてあるか」と「いつ切れるか」が別の列に分かれ、0043 §3.1 の
  「列は文書から導かれた索引である」が導出でなくなる。**文書のバイト列が
  既にその答えを持っている**ので、二つ目の置き場は要らない。
- **export で他人の文書を正規化する。** §3.4。
- **`sources[].last_modified` と `usage_window` も封筒で RFC 3339 に
  揃える。** 揃って見えるが、この二つは**テキストで持っている** — 揃える
  ことは、手元にある持ち主の綴りを捨てて選び直すことであり、§2 が引いた
  線の逆側に出る。ochakai が綴りを選ぶのは、選ぶほかない一つだけでよい。
