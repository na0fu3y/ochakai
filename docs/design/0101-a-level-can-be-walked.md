# ochakai 設計ドキュメント 0101: 一覧は歩ける — 凍結はそれを止めていなかった

Status: Accepted(2026-08-15)。
[0082](0082-what-the-freeze-holds-still.md) §2 を改訂する — **任意のクエリ
パラメータの追加**は、応答専用スキーマへの追加と同じく、そもそも凍結が
止めているものではない(§5)。
[0075](0075-the-bundle-is-the-address-space.md) §4.2 を改訂する — 一階層
1000 件の打ち切りは、JSON では注記ではなく `cursor` になる(§2。markdown
の注記はそのまま)。
[0068](0068-how-a-face-is-added-and-removed.md) §2.1 は改訂しない —
その規則を、届いていなかった一箇所に当てる。
Date: 2026-08-15

## 0. この記録が決めたこと

1. **`index.md` を JSON で読む一覧は `cursor` を持つ。** ページの大きさは
   今日と同じ 1000 件のままで、変わるのは**壁の先へ行けること**である(§2)。
2. **cursor は二つの位置とディレクトリを運ぶ**(§3)。
3. **markdown の `index.md` は歩かない**(§4)。
4. **任意のクエリパラメータの追加は凍結の外である**(§5)。指紋は 2 行
   増え、`truncated` は残る(§6)。

## 1. 一覧だけが、壁で終わっていた

[0068](0068-how-a-face-is-added-and-removed.md) §2.1 は一覧について
こう決めている。

> **`cursor` は不透明である。**……**総件数は返さない。** `cursor` の不在が
> 「ここで終わり」であり……保証するのは歩き切ることではなく、**上限で
> 静かに止まらないこと**である。

`GET /api/v1/search` の一覧モードはそのとおりに動く。**バンドルの一覧だけが
別の操作なので、この規則が一度も届いていなかった** — `internal/store/browse.go`
は `ORDER BY id LIMIT 1001` で切り、`truncated: true` を立てて終わる。

**静かではない。** 打ち切ったことは言う。だが**先へ行く綴りが無い**ので、
1000 件を超えるディレクトリは一覧から歩けない。回避は prefix を細かく
切るか、アーカイブを取るかで、どちらも「このディレクトリに何があるか」
という問いへの答えではない。0068 §2.1 の言う保証の、後半だけが無かった。

## 2. 決定: JSON の一覧は cursor を持つ

`index.md` を `Accept: application/json` で読むと `BundleListing.cursor` が
付き、次のページはそれを `?cursor=` で返す。無ければそこで終わりである。

**ページの大きさは動かさない。** `MaxBrowseEntries` は 1000 のままで、
既定を 0068 の一覧の 100 に揃えることはしない —— **今日 900 件を一度に
受け取っているクライアントが、明日 100 件と cursor を受け取るのは挙動の
変更**であり、この記録が買いたいものではない。数を据え置けば、今日
収まっている呼び出し元は**今日と同じものを受け取る**。壁に当たっていた
呼び出し元だけが、先へ行けるようになる。

同じ理由で `limit` も足さない。0064 §2 が未知キーを 400 にしたので、
必要になった日に足すのは安全である(§5 がそれを一般則として書く)。

## 3. 一つの cursor が、二つの走査を運ぶ

一階層は**三つの配列**である(0075 §4.2: サブディレクトリ・概念・
ファイル)。cursor はそれをこう扱う。

- **概念とファイルは独立した二つの走査**で、それぞれ id と path の全順序を
  持つ。cursor は**両方の位置**を運び、走査が尽きた側は「不在」として
  packing される — 次のページはその問い合わせを二度と投げない。
- **サブディレクトリは初回のページにだけ載る。** あれは走査ではなく
  `GROUP BY` の結果で、名前の数だけ行がある。位置が無いので resume でき
  ず、毎ページ繰り返せば**歩いた人は同じディレクトリを N 回受け取る**。
- **ディレクトリ自身が cursor に入る。** 一覧は prefix ごとに別の listing
  なので、`glossary/` を歩いた cursor で `sales/` を再開すれば**両方で行を
  飛ばす**。400 で両方の名前を言う。

三つを一本の全順序に混ぜて配列を一つにする案は採らない。応答の形
(三つの節)は SPEC §8 の index.md がそう言っているからその形であり、
cursor を綺麗にするために変える対象ではない。

## 4. 文書は歩かない

markdown の `index.md` は今までどおり一階層を丸ごと(上限まで)描き、
打ち切りは注記の行のままである(0075 §4.2)。**SPEC §8 に「続きがある」
と書く綴りが無い**ので、二ページ目の index.md は自分が何なのかを言えない
文書になる。`?cursor=` を markdown に送れば 400 で、これは 0064 §2 が
閉じた沈黙と同じ形である —— 受け取って無視すれば、ページを求めた
呼び出し元が一ページ目を受け取る。

一つの住所の二つの表現が食い違うわけではない: どちらも「この階層に何が
あるか」を言い、**続きの示し方がそれぞれの形式の綴りに従う**だけである。

## 5. 凍結: 任意のクエリパラメータの追加は、止められていない

`cursor` は新しいクエリパラメータで、指紋が 1 行増える。今日の検査は
それを凍結違反として落とす —— `onlyResponseAdditions` が外に置くのは
応答専用スキーマへの追加だけで、テーブルには
`{"an added request parameter", …, false}` という行がある。

**それは 0064 §2 自身の意図と食い違っている。** あの節は、未知のクエリ
キーを 400 にした理由をこう書いた:

> これが今回の一番重い決定である: **凍結後に何かを安全に足せるかどうかを
> 決める**。

リクエスト側を厳格に閉じたのは、**後から足せるようにするため**だった。
0082 はその土台の上で応答側の追加を凍結の外に置いたが、**リクエスト側は
書かないままだった** —— 0082 §3 が丁寧に説明したのは「リクエストで
`required` を足せば既存クライアントが 400 になる」という**必須の**追加の
話で、任意の追加は誰も壊さない。送っていない呼び出し元は、今日と同じ
答えを読む。

**決定: 任意のクエリパラメータの追加は凍結の外である。** 検査は三つに
絞る。

- **`query` だけ。** リクエストヘッダは中継が足すことがあり、呼び出し元が
  握っていない(0064 §11)。パスパラメータは住所である。
- **`required=false` だけ。** 必須の追加は、それを送らない全クライアントに
  とって 400 である —— 0082 §2 が凍結の本体と呼んだものそのもの。
- **パラメータ一本まるごとの行だけ。** 既存パラメータのキーを動かす変更は
  削除と追加の対で届くので、削除の側が先に落ちる。

golden の再生成は今までどおり要る。**買っているのは「黙ってやれなくする」
ことだけ**であり(0082 §4)、追加はレビューする人の diff に出る。

## 6. `truncated` は残る

ページングが入れば `truncated` は cursor と同じことを言う二つ目の綴りに
なる。それでも**外さない** —— 応答からの削除は 0082 §2 が凍結の本体と
呼んだものであり、これは §5 が外に置いた追加ではない。1.0 の仕事である。

同じ取引を [0097](0097-a-write-says-what-it-did-in-the-body.md) §2 が
`Ochakai-Plan` で一度している: **消せる半分だけ先にやり、残りは 1.0 に
渡す**。契約の散文がそう書く。

## 7. 面への配分(0067)

- **REST** — 上のとおり。操作は 11 のまま、`cursor` は PARAM に既にある
  語なので [docs/surface.md](../surface.md) の数は動かない(19 のまま)。
- **CLI** — `ochakai browse --cursor`。`ochakai list` と同じ形で、続きが
  あるページは次の cursor を stderr に出す。`--cursor` も既にある FLAG の
  名前なので数は動かない(29 のまま)。
- **MCP** — 載せない。ブラウズはそもそも MCP に無く(0067 §5.1: 多
  ラウンドトリップの探索は `get_context` の正反対)、無い面にページングは
  足せない。
- **Web UI** — 今回は変えない。ページは一覧を JSON で読んでいるので
  cursor はそのまま届いており、「もっと見る」を描くかは curation 面の
  UI 判断である。1000 件幅のディレクトリに人が出会ったときが、それを
  足すときである。

## 8. 採らない案

- **既定を 100 にする**(0068 の一覧に揃える)。挙動の変更を全呼び出し元に
  配ることになる(§2)。
- **三配列を一つの全順序に畳む。** cursor は綺麗になるが、応答の形は
  SPEC §8 が決めている(§3)。
- **`truncated` を外す。** 凍結の本体である(§6)。
- **markdown もページングする。** SPEC §8 に綴りが無い(§4)。
- **総件数を返す。** 0068 §2.1 が断った理由がそのまま当てはまる ——
  正確な件数は一ページ目の費用を毎回倍にする。
- **cursor に filter を入れる。** 一覧に filter は無い。prefix は住所
  そのものなので cursor が運び、それは検査のためである(§3)。
