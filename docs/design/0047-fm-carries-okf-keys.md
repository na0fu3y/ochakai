# ochakai 設計ドキュメント 0047: 問いの語彙は OKF が定義するキーである

Status: Accepted(2026-07-28)。[0046](0046-bundle-address-space.md) §3.11 の
2 点を改訂する — 「named フィルタは**式への糖衣**になる」は採らず named
フィルタは typed column のまま残し、「**任意の** frontmatter キーを
`fm.<key>=<value>` で引ける」は **OKF が定義するキーのうち専用のフィルタを
持たないもの**に狭める。producer が発明したキーは**保存され往復するが、
問いの語彙には入らない**。0046 の残り(frontmatter jsonb の索引と、
additive なクエリ面という目的)は不変であり、その目的は §2.3 で果たされる。
[0015](0015-surface-consistency.md) §3 に、`fm.` を Web UI に載せないという
意図的な省略を 1 件足す。**§4 のサーフェスは [0058](0058-filters-nobody-arrived-through.md)
§2.2 が改訂した** — `fm.` は MCP にも載せない(REST と CLI には残るので、
ここで決めた語彙も導出もそのまま)。

本ドキュメントは同じ日に採択した同番号の初版(「`fm.` は ochakai が名前を
付けていないキーだけを運ぶ」— 重なる 5 キーを 400 で拒否するだけの案)を、
実装がリリースに乗る前に**差し替えた**ものである。番号を足さないのは
[0048](0048-decision-records-for-wire-contracts.md) §2.3 による — 不変性は
リリースに乗った決定に対する約束であり、これはその規則の最初の適用である。
Date: 2026-07-28

## 1. 問題

0046 §3.11 は frontmatter 全体を `jsonb` に索引し、任意のキーを引く
`fm.<key>=<value>` を足した。目的は明快である — **SPEC が新しいキーを
足した日から、マイグレーション無しで引ける**。この目的は正しい。

### 1.1 同じキーが、綴りによって別の問いになった

同じ節が「named フィルタは式への糖衣になる」とも書いたが、実装は
そうしなかった。typed column の方が索引として優れているからで、その
判断自体は正しい(trigram、`date`、配列)。しかし帰結として、
**同じキーが綴りによって別の問いになった。**

- `?status=stable` は `status: stable` と書いた文書**と、何も書いていない
  文書**の両方に当たる。列は投影の既定値を持つからである
  (0046 §3.9、SPEC §5.4 の既定は `stable`)。`?fm.status=stable` は
  前者にしか当たらない。
- `?type=metric` は case を畳む(`lower(type) = ANY(...)`、0023 §3.3)。
  `?fm.type=metric` は畳まない。
- `?source=` は `sources[]` の中の `resource` を照合する(0037 §2.3)。
  `?fm.sources=` はその問いを表現できない。
- `?sort=stale_after` は `date` 列として比較する。`fm.stale_after` は
  文字列の完全一致なので、`2026-6-1` と `2026-06-01` が別物になる。

どれも単体では間違っていない。問題は**利用者がどちらの綴りを使ったか
自覚できない**ことであり、とりわけ status の食い違いは、0046 §3.9 の後は
**`draft` と書かずにエージェントが作った全エントリ**に効く。「片方の
綴りが静かに少なく返す」は、間違った答えのうち正しい答えに見える種類の
ものである。

### 1.2 開いた語彙は、空の結果を読めなくする

本ドキュメントの初版は §1.1 で止まり、重なる 5 キーを 400 で拒否した。
食い違いは消えたが、**残りの語彙は開いたまま**だった。そこにもう一段の
問題がある。

- **空の結果が答えなのか綴り間違いなのか、利用者に判定できない。**
  `?fm.owner=finance` が 0 件を返したとき、それが「owner が finance の
  エントリは無い」なのか「その producer は `team` と書いていた」なのかは
  区別がつかない。閉じた語彙なら前者しかありえず、開いた語彙では常に
  両方でありうる。
- **引けるキーの一覧が、どこにも書けない。** producer が発明したキーの
  集合は ochakai が知り得ない。だから OpenAPI にも MCP のツールスキーマにも
  CLI の `--help` にも列挙できず、呼び手は**推測で引く**ことになる。
  MCP のスキーマしか見えないエージェントには特にそうである。
  ochakai は中に LLM を置かない(0001)。**推測を要求する面**は、その
  姿勢と噛み合わない。
- **SPEC が要求しているのは保存と往復であって、問いではない。** §4.1 は
  consumer に未知のキーを保存し往復させることを求め、§11 はそれを理由に
  文書を拒否することを禁じる。**引けること**はどちらにも書かれていない。

3 つは同じ 1 つのことを別の角度から言っている — **問いの語彙は、
どこかで閉じていなければ語彙として働かない。**

## 2. 決定: `fm.` は OKF のキーのうち、他に問い方の無いものを引く

### 2.1 列を持つキーは、列が答える

ochakai が自分の列で読むキーを `fm.` で名指したら、答えずに 400 を返す。

| `fm.` で拒否するキー | 使う filter | 拒否の理由 |
|---|---|---|
| `type` | `type=` | 列は case を畳む |
| `status` | `status=` | 列は SPEC §5.4 の既定を適用する(沈黙 = `stable`) |
| `tags` | `tag=` | 列は配列索引で照合する |
| `sources` | `source=URI` | 列は `sources[].resource` を照合する |
| `stale_after` | `sort=stale_after` | 列は `date` として比較する |

**拒否は必ず使うべき filter を名指す。** 400 の本文が次の 1 リクエストに
なる。

### 2.2 OKF が定義しないキーは引けない

producer が発明したキーを `fm.` で名指したら、400 を返し、**引けるキーの
一覧を返す**。

- **保存と往復には一切触れない。** 文書は届いたキーをすべて保ったまま
  保存され(0046 §2.2)、エクスポートはそれをすべて返す(0046 §3.2)。
  SPEC §4.1 と §11 が要求するのはそれであり、本ドキュメントが変えるのは
  **引けるもの**であって**保存されるもの**ではない。
- **`fm.tag` や `fm.source`(単数形)も拒否する。** 初版はこれを
  「producer が書いた可能性の方が高い」として通していたが、通した先に
  あるのは 0 件の結果と、それを読めない利用者である。OKF のキーでない
  以上、拒否して一覧を見せる方が、次の 1 リクエストに近い。
  **サーバーが綴りを勝手に直さない**という 0046 §3.9 の姿勢は変わらない
  — 拒否は書き換えではない。

### 2.3 引けるのは OKF のキーから導出する

`fm.` が答えるのは、**OKF v0.2 が定義するキーから §2.1 の 5 つを引いた
残り**である:

```
attester, computation, description, executor, id,
parameters, resource, runtime, status_note, title, usage_window
```

- **この一覧は書き下さない。** `domain.EnvelopeKeys` — 既にある、OKF の
  キーの唯一の住所 — から導出する。OKF が新しいキーを足し、そのキーの
  綴りをこの一覧が覚えた日に、**そのキーは引ける**。**列も要らず、
  マイグレーションも要らない。**
- **これが 0046 §3.11 の目的の達成である。** 0046 が消したかったのは
  「SPEC の一挙一動が写像の再設計になる」ことだった。差は依然として
  リリース 1 本だが、その中身は**一覧に 1 行**であって、列の追加でも
  データの移動でもない。開いた語彙は、その目的に必要ではなかった。
- **jsonb 索引は残る**(0046 §3.11、マイグレーション 0027)。上の性質を
  買っているのはこの索引だけであり、これが「何が索引を読むのか」への
  答えでもある。
- **どの面も同じ一覧から自分を説明する。** OpenAPI・MCP のスキーマ・
  CLI の `--help` は導出された一覧を出す。ヘルプがサーバーの拒否する
  キーを約束することがない。
- **store は拒否しない。** `Filter.Frontmatter` は任意のキーを引ける
  ままで、拒否はサービス層 1 か所(`checkedFilter`)にある。prefix の
  正規化と同じ場所であり、REST・MCP・CLI はいずれもそこを通るので、
  面ごとに実装がずれることがない(0015 §2「契約はサーバー側」)。

## 3. 選ばなかった案

- **named フィルタを本当に糖衣にする**(0046 §3.11 の字義どおり)。
  `status=` が「stable と書いてある、または何も書いていない」に展開され、
  食い違いは消える。採らないのは、trigram・`date`・配列という索引を
  手放すか、キーごとに式インデックスを積み増すことになるからで、
  0046 が typed column を残した理由がそのまま反対理由になる。
  case の畳み込み(`lower(type)`)は jsonb path では素直に書けない。
  「重なりの解消」は目的だが、その代償として**性能特性を全面的に
  作り直す**のは、問題の大きさに見合わない。

- **producer のキーも引けるままにする**(本ドキュメント初版)。
  §1.2 の 3 点がそのまま反対理由である。加えて、初版の境界は
  「ochakai が列を持っているか」という**実装の都合**であり、利用者から
  見えない線だった。§2 の境界は「OKF が定義しているか」であり、
  利用者は SPEC を読めば分かる。

- **`fm.` を全面的に撤去する。** 語彙は named フィルタだけになり、
  拒否は 1 行も要らなくなる。採らない。`resource` / `runtime` /
  `status_note` / `usage_window` のように **OKF が定義しているのに
  フィルタを持たないキー**を訊く綴りが 1 つも残らないからである。
  とりわけ「この BigQuery テーブルを説明しているエントリはどれか」は
  ochakai の中心的な問い(0001)であり、`fm.resource=` はその唯一の
  綴りである。さらに jsonb 索引の読み手が消えるので索引ごと落とすことに
  なり、0046 §3.11 の目的 — 後の OKF 版が足したキーがマイグレーション
  無しで引ける — を放棄することになる。**問題は語彙が開いていたこと
  であって、語彙があったことではない。**

- **キーごとに named フィルタを足す**(OKF が足すたびに 1 本)。
  §2.3 と同じリリース 1 本を払いながら、フィルタ名という**第二の語彙**を
  増やす。`fm.<OKF のキー>` は綴りが SPEC と同じであり、覚えるものが
  1 つ少ない。

- **差分を文書化するだけ。** 一貫性の欠如を利用者の注意力に転嫁する。
  ochakai の答えは行ではなく知識であり(0046 §5)、「どちらの綴りが
  何に当たるか」を覚えていないと少なく返る API は、覚えなくてよい
  API に直せるうちは直す。

## 4. サーフェス(0015)

`fm.` は既に REST(`?fm.<key>=`)・MCP(`fm: {}`)・CLI(`--fm key=value`)に
載っており、本ドキュメントはそのいずれにも新しい入口を足さない —
拒否は 3 面が共有するサービス層に入り、引けるキーの一覧は 3 面が同じ
導出から出す。

**Web UI には載せない。** 0015 §2 の「Web UI はループの人間側、
キュレーション面であって BI ツールではない」に照らした意図的な省略で
ある。理由は 2 つ:

- `fm.` が答える問いは「OKF のキーで絞る」であり、絞り込みの語彙を
  **利用者が既に知っている**ことを前提にする。Web UI のフィルタは、
  選べる値がその場に見えている(type、status、trust のチップ)ことで
  成立しており、自由入力の key/value 行はその性質を持たない。
- 人が知りたいのは通常「どの実体を指しているか」ではなく「何が古いか・
  誰が確認したか」で、それらは既にフィルタ列に載っている。

見直す条件: Web UI の利用者が URL を手で編集して frontmatter キーで
絞り始めたら、フィルタビルダーに key/value 行を足す。

## 5. 互換性

`fm.` は未リリース(0.15.0 の次のリリースで 0046 の実装と束ねて出る)
なので、**破壊的変更は無い**。CHANGELOG の Unreleased 節が `fm.` を
「任意の frontmatter キー」と書いているところを「OKF のキー」に
書き替える。

**保存されるものは何も変わらない。** producer のキーは今までどおり
届いたまま保存され、往復し、エクスポートに出る(0046 §2.2、§3.2、
SPEC §4.1・§11)。
