# ochakai 設計ドキュメント 0082: 凍結が止めているのは何か

Status: Accepted(2026-08-08)。[0064](0064-rest-stops-at-api-v1.md) §11 の
「凍結を破ってよい唯一の理由はセキュリティ上の欠陥である」を改訂する —
**応答専用スキーマへのプロパティ追加は、そもそも凍結が止めているものでは
ない**。0064 の他の決定は一つも動かない。REST の安定性契約は引き続き
0064 と [docs/compatibility.md](../compatibility.md) が現行である
Date: 2026-08-08

## 1. 何が起きたか

`GET /api/v1/stats` に数を一つ足そうとして、`TestFrozenWireHasNotMoved`
が落ちた。

```
+ components/schemas/Stats.dropped required=true type=object
+ components/schemas/Stats.dropped.events required=true type=integer
```

足そうとしていたのは、ループが観測して失った件数である。利用回数は
best-effort で([0029](0029-usage-metrics.md) §3.1)、バッファが溢れれば
捨て、flush が失敗すればバッチごと失う。**その損失がログにしか出ない**
ので、「この concept は 4 回参照された」を読んだ人に、4 なのか 40 なのかを
知る手立てが無い。C7(改善ループが測れる)が測れていない一点だった。

迂回路は無い。CLI も Web UI も REST のクライアントであり
([0067](0067-four-faces-and-what-they-decline.md) §2)、REST が返さない数は
どちらにも出せない。stats は MCP に載っていない。**凍結が止めていたのは
契約ではなく、製品の中核条件の計器だった。**

## 2. 決定: 凍結が守るのは、住所・リクエストの形・応答の削除と変更

凍結の対象は次のとおりである。

- **住所** — 操作、`operationId`、パス、メディアタイプ、ステータスコード、
  ヘッダ名。
- **リクエストの形** — クエリパラメータ、リクエストヘッダ、リクエスト
  ボディのスキーマ。**必須プロパティの追加を含む**。
- **応答からの削除と変更** — プロパティが消えること、型が変わること、
  必須が任意になること、名前が変わること、enum や制約が動くこと。

**応答専用スキーマへのプロパティ追加は、この外である。**

## 3. なぜ安全か

**0064 自身がこのために機構を作っている。** §2 の一番重い決定は「宣言して
いないクエリキーは 400」で、その目的を 0064 はこう書いた —
「**凍結後に何かを安全に足せるかどうかを決める**」。リクエスト側を厳格に
閉じたのは、追加を安全に扱える土台を作るためだった。その土台の上で、
応答への追加は誰も壊さない: 知らないキーは JSON デコーダが既定で無視する。

**応答の `required` はサーバの約束であって、クライアントへの要求では
ない。** リクエストで required を足せば、それを送らない既存クライアントは
400 になる。応答で required を足しても、既存クライアントは読まないだけ
である。同じ語が二つの向きで別の意味を持つので、規則も向きで分ける。

**応答*専用*に限るのは、スキーマが両方から参照され得るからである。**
`components/schemas/X` という指紋の一行だけでは、X がリクエストボディにも
使われているか分からない。使われていれば、そこへの必須プロパティ追加は
0064 §2 の下で 400 を生む破壊的変更である。どのスキーマが応答専用かは
契約から判定できる — `requestBody` から(推移的に)到達できないもの。

## 4. 追加は、それでも diff に出る

`api/openapi.frozen.txt` は今までどおり実物と一致していなければならず、
追加した PR は golden を再生成する。変わるのは**何が正当な再生成かと、
テストが何と言うか**だけである。

- 削除・変更が一行でもあれば、これまでどおりの失敗 — 破ってよい理由は
  セキュリティ上の欠陥だけ。
- 追加だけで、かつすべてが応答専用スキーマなら、失敗の文面が変わる:
  本書が許した追加であり、同じ PR で golden を再生成せよ、と言う。

**通らなくなるわけではない点が重要である。** この repo の仕組みが買って
いるのは「黙ってやれなくする」ことだけで([docs/surface.md](../surface.md))、
追加が自由になったら応答は誰も数えないまま太る。golden の再生成を要求し
続けることで、追加は必ずレビューする人の目の前の diff に出る。

## 5. 採らなかった案

- **凍結をそのまま守り、メジャーまで待つ。** compatibility.md は 1.0 を
  未定と書いており、その間 C7 の計器は増やせない。凍結は 6 日前(0064 は
  2026-08-02)、REST の外部利用者は実質ゼロで、**規則の欠陥を直す代金が
  今より安いことは二度とない**。
- **今回だけ例外にして golden を再生成する。** 規則を書き換えずに曲げる
  のは、この repo の文化が最も防ごうとしている形である。以後、追加のたびに
  「これはセキュリティ修正か」という意味の無い問答が要る。
- **応答スキーマを指紋から丸ごと外す。** 削除・改名・型変更という**本当の
  リスク**まで見えなくなる。0064 が指紋を作った動機そのもの
  (`concepts` → `entries` のような改名が誰にも見えなかったこと)を捨てる
  ことになる。
- **応答の追加を任意(`required` から外す)に限る。** 応答の required は
  サーバの約束なので(§3)、制限しても誰も守られない。守られないのに
  書き手が迷う規則は、規則の側が間違っている。

## 6. やらないこと

- **リクエスト側の緩和。** クエリパラメータ、リクエストヘッダ、リクエスト
  ボディは 0064 のまま凍っている。0064 §11 の「凍結後、新しいリクエスト
  ヘッダに安全性を左右する意味を持たせない」もそのままである。
- **応答からの削除・改名・型変更。** ここが凍結の本体であり、本書は一行も
  緩めていない。
- **応答が太ることへの上限。** 数えるなら [docs/surface.md](../surface.md)
  の仕事で、今日それを足す理由はまだ無い — 追加が diff に出る以上、
  太り始めたことは見える。見えても止まらなくなったときが、上限を置く
  ときである。
- **メジャーバージョンの前倒し。** 本書は 1.0 の基準を動かさない。
