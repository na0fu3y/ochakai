# ochakai 設計ドキュメント 0035: 不変条件を機械に検査させる

Status: Accepted(2026-07-26)
Date: 2026-07-26

## 1. 背景

ochakai の不変条件の多くは、型ではなく**散文とテスト**が支えている。

- 「型は開集合、status は閉集合」(0023、0017)
- 「curated status は If-Match の無い面から置換できない」(0015 §3.1)
- 「4 つの面は同じ機能に同じ意味を持たせる」(0015)
- 「ochakai → ochakai の往復は正確」(0036 §3.4)

Rust や F# であれば、この種の規律のかなりの部分は直和型・網羅性検査・
newtype がコンパイル時に受け持つ。Go にその層は無い。`domain.Status` は
`string` の別名であり、値を 1 つ足しても既存の `switch` は黙って
`default` に落ちる。`ValidID` は述語であって型ではないので、検証済みの
id と未検証の文字列はシグネチャ上で区別できない。

代わりに ochakai が持っているのは `gofmt` / `go vet` / `go test -race` /
`CGO_ENABLED=0` ビルド / `govulncheck` である。Go の標準装備としては
手堅いが、**上に挙げた不変条件はどれ 1 つ検査していない**。

## 2. 問題

型に載らない不変条件は、レビューと記憶で守るしかない。そこには 3 つの
具体的な穴がある。

1. **網羅性。** `Status` に値を足したとき、対応が要る `switch` を
   人間が全部見つける必要がある。見落としは実行時まで現れない。
2. **契約。** [api/openapi.yaml](../../api/openapi.yaml) は「公開 wire
   surface」と宣言されているが、**どのテストからも参照されていない**。
   `internal/apiclient/wire_test.go` はサーバ型とクライアント型を JSON
   往復で結んでいるので、この三角形のうち 2 辺は結ばれている。spec だけが
   孤立点で、実装と spec の同期は CONTRIBUTING の散文が頼りである。
3. **性質。** テストは例に対する主張である。「往復が正確」「パーサは
   どんな入力でも落ちない」は例ではなく性質で、書かれた例の外側は
   誰も見ていない。実際 fuzz テストは 0 件である。

## 3. 決定

**この 3 つの穴を、それぞれ機械に検査させる。** 型を模した抽象を
足すのではなく、Go にある道具で外側から検査する。

### 3.1 静的解析 — golangci-lint

`go vet` が見ない検査を [.golangci.yml](../../.golangci.yml) で足し、
CI のジョブにする。

選定の基準は **「clean tree で 0 件」** である。指摘が出たら常に
「新しいコードが何かした」を意味し、「linter の好み」を意味しない。
これを満たさない検査は、どれだけ有名でも入れない — CI が硬いゲートで
ある以上、恒常的にノイズを出す検査は `nolint` の乱発に化けるだけである。

有効にするもの:

| linter | 何の代わりか |
| --- | --- |
| `exhaustive` | 直和型の網羅性検査。**この決定の中心** |
| `errorlint` | `err == Sentinel` は誰かが `%w` で包んだ瞬間に黙って外れる |
| `staticcheck` | 非推奨 API、デッドコード、標準ライブラリの誤用 |
| `bodyclose` | 閉じ忘れたレスポンスボディ |
| `nilerr` | `err != nil` を見た直後に `nil` を返す |
| `unconvert` / `unparam` | 変換しない変換、誰も変えない引数 |

`exhaustive` は `default-signifies-exhaustive: true` で運用する。
`default` を書いた `switch` は、名前を挙げなかった値をどう扱うか既に
表明している。検査したいのは**全部を挙げきるつもりの `switch`** の方で、
値の追加が壊すのはそちらである。

`govet` は golangci-lint 側では有効にしない。CI に `go vet ./...` が
既にあり、二重に走らせる理由が無い。

### 3.2 契約テスト — openapi.yaml を実装に結びつける

`internal/restapi` のテストを通るリクエストとレスポンスを
`api/openapi.yaml` に照合する。spec を孤立点でなくすこと、それだけが
目的である。

生成器(oapi-codegen 等)は採らない。手書きのハンドラを保つ現状の形は
0015 の「面ごとに意味を設計する」姿勢と一体で、22k 行の規模なら
**同期は生成ではなくテストで足りる**。

### 3.3 性質テスト — fuzz と round-trip

Go 標準の `testing.F` で、性質として書けるものを性質として書く。

- `internal/okf` のパーサ — 信頼できないバンドル入力を食う唯一の場所
- `internal/domain` の id / リンク導出 — 述語と正規化の関係
- **往復**: 0036 §3.4 が明文で主張する `export → import` の同一性、
  `OKFStatus` / `StatusFromOKF` の整合

シードコーパスの回帰は通常の `go test` が実行するので、CI の形は
変わらない。外部依存も増えない。

## 4. 採らないもの

- **parse-don't-validate の全面適用。** `ValidID` を検証済み型に
  置き換える案は理論上正しいが、Go ではメソッドの増殖とゼロ値問題を
  買う。境界が 3 つの面に集約済みの現構造では割に合わない。
- **NilAway。** この規模では誤検知の対応コストが上回る。
- **形式手法。** 0030 の楽観ロック程度の並行性に TLA+ は要らない。

## 5. 影響

`Rewrite` への移行(`ochakai ui` / `serve-ui` の逆プロキシ)が
3.1 の最初の指摘だった。副次的に、ブラウザが送った `X-Forwarded-*` は
追記されずに**捨てられる**ようになる — 何も信じないプロキシとして
そちらが正しい(0032)。読んでいる箇所は無いので、外から見た挙動は
変わらない。
