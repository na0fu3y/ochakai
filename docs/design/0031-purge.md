# ochakai 設計ドキュメント 0031: purge — id を解放する二段階目の削除

Status: Accepted(2026-07-26)。[0044](0044-bundle-address-space.md) §3.5 が
面をオブジェクトの語で言い直す(`DELETE /api/v1/bundle/{path}?purge=true`)。
二段階・不可逆・監査行・GCS の blob を回収しないという決定は不変
Date: 2026-07-26

## 1. 背景: 決定はランドしていたが、記録されていなかった

purge は 2026-07-22 の PR #116 でランドし、監査ログは PR #127 で足された。
新しい破壊的インターフェースでありながら設計ドキュメントを持たず、
[0015](0015-surface-consistency.md) §3.1 は「id を完全に解放したければ
purge がある(0021)」と、purge を一言も含まない
[0021](0021-move-and-webui-refinements.md) を引いていた。本ドキュメントは
その決定を事後に記録し、参照の宛先を与える。決定自体は変更しない。

## 2. 問題: 墓標が住所を握ったままになる

delete はソフト削除である — 行は残り、`deleted_at` が立つだけで、リビジョン
履歴も保持される。これは正しい既定である(履歴が価値の本体である)。

しかしソフト削除された行は**主キーを所有し続ける**。0021 が決めたとおり、
move は墓標の上へは動かせない — その行はまだ id とリビジョン履歴を持って
おり、上書きは 2 系統の履歴の合流になるからである。0015 §3.1 が
create による墓標の復活を MCP から塞いだことで、この閉じ方はさらに強くなった。

結果、**一度使った id は永久に塞がる**。`metrics/revenue` を作って消したら、
そのアドレスは二度と使えない。ID がアドレスである(0017)以上、これは
「あるべき場所に置けない」という設計上の欠陥になる。

## 3. 決定

**purge を足す — ソフト削除済みのエントリを完全に破棄し、id を解放する。**

### 3.1 二段階であること

purge は live なエントリを受け付けない(`ErrNotDeleted`、REST 409)。
必ず delete が先である。

これは意図的な摩擦である。1 コールで、直前まで使われていた履歴を消せて
しまってはいけない。一段目は可逆(復活できる)、二段目は不可逆、という
形にしておけば、不可逆な操作は必ず「もう消えていたものを、さらに消す」
という文脈でしか起きない。

### 3.2 消えるもの、残るもの

同一トランザクションで、その id を鍵に持つすべてを消す — エントリ行、
リビジョン、添付メタデータ、利用集計、生イベント、埋め込みベクトル。

**GCS 上の添付バイト列は回収しない。** blob はコンテンツアドレス
(sha256、0011)で共有されており、同じバイト列を別のエントリが参照して
いるかもしれない。参照カウントを持たない以上、安全に消せるのは
「どこからも参照されていないと確認できたとき」だけで、その確認は
全エントリの走査になる。孤児 blob のストレージ代は、誤って生きている
添付を消すリスクより安い。

### 3.3 purge した事実は残る

`knowledge_purge` に 1 行残す — id、type、title、消えたリビジョン数、
実行者(via 込み)、時刻。**内容は残さない**: 呼び出し元が消せと言ったのは
内容である。

理由は provenance が製品価値の本体だからである。そして ochakai には
認可機構が無い(0002)ので、「人間しか呼ばない」は**どのサーフェスが
露出しているか**の話であって、**誰が到達できるか**の話ではない。追跡不能な
破壊経路は、この製品では間違った種類の穴である。ログにも残す。

### 3.4 サーフェス配置(0015)

- **REST**: `DELETE /api/v1/knowledge/{id}?purge=true`。既存の削除動詞に
  乗せる — 別パスを切るほど別の操作ではない。
- **CLI**: `ochakai purge <id>`。
- **MCP には出さない。** 履歴の破壊は人間の判断であり、エージェントに
  渡す操作ではない。0015 §3.1 がエージェントから墓標の復活を塞いだのと
  同じ理由づけの裏面である: 塞いだ結果として必要になった逃げ道は、
  塞いだ相手ではなく人間の面に置く。
- **Web UI には出さない**(現時点)。UI の削除ボタンの隣に不可逆な破棄を
  置くと、二段階にした意味が薄れる。必要になったら別途決める。

## 4. 壊れるもの

- 無い。purge は新しい操作であり、既存の delete の挙動は変わらない。
- ただし **purge した id のリビジョン履歴は復元できない**。バックアップ
  (`ochakai export`)以外の復旧手段は無い。
