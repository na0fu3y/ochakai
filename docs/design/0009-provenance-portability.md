## 1. 目的

「サーバー所有キー」の規則(provenance はペイロードからではなく認証から
来る)の帰結として生じる問い —— **export → Git → import の往復で
provenance は誰のものになるのか** —— に答える(issue #42)。

検討した選択肢:

- **案 A**: インポート経路に限り `--preserve-provenance` を許す
- **案 B**: 「Git はレビュー経路」ワークフローを規範化する(コード変更なし)
- **案 C**: provenance はインスタンス固有であり、バンドルは知識のみを運ぶ

**決定: 案 C を世界観として採用し、案 B をその上の推奨ワークフローとして
規範化する。案 A は不採用。**

## 2. 往復で何が動き、何が動かないか

起票時の想定 ——「往復で全 concept の provenance がインポート実行者に
付け替わる」—— は正しくない。**同じインスタンスへの往復では、provenance は
一つも動かない。**

- 書き込みは `created_by` / `created_at` を保存済みのものから引き継ぎ、
  台帳(検証・却下)には触れない。**更新は何も裁定しない**
  ([0043](0043-document-first.md) §§3.2-3.3)。
- 自分の export 形に付いている trust family は主張ではなく**このインスタンス
  の観測**なので、書き込み経路がそれと認めて取り除く(0075 §3.1)。だから
  export した木をそのまま取り込むと `unchanged` になり、リビジョンも増えない。

provenance がインポート実行者のものになるのは **Create 経路だけ**である ——
(a) 空のインスタンスへの移行、(b) 他インスタンスへの共有、(c) バンドル内の
新しい concept。したがって答えるべき実質は「(a) 移行と (b) 共有のとき、
provenance を運ぶべきか」に絞られる。

## 3. 決定

### 3.1 世界観(案 C): 観測は運ばない、知識は運ぶ

**provenance はインスタンス固有の観測記録であり、可搬な属性ではない。**
`created_by` / `verified` は「このインスタンスで誰が入れ、誰が確かめたか」を
サーバーが観測した事実であって、文書の自己申告ではない —— **文書には観測者が
いない。**

「Your knowledge is yours」との緊張はこう整理する: **持ち出せるのは知識で
あり、バンドル(と Git 履歴)が旧インスタンスの provenance のアーカイブに
なる。** 移行しても記録は失われるのではなく、「live な記録」から「歴史的
記録」に変わる。新インスタンスで importer が `created_by` になるのは、
むしろ正確な記録である。

受け取った主張をどう保存するか —— 台帳にも trust tier にも入れず `received:`
の下に残し、note として報告する —— は 0075 §3.1 が現行の記述を持つ。

### 3.2 ワークフローの規範化(案 B): Git はレビュー経路である

Git を知識のレビュー経路にする運用を、推奨として規範化する。決定はこの
三つで、手順は [git-review ガイド](../guides/git-review.md)が持つ。

1. **バンドルは Git に置ける形で出る。** export された木は markdown +
   frontmatter であり、レビューできるのは知識だけである —— 台帳は出ない。
2. **取り込んだ者が actor になる。** merge 後に import した人間か CI の
   サービスアカウントが記録される。これは正確な記録であり、「レビュー
   ゲートを通したのが誰(何)か」を言っている。
3. **merge は verify ではない。** Git のレビューは ochakai の裁定面では
   ないので、取り込みは trust tier を動かさない。frontmatter に書かれた
   `verified` も §3.1 のとおり主張のまま残る。検証は
   `POST /api/v1/review/{id}` から下る。

### 3.3 案 A の不採用理由

1. **認可機構が無い。** 到達できた者は読み書きできる
   ([0065](0065-identity-and-provenance.md) §1)ので、
   `--preserve-provenance` を管理者だけに限る手段が無い ——
   **誰でも任意の provenance を自己申告できる**ことになる。認可ではなく
   記録で担保するモデルは、provenance が観測記録であることに全面的に
   依存しており、ペイロードから受けた瞬間に信頼のアンカーが消える。
2. **救いたいユースケース(移行)は運用で足りる。** 移行専用の
   サービスアカウントで import すれば「移行で入った」と一目で読める。
   何が持ち帰らないかは
   [運用ガイド](../guides/operating.md#バンドルからのリストア)にある。

## 4. やらないこと

- **`--preserve-provenance`(いかなる経路でも)。** §3.3 のとおり。
  role/認可を導入する日が来たら、そのときに再検討してよい。
- **provenance の署名付きエクスポート。** 信頼はインスタンス運用者に
  置く。インスタンス間で暗号学的に provenance を運ぶ需要が実在してから
  検討する(おそらく過剰であり続ける)。
- **サーバー側の一括 import。** レビュー経路が要求するのは既存
  エンドポイントのループで足りる
  ([0067](0067-four-faces-and-what-they-decline.md) §5.2)。同じ理由で
  `ochakai sync`(差分だけの取り込み)も断っている(issue #43)。
