# ochakai 設計ドキュメント 0137: 報告は、何を見たかを言う

Status: Accepted(2026-08-31)。[0069](0069-the-loop-and-what-measures-it.md)
§3 が測ってきた結果報告に、**読む面**を与える — `--note` は最初から
書けたが、どの面も読み返せなかった。0069 の決定は一つも動かない(§1)。
[0065](0065-identity-and-provenance.md) §4 が producer を
`knowledge_event` に足さない理由として挙げた「書き込み専用」は、この
記録によって古くなる。**決定のほうは動かない**ので Superseded にはしない
([0133](0133-an-okf-moment-is-an-instant.md) §6 と同じ扱い、§4)。
Date: 2026-08-31

## 0. この記録が決めたこと

1. **`GET /api/v1/usage/{id}` が `reports` を返す** — note を持つ結果報告を
   新しい順に最大 10 件、worked と failed の両方(§2)。
2. **報告者は kind + name で出る。** `via` と `producer` はこれらの行に
   無く、この記録は足さない(§4)。
3. **180 日の刈り取りが利用者に見えるようになるので、面がそう言う。**
   この数は継承であって導出ではない(§3)。
4. REST・CLI・Web UI に載り、**MCP には載らない**(§5)。

## 1. 書かれているものが、届いていなかった

`report_outcome` は最初から `--note` を持っている。「2026-07 の出荷分割
以降、二重計上している」と書ける口があり、`POST /api/v1/usage/{id}` の
`note` は 2,000 バイトまで取り、`knowledge_event.note` に落ちる。

**そこから先が無かった。** この列を `SELECT` する SQL はどこにも無い。
`GET /api/v1/usage/{id}` は数だけを返し、`GET /api/v1/stats` は件数だけを
数え、`revisions` が運ぶ note は却下理由
([0135](0135-a-rejection-is-a-deletion.md))であって結果報告のものでは
ない。**書き込み専用の列が一つ、二か月ぶん貯まっていた。**

詰まったのは `ochakai list failed` を開いた人である。フィードは
「この concept は 3 回誤りと報告された、未処理である」までを言い、
0069 §2.1 はそれを「在否が『未処理か』を、並びが『どれだけ悪かったか』を
表す」と設計した。**その次に要るのは「何が悪かったか」で、報告者は既に
書いている。** 書いたものが読めない口は、次の報告者に「書いても読まれ
ない」と教える口でもある。

三つの問い([docs/surface.md](../surface.md))への答え:

1. **誰が詰まったか** — 再検証フィードから concept を開いたキュレーター。
   数は「直せ」と言うが、何を直すかは言わない。
2. **既存の面で回避できるか** — できない。この列を読む面が一つも無い。
3. **何が畳めるか** — 何も畳めない。代わりに、**この記録は住所も
   パラメータも語彙も足さない**: 既存の応答に欄が一つ増えるだけで、
   `outcome.worked` / `outcome.failed` は VOCAB に既出、`Actor` は既存の
   スキーマである。増えるのは `REST-LINES` の散文と CLI の一段落だけで、
   単調増加の代金としてはこれが一番安い形である。

条件は **C7**(人間の改善ループが測れる)。C7 に当たることは足す理由に
ならないので、上の三つが理由である。

## 2. 形

応答専用スキーマへの追加なので凍結の外
([0082](0082-what-the-freeze-holds-still.md))であり、`/api/v1/usage` は
そもそも OKF コアの外である([0107](0107-the-freeze-holds-the-okf-core.md))。

```json
"reports": [
  { "outcome": "failed", "at": "2026-08-29T04:12:55Z",
    "by": { "kind": "process", "name": "insightflow@….iam.gserviceaccount.com" },
    "note": "2026-07 の出荷分割以降、二重計上している" }
]
```

- **新しい順、最大 10 件。** 10 は `stats` の `misses.queries` と同じ根拠
  — 人が一度に読んで動ける量を超えて返す意味がない(0069 §5)。順序を
  「failed を先に」にはしない: フィードが既に failed で並べて人を連れて
  きており、開いた先で二つ目の並べ替えが起きると、どちらの順に従って
  いるのかが読めなくなる。時刻順は説明を要しない唯一の順である。
- **worked も出す。** 「FY2025 で回して締めと円まで一致した」は draft を
  昇格させる証拠であり、0069 §2 の下書きレビューキューが探している当の
  ものである。failed だけに絞れば、**ループの半分だけが声を持つ。**
- **`reports` は note を持つ報告だけを運ぶ。** 報告の件数は `worked` と
  `failed` である。大半の報告は note を持たないので、`failed: 12` の隣に
  `reports` が 3 行、は普通に起きる。**数と行数が一致しないことは、面が
  言う。**
- **空なら欄ごと無い。** `View` が `files` / `plan` / `notes` をそう扱って
  いるのと同じで、「言うことがあるときだけある」。
- 欄の名前が `notes` ではないのは、`View.notes` が既に別のもの(書いた
  ものと違う読み方をした値の申告、[0113](0113-a-reinterpretation-says-itself-in-the-body.md))
  だからである。同じ綴りが一つの API で二つを指すのは
  [0102](0102-one-history-in-one-spelling.md) が畳んだ側の形である。

- **運ぶのは一件の読みだけである。** `SearchHit.usage` は同じスキーマを
  参照するが、一覧はこの欄を埋めない(§5)。

認可は動かない。`report_outcome` は読み取り権限で通る(0069、
[0109](0109-a-directory-has-readers-and-writers.md))ので、**note を読める
集合と書ける集合が一致する** — 新しい判断が一つも要らない。

## 3. 180 日は、ここで初めて利用者に見える

生イベントの保持 180 日は、いままで**実装の詳細**だった。累計は
`knowledge_usage` に残るので、刈っても `/usage` の数は正確なままであり
(0069 §3)、利用者から見て何も起きない。

**note を読める面に出した瞬間、それは地平線になる。**「半年前の失敗報告に
何が書いてあったか」は、もう答えられないことが**見える**質問である。
なので面がそう言う — 0069 §4 がミスについて「刈られた期間は完全に消える」
と明言したのと同じ扱いで、黙って短い履歴を返さない。

**この数を動かさない。** 90 日の窓は保持の内側でなければならず
([0090](0090-a-queue-ranks-on-what-happened-lately.md) §2)、`stats` の
`days` は 180 を上限として超えを 400 で断る(0069 §5)。保持を動かせば
両方が動く。それはこの記録が背負う決定ではない。

**そして正直に言うべきことが一つある: 180 に導出は無い。** 初出は
`dc3ad27`(2026-07-16、書き戻しループを固めた最初のコミット)で、
[0001](0001-architecture.md) §9.2 に「生イベントは 180 日で刈り取り、
累計は無期限」と置かれたきりである。0029 §3.4 と 0069 §3 は同じ文を運び、
0090 §2 と 0069 §5 は 180 **から**導いている。**下流はすべて 180 に
依存して導出され、180 自体は誰も導出していない。** 半年という人が言える
単位、というのが実際のところである。利用者に見えるようになる以上、
それを記録が言わないままにはしない。

## 4. 報告者は kind + name で出る

`knowledge_event` が持つ actor の列は `actor_kind` と `actor_name` の
二つだけである。`Actor` の残り二つ — `via`(委譲元)と
`producer`(名乗ったソフトウェア)— は 0065 §4 が意図して落としている:

> 記録先は actor が `via` を持つ場所すべて。書き込み専用で 180 日で
> 刈られるテレメトリ(`knowledge_event`・`search_miss`)には足さない —
> 読まれない列は何も記録しない。

**この理由の前提が、この記録で崩れる。** 列は読まれるようになる。

それでも**結論は動かさない。** 今回の動機は「何が間違っていたか」で
あって「誰の系列か」ではなく、委譲が効いていれば `actor_name` は委譲先
(実際に使ったエンドユーザー)なので、「誰の報告か」には kind + name で
答えが着く。落ちるのは「どのアプリ経由か」「どのソフトウェアが名乗ったか」
の二つで、それを足すのは 0065 の領域の決定であり、この記録の中で黙って
巻き取るものではない。

したがって 0065 は Superseded にしない — §4 の**決定**は一字も変わらず、
古くなるのは理由づけの一節だけである。0133 が 0069 §2.2 と 0074 §4.1 に
ついて同じ判断をしている。**理由が消えたのに結論だけ残っている状態を、
黙って残さない**のがこの節である。

## 5. 面(0015 / 0067)

| 面 | 何が出るか |
|---|---|
| REST | `Usage.reports`。唯一の契約 |
| CLI | `ochakai usage <id>` が続けて出す。完全性の面なので、ワイヤに在るものは出す(0067 §3) |
| Web UI | 詳細ページの利用タブ。**これが動機である**(下段) |
| MCP | **出さない。** `get_concept_usage` は [0076](0076-two-tools-leave-mcp.md) で既に降りており、これはループの人間側である(0069) |

**Web UI に載ることは 0067 §5.4 と衝突しない。** あの節が断ったのは
worked / failed の**ボタン**であり、理由は「実行しない UI に置くと裏付けの
ない報告が再検証フィードの信号を汚す」だった。**読むことは書くことでは
ない。** 報告を読んで裁定に進むのはキュレーションそのもので、Web UI は
そのための面である。ボタンは今も載らない。

**カードには載らない。一件の読みにだけ載る。** 再検証フィードは
`sort=failed` の一覧で、行の `usage` は一覧のための lateral が埋めている
(0090 §3)。note をそこに足すと**行ごとに問い合わせが一本**増え、
50 行の一覧が最大 500 件の自由文を運ぶ。一覧はランキングであって読み物
ではなく、応答の予算は全体を縛る([0093](0093-the-budget-governs-the-whole-response.md))。
フィードは「どれを見るか」に答え、開いた先が「何が書いてあったか」に
答える — 順序としてこれが正しく、一覧に畳み込むと両方が薄まる。

## 6. やらないこと

- **note の絞り込み・ページング・カーソル。** 10 件で切る。11 件目が要る
  という要求は、まだ誰も出していない。
- **報告者での逆引き**(「この agent の報告を全部見せろ」)。0069 §4 が
  ミスについて引いた線と同じで、**キュレーションの道具ではなく監視の
  道具**になる。行は actor を持ち、面はそれを一件ずつ見せるだけである。
- **note の編集・削除・返信。** 報告は観測であって会話ではない。訂正は
  次の報告を書くことであり、それが台帳の形である。
- **verify に note を持たせること。** 0068 §4 が既に断っている
  ——「verified はそのままで正しいと言う語であり、言うことがあるなら
  concept に書く」。
- **保持を延ばすこと・note だけ別表に逃がすこと**(§3)。後者は刈り取り
  から外れた行を増やす可動部である。
- **note を検索に入れること。** 索引に入るのはナレッジであって、それに
  ついての報告ではない(0069 §7 が `sort=gaps` を断ったのと同じ線)。

## 7. 互換性

**破壊的変更は無い。** 応答に欄が一つ増えるだけで、既存の呼び出し元は
無視できる。移行も、運用者の作業も、環境変数も無い。既に書かれている
note は**そのまま読めるようになる** — 保持の内側にある限り。
