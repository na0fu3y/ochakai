## 0. この記録が決めたこと

**四つの記録が一つの絵であること。** 領域の現行ドキュメントを七冊読まないと
現在の姿にたどり着けない状態を畳む(issue
[#471](https://github.com/na0fu3y/ochakai/issues/471))。決定は一つも動かない。

七冊を一冊にしようとすると 277 行になった。CONTRIBUTING.md の
`RECORD-LINES` が言うとおり、**超えたということは二つの決定だった**という
ことである。継ぎ目は探すまでもなく §2 と 0066 §1 の表の軸そのもので、
**誰として記録するか**(この記録)と**このデプロイは何をするか**(0066)に
割れた。七冊が二冊になる。

畳んだ代金は書いておく。**四冊が持っていた論証は、ここには来ていない。**
なぜ委譲を合成で記録するのか、なぜ allowlist を producer には要らないと
判断したのか — そういう「なぜそう決めたか」の全文は、各記録の墓標が指す
コミットに残る。ここに残したのは**いまも参照される理由**だけである。
再係争されていない論証より、いま読む人を優先した。

四冊のうち 0002 は、本文が既に現在を説明していなかった — `OCHAKAI_AUTH`、
削除済みの `clients` モード、0043 が `process:` に改めた `agent:` の綴り、
0060 が畳んだ `OCHAKAI_INSECURE_DEV`。Status ヘッダだけが、そのうち一つを
断っていた。0027 §5.1 の「kind は `human` か `agent`」も同じ綴りのまま
残っていた(実装は `human` / `process` を受け取る)。これは統合の理由で
あって、副産物ではない。

## 1. 原則: 認可を持たない

**到達できた者は読み書きできる。** 誰を到達させるかはデプロイ側
(Cloud Run IAM / プライベートネットワーク)の責務であり、ochakai は認可
機構を一切持たない — role もスコープもトークン発行/失効も無い。

ochakai がヘッダから読むのは **provenance(誰として記録するか)だけ**で
ある。status の遷移も制限しない。誰が検証したかは台帳に actor として必ず
記録されるので、**信頼の判断は参照側が provenance を見て行う**。認可では
なく記録で担保する、というのがこの領域全体の設計である。

「読めるが書けない人」が要るようになったら、この記録を改訂する。
**そうなった** — [0109](0109-a-directory-has-readers-and-writers.md) が
この段落を改訂している。ただし**付与を一つも持たないデプロイでは、この節
は一字も変わらない**: 認可機構が既定で不在であることは動いていない。

## 2. actor は認証から来る

Cloud Run の IAM を通過したリクエストには Google 検証済みの ID トークンが
届く。`X-Serverless-Authorization`(両方あるとき Cloud Run が検証するのは
こちら)を優先して読み、無ければ `Authorization` を読む。署名の再検証は
しない — IAM を通過したことが検証である。**この優先はこの経路の規則で
あって、両経路の規則ではない** — 自分でトークンを検証するデプロイ
(0086)は `Authorization` だけを読む([0121](0121-each-path-reads-its-own-header.md))。

actor の綴りは `human:` と `process:` の二つで、`*.gserviceaccount.com` は
`process:`、それ以外は `human:` になる。人の資格情報で動くエージェントは
human として記録される(「あなたの鍵で動くものはあなた」)。

**絶対条件はサービスが非公開であることである。** 公開されたサービスでは
ヘッダは自称にすぎない — その状態のための姿勢が 0066 §3 である。

## 3. 委譲: 呼び出し元がエンドユーザーを名乗る

埋め込みホストは自分の SA で IAM を通過するので、放っておけば**利用者が
何人いようと provenance は一つの SA に潰れる**。

`OCHAKAI_DELEGATING_CALLERS`(カンマ区切り、`*` は認証済みの全呼び出し元、
**既定は空 = 委譲無効**)に載った呼び出し元は、`Ochakai-On-Behalf-Of:
<kind>:<identity>` でエンドユーザーを名乗れる。kind は `human` か
`process` で、**推測しない** — 呼び出し元は人を代理しているのか別の
エージェントを代理しているのかを知っている。空白を含む identity・320 バイト
超・未知の kind は 400。

**置き換えではなく合成する。**

```
created_by: human:tanaka@example.co.jp via process:app@proj.iam.gserviceaccount.com
```

単純に置き換えると、tanaka が自分で書いたエントリとアプリ経由のエントリが
記録上まったく区別できなくなる。**区別できない委譲は偽装と同義**であり、
provenance を回復するはずの機構がそれを壊す。呼び出し元は `via` として必ず
残り、参照側は「人が自分の資格情報で書いたのか、アプリ経由か」を見て信頼を
判断できる。

許可されていない呼び出し元がヘッダを送ったら **403 を返す。無視しない。**
黙って呼び出し元自身として記録すると、アプリは自分が利用者名義で書けている
と信じたまま動き続け、数か月後に全エントリが SA 名義だったと気づく。
**静かな降格は、明示的な失敗より常に高くつく。**

バンドルが運ぶ自称 provenance は、これとは別物として拒否したままである
([0009](0009-provenance-portability.md))。委譲が認められるのは、**誰の
主張かを Google が検証した呼び出し元が居る**からである。

## 4. producer: 名乗りは actor の隣に置く

「どのソフトウェアが書いたか」は「誰が書いたか」の代替ではなく、同時に真な
二つ目の事実である。`Actor` は四つ目のフィールド `producer` を持つ。

```json
{"kind": "human", "name": "tanaka@example.co.jp",
 "via": "process:app@example.iam.gserviceaccount.com",
 "producer": "insightflow/1.4.0"}
```

**隣に置くことが、自称を認めてよい条件そのものである。** 認証済みの名前の
*代わり*に置けば、誰が書いたかは誰でも名乗れる文字列になる。隣に置く限り、
その主張は「Google が検証した呼び出し元がそう言った」という形でしか記録
されない。§3 の合成規則の二度目の適用であり、新しい原則ではない。

形は SPEC §7 の `<producer>/<version>` — スラッシュちょうど一つ、両側非空、
空白・制御文字なし、**コロン禁止**(SPEC §7 は三つの形をまさにその文字で
見分けるので、コロンを含む producer は identity に見える)、128 バイト以内。
版の綴りは検査しない — semver を強いれば git sha を記録できなくなり、
**文法を発明すれば正直な書き手だけが記録不能になる**。不正な値は
**400 で拒否する。黙って落とさない。**

出所はサーフェスごとに決まる([0015](0015-surface-consistency.md))。REST は
`Ochakai-Producer` で、契約はここだけ。MCP は同じヘッダ、無ければ
initialize の `clientInfo` を**フォールバックとして**読む(上書きではない
— ヘッダは「この呼び出しで何を動かしているか」を、`clientInfo` は「誰が
セッションを開いたか」を言う。SPEC §7 の形に収まらない `clientInfo` は
落とす)。CLI は `OCHAKAI_PRODUCER` を同じヘッダに載せ、`whoami` が申告値を
出す。**Web UI には出さない** — 人が自分で書く編集面には名乗るソフトウェア
が無い。解決は委譲の後に行う。

**allowlist は持たない。** 委譲が allowlist を要るのは*他人の* identity を
名乗る行為だからで、producer が名乗るのは呼び出し元自身のビルドであり、
その呼び出し元は同じ actor の中に認証済みで記録されている — 詐称する相手が
居ない。

記録先は actor が `via` を持つ場所すべて。書き込み専用で 180 日で刈られる
テレメトリ(`knowledge_event`・`search_miss`)には足さない — 読まれない列は
何も記録しない。ファイルの行は actor を kind + name だけで持ち(`via` も
持たない)、ファイル書き込みの producer はリビジョン台帳の側に残る。
バックフィルはしない(埋めるべき値が存在しない)。
インポートは読み戻さない — 他インスタンスのバンドルが運ぶ producer は、
裏づける認証を持たない自称そのものである。

## 5. identity を差し替える者は、identity の自称を運んではならない

`ochakai ui` と `ochakai serve-ui` の二つのプロキシに共通する役割は
「**呼び出し元が誰であるかを、上流に対して言い直す**」ことである。その役割を
持つコンポーネントが、言い直す対象であるはずの自称を横に添えて渡すのは、
役割の裏切りである。**削るのが既定であり、載せるのは例外である。**

1. ブラウザから来た `Ochakai-On-Behalf-Of` は、両プロキシとも**常に捨てる**。
2. `OCHAKAI_IAP_AUDIENCE` が設定されているとき、`serve-ui` は IAP の署名付き
   アサーション(`X-Goog-IAP-JWT-Assertion`)を検証し、その `email` クレーム
   からヘッダを**作り直す**。検証は既存の依存
   `google.golang.org/api/idtoken` で行い、**`iss` は自分で確認する**
   (idtoken は issuer を見ない)。audience は運用者が与える — 推測した
   既定値は「検証しているつもりで検証していない」という最悪の状態を作る。
3. audience が設定されているのに検証できないリクエストは **403** で拒否する。
   SA 名義へ黙って落とすのは §3 が拒否した静かな降格そのものであり、IAP が
   実際には前に立っていない構成を運用者が気づける形にもする。

audience 未設定なら削るだけで作らず、書き込みは SA 名義になる。起動ログが
どちらのモードかを言う。`ochakai ui` は 1 だけを行う — 作り直す材料が無い。

サーバー側(`serve`)は何も変わらない。これは**プロキシがそのヘッダに何を
入れるか**だけの決定であり、信頼モデルは一行も動かない。

## 6. 委譲も producer も、認可ではない

- **委譲**が決めるのは「誰の identity 主張を記録するか」であって「誰が何を
  してよいか」ではない。設定を空にしても誰の権限も増減せず、記録される名前が
  変わるだけである。
- **producer** で読み書きを制限せず、ランキングも変えない。SPEC §5.3 の
  trust tier は検証台帳の `human:` だけから導かれる。producer は**記録**で
  あり、判断は参照側が provenance を見て行う(§1)。

producer 別の集計面は作らない。それは
[0051](0051-instance-metrics-and-search-misses.md) が引いた `stats` 側の
問いであり、**記録が先、集計が後**という順序は「その場で記録しなかったものは
消える」という非可逆性から来ている。

## 7. やらないこと

- **認可**(role / スコープ / エントリ単位 / 呼び出し元単位)。要るなら
  Cloud Run IAM で到達を分ける。
- **委譲された identity のドメイン検証。** 呼び出し元を信頼して委譲を許した
  以上、その先の値まで疑うのは一貫しない。
- **producer ごとの allowlist**(§4)、**User-Agent からの推測**(HTTP
  スタックが書き換える値であり、推測した provenance は provenance ではない)、
  **サーバによる版の検査**(§4)。要るようになれば §3 と同じ形で後から足せる。
- **actor の位置に `<producer>/<version>` を入れること。** 認証済みの名前を
  自称で置き換えることになり(§4)、委譲と同時に起きると席が足りず、
  どの位置が認証済みか読み手に分からない `via` の連鎖を作る。
