# ochakai 設計ドキュメント 0132: ディレクトリは、丸ごと動くか、動かない

Status: Accepted(2026-08-27)。[0075](0075-the-bundle-is-the-address-space.md)
§2 の「パスが住所であり、move はその住所を動かす」に**ディレクトリの形**を
足す。[0129](0129-a-move-runs-when-its-rewrite-fits.md) の「はみ出すなら
丸ごと断る」を prefix の粒で読み直したものであり、どちらも Superseded に
しない — 0129 が決めたのは**誰が動かせるか**で、ここで決めるのは**何を
動かせるか**である。
Date: 2026-08-27

## 1. 問題: クライアントには書けないループ

ディレクトリの名前を変えたい、という声が現場から時々上がる。今日の答えは
`move` を一件ずつ回すシェルループで、`ochakai list --prefix` が素の列挙に
なった今は二行で書ける。

```sh
ochakai list --prefix old --json | jq -r '.hits[].id' \
  | while read -r id; do ochakai move "$id" "new/${id#old/}"; done
```

**このループは不便なのではなく、原理的に不完全である。** 一覧が立てる
述語がこれだからで([internal/store/filter.go](../../internal/store/filter.go))、

```sql
deleted_at IS NULL AND id IS NOT NULL
```

クライアントからは次の三つが**見えない**。

| 取り残されるもの | 見えない理由 | ディレクトリに残るもの |
|---|---|---|
| prefix の下にあって、動かした concept の名前空間の下ではないファイル | ファイルは `id` を持たない | `old/diagram.png` は `old/` に残る。`old/a/fig.png` は concept `old/a` に付いて動く(0075 §4、既存の move が既に運ぶ) |
| 却下された concept | 一覧の既定が hide。`--rejected` は却下分だけを返すので二周要る | 墓石が古い住所を握ったまま |
| 論理削除された concept | `deleted_at IS NULL` で落ちる。さらに `move` 自身が `deleted_at IS NULL` を条件に書くので、**一件ずつでも動かせない** | 同上。後で `old/` に import すると衝突する |

**ディレクトリの全体を見られるのはサーバーだけである。** どれだけ丁寧に
書いたクライアントも、自分に見えないものを動かすことはできない。これが
「あると便利」と「クライアントには書けない」を分ける線で、この記録が越え
ているのはその線である。C4(必要な操作には自分で打てるコマンドがある)。

`export --prefix` して書き換えて `import` し直す迂回路は答えにならない。
来歴・リビジョン・利用実績を運ばないからで、それは
[0009](0009-provenance-portability.md) が意図してそう決めた往復である。

## 2. 決定: prefix を動かす形を `move` に足す

**`POST /api/v1/move` は `from_prefix` / `to_prefix` を取る。** `from` /
`to` と排他で、両方送れば 400 である([0125](0125-a-body-names-each-field-once.md)
の完全一致の下で、鍵の組が形そのものを言う)。

**動くのは prefix の下にある全オブジェクトで、一つのトランザクションで
動く。** live な concept、却下された concept、論理削除された concept、
そして prefix の下のすべてのファイル。一件の move が運ぶもの — リビジョン、
検証と却下の台帳、利用実績、イベント、埋め込み、そして内向き参照の
書き換え — は、そのまま全件について運ばれる。

**論理削除された concept を連れて行くのは、住所を握っているからである。**
置いていけば `old/` は空にならず、そこへ import した誰かが、見えない行と
衝突する。丸ごと動くとは、住所空間が丸ごと空くことである。

## 3. 推測しない: concept とディレクトリは同じ名前を持てる

なぜ `move old new` が「`old` が concept ならそれを、ディレクトリなら
その下を」と振る舞わないのか。**0075 §2 が両立を許しているからである**:

> **concept とディレクトリが同じ名前を持つこと**(`metrics/revenue.md` と
> `metrics/revenue/`)は許す。

`metrics/revenue` と打たれたとき、サーバーには**どちらの意図か決める根拠が
無い**。推測すれば、ある日、隣の 40 件を巻き込んで一件だけ動かすつもりの
呼び出しが通る。だから鍵で言わせる。`ochakai move --directory` の
`--directory` も同じ一語で、糖衣ではなく曖昧さを断つ語である
(`FLAG` は 28 → 29。**天井を上げる決定**であり、そう言って上げている)。

末尾スラッシュに意味を持たせる案は採らない。`normalizePrefix` が今日
`old/` と `old` を同じものに正規化しており(`browse`・`--prefix` の全部が
そう振る舞う)、`move` だけがスラッシュを読むのは、一つの綴りが場所に
よって別のことを意味する規則になる。

## 4. 範囲(0129)は、爆風の全体について読む

0129 §2 はこう決めた。

> 書き換えが触れるものすべてが、呼び出し元の書ける範囲にあるとき move は
> 動く。（…）**はみ出すなら丸ごと断る。絞らない。**

**prefix の粒でも同じ文がそのまま効く。** 触れるものは三つとも同じで、
数が増えるだけである: 動かす全 concept、移動先の全住所、そして**その
どれかを指している live な concept すべて**。一件でもはみ出せば、move は
丸ごと断られる。半分動いたディレクトリは、断られたディレクトリより悪い —
0129 §2 の一行を、そのまま一段上で読んだものである。

判定は 0129 §3 のまま、書き換えと同じトランザクションの中で行う。

## 5. 内側のリンクは move の一部であって、update ではない

ディレクトリとは、互いを参照し合うものを一つの場所に置いたものである
(0129 §1)。だから prefix を動かすと、**書き換えの大半はディレクトリの
内側で閉じる**。

一件の move は、動かした concept 自身の本文の書き換えを「move の一部で
あって別の変更ではない」として扱い、`update` リビジョンを積まない
(`rewriteReferences` の既定)。**同じ規則を、一緒に動いた兄弟にも当てる**:
prefix の中の concept が prefix の中の concept を指していたなら、その
リンクは動いた住所に追随しただけであり、記録は各 concept の `move`
リビジョン一本である。

**外から中を指していた concept は、今日どおり `update` リビジョンを受ける。**
そちらは動いていないのに本文が変わったので、変更である。

この区別を置かないと、100 件の相互参照するディレクトリを動かしただけで
リビジョンが二乗で積まれ、履歴が読めなくなる。

## 6. 断るもの

- **移動先に何かが在るなら、丸ごと断る。** 一件の move が「移動先は空で
  なければならない」と言うのと同じ規則で、論理削除された行も住所を握って
  いる以上「在る」に数える(0075 §2、既存の move の判定)。
- **根は動かせない。** 空の prefix はバンドル全体であり、それを動かすのは
  改名ではなく export と import である(C1・0009)。
- **自分の下へは動かせない。** `old` → `old/sub` は、動かしている最中の
  住所空間の中に移動先がある。
- **prefix の下に一件も無ければ 404。** 無いディレクトリの改名は、成功と
  区別が付かない no-op であってはならない。

## 7. 面([0067](0067-four-faces-and-what-they-decline.md))

| 面 | 現れ方 |
|---|---|
| REST | `POST /api/v1/move` のまま。**操作は増えない**(REST 13)。本文に `from_prefix` / `to_prefix`。凍結は掛かっていない(0107 — 凍るのは bundle の往復と search) |
| CLI | `ochakai move --directory <old> <new>`。**コマンドは増えない**(CLI 25)。`FLAG` が 28 → 29 |
| MCP | **載せない**(0067 §5.1、0129 §5 と同じ理由)。move は curation の操作であって、エージェントのループが一回で要るものではない |
| Web UI | ツリーのディレクトリノードが掴めるようになる。**API は増えない** — concept の drag & drop が叩いている同じエンドポイントに、ディレクトリの形で送る |

## 8. 検査する不変条件([0035](0035-verifiability.md))

- prefix の下の live・却下・論理削除の concept と、名前空間の下に無い
  ファイルまでが、一回の呼び出しで新しい住所に在ること。
- 断られた move が**一つも動かしていない**こと — 移動先の衝突、範囲外の
  参照元、根、自分の下、のそれぞれについて。
- 内側で閉じたリンクが書き換わっており、動いた concept に `update`
  リビジョンが積まれていないこと。外から指していた concept には積まれて
  いること。
- `old/` に一件も残らず、そこへの import が衝突しないこと。
- `from` と `from_prefix` を同時に送れば 400 であること。

## 9. 採らなかった案

- **一件ずつの move をサーバー側で回すこと**(トランザクションを分ける)。
  §4 の「半分動いたディレクトリ」がそのまま起きる。一つのトランザクション
  であることが、この操作が在る理由の半分である。
- **件数の上限を置くこと。** 大きなディレクトリは大きなトランザクションに
  なり、ロックの占有と statement timeout は本物の心配である。それでも
  **測っていない数を宣言しない**: timeout で丸ごと巻き戻るのは、この記録が
  約束したとおりの振る舞いである。上限を置くのは、実際に詰まった人が出て、
  その人の件数が分かってからでよい。
- **`--prefix` という綴りを CLI で使うこと。** `search` と `list` の
  `--prefix` は**絞り込み**であって操作の対象ではない。同じ語を、片方では
  フィルタ、片方では動かす当のものにするのは、`usage` が二つの命令を名乗って
  いる問題を新しく一つ作ることである。
- **ディレクトリを concept にすること**(`index.md` を実体化して動かす)。
  導出面を実体にすることであり、0075 §4.2 が予約した住所の意味が変わる。
- **却下と論理削除を置いていくこと。** 見えないものが古い住所を握り続け、
  ディレクトリは「丸ごと動いた」ように見えて空いていない。§1 の三つ目の
  盲点を、サーバー側で再現することになる。
