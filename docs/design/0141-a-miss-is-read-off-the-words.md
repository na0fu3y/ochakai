## 0. この記録が決めたこと

1. **ミスは、どの concept の言葉にも一致しなかった検索である**(§4)。
   0069 §4 は「ヒット 0 の検索」と定義していた。ベクトルの一覧には距離の
   床が無く、最も近い N 件をどんな距離でも返すので、**埋め込むデプロイ
   では空でないベースに対して 0 件が起こらない** — Google Cloud の既定の
   構成で、ループが最も価値のある信号と呼んだものが記録されていなかった。
   数えるのは lexical の一覧が空だったかどうかで、呼び出し元が受け取る
   順位は一件も変わらない。
2. **五冊を一冊に畳む。** 0128 §2.2 のとおり、リリース済みの親の文面と
   矛盾する改訂は差分ではなく領域の全体で書く。0069 の上に四冊が積まれて
   いたので、早見表の一行はここを指すだけになる。

論証の全文 — 生涯累積の並びが壊れていた経緯、90 日と 8 週の根拠、
note が二か月書き込み専用だった経緯、tier の失効を減点にしなかった実測 —
は各記録の墓標が指すコミットに残る。以下は決定だけを書く。

## 1. ループは三つの部品で締まる

中核仮説は「エージェントが下書きし、人が検証する」双方向ループである
([0081](0081-what-ochakai-is-and-what-it-refuses-to-hold.md) §1)。
締まるには、**利用が測られていること**、**検証が時効を持ち古くなると
浮上すること**、**再検証が証拠で優先され、人が回すワークフローの中で
拾われること**の三つが要る。時間にもとづく陳腐化(`verified_at` の古さ、
書き手が宣言した `stale_after`)に、証拠にもとづく陳腐化(失敗報告)を
足す — 後者が無いと、golden query で誤った数字を得たエージェントが
報告しても、次のエージェントは同じ concept を同じ信頼度で引く。

## 2. 四つのキューと、キューではない一つのフィード

| キュー | 一覧 | 空になる条件 |
|---|---|---|
| `drafts` | `ochakai list usage --status draft` | 公開する編集 / 削除(却下を含む) |
| `failed` | `ochakai list failed` | 最後の失敗報告より後の verify |
| `stale_after` | `ochakai list stale_after` | 書き手が期限を宣言し直す編集 |
| `edited` | `ochakai list verified_at --trust unverified` | verify / 削除 |

**四本とも空にできる。** 空にできないキューは読まれなくなる。
`sort=verified_at` はランキングであってキューではなく、数えない — 件数は
ベースの大きさそのもので、誰にも 0 にできない。

### 2.1 `failed` — 証拠にもとづく再検証

対象は `failed > 0` かつ未処理(`verified_at IS NULL` または
`last_failed_at > verified_at`)。**在否が「未処理か」を、並びが
「どれだけ悪かったか」を表す。** 未検証の draft は最後に並ぶ — 認証済み
concept の失敗のほうが緊急である。

### 2.2 `stale_after` — 宣言した期限は、verify では空にならない

期限が今日以前の concept を超過の大きい順に返す。「今日」は UTC で明示的に
綴る。**verify では動かない** — 書き手の宣言をサーバーが書き換えることに
なる。解消は再確認して期限を引き直す編集で、何日延ばすかをサーバーは
知らないし知るべきでもない。

### 2.3 引用元からの逆引き

`source` は `sources[].resource` の**完全一致**のフィルタで、フィードでは
ない。クエリとも `sort` とも組み合わせられ、単独なら住所順の一覧になる。
`sources[].id` は文書内のキーなので引かない。前方一致・部分一致はしない。

### 2.4 `edited` — 検証は、内容が動くまで立っている

**trust tier は「立っている検証」から導く**(0065 §6 を改訂する)。立って
いるとは、台帳の行の `at` が concept の `generated.at`(内部では
`content_changed_at`、最後の意味のある変更)以降であること。編集と move
は失効させ、整形だけの書き込みは失効させない。move が失効させるのは
[0036](0036-okf-schema-first.md) §3.3 が move で `generated.by` を付け替える
からで、move を跨ぐ機構は tier をバンドルから再計算できなくするので
採らない。verify は `GREATEST(now(), content_changed_at)` で記録する。

- **検索順位に減点は入れない。** 失効で消えるのは tier から読む 1 順位
  ぶんの加点の根拠だけである。誤りと報告された concept ですら順位に
  混ぜない(§7)。
- `verified_at` は台帳の最新行のまま、failed の述語と MCP の裁定ガードは
  台帳の在否のまま、export は全行を書き、台帳は一行も消えない。
- `edited` は台帳に行があり立っている行が無い concept で、単一の sort
  ではないので自分の語を持つ(§5.2)。MCP には出さない。

### 2.5 並びは直近 90 日で決まる

`sort=usage` と `sort=failed` は**直近 90 日の数**で並び、生涯累積は同点を
割る。窓は数と一緒に `usage.recent`(`days` / `fetches` / `failed`)として
ワイヤに出る — 期間の暗黙な数は読者が検算できない。窓は**定数**で、
生イベントの保持(180 日)の内側にある。`knowledge_event` を数え直して得、
減衰する列も定期実行も持たない。`search_hits` と `worked` には窓を掛けない。

## 3. 利用測定は読み取りパスに触れない

利用イベント(`search_hit` / `fetched`)はメモリにバッファし、背景ループが
5 秒ごとにフラッシュする。**利用測定は best-effort である** — 失われては
いけないのはナレッジ本体であって端数ではない。バッファ上限は 20,000 件で
超過分は捨て、捨てたことは返りログに残る。`Close` はドレインしてから
終わり、HTTP サーバーのドレインの後に store を閉じる。

**`report_outcome` は含めない。** 結果報告は意図的な書き込みで、同期的に
書き、失敗は面に返る。生行は **180 日で刈り**、running total は残る。
180 に導出は無い — 半年という人が言える単位で、下流(90 日の窓、`stats` の
`days` の上限)はすべてここから導かれている。

### 3.1 報告は、何を見たかを言う

`GET /api/v1/usage/{id}` は、note を持つ結果報告を**新しい順に最大 10 件**、
worked と failed の両方、`reports` として返す。報告者は kind + name で出る
(`via` と `producer` は `knowledge_event` に無い)。件数は `worked` / `failed`
の側で、行数とは一致しない — 面がそう言う。180 日より古い note は無く、
面がそれも言う。REST・CLI・Web UI の詳細ページに載り、一覧のカードにも
MCP にも載らない。note の絞り込み・報告者での逆引き・編集・検索への索引は
しない。

## 4. 答えられなかった問いも記録する

**ミスとは、どの concept の言葉にも一致しなかった検索である** — lexical の
一覧(id・title・description・tags・本文・`synonyms`・名前空間内の
ファイル名、[0080](0080-search-and-how-a-deployment-embeds.md) と
[0105](0105-a-concept-answers-to-its-other-names.md))が空だったこと。
キュレーションされたベースにとって、*誰かが求めて無かったもの*は次に何を
書くべきかを教える唯一のリストである。

### 4.1 なぜ答えの件数ではないか

0069 は「0 件はモードに依存しない」を理由に件数で定義した。**前提が
違っていた。** 埋め込むデプロイでは lexical・ベクトル・ファイルの三つの
一覧を融合し([0080](0080-search-and-how-a-deployment-embeds.md) §1)、
ベクトルの二つは最も近い N 件を距離によらず返す。だから件数が 0 になるのは
ベースが空か、絞り込みが全部を落としたときだけで、**0 件は埋め込むか
どうかに依存していた** — 埋め込まないデプロイでだけ意味のある数だった。
Google Cloud の既定([0053](0053-embeddings-by-default.md))がその反対側で
ある。テストは件数で書かれており、埋め込まない service で走っていたので、
誰も気づかなかった。

lexical の一覧は**どちらのデプロイでも同じ計算**で、埋め込むデプロイの
融合の一本目でもある。「言葉の一致が無かった」は、0069 が件数に求めた
性質 — モードに依存しない — を実際に持つ。

### 4.2 何を差し出しているか

**意味では答えられたが言葉では一致しなかった問いが、ミスに入る。**
「売上」で訊かれて `revenue` の concept がベクトルで一位に来ても、
その concept が「売上」という語をどこにも持たなければミスとして数える。
これは誤検出ではなく、この一覧の使い道に合っている: gap 行は人が 10 件
読むリストで、そこに並ぶのは**書き足すべき concept か、既にある concept に
足すべき語**のどちらかである。後者の直し方は `synonyms` で、lexical 側は
日本語の二文字語を引く側でもある([0080](0080-search-and-how-a-deployment-embeds.md)
§1、条件 C8)。どちらかを見分けるのは読む人である(「最初のひと月」§3)。

### 4.3 動かないもの

- 記録はサービス層の検索一か所で、どの面から来た問いも数える。フィード
  (クエリの無い一覧)は数えない。**呼び出し元に返る順位は一件も変わらない。**
- 打たれたそのままの文字列を先頭 500 バイトまで保存し、保持は 180 日で、
  累計を持たない。provenance は利用イベントと同じで、面は actor を返さない。
- `OCHAKAI_RECORD_MISSES=false` で止まる(既定 on)。公開デプロイは記録せず、
  read-only は記録する。範囲を持つ呼び出し元には `misses` を差し控える
  ([0123](0123-the-numbers-say-what-they-counted.md))。
- **スコア閾値は採らない。** スコアはモードごとに較正されておらず
  ([0068](0068-how-a-face-is-added-and-removed.md) §3)、床を置くなら
  埋め込みモデルごとに較正し直すことになる。

## 5. インスタンスを一回で答える — `GET /api/v1/stats`

窓 `days`(既定 30、上限 180、超えは 400 — 足りない答えを黙って返すより
答えないほうがよい)を取り、ループの数を**いまの姿**と**窓の中で起きた
こと**に分けて返す。

| いまの姿(state) | 窓の中(flow) |
|---|---|
| `concepts.total` / `.status` / `.trust` | `concepts.created` |
| `queues.drafts` / `.failed` / `.stale_after` / `.edited` | `review.verifications` / `review.weekly` |
| `misses.recording` | `outcomes.worked` / `.failed` / `misses.count` / `.queries` |

- **キューの述語はフィード自身のものを共有する。** 開いたら件数が違う
  キューは、件数が無いより悪い。
- `status` と `trust` は語彙の全値を 0 込みで返す。
- `review.verifications` は台帳の行を数える — 深さは残量であって通過量では
  ない。
- `misses.recording` が false のとき、`count` と `queries` は 0 ではなく
  無意味である(CLI は `-`)。`queries` は最大 10 件。
- **ロールアップを持たない。** すべてオンデマンドで計算する。

### 5.1 `prefix` は、ミス以外のすべてを絞る

エントリに紐づく数はすべて絞られ、outcome は台帳の id で絞る。
**`misses` は絞れない** — どの concept の言葉にも一致しなかった問いには、
それが属する id が無い。

### 5.2 キューは、それを一覧する sort の名で呼ぶ

`failed` と `stale_after` は sort の名で、既にある語を使い回している。
単一の sort ではない `drafts` と `edited` だけが自分の名前を持つ —
**規則が当てはまらない一件を、規則の形に合わせて曲げない。**
`docs/surface.md` の VOCAB は sort 名を着たキューを数えず、自分の名を
持つキューを数える。

### 5.3 レビューの形 — `review.weekly`

**キューの深さの履歴はどこにも記録されていない**ので、ループの形は
フローの側、検証の台帳から数える。今日から遡る 7 日ずつ 8 本、古い順。
定数であって設定ではなく、`days` に従わない。誰も検証していないベースには
出さず、一件も無い週は 0 として並ぶ。Web UI はレビューページに軸も目盛りも
無い SVG を一枚だけ持ち、MCP には出さない。

## 6. 押すのは数であって、通知ではない

ochakai は LLM もスケジューラも secret も持たないので、人に届ける機構を
製品の中に作る道は閉じている。`ochakai stats --exit-code` はどれか一本でも
キューが空でない間 **2** で終了し(1 は「コマンドが失敗した」)、届けるのは
運用者の cron / CI である。`stats` の各行は次に打つコマンドを持ち、キーと数は
第一・第二フィールドのままである。

## 7. やらないこと

- **自動 demote と status ゲート、順位への減点。** failed も期限切れも
  失効も、フィードで浮上させるだけで順位には混ぜない。
- **配送とスケジューラ、閾値と抑制、時系列 API、キューの深さの時系列。**
- **窓・形の長さを設定可能にすること**、減衰する列、半減期。
- **`sort=gaps` というフィード。** 問いはナレッジではない。
- **ミスの検索・エクスポート・per-actor の内訳、報告者での逆引き。**
  キュレーションの道具ではなく監視の道具になる。
- **ミスからの自動生成・クラスタリング・言い換えの名寄せ。** どれも LLM を
  要求する。
- **ミスに下限つきのベクトル距離を使うこと**(§4.3)、および**検索の後に
  何も fetch されなかったことをミスとすること** — 検索と fetch は別の
  呼び出しで、MCP は stateless である
  ([0118](0118-a-call-carries-everything-it-needs.md))。二つを結ぶには
  呼び出しをまたぐ状態が要る。
- **二つの数を並べること**(件数 0 と言葉の不一致)。同じ問いに二つの
  答えがあれば、どちらを読むかを読み手が決めることになる。

## 8. 互換性

ワイヤの形は 1 バイトも動かない。**埋め込むデプロイでは `misses.count` と
`misses.queries` が埋まり始める** — それがこの記録の目的である。埋め込まない
デプロイでは lexical の一覧が答えそのものなので、数は変わらない。
移行も環境変数も無い。過去の窓に遡っては埋まらない。
