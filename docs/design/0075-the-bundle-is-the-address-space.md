## 1. バンドルが主概念であり、concept はその中の一種類のオブジェクトである

**ochakai が保持するのは、一つのバンドル — パスからオブジェクトへの写像で
ある。** オブジェクトは二種類しかない。

| | 何か | どこに置くか |
|---|---|---|
| **concept** | `type` を持つ frontmatter のある `.md` | 文書のバイト列(DB) |
| **ファイル** | それ以外のすべて | markdown は DB、非 markdown は GCS |

**バンドルに入ったものは出てくる。** これが中心的な不変条件である。
`type` を持たない `.md` も、どの concept からも参照されない `.txt` も、
ファイルとして保存され往復する。取り込みが `skipped` に落としてよいのは
**バンドルパスとして不正なもの**(文字種違反、`..` の脱出、隠しパス)と、
導出面である `index.md` / `log.md` だけである。

かつては三種に割っており、三番目は**取り込みで消えていた** — エクスポート
したバンドルを取り込み直すとファイルが減った。`skipped` の行の意味は
「取り込めなかった」から「concept として索引しなかった」に変わった。

**添付(attachment)という概念は対象消滅している。**「このファイルはどの
concept のものか」は、リンクと同じく**本文からの導出**である(§5)。
`attach` / `detach` という操作も消え、ファイルを置くことは `PUT`、外すことは
`DELETE` である。

- **上限は一オブジェクト 5 MiB**、concept 本文は 4 MiB。「一 concept に
  20 ファイル」という上限は、帰属が導出になった時点で意味を失ったので廃した。
- **GCS が未設定なら非 markdown の書き込みは 501。** markdown だけの知識
  ベースとして動く姿勢は変わらない。
- **メディアタイプはバイト列の sniff で決める**(クライアントの申告は
  信じない)。ただし**拒否はしない** — 拒否するとバンドルが往復しない。
  SVG と HTML を書き込みで拒んでいた理由(Web UI への script 混入)は
  **配信側で解く**: 画像・PDF・プレーンテキスト以外は
  `Content-Disposition: attachment` と `nosniff` と `sandbox` を付けて返し、
  `text/html` と `image/svg+xml` はインラインで配信しない。
  **受けるが描画しない。**

## 2. パスが住所であり、型は属性である

concept の id は**バンドル・ルートからのフルパスから `.md` を除いたもの**で
ある(SPEC §2)。第一セグメントに意味は無く、ルート直下の一セグメント id も
正規である。同じパスに二つの concept は存在できない — ファイルシステムと
同じである。

**型は「それが何であるか」であり、「それがどこにあるか」ではない。** 何で
あるかは frontmatter が言い、どこにあるかはパスが言う。**両者は直交する。**

- **配置は利用者のものである。** 型先頭(`metrics/sales/...`)もドメイン
  先頭(`sales/orders.md` に `type: Metric`)も一級で、サーバーはどちらも
  強制しない。**パスから型を推測する規則は持たない。**
- **推奨するのは語彙まで、配置には原則だけ。** 示すのは一行
  ——「LLM に一緒に読ませたいものを同じディレクトリに置く」。
- **tar に入れた形がそのまま構造である。** アーカイブの自動アンラップは
  持たない。`tar czf ga4.tgz ga4/` は `ga4/` 配下に取り込まれ、**バンドル =
  名前空間ディレクトリ**が既定の、そして唯一の動作である。見たままが構造で、
  通知も抑止フラグも要らない。
- **末尾セグメント `index` と `log` は予約する。** 導出面(§4.2)の住所で
  あり、構文的に塞いでおかないと export で出て import で黙って消える。
- **複数バンドルは持たない。** 一デプロイ = 一バンドルであり、名前空間は
  ディレクトリである。

**concept とディレクトリが同じ名前を持つこと**(`metrics/revenue.md` と
`metrics/revenue/`)は許す。ファイルシステム上も別であり、`index.md` が
節見出しで両者を区別する。

## 3. サーバーは、受け取った文書を書き換えない

**書き込みで保存するのは、受け取ったバイト列そのものである。** 正準形は
保存形ではなく**導出値**になり、内容が変わったかの判定と索引にだけ使う。

同じ原則が語彙にも及ぶ — 書き手の書いた `type` の case を直さず、書き手が
書かなかった `status` を書かない。SPEC §5.4 は不在の既定を `stable` と
定めており、**既定を適用するのは読み手であって保存側ではない**。

保存の前に施す正規化は二つだけである: **CRLF → LF** と **末尾に改行一つ**。

### 3.1 主張と観測を分ける

例外が一つある。**サーバー所有キー**(`generated` / `verified` /
`created_by` / `rejected_*`)は受け取った位置に置いておけない — エクスポート
で**このインスタンスの観測**を同じ名前で書き戻すのに、YAML はトップレベルの
重複キーを許さないからである。だから書き込みで**行単位に外科的に取り除き**、
エクスポートで書き戻す。再シリアライズではなく行の削除・追記なので、他の
キーもコメントも順序も動かない。

**取り除くことは、捨てることではない。** 文書が自分について書いた trust
family は、`received:` の下に**主張(claim)として残す**。

- **台帳は「このインスタンスが観測したこと」だけを意味し、主張はどの台帳にも
  入らない。** trust tier も `trust=` も、主張からは導かない。
- **入れ子が両者を一つのファイルに同居させる。** `verified` は常にこの
  インスタンスの台帳、`received.verified` は常に他者の主張である。
- **捨てた主張は、後のどのリリースでも復元できない。** 移行と共有で失われる
  のは、**他人が誰の何をいつ確かめたか**という復元不能な事実である。
- **自分のエクスポート形は主張ではない。** 添えられた trust family が
  このインスタンスの観測と一致すれば、それは戻ってきた自分の観測であり、
  書き込み経路が取り除く。これが get → 編集 → PUT と
  export → レビュー → import が**前と同じバイト列を保存する**条件である。
- **黙って落とさない。** 主張として受け取ったことは取り込みの note に出る。

### 3.2 版は保存バイト列のハッシュ、意味の変更は正準形で判定する

**ETag = 保存されたバイト列の SHA-256。** 一方
`content_changed_at` と `generated.at` を進めるかの判定は**正準形の一致**で
行う。整形だけの編集は ETag を動かす(ファイルは実際に変わった)が、
`generated.at` は動かさない — SPEC §5.2 の "last meaningful change" は内容の
変更である。**版と意味の変更を別の値にできる**のがこの分離の効果である。

裁定はオブジェクトに触れないので ETag を動かさない。ファイルの追加・削除も、
concept のバイト列を動かさないので同じである。

### 3.3 概念かどうかの判定に失敗しても、書き込みは通る

`type` の無い `.md` を PUT すると、それはファイルとして保存される(400 に
しない)。SPEC §11 の「consumer は拒否してはならない」を書き込み面にも
広げる — ただし `text/markdown` で PUT したものが concept にならなかった
ときは、応答に note を返す。**黙って読み替えない。**

## 4. 一つのアドレス空間

**`GET|PUT|DELETE /api/v1/bundle/{path...}`** が唯一の住所である。
`/api/v1/knowledge`・`/browse`・`/revisions/{id}`・`/backlinks/{id}`・
`/attachments/{path}`・`/export` は対象消滅した。REST の現在の一覧と表現の
優先順位は 0064 が持ち、面の配分は
[0067](0067-four-faces-and-what-they-decline.md) が持つ。

- **表現は `Accept` が決める。** 一つの住所の複数の表現であって、第二の
  サーフェスではない。
- **ディレクトリに `Accept: application/gzip` は部分木の tar.gz** である。
  ルートなら全体 — これが `export` の後身であり、**`prefix` は URL そのもの
  になる**。
- **`?history` はそのオブジェクトの履歴**である。**concept かファイルかは、
  パスの綴りではなくその住所に何が入っているかで決まる** — type を持たない
  `.md` はファイルなので、`.md` で終わることを理由に concept の台帳だけを
  引くと、markdown が答える住所で JSON が 404 を返す。**一つの住所の二つの
  表現は同じことを言う。**
- **書き込みで concept かファイルかを決めるのは frontmatter の `type` キー**
  であって `Content-Type` ではない。
- **削除は `DELETE`(ソフト削除)、`?purge=true` で不可逆な破棄**
  ([0031](0031-purge.md))。

### 4.1 trust tier は SPEC §5.3 の三段

投影は `verified: bool` ではなく
**`trust: unverified | machine-confirmed | human-reviewed`** を出す。検証
台帳から導く — `human:` の行があれば human-reviewed、行があれば
machine-confirmed、無ければ unverified。検索フィルタは `trust=` である。

### 4.2 予約ファイルは導出面である

`index.md`(SPEC §8)と `log.md`(SPEC §9)は、ochakai が既に持っている
情報の **OKF が定めた表現**である。別のアドレスと別の形を発明する理由がない。

- **`index.md`** の節は「サブディレクトリ」「概念」「ファイル」。ルートの
  それだけが `okf_version` を frontmatter に持つ。一階層 1000 件の打ち切りは
  **注記の行として文書に出す**。**利用を記録しない** — ツリーを歩くことは
  需要の信号ではない。
- **`log.md`** は新しい順に日付でまとめ、一行一リビジョン。**リンクはその
  `log.md` が置かれたディレクトリからの相対**である — ルート絶対だと、
  アーカイブを展開した先でファイルシステムの根を指し、同じディレクトリに
  置かれた二つの生成物が「バンドルのパス」の意味で食い違う。
- **取り込みは読み戻さない。** 他インスタンスの履歴を自分の台帳に入れる
  ことは、provenance を読み戻さないのと同じ理由で誤りである。purge で消えた
  履歴は出てこない — **台帳が唯一の出所である。**
- **予約ファイルの住所を「そこにあるオブジェクト」以外として読む面は、
  すべて 409 である。** 書き込みだけの規則ではない — `application/gzip` は
  パスを部分木として読み、`?history` はオブジェクトの出来事として読むが、
  生成されるファイルはどちらでもない。ファイル自体を読むのは 200 で、
  生成するのはそのためである。

## 5. 帰属は導出し、move は名前空間ごと動かす

「この concept のファイル」は、リンクと同じ導出関係である — その concept の
本文が指すバンドル内の非 concept パスと、`<id>/` 名前空間の直下にある
**concept でない**オブジェクトである。

「concept でない」という限定は必要だった。SPEC §2 は
`metrics/revenue/breakdown.md` に concept id を与え、§11 は非予約 `.md` が
type を持つことを要求する。つまり**ディレクトリ下の `.md` は誰かの根拠では
なく、住所と履歴を自分で持つ知識である** — 根拠は知識ではない。

**move は id の書き換えを一トランザクションで行う。**

- concept 本体の id、**履歴**(move 自体も `change: move` として追記する)、
  利用実績、埋め込みのキー。埋め込みテキストは id を含まないので**再埋め込みは
  不要**である。
- **内向き参照の書き換え** — 生きている concept のうち本文が旧 id を指すもの。
  各書き換えは `update` のリビジョンとして記録する。**移動の副作用も監査証跡
  に残る。**
- **`<id>/` 名前空間のファイルも一緒に動かす。** 名前空間が住所の一部である
  以上、置いていくほうが驚きが大きい。**名前空間下の concept は動かない** —
  それは自分の住所・履歴・台帳・move を持つ別の concept であり、move は
  一つの改名だからである。一括改名は別の判断になる。
- **移動先が埋まっていれば 409。ソフト削除済みでも拒否する** — その行は
  まだ主キーと履歴を所有しており、上書きは二系統の履歴の合流になる。
- **MCP には出さない。** 整理はキュレーションであり、人の面の操作である。

## 6. 住所で検索の範囲を絞る

`prefix` フィルタは id の前方部分パスで、そのサブツリー(prefix 自身と
その下すべて)に絞る。**フィルタであってモードではない** — クエリとも
`sort` とも組み合わせられ、単独では一覧にならない。

**セグメント境界で照合する。** `prefix=metrics` は `metrics/revenue` と
`metrics` 自身に当たり、**`metrics-legacy/churn` には当たらない**。素の
前方一致にすると、隣にディレクトリを一つ作っただけで他人のスコープが混入
する — **スコープという用途では、これが最も高くつく形の誤りになる。**

**繰り返せる(OR)。** 主用途が「自分のスコープ*と*全社スコープ」だから
である。単一値にすると、その最も普通の問いが二往復とクライアント側マージに
なり、しかも**別々のランキングから来たスコアをマージした順位に意味が無い**。

**索引は張らない。** 範囲述語に書き換えれば btree に乗るが、それは照合順序に
依存する — `text` の `<` は collation 順であって、バイト列の前方一致と一致
する保証が無い。**環境によって答えが変わる。正しさを索引と引き換えにはしない。**
測って足りなくなったら、collation に依らない演算子クラスで張り直す。

**リンク展開には効かない。** `get_context` の prefix は一次ヒットにだけ効き、
リンクで引き寄せられるものはスコープの外からも入ってくる。**チームの指標が
全社の用語を引用しているなら、その用語は一緒に来なければ意味が無い。**

**これは認可ではない。** prefix は誰からも見え、誰でも任意の値を渡せ、
指定しなければ全体が返る。**渡さないクライアントには何も隠れていない。**
閲覧境界が要るならインスタンスを分ける、という 0065 §1 の答えは変えない。

## 7. やらないこと

- **Git や GCS を保存にしないこと**、**型付き JSON の書き込み面**、
  **部分更新**、**退役綴りのデータ移行**、**provenance の読み戻し・実行・
  dereference・採点**。
- **主張を索引・trust tier・ワイヤの一級市民にすること**(§3.1)。
  `received:` は保存された文書の中の一キーであり、それ以上の面は作らない。
  決める前に、**主張を復元不能に捨てることだけ**をやめた。
- **ファイルの中身を解釈すること。** `index.md` / `log.md` を受け取っても
  読まない。
- **`fm.` フィルタに演算子を持たせること**(完全一致と包含だけ。範囲・否定・
  論理式はクエリ言語の入口になる)。
- **スコープの自動判定**(LLM ゼロ)、**スコープのレジストリや封筒フィールド**
  (住所が既にスコープであり、二重に持てば必ずずれる)、**部分一致・glob・
  正規表現**、**検索順位へのスコープの重み付け**(呼び出し側が持つべき方針が
  サーバーの定数になる)。
- **`ls` / `rm` という綴り。** このプロジェクトの語彙は unix の習慣ではなく、
  片方だけを unix 風にすると CLI の中に由来の違う二つの語彙が並ぶ。
- **ファイルの MCP ツール。** エージェントが増やすべきものではない。
