# ochakai 設計ドキュメント 0085: 空のベースと、それを埋めるもの

Status: Accepted(2026-08-09)。[0081](0081-what-ochakai-is-and-what-it-refuses-to-hold.md) §1
の「コネクタによる取り込みは持たない」を一行も緩めずに、空のベースに
最初の内容を入れる経路を CLI に一本足す
Date: 2026-08-09

## 1. 何が起きたか

新しいデプロイが最初に持つのは**空のベース**である。カタログ製品は
そこをコネクタで埋める — ウェアハウスを巡回して数千行のメタデータを
入れ、初日から何かが見える状態にする。ochakai はコネクタを持たないと
決めており(0081 §1: サーバーの中の収集器は、ochakai が意図して持たない
ウェアハウスの資格情報を要る)、その決定は動かさない。

しかし**「持たない」は「空のまま始める」を意味しない**。
[examples/bigquery-catalog](../../examples/bigquery-catalog) が既にこの
仕事をしている — 564 行の Python ジョブが自分のサービスアカウントで
BigQuery を読み、REST の普通のクライアントとして書き込む。揃っている。
足りないのは**その手前**である: 見る前に読むものが多く、Python の実行
環境と `pip install` と receipt の設計が、最初の 30 分の前に来る。

## 2. 決定: `ochakai seed` は、ウェアハウスに接続しない

コマンドは一本、`ochakai seed <file.json | ->`。

**入力**は運用者自身が撃ったクエリの答えである。`INFORMATION_SCHEMA.COLUMNS`
の列名(`table_schema` / `table_name` / `column_name` / `data_type` /
`is_nullable`、あれば `description`)を持つ JSON 行を、配列でも一行一
オブジェクトでも受ける。

**出力**は OKF バンドルの tar.gz で、テーブル一つにつき `BigQuery Table`
concept 一つ、列は markdown の表、住所は `resource` である。

**書き込みはしない。** 既存の `ochakai import` に渡す:

```sh
bq query --format=json --nouse_legacy_sql '…' | ochakai seed - | ochakai import -
```

**この形が満たしているもの。**

- **資格情報を持たない。** ウェアハウスのクライアントはバイナリに
  リンクされず、認証情報は読まれない。撃つのは運用者の道具と identity
  であり、0081 §1 の理由がそのまま守られる。
- **ウェアハウス中立。** `INFORMATION_SCHEMA` は各社が合意している
  数少ないものなので、Snowflake でも Postgres でも同じ行が出せる。
  型名 `BigQuery Table` が BigQuery を名乗っているのは
  [0071](0071-the-recommended-type-vocabulary.md) の語彙の都合であって、
  この経路の都合ではない。
- **書き込み経路が増えない。** 認証も冪等性も `--strict` も dry run も
  `import` のものをそのまま使う。二つ目の書き込み経路は
  [0067 §5.2](0067-four-faces-and-what-they-decline.md) が断ってきた形である。

## 3. 出るのは draft であり、それが要点である

投影された concept は**骨組み**である。そのテーブルが何のためにあるか、
どの列が嘘をつくか、いつロードが遅れるか — 誰かがこの entry を読む理由は
すべてそこにあり、スキーマはその何一つ知らない。

だから status は `draft` で出て、レビューキューに入る
([0069](0069-the-loop-and-what-measures-it.md))。`description` は**空の
まま出す**: 誰も書いていない一文を frontmatter に置けば、その後の全員が
それを信じる。

**コネクタとの違いはここにある。** あちらが作るのは誰も請け合っていない
数千行で、こちらが作るのは数千個の問いである。同じ情報の、正直なほうの
形である。

## 4. 採らなかった案

- **BigQuery クライアントをバイナリに入れる**(`ochakai seed bigquery <dataset>`)。
  一番親切に見えるが、製品がウェアハウスの資格情報を扱い始める。0081 §1
  が断っているのは「サーバーの中の収集器」だが、同じバイナリの CLI が
  それをやるなら、名前が違うだけのコネクタ製品である。
- **サーバー側の投影エンドポイント。** 資格情報がサーバーに来る。同上。
- **example の Python ジョブを消す。** 消さない。あちらは毎日走る
  同期(receipt、attester、差分)で、こちらは初日の一回である。
  違う仕事であり、`seed` の出力に満足した人が次に読むのがあちらである。
- **`import` に `--from-schema` を足す。** フラグ一本で済むように見えるが、
  `import` は「バンドルを書き込む」一つの仕事を持っており、そこに
  「別の形式を読む」を足すと、[0062](0062-a-listing-is-not-a-search.md)
  が `search` について直したのと同じ形になる — 一つのコマンドが二つの
  能力を持ち、引数の形で意味が変わる。
- **concept をサーバーに直接書く。** 書き込み経路が二つになる(§2)。

## 5. 面

- **CLI** — `ochakai seed`。CLI は完全性の面であり(0067 §1)、これは
  シェルの上の変換である。表面は 24 → 25、フラグは `--project` 一本ぶん
  増えて 28 → 29。
- **REST / MCP / Web UI** — 載せない。サーバーは何も新しく提供しない:
  出力は既存の `PUT` が受け取るバンドルであり、変換はクライアント側で
  完結する。エージェントに要るのは投影ではなく、投影された draft を
  読んで**中身を書く**ことである。
