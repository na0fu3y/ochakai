## 0. この記録が決めたこと

**五つの記録が一つの絵であること。** issue
[#471](https://github.com/na0fu3y/ochakai/issues/471) が
[0065](0065-identity-and-provenance.md) / [0066](0066-four-postures-one-word.md)
で始めた統合の二回目である。決定は一つも動かない。

論証は来ていない。なぜ etcd が二つのバイナリに割れたのか、なぜ `hits` の
二重掲載が予算を無意味にしたのか — その全文は各記録の墓標が指すコミットに
残る。ここに残したのは**いまも参照される理由**だけである。

**そして一覧は書き直す必要があった。** 0015 §3 の「載せないもの」は
`search_knowledge`・`get_attachment`・`update_knowledge`・
`POST /api/v1/knowledge`・`browse`・`revisions`・`backlinks` という、
**いま一つも存在しない綴り**で全編が書かれていた。0046 が住所を畳み、
0054/0057 が語を `concept` にし、0056 が backlinks を畳み、0064 が
`get_file` に改めるたびに、この一覧だけが取り残されていた。0015 の
`Status:` ヘッダは六本の改訂を抱えて 1 段落になっており、それでも本文の
綴りには追いついていない。**現行の語彙で読める一覧であることが、この
記録が最初から果たすべき役目である。**

## 1. 四つの面の役割

- **REST は唯一の契約。** すべての機能は `/api/v1` に載るか、どこにも
  載らない。他の三面は全部そのクライアントであり、上限・enum・既定値は
  サーバー側に一元化する。
- **MCP はエージェントの目的特化入口。** ツールスキーマはエージェントの
  コンテキストから支払われるので、**ツール数は予算である**。REST の 1:1
  ミラーは目指さず、「エージェントのループが 1 コールで必要とするもの」
  だけを載せる(`get_context` がその極致)。
- **CLI は完全性の面。** REST の純クライアントとして全操作をカバーする。
  ただし**完全性とは能力の完全性**であって、畳まれた面をコマンドとして
  保存することではない(0068 §1)。
- **Web UI はループの人間側。** キュレーション面であって BI ツールでは
  ない。検索・ブラウズ・裁定・履歴の閲覧まで。ページは認証を知らない
  ([0006](0006-web-ui-serving.md))。

## 2. CLI は REST の薄いクライアントである

サーバー側に CLI 専用の面を作らない。データの出し入れはすべて API 経由で、
**DB の隣でしか動かないコマンドは `serve` だけ**である。

同じ成果物に二つの経路があると、以後の仕様追加のたびに片方だけ直る事故が
起きる。実際に `export-okf` / `import-okf` は client 版と二重実装になり、
`--dry-run` は片方にしかなかった。API 経由なら actor も OS のユーザー名
からの合成ではなく、Cloud Run が検証した呼び出し元になる
([0065](0065-identity-and-provenance.md) §2)。

- **同一バイナリ。** 別バイナリは作らない。ただし `internal/apiclient` は
  `internal/service` を import せず、**OpenAPI 契約をミラーした型を自前で
  持つ** — 分割が必要になったとき依存ツリーごと切り出せる状態を保つ。
- **フラットな動詞コマンド。** リソースが一種類なので `ochakai search`。
  `ochakai` という接頭辞が名前空間を担う。
- **接続先の解決順は `--url` > `OCHAKAI_URL` > `ochakai use` の設定。**
  明示が永続に必ず勝つ — 人間の config に引きずられて CI やエージェントが
  意図しないインスタンスを叩く「隠れ状態」事故を防ぐ。config が持つのは
  URL だけで、トークンは存在しない。
- **`ochakai login` は作らない。** 認可サーバーは Google であり、実装しても
  `gcloud auth login` のラッパーにしかならない。資格情報の状態は
  `ochakai whoami` が「どこに・誰として・届くか」で見せる。
- **終了コードは 0 = 成功 / 1 = エラーの二値**(`--exit-code` を渡した
  `stats` のキュー判定だけが 2 を足す — [0049](0049-queue-counts.md))。
- **引数なしの `ochakai` はヘルプ。** `serve` へは落ちない。

## 3. `mcp-stdio` は面ではなく経路である

stdio しか話せないクライアントは URL を指せず、Cloud Run 上の ochakai には
ID トークンが要る。`ochakai mcp-stdio` は stdin/stdout と remote の
`/mcp` を **JSON-RPC メッセージ単位で素通しする**ブリッジで、サーバーには
何も足さない。

**ツール定義を写さない。** 列挙して再登録する実装も可能だが、それは定義を
二重に持つことであり、引数が一つ増えるたびにブリッジが古びる。素通しなら
`initialize` も `notifications/*` も将来のメソッドも、ブリッジが知らない
まま通る。

**stdout はプロトコル専用である。** 一行でも人間向けの文字列を書いた時点で
セッションが壊れるので、診断・エラー・起動時の「どこに誰として繋いだか」は
すべて stderr に出す。これは規約ではなく不変条件なのでテストで留める。

REST や Web UI に対応物は作らない。§1 が求める面の一貫性は**能力**の話で
あり、これは既存 MCP 面への**トランスポート経路**である。REST に stdio は
意味を持たず、MCP のツール数も一つも増えない。

## 4. 同じ機能が、面によって別の意味を持ってはならない

`GET /api/v1/context` の `hits` は**全サーフェスで順位に徹する** —
`domain.ContextRank`(`id` / `type` / `title` / `status` / `score` と
trust tier)だけを運び、本文も attrs も持たない。

順位はポインタであり、ポインタは fetch するかどうかを判断できるだけの情報を
持つ必要がある。id だけでは、呼び出し側は全部取りに行くか全部捨てるかしか
できない。

`hits` は**バイト予算の外**に置く。予算が縛るのは知識 — 全文で配る
`concepts` と、名前だけ出す `outline` — であり、`hits` は本文を持たず件数にも
上限がある。**検索の `hits` は全文のままである**(そこではエントリが答え
そのものであって、同じ応答に載る別のフィールドの複製ではない)。

この規律が破れていた形そのものが、この節の由来である。MCP だけがローカルな
射影で `hits` を順位にし、REST と CLI は全文を返していた — つまり埋め込み
ホスト(REST を使えと §5.2 が誘導している当の相手)にだけ予算が効いて
いなかった。

## 5. 意図して載せないもの

### 5.1 MCP に載せないもの

ツール数は予算なので、既定は no である。

- **ブラウズ**(`index.md` の階層歩き)。多ラウンドトリップの探索であり、
  `get_context` の「1 コールで全部」と正反対。
- **履歴**(`?history`)。エージェントが要る信頼シグナルは concept 本体に
  載っている。全スナップショット付きの履歴はトークン的に重く、監査は人の
  仕事である。
- **被リンク**。`get_context` がリンクを逆向きにも展開して同梱済み。
- **ファイルの書き込み。** base64 をツール引数に載せるのはトークンの浪費で
  あり、思想にも反する — エージェントの書き戻しは検索可能なテキストである
  べきで、「ファイルから学んだら本文に書け」と `get_file` の説明が既に
  誘導している。
- **バルク(export / import)。** 応答サイズが読めず、tar.gz はツール結果に
  載らない。管理タスクは CLI / CI の領分。
- **purge。** 履歴の破壊は人の判断である([0031](0031-purge.md) §3.4)。
- **reembed。** モデル入れ替え後の運用タスクであってエージェントの仕事では
  ない。
- **インスタンスの集計(`stats`)。**
  ([0051](0051-instance-metrics-and-search-misses.md) §4)
- **frontmatter キーのフィルタ(`fm.`)。** REST と CLI には残る。同じ
  944 文字の説明が 2 ツールに載ってスキーマ説明文の 14% を占めていたのに、
  通行の跡が無かった(0068 §3)。
- **人が判断を下した concept の上書き・削除・復活**(§6)。

### 5.2 REST に載せないもの

- **SQL 実行。** ochakai はウェアハウス資格情報を持たない。
- **LLM を使う機能**(要約・チャット・自動検証)。LLM を持たないことが、
  人の検証への信頼の根拠である。
- **認証・ユーザー管理。** 認証は Cloud Run IAM の仕事で、ユーザー DB を
  持った瞬間 secret-zero が壊れる(0065)。
- **Web UI の配信。** ページを持たないサーバー(0006)。
- **バルクの OKF import。** import は CLI が既存の書き込みを 1 件ずつ叩いて
  合成する。件別のレポート・dry run・部分失敗の位置特定・actor 記録が
  すべて既存の意味論に乗り、「同じ成果物への二経路目」を作らずに済む。
  **できることは増えず、増えるのは利便性だけ**である。

  ただし代償は認めておく。README は CLI を「REST の薄いクライアント」と
  説明しており、**import はその主張の唯一の例外**である。バンドルの解析・
  帰属解決・skip レポートという本来サーバー側のセマンティクスが
  クライアントに住んでおり、帰結は二つ —「どの生成者の OKF バンドルでも
  読める」を Go バイナリ以外から享受できないこと、そして往復の意味論を
  クライアントの版が決めること。**踏み切るトリガは、バイナリを持ち込め
  ない環境からのリストア要求が実際に来たとき**である。

### 5.3 CLI に載せないもの

- **DB 直結コマンド**(`serve` を除く、§2)。
- **レビューキューのヒューリスティック再実装。** Web UI の表示層の閾値を
  複製すると二重実装の drift が始まる。CLI は素材の提供まで。
- **TUI・対話モード。** パイプで合成できる行指向出力が CLI の価値であり、
  対話が欲しければ `ochakai ui` が立つ。
- **ローカルキャッシュ・オフラインモード。** スナップショットは export が
  担い、キャッシュは鮮度と provenance の問題を持ち込む。

### 5.4 Web UI に載せないもの

- **`report_outcome`(worked / failed のボタン)。** outcome は「知識に
  基づいて実行した結果」の証跡であり、実行しない UI にボタンを置くと裏付けの
  ない報告が再検証フィードの信号を汚す。人の判断は verify / reject という
  別の語彙で記録される。
- **context ビュー。** エージェント向けのパッキング面で、UI に置くと
  「質問を入れる箱」になりチャット / BI への滑り坂になる。
- **SQL 実行・チャート・チャット。**
- **OKF import のアップロード**(§5.2 の帰結)。
- **ログインフォーム。** 認証はプロキシの仕事であり、ページが認証を知らない
  から同じ一枚が二通りに配れる。
- **purge**(不可逆な破棄を削除ボタンの隣に置かない)、**reembed**(運用
  タスク)、**`fm.` のフィルタ**、**producer の申告**(人が自分で書く面には
  名乗るソフトウェアが無い — 0065 §4)。

## 6. 人が判断を下した concept は、MCP から動かせない

`put_concept` / `delete_concept` は、対象が verified / rejected /
deprecated ならば拒否する。create による**墓標の復活**も同じく拒否する
(draft の墓標は従来どおり復活できる — 誰も判断を下していない)。
verified → deprecated の遷移も MCP からはできない。廃止は「正しかったが今は
推奨しない」という判断であって、エージェントの観測ではない。

**これは認可ではない。** 0065 §1 の「認可を持たない」は撤回しない。制限する
のは**前提条件を表明できない面からの黙示的な置き換え**だけである。
[0030](0030-optimistic-locking.md) の `If-Match` は REST の ETag に乗って
おり、MCP にはその通り道が無い — つまり MCP の書き込みは last-write-wins で、
draft には許容できるが人がキュレーションしたものには許容できない。

**非対称性の根拠は復旧可能性ではなく可視性である。** soft-delete は目に見え、
復活もする。verified な golden query の本文が黙って置き換わった場合、誰かが
それを実行して間違った数字を得るまで誰も気づかない。

**rejected は verified と同じかそれ以上に重要である。** README が memory
layer との差別化の筆頭に挙げ、配布する指示がエージェントに「再提案の前に
rejected を見ろ」と言っている当のものが、二コールで消せてしまう。しかも
verified の消失と違い、rejected の消失は誰も使っていなかったので誰も
気づかない。

エージェント側の正しい行動は既に用意されている — 誤りなら
`report_outcome` failed(再検証フィードに乗る)、より良いものがあるなら
新しい draft を書く。人の面(REST / CLI / Web UI)は従来どおり動かせる。

## 7. やらないこと

- **MCP の deprecate や機能削減。** シェルを持たないホスト型エージェントに
  とっては MCP だけが入口である。
- **新しいサーバー面**(CLI 専用エンドポイント、認可、トークン)。
- **公開エンドポイント**(0012 が retire した OAuth コネクタ)。
  `mcp-stdio` は利用者の機械の中のプロセスで、listen するポートを持たない。
- **ブリッジでのリトライやキャッシュ。** 状態を持てば remote と食い違いうる
  状態である。切れたら落とす。
