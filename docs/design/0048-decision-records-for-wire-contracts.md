# ochakai 設計ドキュメント 0048: 決定記録はワイヤ契約の決定に絞る

Status: Accepted(2026-07-28)。番号付きドキュメントを**要する決定の範囲**を
狭め、未リリースの決定を改訂するときは新しい番号ではなく元のドキュメントを
差し替えると定める。既存の 47 本は 1 行も書き換えない — 本ドキュメントが
変えるのは*これから*何が番号を取るかであって、既に取った番号ではない。
[the index](README.md) の冒頭に現行ドキュメントの早見表を足し、
[README.en.md](README.en.md) の維持義務を現行ドキュメントだけに縮める。
Date: 2026-07-28

## 1. 問題: 記録が、記録される対象より速く育っている

数えると、この仕組みは自分の想定を超えている。

| | |
|---|---|
| 番号付きドキュメント | 47 本 / 7,994 行 |
| 本番 Go コード | 14,809 行 |
| プロジェクトの年齢 | 全 50 コミットが 2026-07 |
| リリース | 13 日間に 16 本 |

決定記録は、**決定が人と年を跨いで生き延びる**ことで元が取れる仕組みで
ある。ここでは決定が二週間生き延びていない。

- ナレッジモデルの領域は 0005 → 0016 → 0036 → 0043 → 0046 と、二週間で
  4 回置き換わった。
- 0036 は**自分の実装がリリースに乗る前に** 0043 に置き換えられ、0043 も
  同じく実装がランドする前に 0046 に置き換えられた。
- 0034 は main にマージされた後、リリースを迎えないままファイルごと削除
  され 0036 に統合された(欠番)。
- フィルタの語彙だけで、同じ未リリース周期のうちに 0037 / 0046 / 0047 の
  3 本が触っている。

一方でコストは決定ごとに固定である。1 つの判断につき、本体(日本語)+
[README.en.md](README.en.md) の英語要約(`TestEnglishDesignIndexCoversEveryRecord`
が強制)+ index のエントリ + 旧ドキュメントの `Status:` ヘッダ、の 4 箇所。
0046 のように 14 節を持つドキュメントでは、この 4 箇所が繰り返し触られる。

**帰結が二つある。**

第一に、index が果たすと約束した性質 —「ある領域の現在の姿を知るには、
その領域の全ドキュメントを Status の注記に従って読めば足りる」— の
*足りる*が、実際には「10 本読んで括弧書きを追う」を意味するようになった。
ナレッジモデルの節は現在 12 エントリあり、そのうち現行は 8 本である。
どれが現行かは、各エントリの括弧内を最後まで読まないと分からない。

第二に、[ROADMAP](../../ROADMAP.md) が「他人がこれを使えるかを決める、
最も可能性の高い作業」と呼んだ**初見の人への読みやすさ**に対して、
7,994 行の改訂考古学は入口で逆風になっている。`docs/design` はリポジトリで
最も行数の多いディレクトリであり、`docs/README.md` の使い方より先に目に入る。

そして維持者本人が把握できる範囲を超えたとき、記録は自分の目的
(「なぜこうなっているか」に後から答える)を果たせない。**記録が読まれない
なら、書かれた決定は口頭の決定と同じである。**

## 2. 決定: 番号は「利用者が観測できるもの」を変える決定にだけ与える

境界を、書き手の判断の重さではなく、**変更が外から見えるか**に置く。

### 2.1 番号を要する決定

| 領域 | 例 |
|---|---|
| **ワイヤの形** | REST のエンドポイント・パラメタ・レスポンス形、MCP のツールの増減、CLI のコマンドの増減、Web UI が担う面 |
| **保存形と往復** | OKF 文書としての姿、正準化、ハッシュの対象、バンドルのアドレス空間 |
| **identity と provenance の意味** | 誰として記録されるか、何を拒否するか、read-only とその境界 |
| **Google Cloud への依存** | 新しいマネージドサービス、secret-zero(0002 / 0003)に触れる変更 |
| **意図してやらないこと** | ROADMAP の refusal に載る種類の判断 |

共通するのは、**利用者が観測でき、後から「なぜこうなっているか」を
問われる**ことである。0002 の「認可を持たない」や 0003 の「GCP 限定」が
繰り返し問い直されているのは、まさにこの性質による。

### 2.2 番号を要しない決定(PR の説明で足りる)

- 外形の変わらない内部変更 — パッケージ分割、store のクエリの組み方、
  索引の張り方、性能改善、依存ライブラリ。
- 既存の決定の**内側**での追加 — 新しい型の綴り、エラー文言、既存
  エンドポイントへのドキュメント追加。
- ドキュメントとテストだけの変更。

判断に迷ったら「これを 3 か月後に問い直す人がいるか」を訊く。いなければ
PR で足りる。

### 2.3 未リリースの決定は、番号を足さずに差し替える

**不変性は、リリースに乗った決定に対する約束である。** 乗っていない決定に
対するものではない。

したがって、まだリリースに乗っていないドキュメントを改訂するときは、
新しい番号を取らずに**元のドキュメントを書き替える**(または削除して
統合する)。0034 は既にこれを行っており、その経緯は 0036 §1.1 に残って
いる — 例外ではなく、規則にすべき先例だった。

この規則があれば、0043 は 0036 の改訂として書かれ、0047 は 0046 §3.11 の
修正として書かれた。番号は 2 つ減り、`Status:` の連鎖は 2 本減り、
英語要約は 2 本減る。**失うものは、採用されなかった中間案の文面だけで、
それは PR の履歴に残る** — 0034 がそうであるように。

判定は機械的にできる: [CHANGELOG](../../CHANGELOG.md) の `Unreleased`
節にその実装が載っているなら、そのドキュメントはまだ差し替えてよい。

### 2.4 index は現行の姿から読ませる

[the index](README.md) の冒頭に、**領域 → 今読むべきドキュメント**の
早見表を置く。改訂の履歴は各エントリの中に今までどおり残るが、それを
読まなくても現行の姿にたどり着ける。

これは §1 の第一の帰結への直接の答えである。index の約束は「Status の
注記に従って読めば足りる」だったが、**足りるべきは 1 行の表**である。

### 2.5 英語要約は現行ドキュメントだけを要約する

`TestEnglishDesignIndexCoversEveryRecord` はファイル名が現れることしか
検査しない。Superseded になったドキュメントは、要約を維持する代わりに
**1 行の転送**(`Superseded by NNNN` とリンク)で足りるとする。英語話者が
たどり着けなくなる先は無く、改訂のたびに 2 言語で本文を書き直す義務が
消える。

## 3. 本ドキュメント自身について

**§2.1 の基準では、このドキュメントは番号を要しない。** 利用者が観測する
面を何も変えないからである。番号を取るのは、これが「以後どの決定が番号を
取るか」を定義するドキュメントであり、基準そのものは基準の外側にあるため
である。以後、プロセスについての決定は書かない — 書くとすれば、それは
この規則を変えるときである。

## 4. 選ばなかった案

- **決定記録をやめ、README か ROADMAP の節に畳む。** 採らない。§2.1 の
  4 領域は、まさに後から理由を問われる決定であり、0002 / 0003 / 0015 の
  refusal は問い直しに答えるために存在している。これらを箇条書きに畳むと、
  「検討した選択肢」と「不採用の理由」が最初に落ちる — 記録の中で唯一
  再現できない部分である。

- **ドキュメントを書き換え可能にする(不変性を捨てる)。** 採らない。
  「なぜこうなっているか」は、当時の選択肢と一緒でなければ答えにならず、
  書き換えを許すと最初に消えるのがそれである。代わりに §2.3 で、
  **まだ誰も依存していない決定**に限って差し替えを許す。境界が
  「リリースに乗ったか」なので、判定に主観が入らない。

- **番号を領域ごとに振り直し、Superseded を統合する。** 採らない。
  README・`docs/architecture.md`・`api/openapi.yaml`・コードコメントに
  60 以上の「設計ドキュメント NNNN」の引用があり、そのすべてが切れる。
  §2.4 の早見表は、番号を動かさずに同じ読みやすさを買う。

- **既存 47 本を今回まとめて整理する。** 採らない。不変性を守る限り、
  整理とは新しい統合ドキュメントを書くことであり、それは §1 が数えた
  コストをもう一度払うことになる。現行 8 本のナレッジモデルは、0046 が
  実装され切った時点で自然に 1 本に畳まれる — そのときに払う。

## 5. サーフェス(0015)

**該当なし。** REST / MCP / CLI / Web UI のいずれも変わらない。本
ドキュメントが変えるのはリポジトリの書き方であって、ochakai が提供する
面ではない。

## 6. 互換性

**破壊的変更は無い。** 既存の 47 本は 1 行も書き換えず、すべての
「設計ドキュメント NNNN」引用は生きたまま残る。変わるのは
[CLAUDE.md](../../CLAUDE.md)、`design-doc` skill、index の冒頭、
README.en.md の維持義務である。
