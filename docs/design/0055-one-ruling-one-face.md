# ochakai 設計ドキュメント 0055: 裁定は一つの面から下す

Status: Accepted(2026-07-29)。**BREAKING。**
[0025](0025-closing-the-loop.md) §6 が新設した
`POST /api/v1/verify/{id}` と、[0043](0043-document-first.md) §3.3 が
新設した `POST /api/v1/reject/{id}` /
`DELETE /api/v1/reject/{id}` を、**`POST /api/v1/review/{id}`
一本に置き換える** — 本文に `ruling: verified | rejected | withdrawn`
を取る。記録される内容・台帳の形・信頼の導出・各面への配置はどれも
変わらず、変わるのは呼び方だけである。0043 §3.2 の「verify は台帳への
追記であり文書に触れない」と §3.3 の「却下は台帳」はどちらも維持する
— 本ドキュメントはその二つが**同じことを言っている**と気づいた結果
である。[0046](0046-bundle-address-space.md) §3.14 のサーフェス表を
REST 11 操作に言い直す。[0015](0015-surface-consistency.md) §3.1 の
「MCP に載せないもの」は変わらない — 裁定は人が下すものである
Date: 2026-07-29

## 1. 問題: 三つの面が、同じ形をしている

書き戻しループの人間側には、いま三つの面がある。

| 面 | 何を書くか |
|---|---|
| `POST /api/v1/verify/{id}` | 検証台帳に 1 行追記し、却下を解除する |
| `POST /api/v1/reject/{id}` | 生きた裁定を 1 つ立てる(note 付き) |
| `DELETE /api/v1/reject/{id}` | 生きた裁定を降ろす |

三つは別々の時期に生まれた。verify は 0025 §6 が「内容の変わらない PUT
は何も書かないので、再検証を表現できない」ことに気づいて足したもので、
reject は 0043 §3.3 が rejected を lifecycle 値から台帳へ移したときに
足したものである。どちらの判断も正しく、いまも覆さない。

正しくないのは、**三つが並んだ後の姿を誰も見直さなかった**ことである。

三つは構造的性質を**すべて**共有している。

- **文書に触れない。** ライフサイクル値も `updated_at` も ETag も動か
  ない(0043 §§3.2-3.3)。draft を stable に上げるのは PUT である。
- **台帳に書く。** 検証は追記される列、却下は 1 つの生きた行。
- **呼び出し元の identity で記録される。** ペイロードからは採らない
  (0009)。
- **人の面に載り、MCP には載らない**(0015 §3.1)。
- **応答はエントリそのもの**(`View`)。

違うのは**書かれる値だけ**である。

> **構造をすべて共有し、値だけが違う三つの操作は、パラメータを持つ
> 一つの操作である。**

これは実装の重複の話ではない — サーバー側の関数は 3 つのままでよい。
[docs/surface.md](../surface.md) が数えているのは**利用者が払うもの**で
あり、そこでは三つの URL と、二つの動詞と、「なぜ却下の解除だけが
DELETE なのか」という問いを、読む人が覚えることになっている。

## 2. 世界観: 面を分ける理由は「違う行為か」であって「違う値か」ではない

ochakai は既に一度この判断をしている。0046 §3.5 は concept の第二の
住所 `/api/v1/knowledge/{id}` を畳んだ。理由は「`/bundle/{path}` と
同じものを一つの接尾辞違いで読み書きしていた」ことだった。

同じ物差しをここに当てる。**`review` と `PUT` は分かれたままである** —
裁定と編集は違う行為で、片方は文書を動かし片方は動かさない。0043 §3.2
がその線を引き、本ドキュメントはそれを一歩も動かさない。動かすのは
線の**内側**の分割だけである。

そして分けたままにするものがもう一つある。

**`report_outcome`(`POST /api/v1/usage/{id}`)は畳まない。** 数の上
では畳めば 11 が 10 になる。畳まない理由は 0015 §3.4 が既に書いている
— outcome は「知識に基づいて SQL を実行した結果」の証跡であって、人の
裁定ではない。だから Web UI に置いてはならず(行動の裏付けのない
worked / failed が再検証フラグを汚す)、MCP には置かねばならない
(エージェントのループの正規の出口である)。**載る面が逆なのだから、
同じ面にはできない。** 数のためだけの畳み込みは、この文書が数えようと
しているものを増やす。

## 3. 決定

### 3.1 `POST /api/v1/review/{id}` — 一つの裁定

```http
POST /api/v1/review/insights/revenue-seasonality
Content-Type: application/json

{"ruling": "verified"}
```

応答は `View`(エントリそのもの)、ETag 付き。三つのどの ruling でも
同じである。

`{id}` は concept ID であって bundle path ではない — `.md` は付かない。
`/bundle/{path}` が bundle の**オブジェクト**を扱う面なのに対し、これは
**concept について**の裁定であり、concept を呼ぶ名前は id である
(0017、0046 §3.1)。応答本文の `summary.id`、`links[].target`、
`ochakai://` URI がすべてこの綴りを使っている。二つの綴りがあるのは
OKF の形式がそうだから(SPEC §2: concept ID はパスから `.md` を除いた
もの)であって、揃えるべき不整合ではない。

### 3.2 語彙は三つ、`withdrawn` は DELETE ではない

| ruling | 何が起きるか |
|---|---|
| `verified` | 検証台帳に 1 行追記し、生きた却下があれば解除する |
| `rejected` | 生きた裁定を立てる(既存の裁定は置き換わる)。検証台帳は消さない |
| `withdrawn` | 生きた却下を降ろす。無ければ 404 |

`withdrawn` を DELETE で綴らないのは、**何も削除されないから**である。
検証は追記のみの台帳で、却下は 1 つの生きた裁定(0043 §3.3)。
却下を降ろす操作は台帳から行を消すのではなく、**履歴に 1 行増やす** —
リビジョン記録がずっと `unreject` と呼んできたものである。DELETE は
「この id の review を消す」とも読めてしまい、それは検証履歴まで含む
ように聞こえる。読めてはいけないものが読めない綴りを選ぶ。

無い却下を降ろすのが 404 なのは従来どおり — 何もしていないことを成功
として返さない。

### 3.3 `note` は `rejected` のもの

`note` は却下理由であり、`rejected` 以外と一緒に来たら 400 にする。

検証に note を持たせることは**できた**。しかしそれは「三つを一度に
言い直す」ではなく「新しく言えることを増やす」であり、
[docs/surface.md](../surface.md) の既定は no である。検証は「いま
書いてあるとおりで正しい」と言う行為で、それ以上に言いたいことが
あるならエントリ本文に書くべきものである。

400 にするのは、黙って捨てないためである。理由を書いたつもりの
呼び出し元が、どこにも残っていないことに後から気づくのが最悪である。

### 3.4 各サーフェス(0015)

- **REST = yes。** `POST /api/v1/review/{id}`。唯一の契約。
  面は 3 → 1。
- **CLI = yes、ただしコマンドは 2 本のまま。** `ochakai verify` と
  `ochakai reject`(`--lift` 付き)は名前も使い方も変わらない。0015 §2
  が CLI に求めるのは REST 操作との 1 対 1 ではなく完全性であり、
  ターミナルで打つ人にとって「検証する」と「却下する」は別の動詞で
  ある。**畳んだのはワイヤであって、語彙ではない。**
- **Web UI = yes。** verify / reject / 却下の解除のボタンは変わらず、
  叩く先が変わる。
- **MCP = no。** 変更なし。裁定は人が下すものであり、エージェントが
  検証済みエントリを誤りと判断したときの正規の経路は
  `report_outcome failed` か新しい draft である(0015 §3.1、0025)。

## 4. 却下した代替案

- **`report_outcome` も畳んで `POST /api/v1/feedback/{id}` にする。**
  §2 のとおり。載る面が逆であり、人の裁定と機械の観測を一つの語彙に
  すると 0015 §3.4 が守っている汚染防止が表現できなくなる。
- **`PUT /api/v1/review/{id}` にする。** 裁定は冪等ではない — 検証は
  追記であり、二度呼べば二行になる。「何回、誰が」に答えられることが
  0043 §3.2 が台帳を複数行にした理由なので、PUT の意味論とは合わない。
- **`ruling` をパスに置く(`/review/{ruling}/{id}`)。** id が階層パス
  なので、可変長のパス変数の**前**に置くしかない。読みにくく、
  「却下の解除」がパスの語になる利点も無い。
- **三つを残したまま `verify` の綴りだけ直す。** 数が減らない。
  この変更の全部が「読む人が覚える量」の話なので、それでは何もして
  いない。
- **何もしない。** 三つの面は動いており、壊れてはいない。それでも
  やるのは、**これが REST を固定する前の最後の機会**だからである。
  0.x の間は破壊的変更が minor で入る(docs/compatibility.md)。
  三つのまま固定すれば、以後は「なぜ却下の解除だけ DELETE なのか」を
  永久に説明することになる。

## 5. 壊れるもの

- **`POST /api/v1/verify/{id}`、`POST /api/v1/reject/{id}`、
  `DELETE /api/v1/reject/{id}` は消える**(404)。deprecation 期間は
  置かない — 0.x の方針どおり、削除は changelog 付きの minor で入る。
- 移行はどれも 1 行である。

  ```
  POST   /api/v1/verify/{id}        →  POST /api/v1/review/{id}  {"ruling":"verified"}
  POST   /api/v1/reject/{id} {note} →  POST /api/v1/review/{id}  {"ruling":"rejected","note":…}
  DELETE /api/v1/reject/{id}        →  POST /api/v1/review/{id}  {"ruling":"withdrawn"}
  ```

- **CLI は壊れない。** `ochakai verify` / `ochakai reject [--lift]` は
  そのままである。バイナリを上げれば済む。
- **MCP は壊れない。** どの ruling もツールではなかった。
- 保存されたデータ・台帳・エクスポート形式・信頼の導出は 1 バイトも
  変わらない。リビジョンの `change` 値(`verify` / `reject` /
  `unreject`)もそのままである。
