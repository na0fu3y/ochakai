# ochakai 設計ドキュメント 0091: ファイルのベクトルは、パスで引く

Status: Accepted(2026-08-10)。[0080](0080-search-and-how-a-deployment-embeds.md)
を改訂する — §5「ファイルが載るかはモデルが決める」に、**そのベクトルが
何で引かれるか**を加える。0080 は現行のまま。
[0075](0075-the-bundle-is-the-address-space.md) が決めた「パスが住所である」
を、最後まで残っていたテーブルに適用する。
Date: 2026-08-10

## 0. この記録が決めたこと

1. **ファイルのベクトルの鍵は、ファイルのパスである。** `(concept id,
   ファイル名)` をやめる。同名の二ファイルが別ディレクトリにあるとき、
   古い鍵は片方を消していた(§1)。
2. **帰属は検索時に読む。** どの concept のヒットになるかは bundle が
   答えることであって、ベクトルの行が覚えることではない(§2)。
3. **移行は作り直しであって、詰め替えではない。** 起動時に古い形の表を
   落とし、`ochakai reembed` が埋め直す。**アップグレードの手順が一つ
   増える**(§3)。
4. **キューはファイルの列である。** `(concept, ファイル)` の組ではなく、
   そしてこのデプロイのモデルが受け取れる媒体型だけが並ぶ(§4)。

## 1. 同じ名前の二つのファイルは、一つの行になっていた

`attachment_embedding` の鍵は `(knowledge_id, name)` だった。ファイルが
concept の持ち物で、`<id>/<name>` にしか置けなかった頃の形である。

[0046](0046-bundle-address-space.md) と 0075 でファイルは bundle の
オブジェクトになり、**本文がリンクすればどこに置かれていてもその
concept のものになる**。`name` はパスの最後の区切り以降を切り出したもの
になった。すると:

```
metrics/mrr の本文が charts/q1.png と tables/q1.png をリンクしている
  → 鍵はどちらも ("metrics/mrr", "q1.png")
  → 二本目のベクトルが一本目を上書きし、片方は検索から消える
```

**失敗は静かである。** ファイルは保存され、配信され、export に載り、
名前での字句一致にも当たる。落ちているのはベクトル面だけで、それは
「別の言い方で訊いたときに出てくる」経路である — つまり埋め込みが
存在する理由そのものが、この一件についてだけ消える。

パスは住所であり、住所は一意である。鍵はそれで足りる。

## 2. 帰属は bundle の性質であって、ベクトルの性質ではない

行から `knowledge_id` が消えるということは、**どの concept のヒットに
なるかを検索時に決める**ということである。検索はファイルのオブジェクトを
経由してベクトルに届く。帰属の述語(`attributedTo`)は、一覧・backlink・
export が既に通っているものと同じ一本である。

三つのことが、これで初めて正しくなる。

- **本文が今日リンクしたファイルは、今日からその concept を引く。**
  埋め直しは要らない。バイトは変わっていないので、ベクトルも変わらない。
- **本文がリンクをやめたファイルは、その瞬間に引かなくなる。** 古い鍵は
  行を持ち続け、`reembed` するまで消えた関係を答え続けていた。
- **二つの concept が同じファイルを見せているとき、両方が引く。**
  ベクトルは一本で、呼び出しも保存も一回である。

同じ理由で、**どの concept にも属さないファイルも書き込み時に埋め込む**。
以前は「持ち主」をパスから逆算できたときだけ埋め込んでいて、共有
ディレクトリに置かれたファイルは `reembed` を待つしかなかった。鍵が
パスなら待つものが無い。

## 3. 落として、埋め直す

古い行は**移し替えず、落とす**。0080 §3 が幅を変えるときに書いたのと
同じ理由である — ベクトルは導出物であり、詰め直しは呼ぶ側の口座から
支払われる。加えてこの場合、**移し替えようがない**: 上書きで消えた側は
もう存在せず、残った行がどちらのファイルのものかは行からは分からない。
分からないものを推測して埋めるより、空にして正しく作り直すほうが安い。

起動時に古い形を見つけたら、表を落とし、ログに一行出す。**運用者が
やることは一つ、`ochakai reembed` である**。それまでファイルは名前で
引ける — 埋め込みを設定していないデプロイが既にいる場所であり
(0080 §5)、concept のベクトルには何も起きない。

`reembed` の再開カーソルは形が変わる(組ではなくパスになる)ので、
アップグレードをまたいだ古いカーソルは 400 で断る。表が空になる以上、
そのカーソルに再開すべき続きは無い。

## 4. キューは、埋め込めるファイルだけを数える

未埋め込みの列は `(concept, ファイル)` の組ではなくファイルの列になる。
二つの concept が見せている一枚の画像は、仕事としては一件である。

そしてこの列には、**このデプロイのモデルが受け取れる媒体型だけ**が並ぶ。
これは鍵とは別の欠陥の修正である: zip も parquet もフォントも「ベクトルの
無いファイル」であり、列に入れると**永久に減らない**。`ochakai reembed`
は毎回「まだ N 件残っている、詳細はサーバログに」と言って非ゼロで終わり、
そのログには何も無い — モデルが受け取らないファイルを黙って飛ばすのは
0080 §5 が決めた正しい振る舞いだからである。

受け取れる媒体型はモデルの性質なので、列を作る側ではなく**呼ぶ側が
渡す**。テキストのみの embedder では PNG は「待っているファイル」では
なく「対象外のファイル」である。

## 5. 面への出方

外から見える変化は二つある。

| 面 | 何が変わるか |
|---|---|
| REST | 変わらない。`POST /api/v1/reembed` の `cursor` は不透明なままで、`files` と `missing` の意味も同じ |
| CLI | 変わらない。`ochakai reembed` の出力も引数もそのまま |
| MCP | 変わらない |
| Web UI | 変わらない |

**面が増えないのが正しい。** これは保存の形と、検索が同じ問いに返す答えの
訂正であって、新しくできることではない。増えるのは
[CHANGELOG](../../CHANGELOG.md) の一行 —
アップグレード後に `ochakai reembed` を一度走らせること — だけである。

## 6. やらないこと

- **古い行の移し替え**(§3)。
- **`attachment_embedding` の改名。** 中身はファイルのベクトルだが、
  表の名前を変えることは移行をもう一つ増やすことであり、鍵の修正に
  相乗りさせる理由が無い。読む側の Go の関数名は `File` に揃えた。
- **帰属をベクトルの行に持ち直すこと。** 速いのは確かだが、それは
  §2 が消した三つの誤りを戻すことである。bundle が答えを持っている。
- **どの concept にも属さないファイルを埋め込まないこと。** パスに
  置かれたファイルは呼び出せる住所を持っており、本文が明日それを
  指したときに待たされない、というのが鍵をパスにしたことの見返りである。
- **ファイルの切り捨てを数えること。** [0089](0089-a-half-embedded-concept-says-so.md)
  §5 が数えないと決めたところは、そのままである。
