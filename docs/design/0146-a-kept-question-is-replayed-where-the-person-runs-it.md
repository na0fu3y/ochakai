# ochakai 設計ドキュメント 0146: 比較に使う問いは、人が走らせる場所で再生される

Status: Accepted(2026-09-25)。[0141](0141-a-miss-is-read-off-the-words.md)
の検証ループに、答えの側の測定を一つ足す。[0142](0142-ochakai-carries-a-data-agent-that-does-not-rule.md)
§6 の「比較に使う問いのセット」を、読むだけのものから再生できるものにする。
面の配分は [0145](0145-four-faces-and-an-answer-that-shows-its-result.md) の
規則に従う(§5)
Date: 2026-09-25

## 0. この記録が決めたこと

1. **`ochakai eval` が、比較に使うと選ばれた問いをデプロイのエージェントに
   もう一度問い、答えがまだ立っているかを一問ずつ言う**(§2・§3)。
2. **再生は何も書かず、何も数えない。** エージェントは `POST /api/v1/agent`
   に `?dry_run=true` を付けて答え、turn を残さず、draft を書かず、読んだ
   concept に利用イベントもミスも付けない(§1)。
3. **SQL は、コマンドを打った人の手元で、その人として走る。** `ochakai ui`
   が BigQuery の前に置いている関門(dry run・SELECT だけ・課金上限)を
   同じように通る。サーバーは SQL を実行しない(0142 §4 は動かない)。
4. **結果は保存しない。** 行と `--json` で出し、答えたモデルの名前を添える。
   そのために `stats` の `agent` が `model` を返す(§4)。

## 1. 誰が詰まったか、なぜ dry run か

ROADMAP の第二段(2026-09-25)は「比較に使う問いを再生し、モデルと版で
印を付けて採点する」ことを求めた。0142 §1 がエージェントを持つ理由に
挙げた三つのうち、**正解の付いた問い**だけが、集めても使い道が無かった。
棚卸しの Skill は `list_turns(keep=true)` を読み、読まれた concept がまだ
検索の上位 3 件に返るかを比べるが、それは検索の測定であって、答えの
測定ではない。モデルやプロンプトやナレッジを変えたとき、先週正しかった
答えがまだ正しいかを言う手段が無い。

**再生がそのまま問えば、測るものを汚す。** デプロイのエージェントは答える
たびに turn を残し(0142 §6)、読んだ concept に利用イベントを付け、引け
なかった語をミスとして数え(0141)、draft を書くことがある。再生の一問
一問がそれを繰り返せば、`stats` の turn の数、利用の並び、ミスの一覧、
レビューのキューが、測定そのもので膨らむ。

だから再生は **dry run** である。語は新しくない: `dry_run=true` は
書き込みの経路で「何が起きるかを答え、何も保存しない」をすでに意味して
いる([0061](0061-a-dry-run-is-the-write-withheld.md))。エージェントの
一本にとって保存するものは turn・draft・利用イベント・ミスの四つで、
dry run はその四つを止める。答えは同じように返り、`turn` が無いことが
何も残っていないことを言う。PARAM は増えない。

## 2. 何と比べるか

**比べる相手は、keep された答えの会話である。** turn は一回の答えで、
人が 👍 を付けるのはたいてい会話の最後の答え — クエリの結果が戻ってから
書かれ、自分では何も提案せず、ほとんど読まない答え — である。その turn
だけを正解にすると、正解の読みは空に近く、SQL は無い。

そこで正解は、呼び出し元が読める turn から組み立てる: **同じ人、同じ
エージェント(`producer`)、同じ最初の問い、keep された turn までの 2 時間**。
読んだ concept はそれらの和、SQL は最後に提案されたものである。turn の形も
サーバーも変わらない — 束ねるのは読む側である。同じ人が同じ問いを 2 時間
以内に二度始めれば一つに束ねられるが、そのとき混ざるのは同じ問いへの
答えであって、比べる意味は崩れない。

同じ人の同じ問いが二度 keep されていれば、新しい方を一度だけ再生する。

## 3. どう採点するか

一問ごとに、次の二つを見る。

- **読み。** 正解が読んだ concept のうち、再生も読んだものの数。
- **結果。** 正解の SQL と、再生が最後に走らせた SQL を、どちらもその人
  として走らせ、**行が同じか**を見る。行の順は問わず、数は有効数字 9 桁で
  比べ、列は位置で — 位置が合わなければ列の順を問わずに — 比べる。
  text-to-SQL の評価で標準の実行一致である。1000 行を超える結果は比べず、
  比べられないと言う。

**合格は、結果が一致した問いである。** 正解に SQL が無いときは、正解が
読んだ concept をすべて読んだことが合格になる。正解に SQL も読みも無い
問いは、比べるものが無いので数えない。`--exit-code` は不合格が一つでも
あれば 2 を返す — `stats --exit-code` と同じく、エラーの 1 と区別して、
定期の job が回帰で赤くなる。

**答えの文は採点しない。** 文の良し悪しを機械で決めるには、文を読む
モデルが要る。それは LLM に裁定させることで([0145](0145-four-faces-and-an-answer-that-shows-its-result.md)
§5.2)、しかも採点を採点するものが要る。行と読んだ concept は、誰が
見ても同じに数えられる。

## 4. 何を出すか

一問一行(合否、結果、読み、問い、合わない理由)と、最後に一行で**どの
モデルが答えたか**を出す。モデルを替えた日の差を見ることが、再生の一番
多い使い道だからである。モデルの名前は `stats` の `agent.model` が返す
— 運用者が `OCHAKAI_AGENT` に書いたままの名前で、エージェントが入って
いるときだけ載る。応答だけに足すフィールドなので、凍結の対象ではない
([0082](0082-what-the-freeze-holds-still.md))。

**結果はサーバーに保存しない。** 保存すれば、再生の履歴という新しい面と
その保持の決まりが要る。CI に置いて毎回の出力を残す方が、どの版で何が
変わったかを、そのリポジトリの履歴として読める。

## 5. 面

- **CLI** に `ochakai eval` が入る。24 → 25 で、天井を上げる決定である。
  フラグは `--project`・`--limit`・`--exit-code`・`--json` で、どれも既に
  ある語である。
- **REST** は `POST /api/v1/agent` に既存の `dry_run` を許し、`stats` の
  `agent` に `model` を足す。操作もパラメータの名前も増えない。
- **MCP** には載せない。再生は人がモデルや知識を替えたときに走らせる
  測定で、エージェントのループの一歩ではない。
- **Web UI** には載せない(いまは)。SQL を走らせるには本人のトークンが
  要り、ページでは一問ごとにサインインを保つことになる。CI に置けない
  ことが決め手である。見直す条件: CLI を持たない運用者が、再生できずに
  実際に詰まった一件が出たとき。

## 6. 退けた案

- **サーバーが再生する。** SQL をサーバーが走らせることになる(0142 §4)。
- **答えの文を LLM に採点させる。** §3。
- **再生の結果を REST に保存して `stats` に載せる。** §4 — 保持の決まりと
  新しい面が要り、CI の履歴で足りる。
- **再生のための新しい語(`replay=true` など)を作る。** 意味は `dry_run`
  がすでに持っている(§1)。
- **turn に会話の id を足して、束ねる手間をなくす。** 保存の形とワイヤが
  動く。束ねる規則(§2)で足り、足りなくなったら、そのときに足せばよい。
