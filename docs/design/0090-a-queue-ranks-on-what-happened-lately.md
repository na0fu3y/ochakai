# ochakai 設計ドキュメント 0090: キューは、最近あったことで並ぶ

Status: Accepted(2026-08-10)。[0069](0069-the-loop-and-what-measures-it.md)
の利用測定を改訂する — 生涯累積のカウンタは残り、**フィードの並びだけが
固定窓の中の数に移る**。0069 が現行として持っている二つのフィード
(再検証と draft のプロモーションキュー)が、その並びを使う。
Date: 2026-08-10

## 0. この記録が決めたこと

1. `sort=usage` と `sort=failed` は、**直近 90 日の数**で並ぶ。生涯累積
   は残り、同点を割る。
2. その数はワイヤに出る — `usage.recent` の `days` / `fetches` /
   `failed`。**窓は数と一緒に運ぶ。**
3. 窓は**設定ではなく定数**であり、生イベントの保持期間の内側にある。

## 1. 生涯累積は、キューの並びとしては壊れている

利用カウンタは `knowledge_usage` の running total で、**減らない**。
そこにキューの並びを乗せると:

- ナレッジベースの最初の一か月に読まれた concept が、そのデプロイが
  生きているあいだ**ずっと**プロモーションキューの先頭に居る。
- 「次はこれを見よ」と言うためのキューが「あなたが既に見たものを見よ」
  と答える。
- 再検証フィードでは、**とうに直っていない古い常習犯**が、今週燃えて
  いる concept の上に出る。

再検証フィードは検証で**空になる**(0069 §1)ので、片方は既に解けて
いた — 直したものはフィードから落ちる。残って
いたのは**未応答のもの同士の順位**で、そこでは 2 年前の 50 件が今週の
3 件に勝っていた。しかも 2 年前の 50 件は、生イベントの保持期間を過ぎて
**もう手元に無い証拠**である。

## 2. 窓は 90 日で、これは決定である

**なぜ設定にしないか。** これはデプロイごとに違ってよい値ではなく、
「読まれたことが *需要* として数えられるのはいつまでか」という製品の
答えである。設定にすると、キューの意味がデプロイごとに変わる —
`ochakai stats` の数を人と人が比べられなくなり、フィードの並びについて
書けることが「設定による」だけになる。

**なぜ 90 日か。** 生イベント(`knowledge_event`)の保持は 180 日で、
窓はその内側でなければならない。**保持より長い窓は、期間のように読めて
「まだ残っている分だけ」を意味する。** 90 は四半期で、キュレーションの
サイクルとして人が言える単位であり、保持の半分なので保持を縮めても
すぐには嘘にならない。二つはテストが結び付けている。

## 3. 数え直しであって、減衰する列ではない

窓の中の数は `knowledge_event` を数え直して得る。**保存された減衰値を
持たない。**

- `knowledge_usage` の総和からは、窓の中の数は**そもそも取り出せない**。
- 保存された減衰は、定期的に走る何かを要求する。この製品はそういう
  可動部を持たない(cron も worker も無く、あるのはリクエストと、
  一日一度の剪定だけである)。
- `knowledge_event` は既にその行を時刻付きで持ち、`(knowledge_id, at)`
  に索引がある — この範囲スキャンそのものである。

コストは剪定が抑える。保持を過ぎた行は消えるので、この lateral が歩く
のは**履歴ではなく、キュレーションされたベースの活動の有界な窓**である。

## 4. 数はワイヤに出る

**並びを決める数が見えないと、その並びは壊れたソートに見える。** 20 回
読まれた concept が 3 回の下に居る画面は、数字が「20」と「3」しか出て
いなければ誤りである。

`usage.recent` が `days` を一緒に運ぶのは、**期間の暗黙な数は読者が
検算できない**からで、これは 0089 が `stats.embedding` で置いたのと同じ
規則である。

**二つだけである。** `search_hits` は需要ではない — ランカーは結果集合の
全 id に一つ記録するので、窓を掛けても「ランカーの最近の出力が最近の
需要」になるだけである([#566](https://github.com/na0fu3y/ochakai/issues/566)
が並びから外した理由と同じ)。`worked` は何の並びにも使われていない。

面の出方(0067): REST が契約、CLI は `ochakai usage` の三行と `list` の
ヘルプ、Web UI はレビューカードに `fetched 20 (3 in 90d)` として。MCP
には出さない — 並べるのはキュレーターであって、エージェントが一回の
ループで要る数ではない。

## 5. カーソルは、動く順序の上を歩く

窓の中の数は**時間とともに減る**ので、キーセットカーソルは動く順序の上
の位置になる。一回の歩行は数秒で、減るのは一日にイベント一件あたり最大
一である。境界をまたいだときに一件重複するか飛ぶことはあり得るが、
`created_at` と `id` の同点解消がその範囲を抑える。

これは検証時刻で並ぶフィードが既に持っている性質と同じで([0050](0050-listings-page-rankings-do-not.md))、
歩いている最中に誰かが検証すればその順序も動く。**総順序であることと、
その順序が不変であることは別である。**

## 6. やらないこと

- **窓を設定可能にすること**(§2)。
- **減衰する列を保存すること**、およびそれを走らせる定期実行(§3)。
- **`search_hits` と `worked` に窓を掛けること**(§4)。
- **生涯累積を捨てること。** 「これは今までにどれだけ役に立ったか」は
  別の問いで、同点を割るのにも使っている。
- **半減期のような連続的な重み付け。** 窓は説明できる — 「直近 90 日」
  は誰でも検算できる。半減期は、順位を説明するのに数式が要る。
