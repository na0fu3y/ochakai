## 0. この記録が決めたこと

**四つの記録が一つの絵であること。** issue
[#471](https://github.com/na0fu3y/ochakai/issues/471) が
[0065](0065-identity-and-provenance.md) / [0066](0066-four-postures-one-word.md)
で始めた統合の二回目である。決定は一つも動かない。

この四冊は互いを引用し合っていた。0062 は「0056 の系の、書かれていなかった
半分」を名乗り、0056 は 0055 を §0 に吸収し、0058 は 0051 の「較正されて
いない」を借り、0050 は 0049 との住み分けを一節かけて書いていた。**規則は
四つだが、それを読むには四冊を往復する必要があった。**

**そして二箇所が、既に事実でなくなっていた。**

- 0058 §5 は「`min_score=` を送っていた呼び出し元は、そのパラメータが
  無視される(未知のクエリパラメータは 400 にしない)」と書いている。
  [0064](0064-rest-stops-at-api-v1.md) §2 がそれを覆し、**いまは 400 で
  名指される**。released な記録の互換性の節が、後の決定によって逆になって
  いた。
- 0050 §2.3 は `GET /api/v1/queues` との住み分けを書いているが、その面は
  [0051](0051-instance-metrics-and-search-misses.md) §3.5 が `stats` に
  畳んで消えている。§2.1 の例も `/api/v1/knowledge` を叩いている。

論証の全文は各記録の墓標が指すコミットに残る。ここに残したのは**規則と、
それがいま何に効いているか**だけである。

## 1. 能力とコマンドは一対一である

**能力が一つなら、コマンドも一つでよい。** 二本目が買うのは capability では
なく convenience であり、[docs/surface.md](../surface.md) の三つ目の問い
(「既存の面で回避できるか」)の答えが「できる」なら、足さないのが既定で
ある。コマンドも語彙であり、両方を覚えている人は翻訳表を一行持たされて
いる。

**そして能力が二つなら、コマンドも二つである。** 一本に押し込むと、消える
のはコマンド数だけで、利用者が覚える規則は消えない — フラグのヘルプに移る
だけである。

この二つは同じ規則の両面であり、片方だけでは働かない。**畳むのは能力が
同じ二本であって、行為が違う二本ではない。**

適用の記録:

| 何が起きたか | どちらの向きか |
|---|---|
| `ochakai backlinks` を `ochakai search --links-to` に畳んだ | 一つの能力に二つのコマンド |
| `ochakai queues` を `ochakai stats` に畳んだ | 同上 |
| `ochakai search --sort` を `ochakai list [feed]` に割った | 一つのコマンドに二つの能力 |
| `ochakai verify` と `ochakai reject` は**二本のまま** | 行為が違うので畳まない |

第二の住所は無料ではなかった。`backlinks --limit` のヘルプは**嘘になって
いた** — 消えた面の既定値(20 / 100)を説明していたが、実際の経路は
`search` の一覧(100 / 1000)だった。**二つ目の面は二つ目の説明を持ち、
そちらだけが腐る。** `queues` と `stats` は同じ三つの数を
`reported wrong` と `reported_wrong` という別の綴りで印字しており、
片方を grep する読み手にはそれは別の語彙だった。

逆向きの代金も出た。コマンドを割ると**参照文が重複する** —
[cli.md](../cli.md) は九つのフィルタを二度書くことになり、それまでどこにも
現れていなかった代金として `DOC-LINES` に出た。それでも割ったのは、
**どちらのコマンドの `-h` も一つの仕事しか説明しない**ようになるからで
ある(`search -h` の前置き散文は 30 行から 9 行になった)。

`verify` と `reject` を畳まないのは、ワイヤでは同じ操作の値違いでも、
ターミナルで打つ人にとって「検証する」と「却下する」が別の行為だから
である。`--ruling` を打たせるのは CLI を REST の写像にすることである。

## 2. 一覧は検索ではない

一覧と順位は**別物である**。一覧は全順序なのでページングでき、順位は
関連度の順なのでページ二枚目に意味がない。

| | 検索(順位) | 一覧 |
|---|---|---|
| ワイヤ | `GET /api/v1/search?q=` | `?sort=` / クエリ無しの `source=` / `links_to=` |
| `limit` 既定 / 上限 | 10 / 50 | 100 / 1000 |
| `cursor` | **400** | 進み方そのもの |
| CLI | `ochakai search <query>`(クエリ必須) | `ochakai list [feed]` |

**ワイヤは一本のままである。** REST で一覧と順位が同じ操作なのは、
フィルタが完全に共通で応答の形も同じだからで、分けたいのは人が打つときの
規則のほうである。

### 2.1 一覧のページングは keyset である

一覧はいずれも全順序を持ち(最後の同点解決は必ず `id`)、その順序の中の
一点を運べば続きが引ける。`OFFSET` は読み飛ばす行数に比例して遅くなり、
しかもページ間で行が動くとずれる — 検証すれば `sort=verified_at` の順位が
変わる面で「N 件飛ばす」は位置の指定として意味を持たない。

- **`cursor` は不透明である。** 利用者が組み立てるものではなく、直前の
  応答から受け取って返すもの。別の一覧のカーソルを渡したら 400 で、
  どの一覧のものかを言う。
- **フィルタはカーソルに入らない。** カーソルは順序の中の位置であって
  クエリのスナップショットではないので、次のページも同じフィルタを添えて
  呼ぶ。
- **総件数は返さない。** `cursor` の不在が「ここで終わり」であり、それ以上
  は言わない。フィルタの効いた一覧の正確な件数は、ページを一枚返すのと
  同じスキャンをもう一度することであり、**一ページ目の費用を毎回倍にして
  進捗バーを描く**のは、キューを空にするために読む面が払う値段ではない。
  UI が要るのは「まだあるか」で、それは `cursor` の有無が既に答えている。
- **カーソルはスナップショットではない。** フィードは生きているので、
  歩いている間に位置より前へ動いたエントリは見えないことがあり、後ろへ
  動いたエントリは二回見えることがある。これは keyset の性質であって
  欠陥ではない — 保証するのは歩き切ることではなく、**上限で静かに
  止まらないこと**である。スナップショットが要るならエクスポートの仕事で
  ある。
- **カーソルに署名しない。** 改竄されたカーソルは変な位置から始まる一覧を
  返すだけで、フィルタも権限も動かさない。守るものが無いところに鍵は
  置かない(secret-zero)。復号できない値は 400 で落ちる。

### 2.2 順位はページングしない

`q=` と `cursor` の同時指定は **400** である。理由は二つあり、片方は
技術的で片方は製品的である。

**順位に「次のページ」は無い。** 検索は lexical・vector・ファイルの三本を
それぞれ 2×limit 取って RRF で融合する。融合の窓が順位そのものであって、
51 位を出すには窓を広げて上位 50 を捨てる — ページごとに費用が増える
offset になる。しかも順位は書き込みのたびに動くので、その 51 位は一ページ
目と整合しない。**正しく答えられない問いに、答えの形だけを与えない。**

**ochakai が返すのは行ではなく知識である。** 50 件で足りない検索は、ページを
進める問いではなく**絞り込みが足りない問い**である。フィルタはそのために
あり、フィードは「全部読む」ためにある。この二つを混ぜない。

**CLI はページを自分で歩かない**(意図的な省略)。`reembed` は歩き切ること
が目的のコマンドなので自分で回すが、`list` の出力は人とパイプが読むもので
あり、`--limit` は利用者が置いた上限である。それをコマンドが黙って越える
のは、`head` を付けた出力が勝手に伸びるのと同じ驚きになる。見直す条件は
`--all` を求める声が出たときである。

## 3. 通行量の無い入口は降ろす

第二の住所ではなく、**最初から誰も通らなかった入口**を降ろす規則である。
畳み込みと違い、ここでは能力が落ちることがある — そう言って落とす。

**`min_score` は廃した。** スコアはモード依存で較正されておらず
(レキシカルはフラグメント一致重み、ハイブリッドは RRF の ~0.02 スケール)、
片方で意味のある床はもう片方では無意味である。同梱の唯一の利用者である
recall フックが既定 0 = off で渡し、README がその隣で「較正してから使え、
普遍的な既定は無い」と説明していた — **製品が自分で「使うな」と書いている
面**が三つの面に載っていた。代替は置かない。応答を絞る手段は較正の要らない
`budget` が既に持っており、入りきらなかったものは `outline` に名前が返る。
落ちた能力は「較正した呼び出し元が床を置く」ことで、その較正の手順を製品は
説明できなかった。

**`fm.` は MCP からだけ降ろした。** REST と CLI には残るので
[0047](0047-fm-carries-okf-keys.md) の決定も導出も不変である。降ろした
理由は値段で、同じ 944 文字の説明が 2 ツールに載ってスキーマ説明文の
**14%**(1,888 / 13,099 文字)を占めていた — 接続するエージェントが毎回
払う。対して Web UI にも examples にもフックにも通行の跡が無かった。
`fm.` は「どのキーで絞るかを既に知っている人」の語彙であり、エージェントに
その前提を満たさせるための説明は**課金される**。**ツール数は 8 のまま、
エージェントが払う額だけが減る。**

説明を短くする案は採らなかった。944 文字を 200 文字に削ると
「`fm.status` と `status=` はなぜ違うのか」に答えられず、答えられない説明は
間違った使い方を招く。**説明の長さは `fm.` の性質から来ており、縮められる
のは説明ではなく載る面である。**

見直す条件: MCP クライアントが `fm` の無いことで詰まった実例が出たら、
`search_concepts` にだけ戻す。そのときの説明文は 11 個の綴りを列挙せず、
「引けるキーはエラーが教える」形にする — サーバは既に `askableHint` で
それを返している。

## 4. 裁定は一つの面から下し、一つの語で言う

`POST /api/v1/verify/{id}`、`POST /api/v1/reject/{id}`、
`DELETE /api/v1/reject/{id}` は構造的性質をすべて共有していた — 文書に
触れない、台帳に書く、呼び出し元の identity で記録される、人の面に載り
MCP には載らない。**値だけが違う三つの操作は、パラメータを持つ一つの操作で
ある。**

**`POST /api/v1/review/{id}`** が三つを置き換える。本文に
`{"ruling": "verified" | "rejected" | "withdrawn"}` を取り、応答は concept
そのもの(ETag 付き)。`note` は `rejected` 専用で、他の ruling と一緒に
来たら 400。

**`withdrawn` は DELETE ではない。** 検証は追記のみの台帳、却下は一つの
生きた裁定であり、却下を降ろす操作は台帳の行を消すのではなく履歴に一行
増やす。「削除と読まれない綴り」を選んだ判断であり、**選ばれた語のほうへ
四つの面を揃えた**:

| 面 | 綴り |
|---|---|
| REST の `ruling` | `withdrawn` |
| CLI | `ochakai reject --withdraw` |
| Web UI | `Withdraw rejection` |
| リビジョンの `change` | `withdraw` |

ワイヤの ruling は分詞、リビジョンの `change` は動詞である。二つの活用が
あるのは既にそうなっており、語幹が割れていたのはこの一語だけだった。
既存行はマイグレーション `0034` が書き換えている — **書き換えたのは事実
ではなく符号**であり、誰がいつ何を取り消したかは一行も動いていない。

## 5. これらの規則が動かさないもの

- **REST を割らない。** 一覧と順位が同じ操作なのはフィルタと応答の形が
  共通だからで、畳んだものを戻す提案ではない(§2)。
- **`fm.` を REST から消さない。** REST は唯一の契約であり、「利用者が
  自分の Web サービスに埋める小さな API」という条件(C6)は「自分のアプリが
  何を引きたいか知っている」呼び出し元を想定している。`fm.` はその
  呼び出し元の語彙である。
- **スコアを較正し直さない。** モード間で比較可能なスコアを作ることは検索の
  設計をやり直すことであり、そこまでして買えるのは**誰も要求していない床**
  である。
- **非推奨期間を置かない。** 0.x に deprecation window は無い
  ([compatibility.md](../compatibility.md))ので、畳んだコマンドは
  「そんなコマンドは無い」で落ちる。0.x の間だけが、説明を増やさずに
  畳める期間である。
