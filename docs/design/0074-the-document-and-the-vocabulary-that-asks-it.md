[#471](https://github.com/na0fu3y/ochakai/issues/471) が始めた統合の三回目
である。決定は一つも動かない。

0075 が前者を持ち、この記録が後者を持つ — concept 文書が自分について何を

## 1. ファイル名が名前である

**住所の末尾は、多くの場合そのまま名前である。** 特に日本語では、スラグ化
した別名を作る動機がない。

- **`title` は任意である。** 表示名は title があれば title、無ければ id の
  末尾セグメント。title は「ファイル名で足りないときのオーバーライド」に
  降格する — 128 バイトに収まらない題、`/` を含む題、外来バンドルが持ち込む
  題のためにある。OKF SPEC が必須とする frontmatter キーは `type` だけで
  あり、**title 無しの文書を拒んでいた以前のほうが SPEC より狭かった。**
- **エクスポートは、title が空のときだけ省略する。**「末尾セグメントと
  同一なら省略する」ような積極的な正規化は**しない** — 外来バンドルのバイト
  同一の往復を壊すからである。title 無しで入った文書は title 無しで出て行く。
- **id は検索の対象である。** 字句のハイスタックにも埋め込みテキストにも
  id が入る。`用語/売上` は「売上」で引ける。パスはドメイン階層を含むので、
  title を持つ concept でも文脈が増える。

### 1.1 鍵として比較される文字列は NFC に正規化する

macOS のファイルシステムはパス名を NFD 分解して返す。バンドルを macOS で
展開して再 tar すると、**見た目が同一の `サンプル`(NFC)と `サンプル`(NFD)
が別の concept として静かに二重化する。**

だから `domain.Normalize`(Unicode NFC)を、**バイト比較される文字列が入る
すべての境界**で適用する — id を受ける全入口、リンクの target、ファイルの
パス、バンドル取り込みのパス、そして検索クエリ(NFC で保存された本文と
照合するため)。

**本文・title・description は正規化しない。** 内容は書かれたままであり、
**正規化するのは鍵として比較される文字列だけ**である。DB 内の照合は素の
バイト比較のままで、正規化は入口のみで行う。

## 2. リンクは本文から導出する

構造化された `links` 入力は持たない。**本文が関係である。**

理由は三つあった。OKF SPEC はリンクを素の markdown リンクとしてのみ定義し、
関係の種類は「リンク自体ではなく周囲の散文が伝える」と明言している。
`rel`(関係の型)は**機械可読な型として導入されたが、機械が一度も読んで
いなかった** — 値で分岐するコードが一つも無かった。そして本文と `links` は
二重管理で同期せず、move は `links` 列だけを直して**本文中のリンクを壊れた
まま放置していた**。

- **抽出の対象**は本文中の markdown リンク(バンドル絶対 `/path.md` と
  相対 `./x.md`)である。相対パスは concept 自身の id が属するディレクトリを
  基準に解決する。
- **`http(s)://` は抽出しない。** サーバは自分の公開 URL を知らず、環境依存の
  解決はバンドルの可搬性を壊す。
- **フェンスドコードブロックとインラインコードの中は除外する。** コード例に
  書かれたリンクが関係になるのは明確な誤りである。
- **`Link` が持つのは `target` と `text`(アンカーテキスト)**であって
  `rel` ではない。SPEC がリンクテキストを関係名と定めていない以上、型として
  扱うことはできない。空なら表示は末尾セグメント(§1)。
- **move は本文を書き換える。** 参照元の本文も、移動する concept 自身の
  本文も対象で、書き換え後にリンクを再導出する。
- **dangling は許容する。** 存在しない concept へのリンクは、後からその
  concept が作られれば自然に繋がる。

## 3. id の文字種は、パス安全性だけを制約にする

OKF SPEC はファイル名の文字種を規定せず、予約するのは `index.md` と
`log.md` だけである。かつてのスラグ規則は、BigQuery の `_` 始まりデータ
セット(`tables/_intraday.md`)を弾き、日本語の用語集を `用語/売上` に
置けなくしていた。

制約は**非空の正しい UTF-8、128 バイト以下、制御文字なし、先頭 `.` 禁止**
(`.` / `..` / 隠しファイルを一括で排除)だけである。id 全体は 512 バイト
以下、末尾セグメントの `index` / `log` 予約は残る。

**型は語彙であって、パスではない。** 型の綴りにはこの緩和を及ぼさない —
型はフィルタ・frontmatter・ツール引数で綴られるものである
([0071](0071-the-recommended-type-vocabulary.md))。

## 4. 問いの語彙は、OKF が定義するキーである

frontmatter は jsonb に索引され、`fm.<key>=<value>` で引ける。目的は
**SPEC が新しいキーを足した日から、マイグレーション無しで引ける**ことで
ある。だが引ける語彙は閉じていなければならない。

### 4.1 列を持つキーは、列が答える

`type` / `status` / `tags` / `sources` / `stale_after` を `fm.` で名指したら
**400 を返し、使うべきフィルタを名指す。**

理由は、**同じキーが綴りによって別の問いになる**からである。`status=stable`
は「stable と書いた文書」と「何も書いていない文書」の両方に当たる(列は
SPEC §5.4 の既定を適用する)が、`fm.status=stable` は前者にしか当たらない。
`type=` は case を畳み、`fm.type=` は畳まない。`sort=stale_after` は `date`
として比較し、`fm.stale_after` は文字列一致なので `2026-6-1` と
`2026-06-01` が別物になる。

**どれも単体では間違っていない。問題は、利用者がどちらの綴りを使ったか
自覚できないことである** — とりわけ status の食い違いは、`draft` と書かずに
エージェントが作った全 concept に効く。**片方の綴りが静かに少なく返すのは、
間違った答えのうち正しい答えに見える種類のものである。**

### 4.2 OKF が定義しないキーは引けない

producer が発明したキーを名指したら 400 を返し、**引けるキーの一覧を返す。**

- **空の結果が答えなのか綴り間違いなのか、利用者に判定できない。**
  `fm.owner=finance` の 0 件は「owner が finance の concept は無い」なのか
  「その producer は `team` と書いていた」なのか区別がつかない。
- **引けるキーの一覧をどこにも書けない。** producer が発明したキーの集合は
  ochakai が知り得ないので、OpenAPI にも CLI のヘルプにも列挙できず、呼び手は
  推測で引くことになる。**ochakai は中に LLM を置かない。推測を要求する面は、
  その姿勢と噛み合わない。**
- **SPEC が要求しているのは保存と往復であって、問いではない。**

**保存と往復には一切触れない。** 届いたキーはすべて保たれ、エクスポートは
すべて返す。変えるのは**引けるもの**であって**保存されるもの**ではない。

引ける集合は書き下さず、`domain.EnvelopeKeys` から導出する — **OKF が新しい
キーを足し、その綴りをこの一覧が覚えた日に、そのキーは引ける。列も
マイグレーションも要らない。** 拒否はサービス層一か所にあり、どの面も同じ
導出から自分を説明する。導出は OKF が定義するキーに限る — envelope には
ochakai 自身のキーが二つ紛れており(`id`・`status_note`)、「語彙は OKF の
もの」という本節の理由がそのまま二つを読み出しから外す(0064 が凍結の
直前に閉じた)。

## 5. dry run は、書き込みを止めたものである

`ochakai import --dry-run --strict` は CI の関門として文書化されていたのに、
**関門が緑で本番が赤くなった。偽グリーンである。**

原因は、`--strict` が落ちる理由の半分が**パース結果からは決まらない**こと
だった — 文書が持つ trust family が claim として残るかは**保存されている
ものとの比較**であり、サーバがその文書を拒むかも、書き込みが何も変えないかも、
バンドルの外にある。dry run が並べていたのは「パースできた」ことだけだった。

**だからサーバに聞く。** `PUT` に `dry_run` を足し、同じ検証・同じ読み取り・
同じ規則・同じ note を通して、**書かない**。

- 応答は常に **200**。作られていないものに 201 を返すのは、汎用クライアント
  に対する嘘である。**ETag は付けない** — 書かれていないのだから
  precondition に使える version は存在しない。**DELETE では 400**:
  delete に「何が起きるか」は無く、黙って無視すれば聞いたつもりの呼び出し元の
  オブジェクトが消える。
- **ヘッダではなくクエリパラメータである。** proxy に落とされたヘッダは
  dry run を**本番の書き込みに変える**。落ちると壊れるより、落ちると壊れない
  ほうを選ぶ。
- 答えは `Ochakai-Plan: created | updated | unchanged` の三値である。
  `Ochakai-Unchanged` は三値のうち一つしか言えず、二つのヘッダに割ると
  クライアントは片方しか読まなくなる。**ヘッダを知らないサーバへの dry run は
  エラーである** — 不在は「きれいだった」ではなく「書いてしまったかもしれ
  ない」を意味する。
- **判定は一つの経路から出る。** plan は書き込みの判断部分を共有し、その手前
  で返す。**別に書き下した plan は第二の意見であり、二つはいずれずれる。**

クライアント側で作り直す案は却下した。増えないのは表面だけで、増えるのは
**書き込み経路の判断の第二の実装**である。しかも再現は正確にならない —
**推測に推測を重ねた関門は、直そうとしている偽グリーンと同じ種類のもので
ある。**

## 6. 取り込みは、一文書の拒否で止まらない

`ochakai import` はサーバーの 400(入力起因の拒否)を**その一文書のスキップ**
として扱い、レポートに載せて続行する。スキップされた concept に帰属する
ファイルも併せてスキップする。

**認証・ネットワーク・5xx は従来どおり中断する** — パイプラインの故障と、
一文書への判定は別物である。

## 7. やらないこと

- **サーバー側の id 導出**(「フォルダ + 名前 → id」)。正規化・衝突・
  リネームの意味論をサーバーに持ち込む。入力体験はクライアントの仕事である。
- **`title` 列の廃止**、および id 以外の NFC 正規化(§1)。
- **`[[wikilink]]` 記法**と**リンク型の別形での存続。** SPEC に無い。型付きの
  関係が本当に要ると分かったら、SPEC §4.1 の拡張キーとして持つのが筋である。
- **`fm.` を全面的に撤去すること。** `resource` / `runtime` / `status_note` /
  `usage_window` のように **OKF が定義しているのにフィルタを持たないキー**を
  訊く綴りが一つも残らない。とりわけ「この BigQuery テーブルを説明している
  concept はどれか」は中心的な問いであり、`fm.resource=` はその唯一の綴りで
  ある。**問題は語彙が開いていたことであって、語彙があったことではない。**
- **キーごとに named フィルタを足すこと。** フィルタ名という第二の語彙を
  増やす。`fm.<OKF のキー>` は綴りが SPEC と同じで、覚えるものが一つ少ない。
- **一括の plan エンドポイント**(既存のループで足りる)、**dry run を MCP に
  載せること**(バンドル同期を関門に通す人のものである)、そして
  **read-only での dry run を通すこと**(書けないインスタンスの答えは
  「書けない」である)。
- **型の文字種の緩和**(§3)、**取り込みの 4xx 全般のスキップ化**(404 や
  409 は既存の分岐の一部である)。
