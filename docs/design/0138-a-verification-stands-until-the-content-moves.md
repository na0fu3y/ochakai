# ochakai 設計ドキュメント 0138: 検証は、内容が動くまで立っている

Status: Accepted(2026-09-02)。trust tier の**導出**を改訂する —
[0065](0065-identity-and-provenance.md) §6 の「trust tier は検証台帳の
`human:` だけから導かれる」の一文と、
[0069](0069-the-loop-and-what-measures-it.md) §2 の表(キューが三本で
あること)を改訂する。台帳が append-only であること、SPEC §5.3 の三値の
語彙、検索が何を融合するか([0080](0080-search-and-how-a-deployment-embeds.md))、
ブーストが 1 順位ぶんであることは、どれも動かない
Date: 2026-09-02

## 0. この記録が決めたこと

1. **tier は「立っている検証」から導く。** 立っているとは、`at` が
   concept の `generated.at`(最後の意味のある変更、SPEC §5.2)以降で
   あること — つまり**いまの内容を確認した行**であること。
2. **編集と move は検証を失効させ、整形は失効させない。**
3. 失効した concept を空にできる**四本目のキュー `edited`** を数える。
   一覧は既存の語彙の組合せで、専用の sort は足さない。
4. **検索順位は変えない。** 失効で消えるのは 1 順位ぶんの加点の根拠
   だけで、減点は入れない。

## 1. 誰が詰まったか

検証済みの concept を verify の後に編集しても、一覧と検索は
human-reviewed を返し続けていた。読み手にこれは「いまの本文を人が確認
した」と読める — が、その本文は誰も確認していない。利用者からの要望は
「verify 後の編集を減点してほしい」だった。

原理は台帳の側に既にあった。墓標の上の Create は台帳を消し、理由を
こう書いている:「**誰も検証していない内容を、検証が保証してはならない**」
(store.go)。Update だけがこの原理の外にいて、編集された内容に古い
検証の保証を着せ続けていた。直すべきは順位ではなく、この非対称である。

## 2. 減点ではなく、導出の正直さ

順位への減点は採らない。理由は三つある。

- **「編集後」は「間違い」ではなく「再確認が必要」である。** 誤りと
  *報告された* concept ですら順位に混ぜない(0069 §7)。それより弱い
  信号を混ぜる理由は立たない。
- **実測が逆を言っている。** かつてブーストは 0.002(≒7.6 順位)で、
  searcheval がそれを測ったら fused MRR は 0.89 → 0.83 に落ちた。
  信頼シグナルを順位が動く強さで効かせると、検索は悪くなる。
- **減点が罰するのは人のキュレーションである。** verified を編集できる
  のは人の面だけ(MCP は裁定済みの置き換えを拒む)。誤字を直し期限を
  引き直す編集に順位で課金すれば、検証済みに触るなと教えることになる。

代わりに導出を正直にする。tier を立っている行だけから導けば、失効した
concept は unverified になり、fuse の 1 順位ブーストと字句側の加点・
同点解消は **tier から読んでいるので自動で消える** — 減点ではなく、
加点の根拠が消える。重みの秤は一つも増えない。

## 3. 何が失効させるか — move も、である

比較対象は `generated.at`(内部では `content_changed_at`)である。
整形だけの書き込みはこれを動かさない(0046 §3.4 の SameContent)ので、
綴り直しで tier は落ちない。編集は動かすので、失効する。

**move も失効させる。** これは今回選んだのではなく、既にある決定の
帰結である — [0036](0036-okf-schema-first.md) §3.3 は move で
`generated.by` を**移動した人に付け替える**と決めており、OKF の目には
move は内容の出来事である。内容が立ち替わったのに確認だけが跨いで立ち
続けるほうが、あの決定と喧嘩する。`moveprefix` も、move が本文リンクを
書き換えた**参照元**も同じである。

move を跨げる検証 — move が動かさない第二の時刻列や、内容ハッシュへの
紐付け — は採らない。どの案も **tier をバンドルから再計算できなくする**:
いまの導出に要る二値(`generated.at` と `verified[].at`)は export が
両方運ぶので、輸入側が同じ答えを出せる(0009 の線)。列は運ばれない。
rename の再検証は移動した本人の一行で済み
(`ochakai list verified_at --trust unverified --prefix … | cut -f1 |
xargs -n1 ochakai verify`)、それは generated.by を引き受けた者が自分の
名前で確認し直すという、台帳として正直な形でもある。CLI の move は
失効が起きたときにこの導線を stderr で言う。
**見直す条件**: 大きな部分木の rename で再検証の実務コストが痛いと
実運用が言ったら、そのとき跨げる機構を秤にかける。

**時計は二つある。** `content_changed_at` はアプリの時計
(NowStored)、検証の `at` は失敗報告と比べるために DB の `now()` で
ある(0069 §2.1 の理由)。DB が遅れていると、直後の verify が
`at < content_changed_at` で立たない。だから verify は
`GREATEST(now(), content_changed_at)` で記録する — 検証は定義上
「いまの内容」の確認なので、その内容より前の瞬間として記録するほうが嘘
である。

## 4. 変わる面と、変わらないもの

変わるのは trust の読みが現れる四か所である: `trust` フィールドと
`--trust` フィルタ、`stats` の trust 集計、字句検索の加点と同点解消、
fuse の 1 順位ブースト。ワイヤの**形**は 1 バイトも動かない。

変わらないものは決定として書いておく。

- **`verified_at` は台帳の事実のまま**(最新の行。立っているかを問わ
  ない)。「最後にいつ誰かが見たか」はフィードの鍵であり、履歴の問いで
  ある。読み手は `trust=unverified` と非空の `verified_at` の並びから
  失効を読める。
- **failed キューの述語は動かない。** あの出口は裁定であって、立って
  いる検証ではない。
- **裁定ガード(MCP の置き換え拒否)は台帳の在否のまま。** 守っている
  のは「この id に人が裁定した」という履歴で、履歴は編集で消えない。
- **export は全行を書く。** provenance は履歴である。在否だけを読む
  素の v0.2 消費者はこの instance より甘い tier を導き得るが、厳しく
  読むための材料はバンドル自身が運んでいる(上の §3)。
- **台帳は一行も消えず、変異しない。**

## 5. 四本目のキュー `edited`

失効した concept は、これまでどのキューにも乗らなかった — failed は
報告が要り、stale_after は宣言が要り、drafts は status が要る。空に
できないどころか**見えない**仕事で、0069 §1 の三部品の穴である。

- **述語**: 台帳に行があり、立っている行が無い。verify(立つ行が増える)
  か削除で空になる。
- **一覧は既存の語彙で引ける**: `ochakai list verified_at --trust
  unverified`。成員は検証時刻の古い順に先頭へ、never-verified の尾が
  空の第一列で後ろに続く。専用の sort はこの一覧で足りなくなった実需が
  来たら足す。
- **名前は `edited`**。単一の sort ではないので、drafts と同じ例外と
  して自分の語を持ち(0069 §5.2)、その瞬間に VOCAB に数えられる
  (45 → 46)。原因で名づけるのは failed(報告された)・stale_after
  (宣言が切れた)と同じ向きである。
- 面: `stats` の `queues.edited` と `--exit-code`、Web UI のフィードと
  バッジ。**MCP には出さない**(0067 — 並べるのはキュレーターであり、
  そもそもエージェントは verify できない)。

## 6. 何を差し出しているか

- **アップグレードで tier が落ちる concept が出る。** verify 後に編集
  ・移動されたものは unverified に戻り、stats の trust の数が動く。
  それがこの記録の目的そのものだが、リリースノートが上の一行と
  re-verify の導線を言う。
- **素の §5.3 消費者との読みの差**(§4)。
- **rename が再検証の作業を作る**(§3、見直す条件つき)。

## 7. やらないこと

- **検証回数・人数による第四の tier。** 語彙は SPEC のもので、閾値は
  読み手の政策である — ochakai は記録し、判断は参照側が行う(0065 §1)。
- **順位の減点**、および tier 間の重み付け(§2)。
- **move を跨ぐ検証**(§3 の見直し条件つき)。
- **台帳の行の削除・変異・自動 re-verify。** move が移動者名義の検証を
  自動で書けば、誰も打っていない裁定が台帳に載る。
- **`edited` 専用の sort・フラグ・エンドポイント**(§5)。
