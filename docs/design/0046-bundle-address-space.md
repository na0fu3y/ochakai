## 1. 目的

0043 は「OKF 文書を保存とワイヤの唯一の正とし、写像を恒等に潰す」と決めた。
正しい決定であり、本ドキュメントはそれを覆さない。しかし 0043 が恒等に
したのは**概念 1 件の表現**までであって、**バンドル**ではなかった。
OKF 互換だけを制約に置いて残りを数えると、写像は 5 か所残っている。

- **バンドルの往復が恒等でない。** SPEC §11 が要求を課すのは非予約の
  `.md` だけで、それ以外のファイルには何も言っていない。バンドルとは
  「パス → バイト列の木」である。ochakai だけがそれを *概念 / 添付 /
  スキップ対象* の 3 種に割っており、3 番目は**取り込みで消える** —
  `type` を持たない `.md`、どの本文からも参照されず `<id>/` にも居ない
  非 md ファイルは `skipped` に落ちる。エクスポートしたバンドルを
  インポートし直すと、ファイルが減る。
- **予約ファイルが導出面になっていない。** SPEC §8 は `index.md`、§9 は
  `log.md` の形を定義している。ochakai は前者をエクスポートでだけ再生成し、
  後者を出さず、代わりに `/api/v1/browse` と `/api/v1/revisions/{id}` という
  2 つの別のアドレスを持っている。0043 §5 は「log.md の中身の規約は SPEC が
  決めること」として見送ったが、**§9 は既に決めている**。
- **本文リンクが非可搬。** SPEC §6 のリンク形はバンドル絶対(`/` 始まり)と
  相対である。ochakai は `ochakai://<id>` という自作スキームを本文の第一級の
  形として教えており(0024)、その本文はそのままバンドルに出て行く。
  他の consumer には解決できない URI であり、**ochakai が書き出すバンドルの
  OKF 互換上の欠陥**である。
- **サーバーが受け取った文書を書き換える。** 0043 §3.7 は書き込みを
  「パース → 検証 → **正準形への再シリアライズ**」と定めた。ハッシュの
  安定のためだが、代償として frontmatter のコメントとキー順が失われる。
  SPEC はどちらも要求していない — 要求しているのは §4.1 の
  「未知のキーを保存し、往復させ、拒否しない」である。同じ手癖は
  `CanonicalType` の case 書き換えと、`status` 既定値の注入にも出ている。
- **クエリ面がキー列挙のまま。** 0043 §3.1 は索引を「type / title /
  description / tags / status / stale_after / sources …」と列挙した。
  保存は additive になったが、**SPEC が新しいキーを足すたびに列が増える**。
  0043 が消したはずの「SPEC の一挙一動が写像の再設計になる」が、
  クエリ面にだけ残っている。

5 つは別々の欠陥ではなく、1 つの前提の帰結である — **ochakai はまだ
「知識エントリの集まり」を主概念に持ち、バンドルをその出力形式として
扱っている。** 本ドキュメントは前提を逆にする: **バンドルが主概念であり、
知識エントリはその中の 1 種類のオブジェクトである。**

### 1.1 実装を伴わない採択について

0043 §1.1 と同じ理由で、決定だけを先に採択する。変更が保存形・ワイヤ・
4 サーフェスに跨り、レビュー可能な 1 PR に収まらない。0034 の教訓も同じく
適用される: 実装が本ドキュメントの規則の誤りを明らかにしたら、リリース前で
あれば部分改訂を積まず本ドキュメントごと置き換える。

## 2. 世界観

### 2.1 バンドルがアドレス空間

**ochakai が保持するのは、1 つのバンドル — パスからオブジェクトへの
写像である。** オブジェクトには 2 種類しかない:

| | 何か | どこに置くか |
|---|---|---|
| **概念(concept)** | `type` を持つ frontmatter のある `.md` | 文書のバイト列(DB) |
| **ファイル(file)** | それ以外のすべて | markdown は DB、非 markdown は GCS(0013 の判断を維持) |

`type` を持たない `.md` は概念ではないが、**ファイルとして保存され往復する**。
どの概念からも参照されない `.txt` も同じである。**バンドルに入ったものは
出てくる** — これが本ドキュメントの中心的な不変条件であり、
`skipped` の行が「取り込めなかった」ではなく「概念として索引しなかった」を
意味するようになる。

添付(attachment)という概念は対象消滅する。「このファイルはどのエントリの
ものか」は、リンクと同じく**本文からの導出**である(0024)。0008 の
「原本ではなく根拠」という位置づけと `<id>/<name>` の慣習は、
**帰属の導出規則**として残る — 保存された関係としてではなく。

### 2.2 サーバーは受け取った文書を書き換えない

**書き込みで保存するのは、受け取ったバイト列そのものである。** 正準形は
保存形ではなく**導出値**になり、内容が変わったかの判定と索引にだけ使う。
0043 が「文書が正」と言ったことを、バイト列の水準まで下ろす。

同じ原則が語彙にも及ぶ。ochakai は書き手の書いた `type` の case を直さず、
書き手が書かなかった `status` を書かない。SPEC §5.4 は不在の既定を
`stable` と定めており、**既定を適用するのは読み手であって保存側ではない**。

例外は 1 つだけで、それは 0009 から続く: **サーバー所有キー**
(`generated` / `verified` / `created_by` / `rejected_*` と、SPEC §13.1 の
v0.1 綴り)は受け取った位置に置いておけない。エクスポートで**このインス
タンスの観測**を同じ名前で書き戻すのに、YAML はトップレベルの重複キーを
許さないからである。したがって書き込みで**行単位に外科的に取り除き**、
エクスポートで書き戻す。再シリアライズではなく行の削除・追記なので、
他のキーもコメントも順序も動かない。

**取り除くことは、捨てることではない。** 文書が自分について書いた
trust family は、`received:` の下に**主張(claim)として残す**。

- **主張と観測を分ける。** 台帳は今までどおり「このインスタンスが
  観測したこと」だけを意味し、**主張はどの台帳にも入らない**。
  trust tier(§3.10)も `trust=` も、主張からは導かない。0009 §3.3 の
  「認可を持たない以上、provenance をペイロードから受けた瞬間に信頼の
  アンカーが消える」は正しく、本ドキュメントはそれを覆さない。覆すのは
  「だから捨ててよい」のほうである。
- **入れ子が両者を 1 つのファイルに同居させる。** `verified` は常に
  このインスタンスの台帳、`received.verified` は常に他者の主張であり、
  同名の 2 つを読み手が見分ける必要も、エクスポートで衝突する余地も無い。
- **捨てた主張は、後のどのリリースでも復元できない。** 0043 §3.6 が
  構造化オブジェクトの内側の未知キーについて言ったことは、trust family
  にもそのまま当てはまる。ここは §3.2「バンドルに入ったものは出てくる」が
  唯一届いていなかった場所だった — 移行と共有(0009 §2 が絞り込んだ 2 例)で
  失われるのは、他人が誰の何をいつ確かめたか、という復元不能な事実である。
- **既に主張を持つ文書の trust family は落とす。** それはあるインスタンスの
  エクスポート形であり、§2.3 の非対称(エクスポートは出し、インポートは
  読み戻さない)がそのまま当てはまる**観測**だからである。`received:` は
  文書が自分について言ったことであって、運んだインスタンスの連鎖ではない。
- **自分のエクスポート形は主張ではない。** 文書に添えられた trust family が
  そのエントリについてこのインスタンスが観測したことと一致すれば、それは
  戻ってきた自分の観測であり、書き込み経路が取り除く。これが
  get → 編集 → PUT と export → レビュー → import が**前と同じバイト列を
  保存する**条件であり、判定にエントリが要る以上、パースではなく書き込み
  経路の仕事である。
- **黙って落とさない。** 主張として受け取ったことは import の note に出る。
  SPEC §11 は consumer に「黙って落とさず表に出す」ことを求めており、
  trust family だけが例外である理由は無い。

### 2.3 予約ファイルは導出面である

`index.md`(SPEC §8)と `log.md`(SPEC §9)は、ochakai が既に持っている
情報の **OKF が定めた表現**である。前者はブラウズ、後者はリビジョン台帳で
ある。別のアドレスと別の形を発明する理由がない。

`log.md` を出すことは 0009 の「バンドルは知識を運び、provenance は
インスタンスの観測」に反しない — `generated` / `verified` と**まったく
同じ非対称**を持つからである。エクスポートは出し、インポートは読み戻さない。

### 2.4 継承する決定

本ドキュメントは 0043 の以下を一字も変えずに引き継ぐ: §2.1(文書が唯一の正)、
§2.2(知識文書とインスタンス台帳の分離)、§3.3(却下は台帳、rejected という
status は無い)、§3.6(構造化
オブジェクト内側の未知キーも保存する)、§3.8(actor は `human:` / `process:`)、
§2.4 が挙げる継承(0017 / 0019 §2 / 0022 / 0038 / 0024 / 0027)、そして §5 の
うち「Git / GCS を保存にしない」「型付き JSON の書き込み面を残さない」
「部分更新を作らない」「退役綴りのデータ移行をしない」「provenance の
読み戻し・実行・dereference・採点をしない」。0001 の中核制約(LLM ゼロ・
SQL 非実行)と 0002 / 0003 にも触れない。

0043 §3.2 は**一字違わずではない**。「status は OKF の 3 値、検証は追記
台帳」はそのまま引き継ぐが、同§末尾の「status 省略は create なら draft、
update なら現状維持」は §3.9 が置き換える — 省略は省略のまま保存され、
既定値は投影が SPEC §5.4 に従って読む。

## 3. 決定

### 3.1 保存形: 1 つの `object` テーブル + 台帳 + 導出索引

`knowledge` と `attachment` を 1 つのテーブルに畳む:

| 列 | 中身 |
|---|---|
| `path` | バンドルパス(PK、NFC、拡張子を含む) |
| `doc` | markdown のバイト列(非 markdown は NULL) |
| `blob_hash` / `size` / `media_type` | 非 markdown の GCS 参照(markdown は blob_hash が NULL) |
| `content_hash` | 保存バイト列の SHA-256(§3.4) |
| `frontmatter` | `jsonb`。概念のときだけ非 NULL(§3.11) |
| 観測列 | `created_by_*` / `generated_by_*` / `content_changed_at` / `created_at` / `deleted_at` |
| 導出索引 | `search_text`(trigram)、`embedding`(pgvector) |

- `doc IS NOT NULL` と `blob_hash IS NOT NULL` は排他(CHECK)。
- **概念**は `frontmatter->>'type'` が非空のオブジェクトである。`.md` かつ
  frontmatter が読めて `type` があるときに、書き込み・取り込みが埋める。
- 台帳(`verification` / `rejection` / `revision` / `knowledge_event` /
  `knowledge_usage`)は 0043 のまま。ただし **`revision` はオブジェクト単位**に
  なり、ファイルの作成・更新・削除も同じ台帳に載る。`change` の語彙から
  `attach` / `detach` が消える — ファイルの作成は `create` である。
- **ID とパスの関係**は 0017 のまま: 概念の id はパスから `.md` を除いたもの
  (SPEC §2)。verify / reject / usage / move は従来どおり id で呼ぶ。

### 3.2 バンドルに入ったものは出てくる

`FromBundle` が `skipped` に落としてよいのは、**バンドルパスとして不正な
もの**(0019 §2 の文字種、`..` の脱出)だけである。

| 入力 | 0.15 まで | 本ドキュメント |
|---|---|---|
| `type` のある `.md` | 概念 | 概念 |
| `type` の無い `.md` | skip(消える) | **ファイル**として保存、report に note |
| 本文から参照された非 md | 添付 | ファイル |
| `<id>/` 直下の非 md | 添付 | ファイル |
| どこからも参照されない非 md | skip(消える) | **ファイル** |
| `index.md` / `log.md` | skip | skip(導出面、§3.7 / §3.8) |
| 隠しパス(`.` 始まり) | skip | skip |

- **上限は 1 オブジェクト 5 MiB のまま**(0013)。概念本文の 4 MiB も維持。
  「1 エントリ 20 添付」は帰属が導出になった時点で意味を失うので**廃止**する。
- **GCS が未設定なら非 markdown の書き込みは 501**(0013 のまま)。
  markdown-only の知識ベースとして動く姿勢は変わらない。
- **メディアタイプはバイト列の sniff で決める**(0013 のまま。クライアントの
  申告は信じない)。ただし **拒否はしない** — 拒否するとバンドルが往復しない。
  0008 / 0013 が SVG と HTML を拒んだ理由(Web UI への script 混入)は
  **配信側**で解く: 画像・PDF・プレーンテキスト以外は
  `Content-Disposition: attachment` と `X-Content-Type-Options: nosniff` と
  `Content-Security-Policy: sandbox` を付けて返し、`text/html` と
  `image/svg+xml` はインラインで配信しない。**受けるが描画しない。**

### 3.3 帰属は導出する

「このエントリのファイル」は、リンク(0024)と同じ導出関係である:

1. その概念の本文 markdown が指す、バンドル内の非概念パス、
2. 加えて `<id>/` 名前空間の直下にあるオブジェクトのうち**概念でないもの**
   (0013 の慣習)。

2 の「概念でないもの」は実装で必要になった限定である。SPEC §2 は
`metrics/revenue/breakdown.md` に `metrics/revenue/breakdown` という
concept id を与え、SPEC §11 は非予約 `.md` が type を持つことを要求する。
つまりディレクトリ下の `.md` は誰かの根拠ではなく、住所と履歴を自分で
持つ知識である。0008 の「`<id>/<name>` はそのエントリの**根拠**が住む場所」
という枠組みは変わらない — 根拠は知識ではない。

概念とディレクトリが同じ名前を持つこと(`metrics/revenue.md` と
`metrics/revenue/`)は許す。ファイルシステム上も別のエントリであり、
SPEC §3 は配置を producer のものとし、§11 の「拒否してはならない」一覧に
名前の話は無い。`index.md` は §3.7 の節見出し(サブディレクトリ / 概念 /
ファイル)で両者を区別するので、記法は増えない。

- 保存された関係が無くなるので、`attach` / `detach` という操作も
  `okf_path` 列も消える。ファイルを置くことは `PUT` であり、外すことは
  `DELETE` である。
- move(0021)は概念の id を書き換え、参照元の本文を書き換え、
  **`<id>/` 名前空間のファイルも一緒に動かす**。名前空間が住所の一部で
  ある以上、置いていくほうが驚きが大きい。名前空間下の**概念は動かない** —
  それは自分の住所・履歴・台帳・move を持つ別のエントリであり、0021 の
  move は 1 エントリの改名だからである。一括改名が要るならそれは
  `move --recursive` という別の判断になる。
- 0020 の添付ベクトル検索は残る。鍵が `(entry, name)` から**パス**になり、
  ランク融合の第 3 リストは「ファイル」のリストになる。ochakai が中身を
  解釈しない(OCR しない・PDF からテキストを抜かない)姿勢は変わらない。

### 3.4 版は保存バイト列のハッシュ、正準形は導出値

**ETag = 保存されたバイト列の SHA-256。** If-Match の機構(0030、opt-in・
条件付き UPDATE 内での判定・412)は維持する。0043 §3.4 との差は、
ハッシュの対象が正準形ではなく**受け取ったバイト列**になることである。

- 保存の前に施す正規化は 2 つだけ: **CRLF → LF** と **末尾に改行 1 つ**。
  本文にも frontmatter にも NFC 正規化をかけない(0022 が正規化するのは
  パス・添付名・リンク先・クエリであって、内容ではない)。
- **`content_changed_at` と `generated.by` を進めるかの判定(`SameContent`)は
  正準形の一致で行う。** 整形だけの編集は ETag を動かす(ファイルは実際に
  変わった)が、`generated.at` は動かさない(SPEC §5.2 の "last meaningful
  change" は内容の変更である)。**版と意味の変更を別の値にできるのは、
  0043 が `updated_at` の三役を解いた効果がここでも効いているからである。**
- verify・reject はオブジェクトに触れないので ETag を動かさない(0043 §3.4)。
  ファイルの追加・削除も、概念のバイト列を動かさないので同じである。

### 3.5 ワイヤ: 1 つのアドレス空間

```
GET|PUT|DELETE  /api/v1/bundle/{path...}
GET             /api/v1/search
GET             /api/v1/context
POST            /api/v1/move
POST            /api/v1/verify/{id...}
POST|DELETE     /api/v1/reject/{id...}
GET|POST        /api/v1/usage/{id...}
POST            /api/v1/reembed
```

`/api/v1/knowledge`(一覧・単体)・`/browse`・`/revisions/{id}`・
`/backlinks/{id}`・`/attachments/{path}`・`/export` は対象消滅する。

**どちらの側に載るかを決める規則。** 面が 2 種類ある以上、新しい操作を
どちらに置くかを決める一文が要る。

> **バンドルの住所(`/api/v1/bundle/{path}`)は、オブジェクトと、OKF が
> そのオブジェクトについて定めた表現を運ぶ。id を鍵にしたトップレベルの
> 面は、このインスタンスが concept について観測した台帳を運ぶ。**

- **`?history` がオブジェクトの住所に載る**のは、それが SPEC §9 の
  `log.md` — **バンドルが持つ表現**だからである(§3.8)。`index.md` も
  同じ(§3.7)。アーカイブ(`Accept: application/gzip`)も、`?rev=N` も、
  同じ理由で同じ側にある。
- **`usage` と `review` が載らない**のは、OKF がそれらを表現しないから
  である。0009 の非対称(エクスポートは出し、インポートは読み戻さない)が
  当てはまるのは**観測**であって、観測にバンドル上の住所は無い。
- 規則は帰結を予言する。**ファイルに usage も review も無く、concept に
  だけある**のはこのためで、`move` が id 面にあるのも同じ — 動かすのは
  concept の id であって、バイト列ではない。**ETag も同じ線で割れる**:
  バイト列の面が版を持ち、台帳の面は文書に触れないので版を動かさない
  (0043 §§3.2-3.3)。
- **「`{id...}` の後ろの接尾辞は ID セグメントと区別できない」は綴りの
  制約であって、どちら側かを決める理由ではない。** `?history` が示す
  とおり、クエリなら住所の上に載せられる。載せないのは上の一文の
  帰結であり、`/review` と `/usage` がトップレベルにあるのは、そう決めた
  後で**どう綴るか**の答えである。
- 綴りは規則を外から読めるようにもしている。**オブジェクトを指す面は
  `{path}`、台帳を指す面は `{id}` と綴る** — concept ID はパスから
  `.md` を除いたもの(SPEC §2)なので、これは 2 つの語彙ではなく、
  同じ住所を**バイト列として**見るか **concept として**見るかの違いで
  ある。`cmd/ochakai/surface_test.go` がこの対応を落とす。

**`GET /api/v1/bundle/{path}`** — 表現は `Accept` が決める:

| Accept | 概念 | ファイル | `index.md` / `log.md` |
|---|---|---|---|
| `application/json` | `{path, id, document, summary, observed, files}`(0043 §3.5) | メタデータ | 構造化された一覧 / 履歴 |
| `text/markdown` | エクスポート形(サーバー所有キー注入済み) | — | 生成された §8 / §9 文書 |
| その他 / 省略 | エクスポート形 | バイト列(§3.2 の配信規則) | 生成された文書 |
| `application/gzip` | — | — | — |

- **パスがディレクトリのとき、`Accept: application/gzip` は部分木の tar.gz**
  である。ルート(`/api/v1/bundle/`)なら全体 — これが `/export` の後身で
  あり、`prefix` は URL そのものになる。
- `?rev=N` はそのリビジョンのスナップショット、`?history` は
  そのオブジェクトの `log.md`(JSON なら台帳の行)。
- **書き込み**は `PUT /api/v1/bundle/{path}`。本文はバイト列そのもの。
  概念かファイルかを決めるのは **frontmatter の `type` キー**であって
  `Content-Type` ではない: SPEC §11 が type を「概念が持つもの」と定めて
  いるので、`.md` でも type が無ければそれは壊れた概念ではなく
  **たまたま markdown なファイル**であり、§3.2 のとおり来た場所に戻る。
  `If-None-Match: *` / `If-Match` は 0030 のまま。概念への書き込みは
  `/api/v1/knowledge/{id}` と同一の実装を通る — 住所は第二のサーフェス
  ではない。予約ファイルへの PUT は **409**(導出面)。
- **削除**は `DELETE`(ソフト削除)、`?purge=true` で 0031 の purge。

**`GET /api/v1/search`** は旧 `GET /api/v1/knowledge` の一覧である。名前を
変えるのは、それが「バンドルの部分集合を返す面」ではなく**順位を返す面**
だからである(0033 と同じ姿勢)。`links_to=<id>` が旧 `/backlinks` を吸収する。

### 3.6 リンクは SPEC §6 の形だけ

本文リンクの正準形は**バンドル絶対**(`/metrics/revenue.md`)と**相対**に
なる。`ochakai://` は本文から退役し、エッジとしても解決しない。

- マイグレーション(§3.13)が既存の本文を一度書き換える。
- MCP の resource URI(`ochakai://{+id}`)は**残す** — MCP が要求する URI
  であって、バンドルには出て行かない。
- move の本文書き換え(0021)は絶対形・相対形の両方を対象にする。

### 3.7 `index.md` は導出面(0014 の置き換え)

`GET /api/v1/bundle/{dir}/index.md` が SPEC §8 の文書を生成する。

- 節は「サブディレクトリ」「概念」「ファイル」。各行は
  `* [Title](path) - description`(SPEC §8 の SHOULD)。
- ルートの `index.md` だけが `okf_version: "0.2"` を frontmatter に持つ
  (SPEC §12)。
- 1 階層 1000 件の打ち切り(0014)は維持し、**注記の行**として文書に出す。
- **利用を記録しない**(0014: ツリーを歩くことは需要の信号ではない)。
- `Accept: application/json` は同じ一覧を構造化して返す — Web UI の
  サイドバーが markdown をパースしないで済むための表現であって、
  第二のアドレスではない。

### 3.8 `log.md` は導出面

`GET /api/v1/bundle/{dir}/log.md` が SPEC §9 の文書を生成する。

- 新しい順、`## YYYY-MM-DD`(UTC)で日付ごとにまとめ、1 行 1 リビジョン:
  `* **Update**: [title](/path.md) — human:tanaka@example.co.jp`。
  先頭の太字は SPEC が「慣習」と呼ぶもので、`change` の語彙
  (create / update / move / delete)をそのまま出す。
- 対象はその部分木。`?history` は 1 オブジェクト分の同じ文書。
- **インポートは読み戻さない**(§2.3)。purge(0031)で消えた履歴は
  出てこない — 台帳が唯一の出所である。
- これが `/api/v1/revisions/{id}` の後身であり、**履歴が可搬になる**。

### 3.9 書き手の語彙を書き換えない

- **`CanonicalType` を撤去する。** 保存されるのは書き手の綴りそのもの。
  照合(検索フィルタ、推奨語彙の判定)は従来どおり case 非依存
  (`FoldType`)である。0038 が退役綴りを自由型として残した理由 —
  「型は書き手の語彙であり、サーバーが書き換えることは『解釈しない』
  からの逸脱」— を case にも適用する。
- **`status` の既定を注入しない。** 書き手が書かなければキーは不在のまま
  保存される。**投影(§3.10)が SPEC §5.4 の既定 `stable` を適用する**ので、
  検索の `status=stable` は「明示的に stable」と「不在」の両方に当たる。
  - 帰結として、**エージェントが MCP で作った新規エントリは、明示しなければ
    consumer から `stable` に見える。** これは SPEC の読みとして正しく、
    ochakai の二層(消費してよいか / 人が確認したか)は 0043 §3.2 で既に
    分離されている — 未検証であることは trust tier が言う。MCP の書き込み
    ツールの説明は「下書きなら `status: draft` と書け」と明示する。
- **`title` を補わない**(0022 のまま。表示名の fallback は投影の仕事)。

### 3.10 trust tier は SPEC §5.3 の 3 段

投影の `verified: bool` を廃し、**`trust: unverified | machine-confirmed |
human-reviewed`** を出す。検証台帳(0043 §3.2)から導く: `human:` の行が
あれば human-reviewed、行があれば machine-confirmed、無ければ unverified。

- 検索フィルタは `trust=` になる(`verified=` は消える)。`rejected=` は
  インスタンス固有の裁定なので bool のまま残る。
- 0033 の `hits` は `id` / `type` / `title` / `status` / `score` に `trust` を
  足す。順位に徹する姿勢は変わらない — trust は本文ではない。

### 3.11 索引は frontmatter の jsonb、フィルタはその上の式

`frontmatter jsonb` に文書の frontmatter 全体を展開し、GIN
(`jsonb_path_ops`)と、よく引くキーの式インデックス
(`(frontmatter->>'type')`、`lower(frontmatter->>'type')`、
`(frontmatter->>'status')`、`(frontmatter->>'stale_after')`)を張る。

- 0037 の `source` 逆引きは `frontmatter->'sources'` の containment、
  0041 の prefix はパスの照合(索引と無関係)。named フィルタは
  **式への糖衣**になる。
- **`fm.<key>=<value>` を足す** — 任意の frontmatter キーに対する完全一致
  (値がリストなら包含)。**SPEC が新しいキーを足した日から、
  マイグレーション無しで引ける。** 0043 が保存で達成した additive 性を
  クエリ面にも届かせるのが目的であり、named フィルタを増やし続ける
  必要が無くなる。
- 矛盾したら文書が正であり、`frontmatter` は再構築できる(0043 §3.1)。
- **embedding の入力は変わらない**(id / title / description / tags /
  `question` / 本文)。**再 embed は不要**である。

### 3.12 検証(validation)

0043 が引き継いだ 0036 §3.10 の表はそのまま効く(書き込みは 400、
インポートは note)。加えて:

- **概念かどうかの判定に失敗しても書き込みは通る。** `type` の無い `.md` を
  PUT すると、それはファイルとして保存される(400 にしない)。SPEC §11 の
  「consumers MUST NOT reject」に沿う姿勢を、書き込み面にも広げる —
  ただし `text/markdown` で PUT したものが概念にならなかったときは、
  応答に note を返す(黙って読み替えない、0036 §3.4)。
- サーバー所有キーは行単位で剥がして受ける(§2.2)。400 にしない。

### 3.13 マイグレーション(0025)

起動時に一方向で適用する。

- `knowledge` を `object` に改め、`doc` を保存バイト列とする(0043 の
  マイグレーション 0024 が合成した正準文書が、そのまま最初のバイト列に
  なる)。`content_hash` を再計算する。
- `attachment` 行を `object` 行にする。パスは `okf_path` があればそれ、
  無ければ `<id>/<name>`。**衝突したら `okf_path` を優先し、負けたほうは
  `<id>/<name>` に置く**(両方失うより良い)。`attachment_embedding` の
  鍵をパスに移す。
- 本文の `ochakai://<id>` を `/<id>.md` に書き換える(§3.6)。
  **`content_changed_at` は進めない** — 表現の変更は内容の変更ではない
  (0036 §3.13 の姿勢)。ETag は動く(バイト列が変わるので不可避)。
- `frontmatter` を展開し、索引を張る。
- リビジョンはオブジェクト単位に読み替える。`attach` / `detach` の行は
  対象のファイルの `create` / `delete` として読み替える。
- **再 embed は不要**(§3.11)。

### 3.14 各サーフェス(0015 §4)

- **REST = yes。** 唯一の契約。§3.5 の 8 面。`openapi.yaml` は
  `bundle` の 3 メソッドと、表現ごとのスキーマを記述する。
- **CLI = yes。** `ochakai put`(旧 `create` + `update`)は 1 本になる —
  ワイヤが create-or-replace である以上(0043 §3.5)、存在の有無は
  precondition であって別の行為ではなく、2 本あることは呼び手に
  フォーマットが訊いていない問いを答えさせていた。`--only-if-new` が
  `create` の送っていた `If-None-Match: *`、`--if-match` が `update` の
  取っていた版である。`ochakai log` は `log.md` を出す。
  `export` / `import` はほぼ恒等の tar 転送になる。

  **実装時に採らなかったものが 2 つある**(0048 §2.3 に従い、本節を直接
  直してある)。

  1. **`ls` / `rm` という綴りは採らない。** `browse` と `delete` のまま
     である。0049 §3.4 が `ochakai status` を退けたのと同じ理由で —
     このプロジェクトの語彙は `verify` / `reject` / `queues` であって
     unix の習慣ではなく、片方だけを unix 風にすると CLI の中に由来の
     違う 2 つの語彙が並ぶ。改名は利用者が打つものを変える支払いであり、
     ここではその対価が「他所の慣習に似ること」しかなかった。
  2. **`attach` / `detach` は吸収しない。** 吸収するには
     `get` / `put` / `delete` の引数をバンドルパス(`<id>.md`)に変える
     必要があり、そうすると **id を取るコマンド**(`verify` / `reject` /
     `usage` / `report` / `move` / `revisions`)と**パスを取るコマンド**が
     CLI の中で割れる。REST では `bundle/{path}` と `verify/{id}` が
     別の**住所**なので割れても筋が通るが、CLI では同じエントリを
     指す 2 つの綴りになる — §3.5 が REST から取り除いたものそのものが
     CLI に現れる。`.md` が全呼び出しと全ドキュメント例に付く支払いも、
     1 の改名より大きい。ファイルを 1 本の書き込み面に畳むなら、
     引数の形をどうするかを先に決める別の記録が要る。
- **MCP = yes。** ツールは 8 本: `search_knowledge` / `get_context` /
  `get_knowledge` / `put_knowledge`(`{path, document}`)/ `report_outcome` /
  `delete_knowledge` / `get_knowledge_usage` / `get_attachment`。
  verify / reject は従来どおり出さない。ファイルの**書き込み**も出さない —
  エージェントが増やすべきものではない。

  当初は 5 本とし、後ろの 3 本を落とすとしていた。実測が反対した:
  `tools/list` の JSON は全体 33.5 KB で、落とす 3 本は合計 3.3 KB
  (9.8%)にすぎず、一方 `create_knowledge` + `update_knowledge` →
  `put_knowledge` の統合だけで約 6 KB が浮く。つまり**節約は統合で取れて
  おり**、残り 3 本は能力を失うだけだった — 0015 §3.1 のキュレーション
  保護規則(`delete_knowledge` が対象)、0025 の書き戻しループ
  (`get_knowledge_usage`)、0008 / 0013 の添付読み取り(`get_attachment`)を
  同時に撤回することになる。統合の側には数以外の理由がある: 0043 §3.5 に
  より書き込みは「エントリが何を言うべきか」の表明であって存在の有無の
  表明ではないので、書き込み面は 1 つが正しい姿である。
  `get_attachment` は §3.3 の後、引数が `(entry, name)` からパスになる。
- **Web UI = yes。** サイドバーは `index.md` の JSON 表現、詳細は投影、
  編集は文書エディタ([0044](0044-web-ui-edits-documents.md) がフォーム
  糖衣を撤去したので、経路は 1 本しかない)。0044 の判断は本ドキュメントを
  先取りしていた: 糖衣は保存のたびに文書を正準形へ書き換えるので、
  §2.2 の「受け取った文書を書き換えない」と両立しなかった。履歴タブは
  `log.md`(§3.8)、ファイルの一覧は導出された帰属(§3.3)である。

## 4. 壊れるもの

**基準線は 0.15.0** であり、0043 の実装と本ドキュメントの実装は同じ
次のリリースに束ねて出る。0043 §4 の一覧はすべて有効で、以下が加わる。

**ワイヤ**

- `/api/v1/knowledge`・`/browse`・`/revisions`・`/backlinks`・
  `/attachments`・`/export` が消え、`/api/v1/bundle/{path}` と
  `/api/v1/search` になる。
- 一覧・検索の応答が `verified: bool` ではなく `trust` を持つ。
  `?verified=` フィルタは `?trust=` になる。
- MCP の `create_knowledge` と `update_knowledge` が `put_knowledge` に
  なる(§3.14)。`delete_knowledge` / `get_knowledge_usage` /
  `get_attachment` は残る。`attach` 系はもともと MCP に無い
  (0015 §3.1 が添付の**書き込み**を最初から出していない)。
- ETag が「正準文書のハッシュ」から「保存バイト列のハッシュ」になる。
  整形だけの編集で ETag が動くようになる(`generated.at` は動かない)。

**保存**

- マイグレーション 0025(§3.13)。一方向。添付行はオブジェクトになり、
  `okf_path` の衝突は一方が正準レイアウトへ移る。

**バンドル**

- **`ochakai://` を含む本文が `/path.md` に書き換わる。** git 管理された
  バンドルは次回エクスポートでこの差分が出る。
- **エクスポートの差分が「受け取ったまま」になる。** 0.15 までは全文書が
  正準形で出ていた。本ドキュメント以降、ochakai が受け取った文書は
  受け取った整形のまま出る(サーバー所有キーだけが追記される)。
- `index.md` が「ファイル」節を持ち、`log.md` が出るようになる。
- **これまで消えていたものが消えなくなる**(§3.2)。破壊ではなく回復である。

**書き込み**

- `type` の case が保存される(`metric` は `Metric` にならない)。
- `status` を書かない create が、`status` を持たない文書として保存される。
  読み手には SPEC の既定(`stable`)として見える。
- SVG / HTML の書き込みが 400 でなくなる(配信で守る、§3.2)。
- **他インスタンス・他 producer の文書が `received:` を持って保存される**
  (§2.2)。0.15 まではその trust family が消えていた。frontmatter の
  jsonb には他のキーと同じく載るが、`fm.` の語彙は OKF が定義するキーだけ
  なので([0047](0047-fm-carries-okf-keys.md))引く面は無く、trust tier も
  `trust=` もそこからは答えない。

## 5. やらないこと

- **0043 §5 の全項目**を維持する(Git / GCS を保存にしない、型付き JSON の
  書き込み面を残さない、部分更新を作らない、退役綴りのデータ移行をしない、
  provenance の読み戻し・実行・dereference・採点をしない)。
- **`log.md` を読み戻さない**(§2.3)。他インスタンスの履歴を自分の台帳に
  入れることは、provenance を読み戻さない理由と同じ理由で誤りである。
- **主張を索引・trust tier・ワイヤの一級市民にしない**(§2.2)。`received:`
  は保存された文書の中の 1 キーであり、それ以上の面を今回は作らない。
  「`trust=human-reviewed` が主張でも満たされるか」「ヒットがどちらで
  答えたかを言うか」は別の決定であり、それを決める前に**主張を復元不能に
  捨てることだけ**をやめる。
- **ファイルの中身を解釈しない。** OCR も PDF のテキスト抽出もしない
  (0020)。`index.md` / `log.md` を**受け取って**も読まない。
- **複数バンドルを持たない。** 1 デプロイ = 1 バンドルであり、
  名前空間はディレクトリである(0017 §4.3)。
- **`fm.` フィルタに演算子を持たせない**(§3.11)。完全一致と包含だけで
  あり、範囲・否定・論理式は作らない。クエリ言語の入口になる。
- **ファイルの MCP ツールを作らない**(§3.14)。
