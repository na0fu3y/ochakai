# ochakai 設計ドキュメント 0049: 埋め込みは既定であり、ベクトル空間は捨ててよい

Status: Accepted(2026-07-28)。[0001](0001-architecture.md) §4 の
「埋め込みは設定した場合にのみ有効化される」を改訂し、**Google Cloud の
上では既定で有効**にする。[0003](0003-gcp-only.md) の前提に Vertex AI を
**既定パスの依存**として加える(secret-zero は保たれる — Vertex AI も
IAM である)。次元変更時の手作業の `DROP TABLE` を廃し、製品が行う。
検索の姿と添付の扱いは変えない — [0020](0020-attachment-search.md) と
[0046](0046-bundle-address-space.md) はそのまま
Date: 2026-07-28

## 1. 問題: この製品でいちばん効く機能が、いちばん奥に置いてある

[ROADMAP](../../ROADMAP.md) は日本語の字句検索についてこう書いている —
trigram 索引は 2 文字のパターンを引けないので日本語の語はスキャンで
答えることになり、5000 エントリで約 16 ms(latin の語なら 0.2 ms)。
そして「**enabling embeddings is the current answer**」と続く。

その answer に至るまでに、利用者は次を踏まなければならない。

| | |
|---|---|
| 読む場所 | `deploy/cloudrun/README.md` の **§4「Optional:」** — 948 行のガイドの中ほど |
| 有効化 API | `aiplatform.googleapis.com` を enable |
| IAM | サービス ID に `roles/aiplatform.user` |
| 環境変数 | `OCHAKAI_VERTEX_PROJECT`(＋ 任意で model / location / dim) |
| 既存ベースへの適用 | `ochakai reembed` |
| 落とし穴 | `OCHAKAI_EMBEDDING_DIM` を変えると**起動を拒否**し、`psql` で `DROP TABLE knowledge_embedding, attachment_embedding` を手で打てと言われる |

**ochakai の中核の想定利用者(日本語で書かれた知識ベースを持つチーム)に
とって、既定の検索は最良の検索ではない。** それが既定なのは、埋め込みが
「外部 API を呼ぶ」からであって、要らないからではなかった。

最後の行はさらに悪い。次元変更の拒否は、製品の中で唯一「スキーマ操作を
利用者に手で打たせる」箇所であり、この機能が **advanced に見える**理由に
なっている。拒否そのものは正しかった(幅の違う列に書けば全部壊れる)が、
**製品が自分でできることを利用者にやらせていた**。

## 2. 決定: Google Cloud の上では、埋め込みが既定である

### 2.1 プロジェクトは設定ではなく発見する

`OCHAKAI_VERTEX_PROJECT` が無いとき、ochakai はメタデータサーバに自分が
どのプロジェクトで動いているかを訊き、その答えで埋め込みを有効にする。
Cloud SQL IAM 認証が短命トークンを取っているのと同じ出所であり、
新しく持つものは何も無い(0003)。

メタデータサーバが無い環境 — 手元の開発機、CI、Google Cloud 以外 — は
**何も変わらない**。発見できなければ埋め込みは無効で、字句検索だけになる。
手元で有効にしたい場合は今までどおり `OCHAKAI_VERTEX_PROJECT` を置く。

### 2.2 使えるかどうかを決めるのは IAM であって、設定ではない

**ochakai は要求し、IAM が答える。** サービス ID に
`roles/aiplatform.user` が無ければ Vertex AI は答えず、そのデプロイに
埋め込みは無い。設定を増やさずに済むのはこの性質のためで、0002 の
「認可を持たない」と同じ考え方 — 誰が何をしてよいかを製品が二重に持たない。

答えは**起動時に一度だけ、1 語の埋め込みで**訊く。訊かずに走ると、権限の
無いデプロイは書き込みのたびに失敗を記録し続けることになる。呼び出しは
10 秒で打ち切る — cold start は API の不応答を待つ場所ではない。

### 2.3 発見された既定は落ちてよい。名指しされた設定は落ちない

| プロジェクトの出所 | Vertex AI / pgvector が使えないとき |
|---|---|
| 発見(既定) | 警告を 1 行出し、**字句検索だけで動く** |
| `OCHAKAI_VERTEX_PROJECT`(名指し) | **起動しない**(従来どおり) |

名指しした利用者は意味的検索を頼んでおり、黙って劣化した検索を返される
より、なぜ無いのかを知りたい。発見された既定は頼まれたものではないので、
知識を配ることを止める理由にはならない — 落ちた先は、この決定の前に
その利用者が得ていたものである。

同じ区別が pgvector にも及ぶ。拡張を作れない DB(その role に権限が無い)
では、発見されたデプロイは字句検索で動き、名指しされたデプロイは今までどおり
起動を拒否する。

### 2.4 off はただ一つ、`OCHAKAI_EMBEDDINGS=off`

`OCHAKAI_VERTEX_PROJECT` の不在は、もう「off」を意味しない。Google Cloud
の上で意味的検索を持たないと決めたデプロイは、そう言えなければならない。

`on` と `off` 以外の綴りは**設定エラーとして拒否する**。`false` と書いて
有効になったデプロイは、頼んでいない Vertex AI の課金を書き込みのたびに
払うことになる — 推測して外す方向がまずい種類の設定である。

## 3. 決定: 次元の変更は製品が行う

`OCHAKAI_EMBEDDING_DIM` が保存されている列の幅と違うとき、ochakai は
ベクトルのテーブルを作り直す。手作業の `DROP TABLE` は無くなる。

### 3.1 ベクトルは導出物であって、記録ではない

この決定はここに尽きる。**すべてのベクトルは、それが指すオブジェクトから
再計算できる。** だからこそベクトルのテーブルは番号付き migration の外に
あり、`reembed` が存在し、モデルを変えれば古い行が誰にも引かれないまま
残ることを 0020 が「データ損失」と呼んでいない。

誰も問い合わせない空間を捨てて失われるのは、詰め直すための埋め込み呼び出し
だけである。知識は `object` にあり、触れられない。

### 3.2 詰め直しは自動でやらない

作り直したテーブルは空である。ochakai はそれを自動では埋めない — 埋める
ことは利用者の口座から支払うことであり、`reembed` が「意図して払う」ための
面としてすでにある(deploy §4)。作り直したときは、その 1 行のログが
`ochakai reembed` を名指しする。

その間、検索は字句のみで**答えは返る**。ハイブリッド検索は片側が欠けても
成立する(RRF)ので、詰め直しの途中でも壊れない。

### 3.3 モデルだけの変更は今までどおり

幅が同じでモデルだけ変わった場合、古い行は消さない — 0020 §2.3 の
「エントリは書き直されるまで旧モデルの空間に留まる」がそのまま生きる。
本ドキュメントが触るのは**幅が変わったときだけ**である。

## 4. 何を差し出しているか

- **既定パスが Vertex AI に依存する。** 0003 が守っているのは
  secret-zero であって依存の数ではなく、Vertex AI の認証は ADC(サービス
  ID)なので、持つ秘密は増えない。増えるのは「本番で動かす」の敷居であり、
  それは §1 の対価として引き受ける。
- **書き込みが支出になる。** ochakai には認可が無い(0002)ので、到達できる
  誰もが書けて、書き込みは埋め込み呼び出しを生む。逃げ道は二つあり、
  どちらも明示的である — `roles/aiplatform.user` を与えない(何も起きない)、
  または `OCHAKAI_EMBEDDINGS=off`。
- **cold start が 1 回の Vertex AI 呼び出しぶん伸びる。** 1 語の埋め込み
  1 回、10 秒で打ち切り。

## 5. 添付の「昇格」は 0046 で完了している

同じ問いのもう半分 — 添付を昇格させるとは何か — に、本ドキュメントは
**何も足さない**。

- 0046 §§3.1–3.5・3.13 で、ファイルは「エントリの付属物」をやめ、バンドルの
  アドレス空間の**オブジェクト**になった。パスで読み書きでき、履歴を持ち、
  バンドルに入ったものはバンドルから出る。
- 0020 が検索を与えている — ファイル名のレキシカル一致、内容のベクトル、
  `gemini-embedding-2` なら画像と PDF まで。§2 の決定により、これが**既定で**
  効くようになる。添付の昇格が実際に効くための最後の一片は、埋め込みが
  既定になることだった。

そのうえで、二つは**やらない**と決める。

- **ファイルそれ自体を検索結果として返すこと**は、ここでは決めない。ヒットは
  今までどおり所有するエントリである(0020)。これは「添付が一級か」ではなく
  「検索面が何を返すか」の問いで、0046 §3.5 の一覧面と #298 のページングと
  同じ場所で決めるべきものである。
- **`references/` という慣習を ochakai が解釈すること**はしない。SPEC §6 が
  名付ける置き場所は、往復で保たれる**パス**であって、意味ではない。ここを
  解釈し始めることは、ochakai がバンドルの中身を読んで判断する製品になること
  であり、0001 の「解釈はクライアントのエージェントの仕事」から外れる。

## 6. 選ばなかった案

- **opt-in のまま、ガイドの中で目立たせる。** 採らない。§1 の表の 6 行は
  どれも「読んだ人だけが踏む」段であり、既定を変えずに解けるのは 1 行目
  だけである。既定でない機能は、既定を選んだ人には無い。

- **次元変更で新しい列に再埋め込みしてから入れ替える**(issue #300 の案)。
  採らない。検索が字句だけになる窓を消せるのは確かだが、消える窓の代償が
  大きい — 二つの幅の列を同時に持ち、どちらを読むかの状態を持ち、切り替えの
  途中で落ちた場合を持つ。§3.1 のとおり失われるのは再計算できるものだけで、
  そのために状態機械を一つ増やす価値は無い。

- **幅ごとにテーブルを残す**(`knowledge_embedding_768` のように並べる)。
  採らない。設定を戻せば古いベクトルが戻る、という利点はある。だが誰も
  読まないテーブルに行が残ることは、0031 の purge —「消したものは消える」—
  と両立しない。purge が全部の空間を回らねばならなくなり、回り忘れは
  静かに破る種類の失敗である。捨てるほうが正しい。

- **作り直したあと自動で reembed する。** 採らない。再起動が黙って利用者の
  口座から支払う設計になる。§3.2 のとおり、支払いは頼まれてから行う。

- **起動時の probe をやめ、失敗はログに任せる。** 採らない。probe が無いと、
  権限の無いデプロイは「書き込みのたびに失敗を記録する」状態で動き続ける。
  既定で有効にする以上、有効にならなかったことを起動時に一度だけ言えるのは
  条件に近い。

- **ADC の資格情報からプロジェクトを取る。** 採らない。手元の
  `gcloud auth application-default login` まで拾ってしまい、開発機が黙って
  課金を始める。メタデータサーバは「Google Cloud の上で動いている」を
  そのまま意味する。

## 7. サーフェス(0015)

**面の増減は無い。** REST / MCP / CLI / Web UI のどれにも、エンドポイントも
ツールもコマンドも足さない。`reembed` は今までどおり REST と CLI にあり、
MCP には無い(0015 §3.1)。

利用者が観測するのは、既定の挙動(検索がハイブリッドになる)と、起動時の
ログ 1 行と、`OCHAKAI_EMBEDDINGS` という設定である。番号を取るのは
まさにこの二つのため — 既定が変わること、そして Google Cloud への依存が
既定パスに入ること(0048 §2.1)。

## 8. 互換性

**BREAKING。** `OCHAKAI_VERTEX_PROJECT` を置いていない既存の Cloud Run
デプロイのうち、サービス ID が `roles/aiplatform.user` を持ち
`aiplatform.googleapis.com` が有効なものは、次のリリースで意味的検索が
有効になり、書き込みごとに Vertex AI を呼ぶ。これは既定を変える決定の
定義どおりの帰結であり、隠さない。

- 変えたくないデプロイ: `OCHAKAI_EMBEDDINGS=off`。
- 何も起きないデプロイ: ロールを持たないもの(起動時の probe が答えを受け取り、
  ログ 1 行を残して字句検索で動く)、Google Cloud の外で動くもの。
- 次元変更の拒否に依存していた運用: 拒否は無くなり、作り直しになる。
  戻す道は「設定を戻して `ochakai reembed`」で、手で打つ SQL は無くなる。
