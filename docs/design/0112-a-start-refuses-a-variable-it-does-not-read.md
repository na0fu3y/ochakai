# ochakai 設計ドキュメント 0112: 起動は、自分が読まない変数を断る

Status: Accepted(2026-08-17)。どの決定も覆さない —
[0064](0064-rest-stops-at-api-v1.md) §2 が REST に置いた「宣言していない
キーは 400」を、運用者が手で綴るもう一つの面に当てる。
[0066](0066-four-postures-one-word.md) と
[0078](0078-one-variable-says-how-it-embeds.md) が畳んだ綴りは、畳まれた
ままで、**残っていれば言われる**ようになる。
[0088](0088-a-retired-name-answers-for-one-release.md) の一リリースの窓は
環境変数に及ばない(§5)。**BREAKING**(§7)
Date: 2026-08-17

## 1. 値は厳格で、名前は素通りだった

この製品は、環境変数の**値**を疑うことを何度も決めてきた。
`OCHAKAI_MODE` が姿勢の綴りでなければ起動しない —
「読み間違えたデプロイは、既定に落ちるのではなく起動しない」
(0066 §4)。`OCHAKAI_EMBEDDINGS` も同じで、拒否を "false" と
綴ったデプロイは、断ったはずの Vertex AI を書き込みごとに呼ぶ
([0080](0080-search-and-how-a-deployment-embeds.md) §2)。
`OCHAKAI_ADMINS` の主体の綴りも起動時に断る
([0109](0109-a-directory-has-readers-and-writers.md) §3)。

**名前にはその検査が一つも無かった。**

- `OCHAKAI_RECORD_MISSES` を一文字落としたデプロイは、切ったつもりの
  記録を付けたまま走る。切れているかどうかを見る場所は無い。
- 0078 が五つを一つに畳んだあと `OCHAKAI_VERTEX_PROJECT` を残した
  デプロイは、誰も読まない値を持ち続ける。畳み込みは**リリースノートの
  中でだけ**起きていて、環境の中では起きていない。
- どちらも「設定したのに効かない」であり、気付く経路が製品の側に無い。

0064 §2 が REST で同じ穴を塞いだとき、その理由をこう書いた —
未知のキーを 400 にするのは「**凍結後に何かを安全に足せるかどうかを
決める**」ためである。宣言した鍵だけを受け取る面は、鍵が増えても減っても
運用者に届く。環境変数の面には、その土台が無かった。

## 2. 決定: 名前空間の中で読まないものがあれば、名指して止まる

`OCHAKAI_` で始まり、ochakai が読まない変数が一つでも環境にあれば、
**起動しない**。エラーはその変数を名指し、ochakai が読む変数を並べる。

```
ochakai does not read OCHAKAI_VERTEX_PROJECT; it reads OCHAKAI_ADMINS / …
```

- **対象は、環境で構成される二つのプロセス** — `serve` と `serve-ui`。
  どちらもデプロイされるサービスであり、設定は人が Cloud Run のコンソール
  か `gcloud` の引数に手で綴る。
- **見つかったものは全部並べる。** 一つ直して再デプロイし、次の一つで
  また落ちるのは、同じ待ち時間を二度払うということである。
- **読む変数の一覧は `config.Known` に一度だけ書き、ソースから読み戻して
  検査する** — `os.Getenv` の呼び出しと一覧が食い違えば
  `TestConfigKnowsEveryVariableTheSourceReads` が落ちる
  ([0035](0035-verifiability.md):規約を信じず、外から不変条件を読む)。
  一覧に載せ忘れた変数は、**次のデプロイが設定できない変数**になるので、
  この検査は親切ではなく必須である。**読み手が Go でない変数のための
  二本目の一覧が隣にある** — `config.KnownElsewhere`、§4.2。

`PORT` と `NO_COLOR` は入らない。前者は Cloud Run の綴りで、後者は
`NO_COLOR` を読むすべてのプログラムの綴りである
([0111](0111-weight-for-the-eye-and-only-for-an-eye.md) §4)。ochakai が
断ってよいのは自分の名前空間だけである。

## 3. なぜ警告ではなく停止か

**警告は、この失敗の形に届かない。** 設定を間違えた運用者が見るのは
「動いているサービス」であって起動ログではない。0066 §4 が姿勢について
書いたこと ——「既定に落とさない」—— がそのまま当てはまる。

**Cloud Run では、停止の代金が落ちることではない。** 起動に失敗した
リビジョンにトラフィックは移らず、直前のリビジョンが答え続ける。
払うのは「新しい設定が出ない」であり、それは**間違った設定が出るより
安い**。これは 0066 §4 の判断と同じ形で、対象が値から名前に移った
だけである。

## 4. 名前空間には、サーバが読まない住人が二種類いる

「ochakai が読まない」は「誰も読まない」ではない。この名前空間には、
`serve` が一度も見ないのに **ochakai のために置かれている**変数が二種類
いて、どちらも設定の間違いではない。扱いが違うのは、間違えられ方が違う
からである。

### 4.1 harness の半分 — 接頭辞で切る

`OCHAKAI_TEST_` で始まる変数は読み飛ばす。`scripts/check --db` は
`OCHAKAI_TEST_DATABASE_URL` を export したままテスト全体を走らせるので、
これを設定の間違いと読む検査は、それを入れた PR 自身を落とす。CI の
ブラウザ smoke が読む二つ(`OCHAKAI_TEST_SMOKE_REQUIRED` /
`_CDP_PORT`)も同じ理由でこの下にいる — 一段前の step でそれを export
していれば、smoke が叩くはずのサーバが起動しない。

接頭辞で足りるのは、**この下には出荷物の読み手が一人もいない**からで
ある。打ち間違いが素通りする穴ではあるが、素通りする先に製品の挙動が
無い。

**名指しの例外は物を隠せる場所なので、信じずに検査する**(`internal/testdb`
が既に同じ扱いを受けている) — 出荷されるコードが `OCHAKAI_TEST_` の
下を読んでいれば `TestNothingShippedReadsATestVariable` が落ちる。
出荷コードがそこを読めば、それは**運用者が間違えても言われない設定**に
なる。この検査だけが目を逸らしている場所だからである。

### 4.2 Go でない読み手の半分 — 一覧で切る

ochakai が配っているのは binary だけではない。`examples/claude-code` の
想起フック(shell)は `OCHAKAI_RECALL_LIMIT` を読み、
`examples/bigquery-catalog` の python job は `OCHAKAI_ID_TOKEN` を読む。
どちらも README と skill が利用者に export させている名前であり、
**その shell で `ochakai serve` を上げると、ochakai 自身の説明書が
「ochakai が読まない変数」として名指される**。手元でサーバを上げる手順
は自分たちの dogfood 手順そのものなので、これは想像上の衝突ではない。

前例は既に `Known` の側にある。`OCHAKAI_URL` はサーバが一度も読まない
のに一覧にいて、理由は「client のために export した shell は誤設定の
サーバではない」である。この二つはその同類で、違うのは読み手が Go で
ないことだけ — `Known` がソースの `os.Getenv` から作られるのに対し、
拒否は接頭辞で当たる。その差にちょうど落ちる。

そこで `config.KnownElsewhere` を `Known` の隣に置き、判定は和集合で
行う。**接頭辞ではなく一覧なのは、ここが 4.1 の裏返しだからである**:
この下には読み手が実在するので、`OCHAKAI_RECALL_LMIT` と一文字落とした
綴りは本書が捕まえるべき失敗そのものであり、接頭辞で切ればそれが素通り
する。`OCHAKAI_ID_TOKEN` にはそもそも隠れる接頭辞が無く、接頭辞に寄せる
なら利用者が export している名前の改名になる — 環境変数に窓は無い(§5)
ので、それは黙って壊れる側に振れる。

一覧は信じずに検査する。`examples/` と `.claude/` を読み戻し、そこに
現れる `OCHAKAI_` の綴りが「Go が読む(`Known`)/ ここに載っている /
harness の(§4.1)」のどれでもなければ
`TestConfigKnowsWhatTheShippedReadersRead` が落ちる。散文も読み手に
数える — 綴りを教えるページこそが、それを誰かの shell に置くものだから
である。実際この検査は、0.17.0 で `OCHAKAI_MODE` に畳まれた
`OCHAKAI_INSECURE_DEV` を、まだ教えている例の中から見つけた。

エラーメッセージが並べるのは `Known` だけにする。拒否されている人が
設定しているのはサーバであり、そこにフックの変数が候補として並ぶのは、
何も並ばないより悪い答えである。

## 5. 環境変数に窓は無い

0088 は、改名された MCP ツール名と CLI コマンド名が一リリースだけ古い
綴りで答えることを決めた。**環境変数はその窓を受け取らない。**

窓が意味するのは「古い綴りでも動く」であり、環境変数においてそれは
**黙って効く**ことそのものである。窓は呼び出しの場所で名前を告げられる
面のためのものだった(0088 §2:「改名は changelog ではなく呼び出しで
届く」)。環境変数にとって、その「呼び出しで届く」に当たるのは窓では
なく、**起動時の名指し**である。畳まれた綴りを持ったまま上げたデプロイ
は、リリースノートを読んでいなくても、最初の起動で何を消せばよいかを
一行で受け取る。

## 6. 面への出方(0067)

- **REST** — 変化なし。ワイヤは 1 バイトも動かない。
- **CLI** — クライアントの各コマンドはこの検査をしない。`OCHAKAI_URL`
  を export した shell が全コマンドで止まるのは代金に見合わないし、
  クライアントの間違いはすぐ見える(繋がらない、`ochakai use` が言う)。
  `serve` と `serve-ui` は CLI のコマンドではなく、同じ image で起動する
  デプロイ済みプロセスである。
- **MCP / Web UI** — 変化なし。
- **表面の数** — `ENV` は 15 のまま。名前は一つも増えず、減ってもいない。
  増えたのは規則であり、[docs/surface.md](../surface.md) が数えるのは
  名前である(0066 §4 が VOCAB について同じことを書いている)。§4.2 の
  一覧も数を動かさない — あの節が数えているのは製品の `os.Getenv` 呼び出し
  であって、`KnownElsewhere` は定義上その呼び出しが存在しない名前である。

## 7. これは BREAKING である

今日起動しているデプロイが、次のリリースで起動しなくなり得る —
`OCHAKAI_` で始まる変数を、ochakai のためでなく置いていた場合と、
畳まれた綴りを消さずに残していた場合である。changelog にその手当てを
書く(何を消せばよいかはエラーが名指しする)。これが**この決定の代金の
全部**であり、払う相手は「今まさに黙って間違っていたデプロイ」である。

## 8. 採らなかった案

- **警告ログにする。** §3。読まれない場所に書くのは、直したことにする
  ための儀式である。
- **退役した綴りだけを名指す表を持つ。** `OCHAKAI_READ_ONLY` から
  `OCHAKAI_VERTEX_MODEL` まで七つを表に書けば、丁寧な移行案内は出せる。
  だが表は永久に伸び(env に窓は無い、§5)、しかも**打ち間違いは一つも
  捕まらない** — 起きる頻度が高いのはそちらである。
- **CLI にも同じ検査をする。** §6。
- **出荷している読み手の名前も接頭辞で切る**(`OCHAKAI_RECALL_` のように)。
  §4.2。安いが、読み手が実在する下に穴を開けることになり、打ち間違いが
  素通りする。`OCHAKAI_ID_TOKEN` は接頭辞に載せるために改名が要る。
- **許可する名前を設定ファイルで宣言できるようにする。** 設定を設定する
  ものが増え、No FDE(C4)から遠ざかる。
- **`OCHAKAI_TEST_DATABASE_URL` を一覧に一本足す。** harness の名前が
  製品のエラーメッセージに並ぶ。接頭辞で切れば、この repo の外の誰にも
  見えない。

## 9. やらないこと

- **値の検査を増やすこと。** 本書は名前だけを見る。
- **`PORT` / `NO_COLOR` を名前空間に入れること**(§2)。
- **環境変数の凍結。** 名前が動きを止めたと宣言するのは別の決定であり、
  [0107](0107-the-freeze-holds-the-okf-core.md) §2 の体制 —— それ自身の
  記録として凍る —— に従う。本書はその前提を用意しただけである。
