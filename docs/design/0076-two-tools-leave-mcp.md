# ochakai 設計ドキュメント 0076: 二つのツールが MCP から降りる

Status: Accepted(2026-08-02)。MCP のツールを 8 本から 6 本にする。
[0067](0067-four-faces-and-what-they-decline.md) §5.1・§6・§7 を改訂する。
Date: 2026-08-02

## 0. 決めたこと

`delete_concept` と `get_concept_usage` を MCP から降ろす。残る 6 本は
`search_concepts` / `get_context` / `get_concept` / `put_concept` /
`get_file` / `report_outcome` である。

[0068](0068-how-a-face-is-added-and-removed.md) §3「通行量の無い入口は
降ろす」の適用であり、そこが書いているとおり**畳み込みではない —
能力はこの面から落ちる。そう言って落とす。** 落ちるのは MCP からだけで、
REST・CLI・Web UI は一つも失わない(§4)。

## 1. ツール数は予算であり、毎セッション課金される

[0067](0067-four-faces-and-what-they-decline.md) §1 が MCP の既定を no に
している理由は一つだけである — **ツールスキーマはエージェントの
コンテキストウィンドウから支払われる**。八つの条件(C5「Claude Code から
使える」)がここに掛かっており、接続するエージェントは、そのツールを一度も
呼ばなくても八本分の説明文を読まされる。

だから降ろす判断に要るのは「そのツールは正しいか」ではなく、
**「そのツールに通行量があるか」**である。この二本には無かった。同梱の
フック(`examples/claude-code/hooks/`)も配布する CLAUDE.md も
`examples/bigquery-catalog` のジョブも、この二本を呼んでいない — シェルを
持つ Claude Code には CLI を勧めており([0067](0067-four-faces-and-what-they-decline.md) §1)、
その経路には `ochakai delete` と `ochakai usage` がそのまま在る。

`min_score` と `fm.` のときと同じ形である(0068 §3)。違うのは、そこで
降りたのがパラメータだったのに対し、ここで降りるのは**ツールそのもの**
だということで、だから数が 8 → 6 に動く。

## 2. `delete_concept` — 削除は裁定である

こちらが鋭いほうである。

**この面は既に裁定を載せていない。** `POST /api/v1/review/{id}`
(verify / reject / withdraw)は MCP のツールではない —
[0068](0068-how-a-face-is-added-and-removed.md) §4 が三つの裁定面を一本に
畳んだとき、その共有していた構造的性質の一つが「人の面に載り MCP には
載らない」ことだった。api/openapi.yaml のその操作の説明も「裁定は人が
下すものであり、書き戻しループが回るのはその人の判断があるからである」と
書いている。

**それなのに、取り消せない側だけが載っていた。** verify と reject は
台帳への追記で、間違えても `withdrawn` で降ろせる。削除は soft-delete で
履歴こそ残るが、concept を検索から消す**破壊的な**操作である
(唯一 `destructive` アノテーションが付いていたツールだった)。

> 却下を任せられないエージェントに、削除を任せる理由は無い。

これが本記録の発見である。0067 §6 は「人が裁定した concept は MCP から
削除できない」という**ガード**を置いて非対称を塞いだつもりでいたが、
塞いでいたのは裁定済みの concept だけで、**まだ誰も見ていない draft は
二コールで消せた**。下書きを書いたエージェントが、自分の下書きを人が
読む前に消せる面である。

正しい振る舞いは既に用意されている([0001](0001-architecture.md) の
ループ)。悪い draft を書いたエージェントは、それを人の裁定に残す —
人は Web UI か CLI で reject するか消すかを選べて、reject なら
**なぜ却下されたかが台帳に残る**。エージェントが消してしまえば、その
理由は最初から生まれない。

## 3. `get_concept_usage` — 利用回数はループの人間側である

`get_concept_usage` は concept 一件の利用回数の合計(検索に出た回数、
fetch された回数、worked / failed の報告数、`last_used_at`)を返す。

これは [0069](0069-the-loop-and-what-measures-it.md) が**キュレータの
前に置く数**である。draft を昇格させる根拠、古びのシグナル、
deprecated を検討する材料 — どれも人が読んで人が動く。

**エージェントが「この concept に頼ってよいか」を決めるために要るものは
別で、それは既に届いている。** trust tier と `verified_at` は検索ヒットの
一行にも `get_concept` の応答にも載っており、`get_context` は verified を
上位に置いたうえで本文ごと返す。利用回数が 412 か 3 かは、その判断を
変えない。

エージェントが持ち続けるのは**書き込みの側**、`report_outcome` である。
ループのうちエージェントが実際に所有している辺はそれ一本で、その報告が
totals を作る。**作る側は残り、読む側だけが降りる。**

## 4. 落ちた能力と、その残り先

**畳み込みが費用を別の面へ移すだけなら、それは畳み込みではない**
([docs/surface.md](../surface.md) の三つ目の問い)。ここで落ちるのは
MCP の能力そのものであり、代わりを MCP の中には置かない。同じ能力は
他の三面に一つも欠けずに残る。

| 能力 | REST | CLI | Web UI | MCP |
|---|---|---|---|---|
| concept の削除 | `DELETE /api/v1/bundle/{path}` | `ochakai delete` | 削除ボタン | **無し** |
| 利用回数の合計 | `GET /api/v1/usage/{id}` | `ochakai usage` | concept ページ | **無し** |

**CLI が完全性の面である**とはこのことである(0067 §1)。シェルを持つ
エージェントは何も失わない。

## 5. 0067 §7「MCP の deprecate や機能削減はしない」を改訂する

0067 §7 は「シェルを持たないホスト型エージェントにとっては MCP だけが
入口である」を根拠に、MCP の機能削減をやらないことの側に置いていた。
**その一行を改訂する。**

根拠のほうは動かさない — ホスト型エージェントにとって MCP が唯一の入口
であることは事実である。動かすのは、そこから「だから何も降ろさない」を
導いていたことである。**唯一の入口だからこそ、そこに何を載せるかは
選ばれていなければならない。** 入口が一つしかない相手に、その相手が
下すべきでない裁定の口と、その相手が読まない数の口を渡していたのが
これまでの形だった。

0068 §3 が `fm.` を MCP からだけ降ろしたとき、この一行は既に一度譲って
いる。今回それがパラメータからツールに及んだので、§7 の側を書き直す。
**やらないことの側に残るのは、能力を他の面に残さないまま MCP から
降ろすこと**である。それは §4 の表が禁じている。

## 6. 互換性

**BREAKING で、非推奨期間は置かない。** 0.x に deprecation window は
なく([compatibility.md](../compatibility.md))、REST だけが凍結の対象で
MCP は明示的に不安定である。降りた二本を呼ぶクライアントは
「そんなツールは無い」で落ちる。

- `delete_concept` を呼んでいたエージェント → 呼ばない。誤った concept は
  `report_outcome` failed で再検証フィードに乗せ、より良いものがあれば
  `put_concept` で別 id に draft を書く。実際に消すのは人が
  `ochakai delete` か Web UI で行う。
- `get_concept_usage` を呼んでいたエージェント → 判断に要る信頼シグナル
  (trust tier・`verified_at`)は検索ヒットと `get_concept` に載っている。
  数そのものが要る自動化は `GET /api/v1/usage/{id}` か `ochakai usage`
  へ移す。

read-only デプロイの挙動も一つ簡単になる: 降ろす write ツールは
`put_concept` と `report_outcome` の二本になり、`destructive` の
アノテーションを持つツールは MCP に一本も無くなる。

## 7. やらないこと

- **代替ツールを置かない。** `get_concept_usage` の縮小版も、確認を挟む
  `delete_concept` も作らない。二本目の入口は二本目の説明を持ち、
  そちらだけが腐る(0068 §1)。
- **REST・CLI・Web UI からは何も降ろさない。** 落ちるのは MCP からだけ
  である(§4)。
- **裁定を MCP に載せない。** verify / reject を足して対称にするのは、
  この記録と逆向きの決定である。
- **`report_outcome` を降ろさない。** エージェントが所有するループの辺で
  あり、これを降ろせば書き戻しループの測定が止まる(0069)。

見直す条件: シェルを持たないホストのエージェントが、この二本の不在で
実際に詰まった一件が出たとき。そのときも戻すのは一本ずつで、
`get_concept_usage` のほうが先である — 削除は依然として裁定だからである。
