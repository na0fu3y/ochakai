# ochakai 設計ドキュメント 0099: purge の約束はバイト列まで届く

Status: Accepted(2026-08-11)。[0031](0031-purge.md) §3.2 の
「**GCS 上の添付バイト列は回収しない**」を改訂する。0031 の他の決定は
一つも動かない — 二段階であること、二段目が不可逆であること、
`knowledge_purge` に監査行を残すこと、MCP と Web UI に出さないこと。
住所の現行の持ち主が [0075](0075-the-bundle-is-the-address-space.md) で
あることも変わらない。
Date: 2026-08-11

## 0. この記録が決めたこと

1. **purge とファイル削除のあと、どこからも参照されていない blob の
   バイト列を回収する。** 0031 §3.2 は回収しないと決めていた(§1)。
2. **回収は一つの削除の副作用ではなく、大域の問いへの答えとして行う。**
   0031 が「全エントリの走査になる」と書いたその走査を、独立した操作と
   して実行する(§2)。
3. **0031 が避けようとした危険は、受け入れたのではなく閉じた。**
   生きている添付を消しうる競合は、共有ロックと削除順序で消えている
   (§3)。
4. **サーフェスは一つも増えない。** `purge` と `DELETE` は既に言って
   いたことを果たすようになっただけである(§4)。

## 1. 0031 が断ったもの、断った理由

0031 §3.2 はこう書いた:

> **GCS 上の添付バイト列は回収しない。** blob はコンテンツアドレス
> (sha256、0011)で共有されており、同じバイト列を別のエントリが参照して
> いるかもしれない。参照カウントを持たない以上、安全に消せるのは
> 「どこからも参照されていないと確認できたとき」だけで、その確認は
> 全エントリの走査になる。孤児 blob のストレージ代は、誤って生きている
> 添付を消すリスクより安い。

三段の論である。**共有されている**から一つの削除では消せない。
**参照カウントが無い**から確認は全走査になる。そして**全走査は高くつく**
から、孤児のままにしておくほうが安い。

前の二段は今も正しい。取り下げるのは三段目——**天秤の置き方**である。

## 2. 秤が間違っていた: 対価はストレージ代ではなかった

0031 は「孤児 blob のストレージ代」と「誤削除のリスク」を比べた。
比べるべきだったのは**約束**のほうである。

[docs/surface.md](../surface.md) の第一条件は、資産が丸ごと入り、丸ごと
出て、**求められれば消える**ことだと言う。purge は「消せ」と言われた
ときにだけ走る二段目であり、それが消さずに残すものがあるなら、
残るのは容量ではなく**嘘**である。0031 自身が §3.3 で「呼び出し元が
消せと言ったのは内容である」と書いていた。バイト列はその内容だった。

実装はこの矛盾を、記録より先に見つけていた。store のコメントは
「バイト列は残る、掃除したければ運用者が自分で書け」と書いていた——
製品が果たすと言った約束を、運用者への宿題にしていたことになる。

**では全走査の代金はどうなったか。** 0031 の見立ては、走査が一つの
purge の内側で起きることを前提にしていた。実際には外に出せる:
purge は自分のトランザクションで行を消し、コミットしたあとに、
**どの削除にも属さない大域の掃除**が走る。掃除が失敗しても purge は
成功しており、残ったバイト列は次の破壊的操作が回収する。
一つの呼び出しの応答時間に全走査を載せない限り、この代金は
0031 が見積もった額では請求されない。

## 3. 危険は受け入れたのではなく閉じた

0031 が守ろうとしたのは「誤って生きている添付を消す」ことである。
これは値切って通したのではなく、二つの仕掛けで閉じている。

**問いを正確に立てる。** 消すのは「どの object 行も attachment 行も
参照していない blob 行」だけである。参照カウントのような**写し**は
持たない — 写しは本体とずれうるが、行そのものを見る問いはずれない。
0031 が「確認は全エントリの走査になる」と言ったのは、この問いの
コストの話であって、この問いが不正確だという話ではなかった。

**書き込み中のバイト列を守る。** 危ないのは残骸ではなく、
**まだ行になっていないバイト列**である。`PutFile` はバイト列を
create-only で上げ、「既にある」を成功として読む。上げ終わってから
行がコミットされるまでの隙間に掃除が走れば、これから参照される
バイト列を消してしまう。だから書き手はその区間を共有ロックで
持ち(互いには並走できる)、掃除は排他で取る。

**順序も決める。** バイト列を先に、行を後に消す。途中で落ちれば
「バイト列の無い、どこからも参照されていない行」が残り、これは次の
掃除だけが読む — 同じ内容が上げ直されれば、object が無いので普通に
保存される。逆順にすると、ハッシュを忘れたうえにバイト列だけが
残り、**それを名指すものが何も無くなる**。

## 4. 観測できる違い

運用者はバケットを見れば分かる。purge した concept が持っていた
ファイルのバイト列は、もう残らない。

**釈明しておくべき記述が一つある。** v0.13.0 のリリースノートは purge を
紹介して「添付のバイト列は回収しない(It does not reclaim attachment
bytes)」と書いた。その記述は当時正しく、いまは正しくない。0031 を
読んで「バイト列は残る」と設計した利用者がいるとすれば、変わったのは
その一点である。

**サーフェスは増えない。** 掃除を呼ぶための REST 操作も CLI コマンドも
足さない。掃除は破壊的操作の後始末であって、利用者が計画して打つ
ものではない — 打つ必要があるなら、それは破壊的操作が仕事を終えて
いないということである。失敗はログに警告として出るだけで、
リクエストは失敗しない: 呼び出し元が消せと言った行は既に消えている。

## 5. やらないこと

- **参照カウントを持つこと。** 行を数えた写しを別に持てば、問いは
  速くなるが、ずれたときに**生きている添付を消す**。0031 が恐れた事故は
  まさにこの形で起きる。速さは、掃除を要求経路の外に出すことで
  買ってある。
- **上書きのたびに掃除すること。** ファイルを置き換えると古いハッシュが
  孤児になりうるが、その回収は次の破壊的操作まで待つ。すべての
  import の PUT に排他ロックの全走査を負わせるのは、掃除が避けたはずの
  代金をいちばん頻繁な経路で払うことになる。**上書きで生まれた孤児に
  ついては、「消える」は「いずれ消える」である**と認めておく。
- **purge のトランザクションの中で掃除すること。** 大域の問いを一つの
  削除の内側に持ち込むと、0031 の見積もりが正しい世界に戻る。
- **掃除を定期実行にすること。** 破壊的操作のあとに走れば十分であり、
  cron は Google Cloud の依存を一つ増やす([0086](0086-no-secrets-anywhere.md)
  が守っている姿勢の面積を、掃除ごときで広げない)。
