# ochakai 設計ドキュメント 0102: 履歴は一つの綴りで答える

Status: Accepted(2026-08-15)。
[0064](0064-rest-stops-at-api-v1.md) §11 の凍結を破ってよい理由に**三つ目**を
足す — **規格が綴りを定めているものの、二つ目の綴りを畳むこと**(§3)。
同 §14.1 が「コードは変えない、スペックを直す」と決めた `?history` の
`limit` の二重性を撤回する(§1) — 直したのは記述ではなく、二つあったこと
のほうである。[0075](0075-the-bundle-is-the-address-space.md) §4 の
「一つの住所の二つの表現は同じことを言う」は動かない — 表現が一つ減る
だけである。
Date: 2026-08-15

## 0. この記録が決めたこと

1. **`?history` は Accept が何であれ JSON で答える**(§2)。markdown の
   レンダリングは無くなる。
2. **凍結を破ってよい三つ目の理由**を足す(§3)。前の二つより弱い理由で
   あることも書く。
3. **指紋は一行も動かない**(§4)。0100 と同じく、記録が唯一の記載場所で
   ある。

## 1. 同じ要求に、二つの答えがあった

OKF SPEC §9 は markdown の履歴を一つ定めている —— **`log.md`**、オブジェクト
の隣に置かれる予約ファイルである。ochakai はそれを生成しており、それとは
別に `?history` が**同じ台帳の行から二つ目の markdown**を描いていた。

二つ目であること自体より、**それが上限を二つに割っていた**ほうが重い。
0064 §14.1 はこう書いている:

> 同じ `?history&limit=500` が、`Accept: application/json` で概念に対しては
> 400 に、markdown としては 200 になる

あの節の決定は「コードは変えない。**スペックを直す**」だった —— 上限が
対象によって違うと散文に書く。**それは食い違いの記述であって、解消では
ない。** 呼び出し元から見れば、同じ URL に同じパラメータを送って、
`Accept` の一語で通ったり弾かれたりする。0064 §2 が閉じてきた沈黙の
すぐ隣にある形である。

## 2. 決定: `?history` は JSON である

`?history` は概念のリビジョン(50/200)かファイルの変更行(1000/1000)を
JSON で返す。`Accept: text/markdown` を送っても JSON が返る —— 0064 §22 が
「`Accept` は名前の集合として読み、**既定は名指さないことで必ず得られる**」
と決めたとおり、載っていない表現を名指した要求は既定に落ちる。

**markdown の履歴が消えるわけではない。** `log.md` は今までどおり生成
され、ディレクトリの履歴を SPEC §9 の形で publish する。消えるのは、
**一つのオブジェクトの履歴を markdown で描く二つ目の綴り**だけである。

そのオブジェクト一つ分の markdown を読みたい人がどうするかは、正直に
書いておく —— **手立ては無くなる**。`log.md` はディレクトリの単位でしか
描かれないので、一オブジェクトに絞った markdown は JSON から自分で
組み立てることになる。落ちた能力はこれで、`ochakai revisions` も Web UI
の履歴パネルも元から JSON を読んでいるので、**製品の中でこれを使っていた
面は一つも無い**(0068 §3 の「通行量の無い入口」に近いが、あちらは
入口を降ろす規則であり、ここで降ろすのは表現である)。

## 3. 凍結を破ってよい三つ目の理由

0064 §11 は理由を一つ持ち、[0100](0100-md-is-how-a-concept-is-spelled.md)
§4 が二つ目(出力が OKF に適合しないこと)を足した。本書が足す三つ目は
**規格が綴りを定めているものの、二つ目の綴りを畳むこと**である。

**三つとも満たす場合に限る**、と狭く書く。

1. OKF SPEC が、その事柄の綴りを**定めている**(ここでは §9 の `log.md`)。
2. ochakai の面に、**同じ事柄の二つ目の綴り**がある。
3. 畳むのは **ochakai 側の綴り**であって、規格の側ではない。

**前の二つより弱い理由である。** セキュリティ上の欠陥も OKF 非適合も、
判定の全部が外にある —— SPEC が MUST で書いた条件に対する yes / no で
ある。ここは 2 が「同じ事柄か」という判断を含み、**その判断は ochakai の
側にある**。だから条件を三つとも要求し、しかも 1 で「規格が定めている」
ことを要求する: 規格が何も言っていない領域での「こちらのほうが整って
いる」は、この理由に**当たらない**。

もう一つ、歯止めを書いておく。**畳めるのは表現であって、住所ではない。**
住所を消せば呼び出し元は 404 を受け取るが、表現を畳んだ呼び出し元が
受け取るのは**同じ事実の別の形**である。`?history` を送っていた
クライアントは、今日と同じ行を JSON で受け取る。

## 4. 指紋は一行も動かない

`api/openapi.frozen.txt` の
`GET /api/v1/bundle/{path} response 200 content text/markdown type=string`
は**残る** —— 概念のエクスポート形(`Accept: text/markdown` で文書を読む)
が同じ行を使っているからで、OpenAPI は「このモードでは markdown を
返さない」を綴れない。0100 §5 と同じ場所に立っている:

> 凍結が守れるのは「何が在るか」であって「どれを選ぶと何が返るか」では
> ない(0064 §21)。

**だから記録が要る。** 指紋も契約テストも見ない破壊的変更であり、
CHANGELOG と本書だけがそれを書く。

## 5. 同時に閉じるもの

- **`limit` の二つの答え。** 概念の `?history` は 50/200 一つになり、
  0064 §14.1 が散文に書き下した非対称は主語を失って消える。
- **`service.RenderObjectLog` が死ぬ。** 呼び出し元が一つも無くなるので
  削除する(0064 §12 が `queryFloat` にした扱いと同じ)。`renderLog` の
  間接も残る呼び出し元が一つなので畳む。

## 6. 面への配分(0067)

- **REST** — 上のとおり。操作もパラメータもヘッダも動かない。
- **CLI** — 変化なし。`ochakai revisions` は元から JSON を読む。
- **MCP** — 変化なし。履歴は載っていない(0067 §5.1: エージェントが要る
  信頼シグナルは concept 本体に載っており、監査は人の仕事である)。
- **Web UI** — 変化なし。履歴パネルは元から JSON を読む。

## 7. 採らない案

- **markdown を残し、`limit` だけ揃える。** 食い違いは消えるが、SPEC §9 の
  隣に二つ目の markdown の履歴が残る。しかも上限を動かすこと自体が挙動の
  変更なので、**代金を払って重複を買う**ことになる。
- **`log.md` のほうを畳む。** 規格が定めている綴りのほうを消すことになり、
  §3 の条件 3 に反する。
- **1.0 まで待つ。** 待つ理由は「破ってよい理由が二つしか無いから」で
  あり、本書はその規則自体を書き換えている。ただし**急ぐ理由も無い** ——
  0100 のような適合の欠陥ではないので、**この記録の値打ちは規則のほうが
  本体である**と正直に書いておく。
- **理由を広く書く**(「規格に照らして整っているほうを選ぶ」)。判定が
  ochakai の側に丸ごと移り、0082 §5 が最も警戒した「規則を書き換えずに
  曲げる」の一歩手前になる。
