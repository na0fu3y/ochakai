# ochakai 設計ドキュメント 0140: 一つの住所は、読みにも開いている

Status: Accepted(2026-09-09)。[0077](0077-one-address-for-a-file.md) を
Superseded にし、その全体をここに書き直す — **CLI がファイルを名指す綴りの
現行ドキュメント**。0077 が決めた書き込みと削除の綴りはそのまま残り、
同記録 §4 が「やらないこと」に挙げた読みだけが覆る。
[0075](0075-the-bundle-is-the-address-space.md) §§1・4 の「パスが住所で
ある」、[0064](0064-rest-stops-at-api-v1.md) §5 の `<id>.md`、
[0046](0046-bundle-address-space.md) §3.2 の「受け取る、しかし描画しない」は
どれも動かない
Date: 2026-09-09

## 0. この記録が決めたこと

1. **`put`・`delete`・`get` の三本が、バンドルの両方のオブジェクトを
   扱う。** ファイルの住所はそれが置かれているパスそのもので、concept の
   住所は `<id>.md` である。
2. **書き込みはバイト列が決め、削除と読みは綴りが決める。** 綴りが先に
   指した住所を問い、そこに何も無かったときだけもう一方を試す。
3. **`ochakai get <パス>` はファイルのバイト列を stdout に出す。**
   `--json` と `--download` は concept を読む語なのでファイルには断り、
   テキストでないバイト列は端末に対して断る。
4. **コマンドもフラグも増えない。** CLI は 24 のまま、`FLAG` も動かない
   ([docs/surface.md](../surface.md))。
5. Web UI のファイル選択から、**受け取る形式の一覧(`accept`)を落とす**
   — 書き込み側が何も拒まなくなった後も残っていた 0013 の名残である。

## 1. 0077 が読みを断った理由と、それが持っていなかったもの

0077 §4 はこう書いた。「`ochakai get <path>` でファイルのバイト列を出す
こと。読む側は `ochakai get <id> --download <dir>` が既に持っており、
`browse` がディレクトリのファイルを出す。」

**持っていたのは別のものだった。** `--download` は *concept が持つ
ファイルを全部、ディレクトリに落とす*。一つを名指す口ではなく、stdout に
出す口でもない。`browse` が出すのは名前・メディア型・バイト数であって、
中身ではない。そして `ochakai get x/y.py` は `.md` を足して問うので、
404 で終わる。つまり CLI には、**一つのファイルの中身を見る綴りが
無かった**。

2026-09-09、添付された Python スクリプトを四つの面で追って出てきたのは、
この欠落が面ごとに違う形で現れていることだった。

| 面 | ファイルの中身に対して |
|---|---|
| REST | `GET /api/v1/bundle/<パス>` がバイト列を返す。過不足なし |
| MCP | `get_file` が返す。ただし**丸ごと**で、先頭だけ読む術は無い |
| Web UI | クリックで開くが、カードは `TXT` の三文字しか言わない |
| CLI | **読めない。**`--download` でディレクトリに落とすだけ |

人が最初にやることは「まず 40 行だけ見る」であり、それができないのは
CLI だけだった。**完全性の面**([0067](0067-four-faces-and-what-they-decline.md) §2)
がそこを持っていないのは、0068 §3 の「通行量の無い入口は降ろす」の逆
— 通行のある操作に入口が無い、である。

## 2. 決定

### 2.1 読みも、綴りが先に指した住所から

0077 §2.2 が `delete` のために決めた規則を、`get` がそのまま使う。拡張子を
持たない引数は id なので `<id>.md` を先に問い、自分の拡張子を持つ引数は
パスそのものを先に問う。**もう一方は、先に問うた住所に何も無かったときだけ
試す。**

規則は二箇所に書かず、一つの関数を二本が呼ぶ(`bundleAddresses`)。
**二度綴られた規則は、二箇所で違う答えを出す規則である** — 0077 §1 が
`detach` について言ったことが、そのまま規則にも当てはまる。

読みが増やす往復は、以前なら 404 で終わっていた場合の二回目だけである。
そして返す誤りは、**読み手の引数が実際に指した住所のもの**である
— `ochakai get metrics/typo` の答えは「そんな concept は無い」であって、
存在しないファイルの話ではない。

### 2.2 ファイルはバイト列で、その JSON は無い

`--json` は「読み全体(document・summary・observed)」を出す語で、
`--download` は「concept が持つファイルを保存する」語である。ファイルには
どちらも無い — **ファイルとは、そのバイト列の全部である**。だから黙って
無視せず、断る。無視は「フラグが効いた」と読める沈黙で、それが最も高く
つく。

断るのは**バイト列が手に入ってから**である。この読みは同時に「綴りは
concept を指したが、そこには無かった」の後半でもあり、フラグを先に見て
断ると、**存在しないファイルについて「ファイルは --json を取らない」と
答える**ことになる。

### 2.3 テキストでないバイト列は、端末に書かない

curl の規則を、curl の理由で採る。画像や PDF を端末に流せば端末が壊れ、
保存するつもりだった読み手に残るのは、直すべきセッションである。断りは
欲しいリダイレクトを名指す。

**パイプは端末ではない**ので、`| file -` も `| xxd` も影響を受けない。
テキストであること(`text/`)だけを条件にするのは、この綴りが読むために
足されたものがテキストだからである — スクリプト、CSV、JSON。
`application/octet-stream` は「何にも見えなかった」の答えであって、
安全だという答えではない。

### 2.4 増えないもの

新しいコマンドは足さない。`ochakai cat` は覚える語を一つ増やし、
`ochakai get` が既に名指せる住所を二本目の綴りで名指す — 0077 が畳んだ
「一つのオブジェクトに二つの住所」を、読みの側で作り直すことになる。
フラグも足さない。**CLI 24 のまま、`FLAG` は動かない。**

## 3. 0077 が決めて、ここでも動かないもの

| 前 | 後 |
|---|---|
| `ochakai attach <id> <file>` | `ochakai put <バンドルパス> -f <file>` |
| `ochakai attach <id> <f1> <f2>` | シェルのループ |
| `ochakai attach <id> <file> --name <名前>` | `ochakai put <…>/<名前> -f <file>` |
| `ochakai detach <id> <名前>` | `ochakai delete <バンドルパス>` |

- **書き込みはバイト列が決める。** frontmatter に `type` があれば concept
  で住所は `<id>.md`、無ければファイルで住所は引数そのもの。サーバーの
  判定を鏡写しにしたもので、CLI が wire に無い区別を発明しないための形
  である(0077 §2.1)。JSON 入力だけが例外で、concept の住所を名指した
  ときだけ concept として読まれる。
- **貼るためのリンクは `put` が出す。** 0075 §5 が帰属を本文からの導出に
  した以上、**誰もリンクしないファイルは誰にも見つからない**(0077 §2.3)。
- **落ちた便宜は落ちたまま。** 一度に複数ファイルはシェルのループ、
  `--name` はパスそのもの(0077 §2.4)。
- **Web UI は CLI と同じ語を使う。** `Add files` と `Remove`。0064 §8 が
  「対称に残す」と決めたことに従っている(0077 §3)。

## 4. 四つの面

- **REST**: 動かない。`GET /api/v1/bundle/{path}` が既に唯一の契約で、
  CLI はその薄いクライアントである(0067 §2)。
- **CLI**: この記録。既定は yes、完全性の面だから。
- **MCP**: 足さない。`get_file` が既に持っている。**検索ヒットにファイルの
  メタデータを載せないことも、ここで言っておく** — `FillFiles` は
  Web UI が一覧のサムネイルを 1 行 1 往復で引かずに済むよう REST の一覧に
  置いたもので、エージェントが次に打つのは `get_concept` であり、そこに
  ファイルは載っている。名前・メディア型・バイト数・パス・SHA-256 を全ヒットぶん
  コンテキストから払う理由が無い。**能力はどの面からも落ちていない**
  ([0076](0076-two-tools-leave-mcp.md) の規則)。
- **Web UI**: ファイル選択の `accept` を落とす。0013 が許した五種の
  メディア型の一覧で、**0046 §3.2 が書き込み側の拒否を無くした後も
  残っていた** — バンドルは何でも運べるのに、ページからは選べなかった。
  同じファイルが `ochakai put` からは入り、ここからは入らないという非対称
  である。ブラウザが何をしてよいかは配るときに決める(`InlineServable`)
  ままで、そちらは 1 バイトも動かない。

## 5. やらないこと

- **シンタックスハイライト。** [0130](0130-the-web-ui-and-the-fields-of-a-document.md)
  §5 が既に断っている — 依存を増やす。同記録 §2 がバンドラも npm 依存も
  断っているので、残る道は手書きの字句解析器だけである。
- **型ごとの契約セクションを描くこと。** これも 0130 §5 の「型ごとの契約
  セクションの出し分け」で、理由は §3.5 にある: **ochakai は型ごとの
  スキーマを持たない**ので、UI がそれ以上の規則を持つと**面が形式に無い
  規則を教える**ことになる。読み側が「どの frontmatter キーがこのファイルを
  指しているか」を言うのは型に依らないので、その断りの外である。
- **カードに添付の先頭数行を出すこと。** ここでは決めない — 住所の問いでは
  なく、読ませ方の問いであり、0130 のエリアである。
- **メディア型からの言語判定。** `.py` は `text/plain` として保存される
  — sniff がそう答えるからで、拡張子を型に昇格させる決定はここにはない。

## 6. 壊れるもの

**壊れない。** `ochakai get <id>` の出力も終了コードも 1 バイトも動かない。
増えるのは、**以前 404 で終わっていた綴りが答えるようになる**ことだけで
ある — 拡張子を持たない引数については、concept がそこに無く、同じパスに
ファイルが座っているときにだけ起きる。
