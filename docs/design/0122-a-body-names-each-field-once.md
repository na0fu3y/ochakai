# ochakai 設計ドキュメント 0122: 本文は、鍵を一度だけ名指す

Status: Accepted(2026-08-23)。[0064](0064-rest-stops-at-api-v1.md) §2 の
「宣言していないボディキーは 400 で名指す」を、**書かれたとおりに効く**
ところまで進める — 照合が綴りを完全一致で見ることと、同じ鍵が二度
現れたら断ることの二つ。後者は §20.2 がクエリキーに与えた答えを本文に
当てたものである。凍結の範囲([0107](0107-the-freeze-holds-the-okf-core.md))
も、エラーの `code`([0083](0083-an-error-carries-a-code.md))も動かない
Date: 2026-08-23

## 0. この記録が決めたこと

1. **本文の鍵の照合は完全一致である。** `{"RULING": "verified"}` は
   `ruling` を宣言した操作にとって未知の鍵であり、400 で名指される
   (§2)。
2. **同じ鍵が二度現れた本文は 400 で、その鍵を名指す**(§3)。
3. 二つとも**規則の追加ではない**。0064 §2 が決めた規則が、それを実施
   するはずの機構に半分しか無かった、という話である(§1)。

## 1. 規則は書かれていて、守られていなかった

0064 §2 は本文の未知キーを 400 にすると決め、`readJSON` は
`dec.DisallowUnknownFields()` を呼ぶようになった。**そこで閉じたと
思われていた。** 実際には、`encoding/json` は宣言と本文の鍵を**大小を
区別せずに**突き合わせる。だから宣言されているのは `ruling` 一語なのに、

```
{"RULING":"verified"}   → 200
{"Ruling":"verified"}   → 200
```

が通っていた。`DisallowUnknownFields` は「どの Go フィールドにも当たら
なかった鍵」を報告する仕組みなので、**当たってしまう鍵については何も
言わない**。0064 §2 が塞ごうとしたのは「サーバがまだ知らない鍵が黙って
捨てられる」形であり、こちらはその裏返し — **サーバが知らないはずの綴りが
黙って受け取られる**形である。どちらも、リクエストの意味が呼び出し元の
書いたものと違っている。

同じ関数のもう一つ。`encoding/json` は繰り返された鍵に対して**最後の値を
採る**。

```
{"ruling":"verified","ruling":"rejected"}   → rejected として 200
```

0064 §20.2 は、これとまったく同じ問いをクエリキーについて扱っている —
`?limit=10&limit=50` に「求められたとおり」の答えは無い、と。そこで
挙げられた最悪の形(**同じリクエストの中で二つの向きに答えていた**)は
本文には無く、向きは一つ、常に最後である。だが「求められたとおりの答えが
無い」ことは同じで、**一つに決まっているほうが悪い場合がある**: 呼び出し
元は自分がどちらを送ったつもりかを知らないまま、決まった答えを受け取る。
裁定を打つ操作でそれが起きる。

## 2. 決定: 照合は完全一致

`RULING` は `ruling` ではない。これは新しい語彙ではなく、**契約が最初から
そう読める**ことの確認である — `api/openapi.yaml` は鍵を一つの綴りで
宣言しており、二つ目の綴りはどこにも書かれていない。書かれていない綴りが
通っていたのは実装の性質であって、約束ではなかった。

答えは既存のものを使う: 400、`code` は `invalid`、本文は
`unknown field "RULING"`。**未知の鍵と同じ形にする**のは、呼び出し元に
とって実際に同じことだからである — 送った鍵は、この操作が知らない鍵
だった。

## 3. 決定: 重複した鍵は 400 で名指す

`{"ruling":"verified","ruling":"rejected"}` は 400 になり、`ruling` を
名指す。**最後を採るという規則は、書き下せなくなって消える** — §20.2 で
`fm.{key}` の「最後の値が勝つ」が消えたのと同じ形で、規則を廃止したの
ではなく主語が無くなった。

**クエリ側にある「配列として宣言された鍵は反復してよい」という例外は、
本文には無い。** JSON は集合を配列で綴れるので、反復に第二の意味を与える
理由が最初から無い。`?type=Metric&type=Policy` に当たるものは
`{"type":["Metric","Policy"]}` であって、`type` を二度書くことではない。

## 4. 機構: 読む側だけを `encoding/json/v2` にする

Go 1.27 の `encoding/json/v2` は、**この二つをどちらも既定で断る**。
`RejectUnknownMembers` を渡せば未知の鍵は
`SemanticError`(`ErrUnknownName`)として、重複は
`jsontext.SyntacticError`(`ErrDuplicateName`)として返り、**どちらも
鍵の名前を構造化して運ぶ**。0064 §2 の実装がエラーメッセージの先頭を
文字列として剥がして鍵名を取り出していた箇所は、これで消える。

読む側だけである。**応答は `encoding/json` が書き続ける。** v2 は
marshal 側の既定も変えており(`omitempty` の意味、`nil` スライスの綴り、
時刻の書式)、それは凍結された面が実際に運んでいるバイト列である。
`internal/restapi` が二つの package を別名で持つのはそのためで、
**読む側と書く側が違う決定の下にあることを import ブロックではなく
呼び出し側で見えるように**している。

`http.MaxBytesReader` の 413(0064 §2 と同じ)と、JSON 値のあとに続く
内容の 400 は、どちらもそのまま残る。後者は `jsontext.Decoder` に次の
トークンを訊いて `io.EOF` 以外なら断る形になり、**理由を説明する文面
(「本文は一つの JSON 値である」)を保てる** — v2 の構文エラーは
「トップレベル値のあとに不正な文字」としか言わないので、そこは自分で
言う。

## 5. 何が壊れうるか

**今日 200 を得ているリクエストのうち、二種類が 400 になる。**

- 宣言された綴りと大小の違う鍵を送っているもの
- 同じ鍵を二度書いているもの

どちらも、**契約が受け付けると書いたことは一度も無い**。ochakai 自身の
クライアント(`internal/apiclient`)と Web UI はどちらも生成した本文を
送るので、この二つを作らない。凍結
([0107](0107-the-freeze-holds-the-okf-core.md))が止めているのは OKF
コア — バンドルの往復と検索 — であり、本文を読む四操作
(`move`・`review`・`usage`・`access`)はその外側にある。それでも
これは**利用者が観測できる変化**なので、記録がこれである。

`api/openapi.yaml` の散文に二段落を足す。§2 の「宣言していない本文の鍵は
400」に「照合は完全一致である」を添え、その隣に重複の段落を、クエリ側の
段落と同じ形で置く。**同じ文書の中で、クエリと本文が同じ規則を同じ言葉で
言っている**状態がこの記録の成果物である。

## 6. 断ったもの

**`encoding/json/v2` への全面移行。** 応答の側は上のとおり凍結が掛かって
おり、`internal/okf`・`internal/store`・`internal/mcpserver` の JSON は
それぞれ別の理由(保存形、SPEC、SDK の型)で今の綴りに縛られている。
**直すべき欠陥は読む側にあった**ので、動かすのも読む側だけにする。

**MCP のツール引数。** 同じ問いはそこにもあるが、引数を復号しているのは
go-sdk であって ochakai ではない。ochakai が持っていない決定を、ochakai
の記録が決めることはできない。

**移行期間。** compatibility.md の方針(非推奨ではなく撤去)のとおり、
両方の綴りを一リリース受け付ける窓は置かない。
[0088](0088-a-retired-name-answers-for-one-release.md) の窓は**改名された
名前**のためのもので、ここには改名が無い — `ruling` は一度も別の綴りを
持ったことがない。
