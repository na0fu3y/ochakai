# ochakai 設計ドキュメント 0128: 一覧は、いつまで持つかを言う

Status: Accepted(2026-08-23)。[0118](0118-a-call-carries-everything-it-needs.md)
が転送を stateless にしたぶんの後始末で、**プロトコル 2026-07-28 が
list に足した TTL のヒントを、ochakai が自分で答える**ことを決める。
面もツールも動かず、[docs/surface.md](../surface.md) の九つの節はどれも
数が変わらない(MCP-BYTES も — 数えるのはツールの項目であって、応答の
封筒ではない)。ツール名の窓は [0088](0088-a-retired-name-answers-for-one-release.md)
のまま
Date: 2026-08-23

## 0. この記録が決めたこと

1. **`tools/list`・`resources/list`・`resources/templates/list` は
   「5 分持つ」と答える**(§2・§3)。
2. **`resources/read` は 0 のまま**である — concept は知識であって、
   一覧ではない(§4)。
3. 足したのはフィールドではない。**既に答えていたものを、決めて答える
   ようになった**(§1)。

## 1. 決めていない答えを、既に送っていた

2026-07-28 は list 系の結果に `ttlMs` と `cacheScope` を足した。SDK は
その二つを**応答を出すたびに埋める** — `cacheScope` は `"public"`、
`ttlMs` は 0 である。そして仕様は 0 をこう読む: **「直ちに古いものと
みなすべき」**。

つまり ochakai は今日、すべてのクライアントに「この一覧は今この瞬間に
古い」と言っている。**誰もそう決めていない。** SDK の構造体にゼロ値が
入っているという理由だけでそうなっており、`omitempty` が無いので黙って
省略されることもない。0064 §2 が本文の未知キーについて言ったのと同じ
形の問題である — 規則が無いのではなく、**規則を書いていない場所で機構が
何かを答えている**。

## 2. 決定: 構築時に決まる一覧は 5 分持つ

`newServer` が登録するのは、姿勢に応じたツール(6 本、read-only なら
4 本 — 0040 §2.3)と、concept の resource template 一つだけである。
**あとから登録するものは無い。** だから一つのプロセスの中で、この三つの
一覧は定数である。

したがって数字が答えているのは「一覧がいつまで正しいか」ではない —
プロセスが生きている限り正しい。答えているのは、**プロセスが入れ替わった
あとクライアントが古い答えをいつまで信じてよいか**である。これを変える
ものはリリースしか無い。

**5 分**は、その尺度に対して短く、接続に対して長い。stateless な転送
(0118)はクライアントに一覧を掛けておくセッションを与えないので、接続
ごとに引き直す実装は引き続ける — 5 分はその一まとまりの作業を覆う。
一方でデプロイのロールアウトの中で気づかれる短さであり、改名された名前が
答え続ける一リリース(0088)の内側に十分収まる。**古い一覧を掴んだまま
アップグレードを跨いだクライアントが握っているのは、まだ動く名前である。**

## 3. `cacheScope` は `public` のままにする

SDK の既定であり、**ここでは正しい**。一覧はデプロイの姿勢の性質で
あって、呼び出し元の性質ではない — 同じデプロイに来た全員が同じ 6 本を
聞かされ、認可は呼び出しごとに `service` で効く
([0109](0109-a-directory-has-readers-and-writers.md))。だから途中に
立つものが誰にでも配ってよい。

既定と一致するので実装は一行も無いが、**0109 のあとでは確かめる価値の
ある一致**なので、テストが読み取って固定している。付与が一覧を細らせる
ようになった日には、この行が落ちる。

## 4. `resources/read` は 0 のまま

同じフィールドを持っており、**触らない**。concept は誰かが書けば変わる。
キャッシュしたクライアントは、ベースがもう持っていない文書を読み手に
見せることになる。

これは「一覧かどうか」の線ではなく、**知識かどうか**の線である。前者は
このデプロイが何を提供するかの宣言で、構築時に決まる。後者はナレッジ
そのもので、ループが回っている限り動く(0069)。カーソルを持つページも
0 にする — 途中のページは歩いている場所であって、掴んでおくものではない。

## 5. 何を買っていないか

**エージェントのコンテキストは一バイトも減らない。** ツールスキーマの
予算(0067 §1、MCP-BYTES)は一覧を取り直す回数とは無関係で、減るのは
往復だけである。

**「誰が詰まったか」に、この記録は答えられない。** 出どころは報告では
なく、取り入れていない推奨事項を数えた調査である
([0125](0125-a-body-names-each-field-once.md)・
[0126](0126-a-browser-says-where-it-came-from.md) と同じ)。それでも
足す側に立つ理由は、これが**追加ではなく訂正**だからである — 表面の
三つの問いは表面を増やす提案のためのもので、ここでは何も増えていない。
増えていないものについて「何が畳めるか」を問うても答えは無い。

## 6. 断ったもの

**デプロイが選べる値にすること。** 環境変数が一つ増え(ENV 15 → 16)、
運用者が答えられない問いを一つ増やす — 正しい値はこの記録が持っている
情報(一覧が何で決まるか)から導かれるもので、デプロイごとに違う理由が
無い。

**`prompts/list`。** 登録していないので答える一覧が無い。

**`initialize` の結果。** これも封筒を持つが、接続ごとに一度しか起きず、
しかもクライアントの識別を運ぶ(0118 §3)ので、キャッシュの対象という
より接続そのものである。
