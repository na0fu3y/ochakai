# ochakai 設計ドキュメント 0049: 一覧はカーソルでページングし、順位はしない

Status: Accepted(2026-07-28)。一覧面 —
[0025](0025-closing-the-loop.md) §6 と [0037](0037-stale-and-source-lookup.md)
§2.1 のフィード、同 §2.3 の source 逆引き — に `cursor` を足し、
**検索(順位を返す面)にはページングを持たせない**ことを refusal として
記録する。既存の決定を覆さない(足すのはパラメータ 1 つと応答のキー 1 つ)。
[0046](0046-bundle-address-space.md) §3.5 が `/api/v1/knowledge` を
`/api/v1/search` に改名しても、本ドキュメントが決めるのは**その面の
パラメータ**であって住所ではないので、改名にそのまま乗る。
[0015](0015-surface-consistency.md) §3 に、CLI がページを自分で歩かないと
いう意図的な省略を 1 件足す。
Date: 2026-07-28

## 1. 問題

一覧面が受け取るのは `limit` だけである。検索は既定 10・最大 50、
`sort=` のフィードは既定 100・最大 1000。**上限の先へ進む手段が無い。**

- **フィードは台帳であって、上位 N ではない。** `sort=usage` は
  レビュー待ちの下書き、`sort=failed` は未回答の失敗報告、
  `sort=stale_after` は期限切れ、`sort=verified_at` は検証の古い順。
  どれも「キューを空にする」ために読むもの(0025)であり、1000 件で
  静かに切られたキューは、**空になったキューと見分けが付かない**。
- **壁は既に Web UI に見えている。** レビュータブと explore の
  フィードは「最初の 100 件 · <u>最大 1000 件まで読み込む</u>」という
  注記を出す。1000 の先は無い、とは書いていない — 書けないからである。
- **ochakai を自分の web サービスに埋め込んで一覧を作る**のは本
  プロジェクトが掲げる使い方の 1 つで、これはその最初の 1 日に当たる壁で
  ある。

API 内の唯一のカーソルは `POST /api/v1/reembed` のもので、不透明な文字列に
止まった位置を運ぶ keyset である。**先例は既に家の中にある。**

## 2. 決定

### 2.1 一覧はページングする

一覧モード — `sort=verified_at|usage|failed|stale_after` と、query の無い
`source=` 逆引き — が `cursor` を受け取る。応答は、続きがあるときだけ
`cursor` を返す。

```
GET /api/v1/knowledge?sort=usage&status=draft&limit=100
→ { "hits": [ … 100 件 … ], "cursor": "MQBhc2FnZQ…" }

GET /api/v1/knowledge?sort=usage&status=draft&limit=100&cursor=MQBhc2FnZQ…
→ { "hits": [ … 41 件 … ] }        # cursor が無い = ここで終わり
```

**offset ではなく keyset である。** 一覧はいずれも全順序を持ち
(最後の同点解決は必ず `id`)、その順序の中の 1 点を運べば続きが引ける。
`OFFSET` は読み飛ばす行数に比例して遅くなり、しかもページ間で行が動くと
ずれる — 検証すれば `sort=verified_at` の順位が変わる面で、
「N 件飛ばす」は位置の指定として意味を持たない。

**`cursor` は不透明である。** 中身は「どの一覧か」+ その一覧の順序キーの
値 + `id` を base64url で包んだものだが、**利用者が組み立てるものでは
なく、直前の応答から受け取って返すもの**である。別の一覧のカーソルを
渡したら 400 で、どの一覧のものかを言う — 順序キーが違えば位置として
解釈できない。

**フィルタはカーソルに入らない。** カーソルは順序の中の位置であって
クエリのスナップショットではないので、次のページも同じフィルタを添えて
呼ぶ。片方だけ変えると「その位置より後で、新しいフィルタに当たるもの」が
返る — 定義として正しく、意味としては利用者の意図ではない。だから
そう書く。

### 2.2 順位はページングしない

`q=` と `cursor` の同時指定は **400** である。検索の契約は `limit` が
すべてで、上限は 50 のまま。

理由は 2 つあり、片方は技術的で片方は製品的である。

- **順位に「次のページ」は無い。** 検索は lexical・vector・添付の 3 本を
  それぞれ 2×limit 取って RRF で融合する(0020、`rrfFuse`)。融合の窓が
  順位そのものであって、51 位を出すには窓を広げて上位 50 を捨てる
  — つまりページごとに費用が増える offset になる。しかも順位は
  書き込みのたびに動くので、その 51 位は 1 ページ目と整合しない。
  **正しく答えられない問いに、答えの形だけを与えない。**
- **ochakai が返すのは行ではなく知識である**(0046 §5)。50 件で足りない
  検索は、ページを進める問いではなく**絞り込みが足りない問い**である。
  フィルタ(`type` / `status` / `trust` / `prefix` / `tag` / `fm.`)は
  そのためにあり、フィードは「全部読む」ためにある。この 2 つを混ぜない。

400 の本文は次の 1 リクエストになる: 「検索は limit で区切られる。
すべてを歩くなら sort=… の一覧を使う」。

### 2.3 総件数は返さない

ページの後ろに何件あるかは返さない。`cursor` が無いことが
「ここで終わり」であり、それ以上は言わない。

フィルタの効いた一覧に対する正確な件数は、ページを 1 枚返すのと同じ
スキャンをもう一度することであり、**1 ページ目の費用を毎回倍にして
進捗バーを描く**のは、キューを空にするために読む面が払う値段ではない。
概算(`reltuples` の類)はフィルタが効いた瞬間に無意味になる。
UI が必要とするのは「まだあるか」であって、それは `cursor` の有無が
既に答えている。

### 2.4 カーソルはスナップショットではない

フィードは生きている。歩いている間に誰かが検証すれば
`sort=verified_at` の中でそのエントリは動き、`sort=usage` の順位は
検索のたびに動く。したがって:

- 位置より前へ動いたエントリは、そのページ送りでは**見えないことがある**。
- 位置より後ろへ動いたエントリは、**2 回見えることがある**。

これは keyset の性質であって欠陥ではない。台帳を歩き切ることを保証するの
ではなく、**上限で静かに止まらないこと**を保証する。スナップショットが
要るなら、それはエクスポート(0046 §3.5 の `Accept: application/gzip`)の
仕事である。

## 3. 選ばなかった案

- **`limit` の上限を上げる。** 10000 にしても壁の位置が動くだけで、
  壁があること自体は変わらない。1 応答の大きさは本文の上限
  (0001)にも当たる。
- **offset。** 2.1 の通り。実装は最も安いが、性能とページ間の整合の
  両方を捨てる。`reembed` の先例が keyset なのは同じ理由による。
- **検索にもカーソルを付ける。** 2.2 の通り。「窓を広げて捨てる」形なら
  実装できるが、**費用がページ番号に比例して増える API** は、遅いことが
  仕様である点で `limit` より悪い。順位の 51 位という概念自体が
  ochakai の答えではない。
- **総件数を返す。** 2.3 の通り。
- **カーソルに署名する。** 改竄されたカーソルは「変な位置から始まる
  一覧」を返すだけで、フィルタも権限も動かさない(0002 — 到達できる者は
  読める)。守るものが無いところに鍵は置かない(0003 の secret-zero)。
  復号できない値は 400 で落ちる。

## 4. サーフェス(0015)

- **REST**: `GET /api/v1/knowledge` に `cursor` パラメータ、応答に
  `cursor` キー。契約はここにしかない。
- **CLI**: `ochakai search --cursor <c>`。`--json` の応答に `cursor` が
  そのまま乗り、平文出力では**続きがあるとき stderr に次の 1 行**を出す
  (`note: more entries — rerun with --cursor …`)。stdout は 1 行 1 ヒットのまま
  で、パイプの中身は変わらない。
  **CLI はページを自分で歩かない**(意図的な省略)。`reembed` は
  歩き切ることが目的のコマンドなので自分で回すが、`search` の出力は人と
  パイプが読むものであり、`--limit` は利用者が置いた上限である。それを
  コマンドが黙って越えるのは、`head` を付けた出力が勝手に伸びるのと同じ
  驚きになる。見直す条件: `--all` を求める声が出たら、その時に足す。
- **MCP**: `search` ツールに `cursor`(入力)と `cursor`(出力)。
  MCP はツール数が予算であってフィールド数ではなく、ここで足すのは
  フィールド 2 つである。エージェントが未回答の失敗報告を歩き切る
  ときに、1 回の呼び出しを 1000 件に膨らませる代わりに 100 件ずつ
  進めるのは、**文脈の予算にとってもこちらが安い**。
- **Web UI**: レビュータブと explore のフィードの「最大 1000 件まで
  読み込む」が、**追記する「さらに読み込む」**になる。1000 件を一度に
  取りに行く注記は消える — それが壁の正体だったからである。

## 5. 互換性

追加のみで、既存の呼び出しは 1 つも壊れない。`cursor` を渡さない
リクエストは今までどおり 1 ページ目を返し、`cursor` を読まない
クライアントは応答の新しいキーを無視する。

`q=` と `cursor` の同時指定が 400 になるのは新しい拒否だが、今日その
組み合わせを送れる呼び出し元は存在しない(`cursor` が無かった)。

0046 §3.5 の改名(`/api/v1/knowledge` → `/api/v1/search`)より前に入る。
改名は住所を動かすだけで、本ドキュメントのパラメータはそのまま移る —
「退役する面に足すと二度払う」形にはならない。
