# ochakai 設計ドキュメント 0089: 半分しか埋め込まれていない concept は、そう言う

Status: Accepted(2026-08-09)。[0080](0080-search-and-how-a-deployment-embeds.md)
を改訂する — §3「幅はモデルのものであって、デプロイのものではない」が
**列の幅**について言ったことを、**入力窓**について言い直し、§7 の
「やらないこと」に**チャンク化**を加える。0080 は現行のまま。
Date: 2026-08-09

## 0. この記録が決めたこと

1. **モデルの入力窓に収まらなかった concept のベクトルは、収まらなかった
   ことを自分で持つ。** ベクトルの行に真偽値が一つ増える。
2. **その数は `GET /api/v1/stats` に出る** — `embedding.vectors` と
   `embedding.truncated` の対で。CLI と Web UI もそれを読む。
3. **チャンク化はしない。** 長い concept を分割して埋め込み、検索側で
   concept に畳み直す機構は、いま作らない(§4)。

## 1. 窓に収まらない concept は、静かに半分になる

埋め込みは concept 一件につきベクトル一本で、id・title・description・
tags・golden query の question・本文を連結したものを、モデルの入力窓
(`gemini-embedding-001` で 5,000 バイト、`gemini-embedding-2` で 20,000)
に**切り捨ててから**渡す。窓はトークン数で決まり、バイトは近似でしかない
ので、それでも provider が長すぎると答えたときは半分にして再送する — 四回
まで、つまり最悪で八分の一になる。

**そして、その結果は成功と区別がつかない。** 切り捨てられた concept は
ベクトルを持ち、ランキングに乗り、検索結果として返ってくる。ただ後半に
書かれていることでは**引けない**。長くて価値のある文書ほど、消える部分が
大きい。ログには一行出るが、ログは運用者が読みに行くものであって、
キュレーターが自分のナレッジベースについて知る経路ではない。

C7(人間の改善ループが測れる)が測れと言っているのは、まさにこの種の
ことである。**測れない失敗は、無いことと見分けがつかない。**

## 2. 切り捨てはベクトルの性質であって、concept の性質ではない

真偽値を置く場所は `knowledge_embedding` の行である。concept の行では
ない。理由は一つで、**同じ concept が、あるモデルでは切れていて別の
モデルでは丸ごと入る**からである。5,000 バイトの窓で切れた文書は
`gemini-embedding-2` に移せば入る。切り捨ては concept が長いことの帰結
ではなく、**この concept とこのモデルの組み合わせ**の帰結であり、行が
覚えているべきはそちらである。

ベクトルは導出物なので(0080 §3)、この列も導出物である。既存の行は
`false` に落ちる — 「切り捨てられていないことが分かっている」ではなく
**「切り捨てられているとは分かっていない」**であり、埋め直していない行に
ついてそれは正直な値である。次の書き込みか `ochakai reembed` が正す。

真偽値であってバイト数ではない。「どれだけ失われたか」は、切り捨てが
起きたと分かってから concept を開けば分かることで、行に二つ目の数を
置いて全デプロイに払わせるほどのものではない。

## 3. 数はキュレーターが読む場所に出る

`stats` に `embedding` が増える。三つの値を持つ:

| 値 | 意味 |
|---|---|
| `enabled` | このデプロイに embedder があるか |
| `vectors` | 現行モデルのベクトルを持つ live concept の数 |
| `truncated` | そのうち、前半しか見ていないものの数 |

**`enabled` が要るのは、`vectors: 0` が二つの状態を指すからである** —
セマンティック検索が無いデプロイと、コーパスが丸ごと未埋め込みのデプロイ。
前者にやることは無く、後者には `ochakai reembed` がある。ゼロを見て
どちらか分からないのは、`misses.recording` が同じ理由で存在するのと同じ
形の欠陥である。

**二つの数は対で読む。** `truncated` だけでは何も決められない。
`vectors` に対して 3/4 なら、それはコーパス全体の形であって、モデルを
広い窓のものに移す話になる。3/400 なら長い runbook が一本あるだけで、
その concept を分ける話になる。**違う問題であり、違う答えである。**

面への出方は 0067 のとおり: REST が契約、CLI は `ochakai stats` の行と
して(セマンティック検索が無ければ `-`、`misses` と同じ書き方)、Web UI
はレビューページのループ帯に — ただし**ゼロのときは描かない**。常設の
「0 件切り捨て」は読み飛ばす行が一本増えるだけで、`dropped` が同じ理由で
そうしている。MCP には出さない: これは運用者とキュレーターの数であって、
エージェントが一回のループで要るものではない。

## 4. チャンク化はしない

長い concept を分割して一つずつ埋め込み、検索側で chunk → concept に
畳み直す機構は、**要ると決まっていないので作らない**。

理由は順に三つある。

**一つ目 — 誰が詰まったか、まだ誰も言えない。** 表面を増やす前に答える
三つの問いの一つ目である。切り捨ては今日まで**どの面にも出ていなかった**
ので、詰まった人が居ても報告のしようが無かった。だから最初に置くべきは
機構ではなく**数**である。これは #528 で ranking を触る前に評価ハーネスを
置いたのと同じ順番で、同じ理由による。`truncated` が誰かのデプロイで
ゼロでないと分かってから、その形を見て決めればよい。

**二つ目 — チャンク化は安い機構ではない。** 一 concept 一ベクトルという
前提は、テーブルの主キー、検索 SQL、`reembed` の再開カーソル、
`stats` の数え方の全部に入っている。畳み直し方(chunk の最大を取るのか、
合計するのか)は**ランキングの決定**であり、どの記録もまだしていない。
そして埋め込み呼び出しの回数と保存量が concept の長さに比例して増える —
0080 §3 が「詰め直しは利用者の口座から支払う」と書いた、その口座から。

**三つ目 — 分けるべき concept である可能性のほうが高い。** 窓に収まらない
文書は、多くの場合ナレッジが一件ではなく複数入っている。ochakai が
提示すべきは「後半を別のベクトルにしておきました」ではなく、**「この
concept は長すぎる」という事実**かもしれない。`truncated` はどちらの
読み方もできる数であり、機構を先に置くとその問いが立たなくなる。

**再開の条件を書いておく:** 実運用のデプロイで `truncated` が `vectors`
の無視できない割合を占め、かつその concept が人間の目に「一件の知識」と
して妥当だと確認できたとき。そのときチャンク化は記録を一本取る決定に
なる。

## 5. 数えていないもの

**ファイルのベクトル。** 添付の本文も同じ上限で切られ、同じように末尾を
失う。数えていないのは、それが別テーブル・別キーであり、列と数をもう一組
増やすことになるからである。そしてファイルは媒体型やモデルの都合で
そもそも埋め込まれないことがあり、**名前での字句一致は常に効く**
(0080 §5)。`stats.embedding` は concept について答える。

**字句検索。** 切り捨てはベクトル面だけの話である。後半に書かれた語句
そのもので引けば、字句索引(migration 0036)は当てる。失われるのは
「同じことを別の言葉で訊く」経路であり、それが埋め込みの存在理由なので、
失われ方としては最も痛いところではある。

## 6. やらないこと

- **チャンク化と、chunk → concept の畳み直し**(§4)。
- **切り捨てられた concept の一覧面**(feed / `sort=`)。数がゼロでない
  デプロイをまだ誰も見ていない段階で、覚える語を一つ増やす理由が無い。
  `stats` の数が「この問題があるか」を答え、Web UI の一文が「どうするか」
  を言う。どれか、が要ると分かったら足す。
- **切り捨てを避けるための自動的なモデル切り替え。** 幅と窓はモデルの
  ものであり、モデルはデプロイが選ぶ(0080 §2・§3)。製品が請求先を
  勝手に変えることはしない。
- **失われたバイト数を行に持つこと**(§2)。
- **書き込みを拒否すること。** 窓に収まらないのは refuse する理由に
  ならない — concept は保存され、字句検索には丸ごと載る。ochakai が
  やるのは、載っていない部分があると言うことだけである。
