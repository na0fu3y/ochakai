# ochakai 設計ドキュメント 0148: 空のベースは、ページからも本人として埋まる

Status: Accepted(2026-09-25)。[0085](0085-the-empty-base-and-what-fills-it.md) を
Superseded にする — `seed` の決定(ウェアハウスに接続しない CLI、draft、空の
description)はここに再掲し、Web UI に載せないとした 0085 §5 を改める。
[0142](0142-ochakai-carries-a-data-agent-that-does-not-rule.md) §4 がページに
入れた「本人の身元で BigQuery を読む」手段を、エージェント無しでも使う(§2.4)
Date: 2026-09-25

## 0. この記録が決めたこと

1. **Web UI が、データセットのスキーマを本人の身元で読み、`ochakai seed` と
   同じ draft を作る。** 入口はホームの「BigQuery から取り込む」一つ(§2.2)。
2. **サーバーは何も新しく提供しない。** REST・MCP・CLI・環境変数のどの数も
   動かない。書き込みは既存の `PUT` で、既にある住所は上書きしない(§2.3)。
3. **`OCHAKAI_OAUTH_CLIENT_ID` と `OCHAKAI_BIGQUERY_PROJECT` は
   エージェント無しで立つ。** スキーマを読むことはモデルを要らない(§2.4)。
4. **投影は Go と JS の二か所にあり、一つのゴールデンファイルが両方を
   縛る**(§3)。

## 1. 何が起きたか

運用者自身が、使い始めに BigQuery のパブリックデータで定義を書いてみよう
として、`bq query` → `ochakai seed` → `ochakai import` の三段を面倒だと
感じた(2026-09-25)。三段の最初でつまずく理由もあった: README と
[最初のひと月](../guides/onboarding.md)の例のクエリは `COLUMNS` に無い
`description` を選んでおり、BigQuery ではそのままでは動かなかった。

0085 が Web UI を断った理由は、**ブラウザから読む手段が無く、読むなら
資格情報がサーバーに来る**ことだった(0085 §4「サーバー側の投影
エンドポイント」)。0142 §4 がその手段を入れた — ページは本人の短命な
トークンで BigQuery を直接呼び、トークンはサーバーに届かない。手元の
`ochakai ui` ではプロキシが本人として呼ぶ。理由が外れたので、決定を
改める。満たす条件は **C4(FDE なし)** である: gcloud も bq も持たない
人が、空のベースを自分で埋められる。

## 2. 決定

### 2.1 `ochakai seed` は動かない

0085 §2・§3 をそのまま引き継ぐ。

- **ウェアハウスに接続しない。** 入力は運用者自身が撃った
  `INFORMATION_SCHEMA.COLUMNS` の答え(JSON の配列か一行一オブジェクト)、
  出力は OKF バンドルの tar.gz、書き込みは既存の `ochakai import` が行う。
  ウェアハウス中立で、Snowflake でも Postgres でも同じ行が出せる。
- **テーブル一つにつき `BigQuery Table` の concept 一つ**、列は markdown の
  表、住所は `resource`。日付シャード(`events_20260101`…)は二つ以上
  揃えば `events_` の一件に畳み、`events_*` と名乗る。
- **出るのは draft で、description は空である。** スキーマは骨格であって、
  そのテーブルが何のためにあるか、どの列が嘘をつくか、いつロードが遅れるか
  を知らない。誰も書いていない一文を frontmatter に置けば、その後の全員が
  それを信じる。コネクタが作るのは誰も請け合っていない数千行で、こちらが
  作るのは数千個の問いである。

### 2.2 ページが読む

- **入口はホームの「BigQuery から取り込む」**(`#/seed`)。タブは足さない
  — ベースの最初の 30 分の道具で、毎日開くものではない。書けないデプロイ
  (read-only)と、BigQuery を読む手段の無いデプロイ(OAuth クライアントも
  `ochakai ui` のプロキシも無い)では出ない。
- **入力は三つ。** 取り込み元(`project.dataset`、または
  `project.dataset.table` — 末尾の `*` は名前の先頭で絞る)、課金する
  プロジェクト(`OCHAKAI_BIGQUERY_PROJECT` があれば出さない)、置き場所
  (`--prefix` と同じ、既定 `tables`)。取り込み元の `project` がそのまま
  `resource` に入る — パブリックデータなら `bigquery-public-data` で、
  課金するプロジェクトではない。
- **読むクエリは一本。** `INFORMATION_SCHEMA.COLUMNS` に、列の説明を持つ
  `COLUMN_FIELD_PATHS` をトップレベルだけ結ぶ。**列の説明は取り込む** —
  frontmatter の description とは違い、BigQuery の中で誰かが書いた文であり、
  表の Note 列に出所のまま入る(`seed` も `description` があれば同じ
  ことをする)。
- **読み方は 0142 §4 のままである。** 同じサインイン、`bigquery.readonly`
  のスコープ、一回 10 GiB の課金上限。`ochakai ui` はプロキシが dry run で
  SELECT と確かめてから走らせる。
- **上限を超えたら、一部ではなく断る。** 一覧は 50,000 行まで読み、超えれば
  絞るよう求めて何も作らない。途中で切れた一覧は小さなデータセットと
  区別がつかない — `seed` が 100 行ちょうどの入力に注意を出すのと同じ
  教訓である。
- **書く前に見せる。** 作られる id、列の数、畳んだシャードの数を並べ、
  人が押して初めて書く。

### 2.3 書き込みは既存の一本で、上書きしない

各 concept を `PUT /api/v1/bundle/<id>.md` に `If-None-Match: *` で一件ずつ
書く。**既にある住所には触れず、数えて報告する** — `412 already_exists`
がそのまま答えである。`ochakai import` は create-or-replace だが、ページの
ボタンは二度押される。二度目の押下が、誰かが書き足したテーブルの説明を
スキーマで消してはならない。スキーマが変わったテーブルを投影し直したい
人には `seed` と `import` がある。

記録されるのはページを使った人である。エディタから一件作るのと何も
変わらない: 身元も、ディレクトリの書き込み権限([0109](0109-a-directory-has-readers-and-writers.md))も、
書けなかった一件の理由も、既存の書き込みのものである。

### 2.4 二つの変数は、エージェントから離れる

0142 のとき、ページが Google のトークンでしていたのはエージェントの提案を
走らせることだけで、`OCHAKAI_OAUTH_CLIENT_ID` と `OCHAKAI_BIGQUERY_PROJECT`
はエージェント無しでは起動を断っていた。いまはスキーマを読むことにも使い、
それはモデルを要らないので、**どちらもエージェント無しで立つ**。
パブリックデータで試す人に、Vertex AI の設定を先に求めない。

`stats` の中の置き場所(`agent.oauth_client_id`・`agent.bigquery_project`)
は動かさない。名前は最初に現れた場所の綴りで、エージェントが off でも
値は載る。動かせば、それを読むページと `ochakai eval` の古い版が黙って
課金先を失う。

## 3. 投影は二か所にあり、一つのファイルが縛る

ページは投影を自分で行う — `seed.go` の規則(テーブルのまとめ方、シャード
の畳み方、id の NFC、文書のバイト列)を `static/js/seed.js` に写した。
**写しは、片方だけが規則を覚えた日にずれる。** だから二つは一つの
ゴールデンファイル(`cmd/ochakai/testdata/seed-golden.json`)に縛られる:
Go のテストがそれを書き、JS のテストがそれを読んで同じバイト列を求める。
ずれは誰かのベースに届く前に CI で落ちる。

採らなかった案:

- **サーバーに投影の操作を足す**(行を受け取り、draft を返すか書く)。
  投影は一か所で済むが、REST が一本増える。そして 0145 §5.2 が REST に
  載せないとしたバルクの取り込みの隣に、「別の形式を読む」入口を開く —
  0085 §4 が `import --from-schema` を断ったのと同じ形である。
- **Go を WebAssembly にしてページで動かす。** 写しは消えるが、数百 KB を
  全員のページに載せ、[0094](0094-the-page-runs-under-a-policy.md) の
  ポリシーに `wasm-unsafe-eval` を足す。守りたいのは 400 行の規則である。

## 4. 載せない、断るもの

- **サーバーが読むこと。** ウェアハウスの資格情報をサーバーに持たせない
  (0142 §4)。この記録のどこも、サーバーに SQL を走らせない。
- **定期の同期・差分・削除の追従。**
  [examples/bigquery-catalog](../../examples/bigquery-catalog) の job の仕事
  である。ページは初日の一回で、あちらは毎日走る。
- **上書きするモード。** §2.3。
- **BigQuery 以外。** ページが本人の身元で読めるウェアハウスは BigQuery
  だけである(0142 §4「始めは BigQuery だけ」)。ウェアハウス中立なのは
  CLI の `seed` のほうで、それは変わらない。
- **エージェントに取り込ませること。** 0142 §2 の「スキーマを刈り取って
  concept にする経路をエージェントに作らない」は動かない。ページのこれは
  人が押すボタンで、何を作るかを人が見てから書く。
- **OKF アーカイブのアップロード。** 0145 §5.4 が Web UI に載せないとした
  ものはそのまま載せない — これはアーカイブを受けるのではなく、ページが
  既存の一件の書き込みを組み立てているだけである。

## 5. 面

- **Web UI** — ホームに入口一つと、`#/seed` の画面一つ。
- **REST / MCP** — 載せない。サーバーは何も新しく提供しない。
- **CLI** — `ochakai seed` のまま。完全性は既にある。
- [surface.md](../surface.md) の数はどの次元も動かない(REST 17、MCP 6、
  CLI 25、FLAG 28、ENV 18、DOC 27)。
