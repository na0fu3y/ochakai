# ochakai 設計ドキュメント 0100: `.md` は concept の綴りである

Status: Accepted(2026-08-15)。
[0075](0075-the-bundle-is-the-address-space.md) §3.3 と §2 の表を改訂する
(`type` の無い `.md` は 400 になり、ファイルはその住所に座れない)。
[0064](0064-rest-stops-at-api-v1.md) §11 の「凍結を破ってよい唯一の理由は
セキュリティ上の欠陥である」を改訂する — 二つ目の理由として**出力が OKF に
適合しないこと**を足す(§4)。
[0082](0082-what-the-freeze-holds-still.md) の分類はそのまま使う(§5)。
Date: 2026-08-15

## 0. この記録が決めたこと

1. **`.md` の住所に座れるのは concept と予約名(`index.md` / `log.md`)
   だけである。** `type` を持たない `.md` の PUT は 400 になる(§2)。
2. **ファイルは `.md` を名乗れない。** 保存済みのものは移行で
   `.markdown` に改める — バイト列は出てくる、住所の綴りだけが変わる(§3)。
3. **凍結を破ってよい理由を二つ目として足す** — **出力が OKF に適合
   しないこと**(§4)。
4. これは破壊的変更でありながら、**凍結の指紋を一行も動かさない**(§5)。

## 1. export が非適合バンドルを出せる

SPEC v0.2 の実文は二箇所とも短い。

> §3.1: The following filenames have defined meaning at any level of the
> hierarchy and MUST NOT be used for concept documents: `index.md`,
> `log.md`. **All other `.md` files are concept documents.**
>
> §11: A bundle is **conformant** with OKF v0.2 if: 1. Every non-reserved
> `.md` file in the tree contains a parseable YAML frontmatter block.
> 2. Every frontmatter block contains a non-empty `type` field.

ochakai はこの二つを同時に落とせていた。`internal/restapi/restapi.go` の
書き込み分岐は `isMarkdown && okf.CarriesType(body)` が偽なら**その `.md`
という住所のまま**ファイルとして書き(`svc.PutFile`)、
`writeBundleArchive` はファイルを自分の path でアーカイブに載せる。
つまり `notes.md` を PUT した利用者の export には、**予約名でない `.md`
で、frontmatter も `type` も持たないファイル**が入っていた。それを受け
取った consumer の適合検査は §11.1 と §11.2 で落ちる。

§11 が consumer に禁じている拒否は五つだけである — 任意フィールドの
欠落、未知の `type`、未知の追加キー、壊れたリンク、`index.md` の不在。
**frontmatter を丸ごと持たない `.md` はその五つのどれでもない。**

C3(形式は OKF v0.2)は八つの条件の一つで、C1(資産は丸ごと出る)の
出口はその export である。**出口が規格を外れているなら、出口が無いのと
同じ場所に近づく。**

## 2. 決定: 住所が種類を決める

規則は三行になる。

- `index.md` / `log.md` は SPEC §3.1 の予約名。今までどおり導出物である。
- **それ以外の `.md` は concept である。** `type` を持たない本文の PUT は
  `400` / `code: invalid` で、`type` が要ることを名指す。
- **`.md` で終わる住所へのファイル書き込みは存在しない。**

`GET` と `DELETE` の `.md` 分岐にあるファイルへのフォールバックは消える。
`.md` に concept が無ければ 404 であり、それだけである。

**0075 §3.3 に正面から反対している。** あの節は「`type` の無い `.md` を
PUT してもファイルとして保存する(400 にしない)」を、SPEC §11 の
「consumer は拒否してはならない」を書き込み面に広げた形として決めた。
反対の理由は二つある。

- **§11 の寛容は、いま見たとおり frontmatter の不在を含まない。** 広げた
  先の規則が、広げた元の規則の外にある。
- **ここでの ochakai は consumer ではなく producer である。** §11 の適合
  条件は、書かれたバンドルが満たすかどうかの条件であり、書く側を縛る。
  受け取りに寛容であることと、非適合を出力することは別の決定だった。

0075 §2 の中心的な不変条件 —— **バンドルに入ったものは出てくる** ——
は壊さない。バイト列は一つも捨てず、変わるのは `.md` という綴りを
名乗れないことだけである(§3)。

## 3. 保存済みのものと、取り込み

**移行は改名する。** `x.md` というファイル行を `x.markdown` に移す
(`0039_a_markdown_file_is_not_a_concept.sql`。0035 と同じ形の
`UPDATE`)。拡張子を落として裸にしないのは、読む人にとって markdown で
あることが情報だからである。`.markdown` は `.md` ではないので §3.1 の
「All other `.md` files」に当たらない。

**住所が動くので BREAKING である。** 本文からその綴りを指していたリンクは
切れる。それは SPEC が名指しで許している唯一の切れ方でもある ——
§6.1「Consumers MUST tolerate broken links: a link whose target does not
exist in the bundle is not malformed」。CHANGELOG は動いた path を数で
言う。

**取り込みは改名して報告する。** 非適合の `.md` を含むバンドルを
`ochakai import` が読んだら、`.markdown` に置いて行を印字する。サーバが
400 を返す面(呼び出し元がその場で直せる)と、復元の面(捨てればデータが
減る)で答えを変えるのは、0075 §2 が `skipped` の意味を狭めたのと同じ
理由による — 取り込みが黙って何かを失うことのほうが重い。**黙って読み
替えないという 0075 §3.3 の後半は、ここでもそのまま生きる。**

## 4. 凍結を破ってよい二つ目の理由

0064 §11 は「凍結を破ってよい唯一の理由はセキュリティ上の欠陥である」と
書いた。本書はそこに一つ足す —— **契約が OKF に適合しない出力を生む
欠陥**である。

範囲を狭く書いておく。**OKF SPEC の適合条項(§11)に違反する出力を、
ochakai の書き込み面が作れてしまう場合に限る。** 「SPEC に照らして
より良い」でも「SPEC の推奨に沿う」でもない。適合しているかどうかは
SPEC が MUST で書いた三条件に対する yes / no であり、外の文書が答えを
持っているという性質は、セキュリティ上の欠陥が持っている性質と同じで
ある —— **ochakai の都合で判定が動かない。**

これは 0082 §5 が却下した「今回だけ例外にして golden を再生成する」では
ない。あちらは規則を書き換えずに曲げる形だった。本書は規則そのものを
書き換えるので、以後の問いは「これは適合の欠陥か」になる —— 答えは
SPEC を読めば出る。

## 5. 指紋が一行も動かないこと

`api/openapi.frozen.txt` は動かない。`PUT` の `requestBody` は
`text/markdown` と `application/octet-stream` の両方を宣言したままで
(住所ごとに違うことを OpenAPI は綴れない)、`200` / `201` の `anyOf` も
`View` と `File` のままで(`.md` 以外の住所では今までどおり `File` が
返る)、新しい 400 は既に宣言されている `code: invalid` である。

**破壊的変更でありながら golden の diff がゼロになる。** 0082 §2 の分類
では、これは「リクエストの形」が狭まる変更 —— 通っていた要求が通らなく
なる —— であり、凍結の本体側に当たる。それでも指紋には見えない。
0064 §21 が最後に書いたとおりである:

> 凍結が守れるのは「何が在るか」であって「どれを選ぶと何が返るか」では
> ない。

**だから記録が要る。** 指紋が見ない破壊的変更は、記録が無ければどこにも
残らない。

## 6. 同時に閉じるもの

- **PUT の多態が住所で決まる。** 0064 §16 は契約テストの除外を「本文が
  `type` を持てば concept」というハンドラと同じ規則で絞ったが、
  その規則自体が本文を覗くものだった。住所で決まれば、契約と実装が同じ
  一行を読む。
- **0064 §20.4 の隙間が原理的に消える。** あの節は正直にこう書いていた
  —— `type` を持たない `.md` は concept の住所に座るファイルなので、
  そこへの DELETE は concept の経路を通ってから `DeleteFile` に落ち、
  **前提条件が読まれないまま消える**。その組み合わせが存在しなくなる。
- **ファイルへの条件付き書き込みへの道が開く。** 0064 §20.4 が 400 に
  したのは実装が無かったからで、住所で種類が決まれば `If-Match` を
  ファイルにも一貫して適用できる。**本書はその実装を含まない**(§8)。

## 7. 面への配分(0067)

- **REST** — 上のとおり。操作は 11 のまま、PARAM も HEADER も動かない。
  [docs/surface.md](../surface.md) の数は一つも変わらない。
- **CLI** — `ochakai put` がファイルを `.md` の名前で送れば 400 を受け
  取る。クライアント側で先回りして落とすことはしない(0064 §20.4 が
  「サーバが強制していない規則を CLI が知っているのは逆向き」と書いた
  とおり)。`import` は §3 のとおり改名して報告する。
- **MCP** — 変化なし。ファイルの書き込みは載っていない(0067 §5.1)。
- **Web UI** — 変化なし。バンドルのアップロードは無い(0067 §5.4)。
  `.md` という名前のファイル行が一覧から消えるだけである。

## 8. 採らない案・やらないこと

- **現状のまま、export のときだけ非適合の `.md` を落とす。** C1 の出口が
  「丸ごと出る」と言えなくなる。落とすほうが破っているものは大きい。
- **`type` を ochakai が補って concept にする。** 文書が一度も宣言して
  いない値を主張することになり、0064 §15 が `title` について断ったのと
  同じ形である —— 既定を持たないものに既定を書かない。
- **予約名を三つ目に増やす**(`README.md` を予約するなど)。§3.1 の表は
  二つで閉じている。三つ目は OKF の外の綴りを作ることであり、C3 に
  逆行する。
- **1.0 まで待つ。** 待つあいだに export された非適合のバンドルは
  回収できない。**この論拠は弱い** —— 実インスタンスは少なく、踏んだ
  利用者はまだ一人もいない。強いのは §4 のほう、規則の欠陥を直す代金が
  今より安いことは二度とないという 0082 §5 と同じ論法である。
- **OKF 適合検査そのものを実装する**(`ochakai lint`)。表面が増える。
  書き込み面が非適合を作れないなら、検査する対象がそもそも減る。
- **条件付きファイル書き込みの実装**(§6)。道は開くが、開けるのは
  別の決定である。
- **非 markdown の拡張子への規則。** `.py` も `.parquet` も自由のまま
  —— SPEC §6.3 の `references/attesters/revenue.py` が示すとおり、
  バンドルに markdown 以外が居ることは規格の側の想定である。
