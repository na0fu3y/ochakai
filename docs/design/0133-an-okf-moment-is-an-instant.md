# ochakai 設計ドキュメント 0133: OKF の瞬間は、瞬間である

Status: Accepted(2026-08-28)。**OKF が瞬間で定義した値を ochakai がどう綴る
かの現行ドキュメント。** [0069](0069-the-loop-and-what-measures-it.md) §2.2 の
比較の綴りと [0074](0074-the-document-and-the-vocabulary-that-asks-it.md) §4.1
の例示の括弧が、この記録によって古くなる — どちらも**決定は動かない**ので
Superseded にはしない(§6)。凍結された契約の一行を動かすが、それは
[0064](0064-rest-stops-at-api-v1.md) §11 が「OKF 適合の欠陥」として
残した口である([0100](0100-md-is-how-a-concept-is-spelled.md)・
[0102](0102-one-history-in-one-spelling.md) と同じ)
Date: 2026-08-28

## 1. 問題: SPEC が固定した型を、ochakai が狭めていた

SPEC §5 は冒頭で型を固定している — "Every timestamp-valued key in OKF is
an ISO 8601 datetime with an explicit UTC offset" — そして §5.5 は
`stale_after` を "an absolute instant" と呼ぶ。

ochakai が受け取っていたのは `YYYY-MM-DD` の日付だけだった。しかも
その規則は、SPEC がそう言っていると**書いてあった**:

```go
// DateLayout is the date form OKF fixes for its absolute dates — stale_after
// (SPEC §5.5), sources[].last_modified and usage_window (SPEC §5.1).
const DateLayout = "2006-01-02"
```

SPEC はそう言っていない。「タイムゾーンで揉めない」は ochakai の選好で
あって、**仕様の規定として書かれていた**。マイグレーション 0019 の散文も、
列を `date` にした理由として同じことを言っている。

**代金は、SPEC 自身の worked example が読めないことである。** Appendix A の
Attested Computation は三つの鍵を瞬間で書いている:

```yaml
stale_after: 2026-12-31T00:00:00Z
sources:
  - last_modified: 2026-04-02T00:00:00Z
usage_window: { from: 2026-06-01T00:00:00Z, to: 2026-06-30T00:00:00Z }
```

真夜中は日付に潰れて通っていた。**真夜中でない瞬間は落ちていた** — note
一行を添えて、値を空にして。数百件の import で note は誰も読まない。

## 2. 落ち方が、この製品が名指しで断ってきた形だった

文書のバイト列は生のまま保存されるので([0043](0043-document-first.md)
§3.1)、**export は原文を返す。C1 は無事だった。** 壊れていたのは
**読む面の全部**である:

- `GET /api/v1/bundle/{path}` と `get_concept` が、宣言のある concept に
  ついて `stale_after` を**持たない**と答える。
- 期限切れフィード(`sort=stale_after`)に永久に上がらない。書き手が
  期限を宣言したのに、再確認のキューに入らない。
- `ochakai stats` の三つのキューの一つが、その一件を数えない。
- Web UI のフォームが空欄を見せる。

**黙って値を落とす**というのは、[0130](0130-the-web-ui-and-the-fields-of-a-document.md)
§3 がブラウザに部分集合パーサを書くことを断ったときの、まさにその壊れ方
である。同じ壊れ方が、そのとき見ていなかった場所に一つあった。

## 3. 決定

### 3.1 二つの綴りを取り、どちらも書き換えない

`stale_after`・`sources[].last_modified`・`usage_window` の `from`/`to` は、
**RFC 3339 の datetime**(`2026-12-31T18:30:00Z`)か、**`YYYY-MM-DD` の
日付**を取る。日付は**それが開く UTC の真夜中**であり、それが二つを
一つの比較にする。

**offset の無い datetime は取らない。** 絶対にするのが offset であって、
`2026-12-31T18:30:00` はどの瞬間か言っていない。日付が絶対なのは、
真夜中 UTC という読み方をこの記録が与えるからである。

戻すときは**来た綴りで戻す**。ただし UTC の真夜中は日付として戻る —
日付が意味しうる唯一の瞬間が真夜中なので、二つは同じ一つの値であり、
**普通に書く人が書いた綴り**が日付のほうだからである。

### 3.2 列は瞬間で持つ

`object.stale_after` は `date` から `timestamptz` へ移す
(マイグレーション 0046)。既存の値は日で、日は**それが開く UTC の真夜中**
なので、移行は `::timestamp` して `AT TIME ZONE 'UTC'` である。

### 3.3 比較は now() で、タイムゾーンは無い

期限切れフィードは `stale_after <= now()`。0069 §2.2 が守ろうとしたもの —
**同じ concept が、ある環境では期限切れで別の環境ではそうでない、が
起きないこと** — は、これで前より強く成り立つ。両辺が絶対な瞬間なので、
セッションの `TimeZone` が入る隙が無い。**UTC を手で綴らなければ
ならなかったのは `date` 列のほうだった** — 裸の日付には比較する相手の
offset が無いからである。

一箇所だけ手当てが要る。カーソルは読み手が見た綴りを運ぶので、
`'2026-12-31'::timestamptz` はセッションの TimeZone で解決される。
カーソルの値は RFC 3339 に直してから渡す(`utcCursorKey`)。

## 4. 面

**数はどれも動かない。** 新しい名前を一つも発明していない。

| 面 | 現れ方 |
|---|---|
| REST | `Summary.stale_after` の `format: date` が外れる。**操作もパラメータもヘッダも符号も増えない** |
| CLI | `ochakai list stale_after` の並びが日ではなく瞬間になる。フラグは動かない |
| MCP | `put_concept` のスキーマの `stale_after (YYYY-MM-DD)` が二つの綴りを言う。ツールは増えない |
| Web UI | フォームは**日付を書く**ままで、他人が書いた瞬間を**書き換えない** — `<input type="date">` が読めない値は text box に落ちる(元からそうだった)。期限切れの表示は文字列比較をやめて瞬間で比べる |

## 5. 凍結との関係

`stale_after` は bundle の往復に載るので
[0107](0107-the-freeze-holds-the-okf-core.md) のコアの中にある。動かす口は
0064 §11 が二つだけ残しており、その一つが **OKF 適合の欠陥**である。
0100 と 0102 が同じ口を通っている。

動きは `format: date` が外れる一行で、**向きは広がる側だけ**である:
これまで妥当だった値はすべて今も妥当で、拒まれていた値が通るようになる。
契約を持っているクライアントが読めなくなるものは無い。

## 6. なぜ 0069 と 0074 を Superseded にしないか

[0128](0128-a-number-is-for-an-area-not-a-rule-inside-it.md) §2.1 の判定を
そのまま使う — **三か月後に問い直す人は、親の記録と CHANGELOG を読めば
答えに着くか。**

- **0069 §2.2 が決めたのは**「今日は UTC であって、セッションの TimeZone に
  従わせない」ことである。§3.3 はそれを**保っている** — 古びたのは、その
  決定を実現する SQL の綴りのほうである。
- **0074 §4.1 が決めたのは**「列を持つ鍵は列が答え、`fm.` は別の問いだ」で
  ある。`sort=stale_after` が型で比較し `fm.stale_after` が文字列一致だと
  いう対比は**そのまま真**で、括弧の中の型名が `date` から瞬間に変わる
  だけである。

どちらも親の**決定**は動かない。動くのは領域の内側の機構であり、0128 が
「番号を取らない」と決めた当のものである。番号を取っているのはこの記録の
ほうで、それは §1 の狭め方が**面をまたいで観測できる**からである。

## 7. 検査する不変条件([0035](0035-verifiability.md))

- SPEC Appendix A の concept が、note 無しで三つの鍵を保って読めること。
- offset の無い datetime が、`soon` と同じように落ちること。
- UTC の真夜中が日付として戻り、それ以外が RFC 3339 で戻ること。
- 同じ日の一時間前と一時間後に期限を宣言した二件のうち、**前者だけ**が
  フィードに載ること。`date` 列が見分けられなかったのはここである。

## 8. 採らなかった案

- **列を `date` のまま置き、封筒だけ原文を返すこと。** 0069 §2.2 と
  0074 §4.1 の散文に一字も触れずに済み、マイグレーションも要らない。
  外したのは、それが**索引と封筒に別々の値を持たせる**からである — 同じ
  鍵について「何と書いてあるか」と「いつ切れるか」が別の列に分かれ、
  フィードの粒だけが日のまま残る。0043 §3.1 の「列は文書から導かれた
  索引である」が、導出ではなくなる。
- **すべてを RFC 3339 に正規化して戻すこと。** `2026-12-31` と書いた人が
  `2026-12-31T00:00:00Z` を読み戻すことになる。書いていない綴りを返すのは、
  producer の書いたものを保つという 0043 §3.6 の向きに逆らう。
- **`date` を捨てて瞬間だけにすること。** SPEC の例が両方を書いており、
  日付のほうが人が書く綴りである。狭めることが §1 の誤りだった。
