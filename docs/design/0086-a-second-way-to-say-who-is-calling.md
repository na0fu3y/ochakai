# ochakai 設計ドキュメント 0086: 誰が呼んでいるかを言う、二つ目の方法

Status: Accepted(2026-08-09)。[0003](0003-gcp-only.md) の「Google Cloud
以外で本番を動かす方法は無い」を改訂する — **認証だけは第二の経路を持つ**。
secret-zero([0065](0065-identity-and-provenance.md))も、認可を持たない
ことも、埋め込みが Vertex AI であることも動かさない。
**§4 の「email が無い / verified が false」は
[0117](0117-a-person-recorded-as-a-process-says-so.md) が改訂した** —
記録の仕方は同じで、黙って行わなくなった。**この経路が資格情報をどの
ヘッダで受け取るかは [0121](0121-each-path-reads-its-own-header.md)** —
自分で検証するデプロイは `Authorization` だけを読む(検証の中身も記録
される名前も動かない)
Date: 2026-08-09

## 1. 何が起きたか

Google Cloud の外には**姿勢が二つしかなく、どちらもデプロイではない**。
`dev` は誰も認証せず、`read-only` は誰も認証しない上に書き込みを全部
断る。その間にあるもの — 私的で、書き込めて、誰が書いたかを記録する —
はすべて、**Cloud Run の IAM チェックがプロセスの前で既に済んでいること**
に乗っている。ID トークンを検証せずに読んでいるのはそのためである
(`actorFromIDToken`)。

[positioning](../positioning.md) はこれを「多くのチームにとって失格要件で
あり、欠落ではなく決定である」と書いてきた。決定であることは変わらないが、
**代金の見積もりが間違っていた**: 0003 が守ろうとしたのは secret-zero で
あって、Google Cloud そのものではない。

## 2. 決定: OIDC 発行者を名指したデプロイは、自分で検証する

環境変数二つ。

- `OCHAKAI_OIDC_ISSUER` — 発行者の URL(`https://` のみ)
- `OCHAKAI_OIDC_AUDIENCE` — このデプロイが答える `aud`

両方揃うか、どちらも無いかで、片方だけは**起動時エラー**である。
audience の無い発行者設定は、同じ発行者が*別のサービス*のために発行した
トークンを受け入れる — `aud` が存在する理由そのもの(confused deputy)で
あり、後で監査に気づかれる種類の穴である。

設定されたデプロイは、Bearer トークンについて署名・発行者・audience・
有効期限を自分で検証する。設定されていないデプロイは今までどおり、
Cloud Run が検証したものを読む。

**secret は一つも増えない。** 検証に使うのは発行者が HTTPS で公開して
いる公開鍵であり、発行するものも回すものも無い(0065 §1、0003)。
共有鍵(HMAC)系のアルゴリズムを受け付けないのはこのためで、
許可リストは非対称のみ、`none` は当然入らない。

## 3. 何が変わらないか

- **認可は無い。** 発行者が請け合った相手は、Cloud Run の場合と同じく
  全部を読み書きできる(0065 §1)。この記録は「誰が」を増やすだけで、
  「何をしてよいか」には触れない。
- **埋め込みは Vertex AI か、無いか。** Google Cloud の外は lexical のみで
  ある([0080](0080-search-and-how-a-deployment-embeds.md))。ただし移行
  0036 以降、日本語の二文字語は索引で引かれる — **小さい検索であって、
  壊れた検索ではない**。第二の埋め込みプロバイダは別の決定であり、
  ここでは行わない。
- **Cloud SQL IAM もそのままである。** データベース認証は
  `OCHAKAI_DB_IAM_AUTH` の下で Google Cloud のものであり、他所では
  接続文字列を運用者が用意する(それは元から `OCHAKAI_DATABASE_URL` の
  仕事である)。
- **委譲**(`Ochakai-On-Behalf-Of`)は経路に依らず同じ規則で動く。
  検証済みの呼び出し元が許可リストにいるかを見るだけで、そこは
  [0027](0027-delegated-provenance.md) のままである。

## 4. 記録される名前

- **発行者が verified と言った email** — 人として記録する。Cloud Run 経路と
  同じ読み方になる。
- **verified でない email** — 使わない。発行者が請け合わないアドレスは
  利用者が書いた文字列であり、それで作った provenance は誰でも名乗れる。
- **email が無い / verified が false** — `sub` を、process として記録する。
  機械のトークンはこの形をしている。

`email_verified` が**無い**場合は verified として扱う。発行者が自分で所有
するアカウントについてこのクレームを省く実装が複数あり、拒否すると企業で
最も普通の構成が認証不能になる。`false` は決して信じない。

## 5. 採らなかった案

- **API キー。** secret を一つ増やす。0065 と 0003 が守っている性質は
  まさにこれであり、この記録はその性質を保つ*ために* OIDC を選んでいる。
- **mTLS。** 証明書の配布と失効は、鍵を回す運用そのものである。
- **発行者だけを設定させ、audience は任意にする。** §2 のとおり、
  それは confused deputy を既定にする。
- **Cloud Run 経路も同じ検証にする。** できるが買うものが無い: あちらは
  Google が前段で検証しており、二度目の検証は起動時の依存を一つ増やす
  だけである。**二つの経路がある**ことは意図であって重複ではない。
- **OIDC を「姿勢」(`OCHAKAI_MODE`)にする。** 姿勢は排他的な四つ
  ([0060](0060-one-word-for-the-posture.md))で、これはそのどれとも
  直交する — `read-only` の OIDC デプロイは意味を持つ。ただし `dev` と
  `public` は「誰も認証しない」と言っている姿勢なので、その組み合わせは
  起動時に断る。

## 6. 面

- **ENV** — 2 語増えて 11 → 13。天井を上げる決定であり、そう言って上げる。
- **REST / MCP** — ワイヤは変わらない。`Authorization: Bearer` は元から
  読んでおり、変わったのは**その中身を誰が検証したか**だけである。
  ただし契約は**遡及宣言を一つ**得る: 401。両経路とも元から送っていた —
  IAM 経路はトークンが転送されなかったとき(`httpauth`)、この記録の
  経路は検証に落ちたとき — が、`api/openapi.yaml` はこれまで黙っていて、
  info の散文は「ochakai itself verifies nothing」とまで言っていた。
  in-process 検証が 401 を*最初の応答*にした以上、両方とも偽になる。
  [0064](0064-rest-stops-at-api-v1.md) が 400/413 でやったのと
  同じ扱いで、サーバが既に送っているものを
  `components/responses/Unauthorized` として全操作に宣言し、散文を
  二経路の現在形に書き直す。封筒の `code` は `invalid` である —
  落ちたのはリクエストの資格情報であって、ナレッジ側のどの条件でも
  ないから([0083](0083-an-error-carries-a-code.md))。
- **CLI / Web UI** — 変わらない。CLI は Google の ID トークンを自分で
  取るが、他の発行者のトークンをどう取るかは発行者ごとの話であり、
  `Authorization` を持つ普通の HTTP クライアントとして使える。
