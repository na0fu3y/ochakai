# 検索と埋め込み

問いに対して**どの concept を読むべきか**を順に並べること、そのための
埋め込みをどこで・どのモデルで作るか。C8(日本語話者にとって最適な
選択肢の一つ)が最も直接に乗っている領域である。

## 検索は順位を返す

`GET /api/v1/search?q=…`(MCP `search_concepts`、CLI `ochakai search`、
Web UI の検索)は、**問いに答える concept の順位**を返す。

- ヒットが運ぶのは id・型・title・description・status・trust・score などの
  **ポインタ**で、本文は運ばない。読むかどうかを決めて `GET` で取る
  (search → get)。取った concept は、それを指す concept を
  `linked_from` で運ぶ — 指標の読み方を書いた insight はそこにある。
- **本文で一致したときだけ `snippet`** を付ける(140 文字前後、切った端に
  …)。名前か description で一致したとき(行が既に見せている)と、ベクトルで
  見つかったとき(指させる一節が無い)には付けない。
- `limit` は既定 10、上限 50。**スコアの床は持たない** — スコアはモード
  ごとに較正されておらず(字句は断片の重み、融合は RRF の小さな値)、
  一つの床はどちらかで無意味になる。
- `q` の無いリクエストは検索ではなく**一覧**(住所順、または `sort=` の
  フィード)になる。一覧はページングし、検索はしない。MCP では
  `list_concepts` と `search_concepts` の二本に分けている。
- 住所で絞る `prefix`、`type`・`status`・`trust`・`tag`・`source`・
  `links_to`・`created_by`・`fm.<key>` の絞り込みは検索と一覧で共通である
  (`fm.` は MCP には載せない)。範囲を持つ呼び出し元の結果は、フィルタの
  段階で読める範囲に絞られる([identity.md](identity.md))。

## 三本のリストを融合する

1. **字句** — 問いを断片に割り、`search_text`(id・title・description・
   tags・本文・`synonyms`・名前空間内のファイル名)がそれをいくつ含むかで
   点を付ける。断片の重みは候補の中での出現頻度で決まる。**日本語の
   二文字語も索引で引ける**。埋め込みの無いデプロイでもそのまま効く。
2. **concept のベクトル。**
3. **ファイルのベクトル** — concept ごとに最良の一件を取り、その concept の
   ヒットとして数える。

三本を RRF(k = 60)で融合する。並べ方の規則は次の順に効く。

1. **問い(またはその語の一つ)が title か id の最後のセグメントと一致する
   concept が先に来る。** 「EC事業の継続率を計算して」は何の名前でも
   ないが、`EC事業` と `継続率` の定義が、全部の語を含むだけの報告に
   負けてはならない。
2. 融合したスコア。いまの内容を確認する検証が立っている concept には、
   一順位ぶんの小さな加点がある(人か確認ジョブかを問わない —
   設計記録 [0141](../design/0141-a-miss-is-read-off-the-words.md))。
3. 同点なら字句のスコア、次に最後に確認された時刻の新しさ(確認された
   ことのある方が先)、最後に id。字句のリストの中の同点は、先にその語を
   **見出しか表の行の最初のセル**に持つ concept が取る — そこに語がある
   concept はその語について書かれており、言及しているだけではない
   (`ochakai seed` はテーブルの列をこの形で書く)。

**`synonyms` は索引が読む唯一の producer キーである。** 配列でも文字列でも
読み、検証もワイヤの欄も専用フィルタも持たない。書き手が与えた別名に
答えるためで、他のキーは名前でないので索引しない。

**ファイルは独立して返らない**(ヒットは所有する concept)。**ochakai は
ファイルを解釈しない** — OCR もキャプションもパースもしない。埋め込みは
決定的なエンコーダであって解釈ではない。

### 退化は名乗る

埋め込むデプロイで**問いを埋め込めなかった**検索は、字句だけで答え、
応答に `degraded: true` を載せる(四面すべて)。埋め込みを持たない
デプロイは退化していない — 字句が毎回の答えなので、この欄は立たない。

### 答えの無かった問い

どの concept の**言葉**にも一致しなかった問い(字句のリストが空)を
ミスとして記録する。ベクトルのリストは床が無く必ず何かを返すので、
「答えが空だった」では数えられない。記録はサービス層の一か所で、
呼び出し元に返る順位は変わらない。保存するのは打たれた文字列の先頭 500 バイトで、180 日で刈る。
`OCHAKAI_RECORD_MISSES=false` で止まり(既定 on)、公開デプロイは記録しない。
`stats` への出方は設計記録 [0141](../design/0141-a-miss-is-read-off-the-words.md) §4–§5 が持つ。

## どこで、どのモデルで埋め込むか

`OCHAKAI_EMBEDDINGS` 一語が言う。

| 値 | 意味 |
|---|---|
| 未設定・`on` | メタデータサーバが答えたプロジェクトで、**ベースが生まれたときの既定**で埋め込む |
| `off` | 埋め込まない。Vertex AI を一度も呼ばない |
| `projects/<p>/locations/<l>/publishers/google/models/<m>` | そのプロジェクト・場所・モデルで埋め込む |

**三つのどれでもない綴りは起動エラー**である(`true` も `my-project` も
モデル名だけも)。`false` のつもりで課金され続ける、綴りを外して既定の
モデルで埋め込み続ける、のどちらも黙って起きるからである。Terraform では
モジュールの `embedding_model` が同じことを言う。

### 既定はベースが生まれたときに決まる

| ベース | 何も名指さないときの埋め込み |
|---|---|
| v0.29.0 以前に作られた | `gemini-embedding-001`、**動いているリージョンで** |
| それより後に作られた | `gemini-embedding-2`、**`global` で** |

- ベースは生まれを一行覚える(`base_birth`)。見分けるのはベースであって
  保存済みのベクトルの有無ではない — 字句だけで動いていた既存のデプロイが、
  次の起動で黙って `global` へ本文を送り始めないように。
- **新しいベースのテキストは既定で `global` へ行く。** `gemini-embedding-2`
  は `global`/`us`/`eu` にしか無く、このモデルを既定にすることが場所を
  決める。代わりに画像と PDF を中身で検索でき、入力窓が四倍になる。
- **リージョンに留めたいときは名指す**:
  `…/locations/asia-northeast1/publishers/google/models/gemini-embedding-001`
  (画像と PDF はファイル名でしか見つからなくなる)。古いベースで画像・PDF
  検索を使いたいときは `gemini-embedding-2` を `global` で名指し、
  `ochakai reembed` を打つ。
- export して別のデータベースに import したベースは新しいベースである
  (生まれはデータベースの性質で、バンドルは運ばない)。
- 古いベースでリージョンが読めなかったときは、埋め込みを有効にしない。
  誰も選んでいないリージョンへ本文を送るより、字句で動くほうを選ぶ。

### 使えるかは IAM が決める

プロジェクトは設定せず**メタデータサーバから発見する**(ADC からは取らない
— 手元の開発機が黙って課金を始める)。呼べるかどうかはサービスの身元の
`roles/aiplatform.user` が決め、起動時に一語の埋め込みで一度だけ(10 秒で
打ち切り)問い合わせる。

| 埋め込みの出所 | Vertex AI か pgvector が使えないとき |
|---|---|
| 発見(未設定・`on`) | 警告を一行出し、字句だけで動く |
| resource name(名指し) | 起動しない |

メタデータサーバの無い環境(手元・CI・Google Cloud の外)では何も
有効にならない。起動ログの `semantic search enabled` がモデルと場所を
名指す。

### ベクトル

- **幅はモデルの定数である**(どちらの既定も 768)。設定ではなく、知らない
  モデルは起動エラーにする — 推測した幅は保存済みのベクトルと比べられない。
  幅が変わればベクトルのテーブルを作り直し、ログが `ochakai reembed` を
  名指す。**詰め直しは自動でやらない** — 埋めることは利用者の支払いである。
  幅が同じでモデルだけ変わったとき、古い行は消さない(検索はモデルで絞る)。
- concept 一件にベクトル一本で、id・title・description・tags・`question`
  キー(golden query の問い)・本文を
  連結し、**モデルの入力窓に切り捨ててから**渡す(001 で 5,000 バイト、
  2 で 20,000)。窓に収まらなかったベクトルはそう記録し、`stats` の
  `embedding.vectors` / `embedding.truncated` に数が出る。**チャンク化は
  しない。**
- **ファイルのベクトルはファイルのパスで引き**、どの concept のヒットに
  なるかは検索時にバンドルから読む。ファイル入力を取れるモデル(2 系)は
  画像と PDF のバイト列を埋め込み、取れないモデルは飛ばしてファイル名の
  字句一致に任せる。テキストファイルはどのモデルでも本文を埋め込む。
- 埋め込むのは書き込み時だけで、バックフィルはしない。詰め直しは
  `ochakai reembed`(管理者)である。

## 差し出しているもの

- 既定の経路が Vertex AI に依存する(秘密は増えない — 認証は ADC)。
- 書き込みが支出になる。止めるのはロールを与えないか `off` である。
- cold start が一回の Vertex AI 呼び出しぶん伸びる。
- 同じイメージの二つのデプロイが、生まれで違う既定を持つ。

## やらないこと

- スコアの床、LLM による順位付け、順位の代わりに要約を返すこと。
- PDF のテキスト抽出・OCR、どのファイルが当たったかの帰属表示、
  ファイル本文の DB への複製。
- 受け取るファイル形式を埋め込みの都合で狭めること。
- 幅の設定、未知のモデルの受け入れ、768 より広げること。
- 既存のベースを新しい既定へ自動で移すこと、モデルや幅の変更後の
  自動 reembed。
- リージョンや世代を言う変数を足すこと(resource name が一度に運ぶ)。
- Google Cloud の外の埋め込みプロバイダ(API キーは secret である)。
  外を正式に支える条件は [identity.md](identity.md) の末尾にある。
