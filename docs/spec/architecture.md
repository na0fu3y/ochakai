# 全体アーキテクチャとデータエージェント

ochakai が何であり、何を持たないか。そして、デプロイが入れられる
データエージェントが何をし、何をしないか。

## ochakai とは

データエージェントに、メトリクスの定義だけでなく**その値をどう読むか**
までを渡す **Context Provider** である。メトリクスの定義・人が認めた
計算(golden query)・数字の読み方・用語・テーブルのカタログを一つの
ベースに集め、どのエージェントにも同じ契約(REST と MCP)で配る。
その上で、**問いに答えるデータエージェントを一つ持つ**(既定 off)。
自分のエージェントも、その契約の読み手の一人にすぎない。

**キュレートされたナレッジベースであって、カタログではない。** コネクタで
自動収集しない。空のベースを埋めるのは、人が自分の身元で読んだスキーマから作る
draft である(設計記録 [0148](../design/0148-the-empty-base-fills-from-the-page-too.md))。

## 動かない三つ

1. **配るものを変えるのは裁定だけで、LLM は裁定しない。** 裁定は人の
   verify と却下、または確認ジョブが `process:` として残す確認
   (`machine-confirmed` と読まれる)である。検索と読みの面には LLM が
   入らない — 順位は全クライアントが同じものを受け取る契約で、決定的で
   なければ比べられない。
2. **サーバーは SQL を実行しない。** ウェアハウスの資格情報もクライアントも
   持たない。実行するのは常に問うた本人の身元である。
3. **secret を持たない**([identity.md](identity.md))。

## 形

- **Go の単一バイナリ**が REST(`/api/v1`)と MCP(`/mcp`)を同じポートで
  出す。エージェントも同じバイナリの中にある — デプロイを二つにすると、
  自分で立てられること(C4)の代金が倍になる。
- **実行時の依存は PostgreSQL だけ。** Redis も別のベクトル DB も検索
  クラスタも持たない。ベクトルは pgvector、会話の記録も同じデータベースに
  置く。
- Google Cloud の上では、埋め込みとエージェントのモデルを Vertex AI で、
  ファイルのバイト列を GCS で持つ。どれも無ければその機能が無いだけで、
  サーバーは動く。
- Web UI は `/api/v1` のクライアントで、LLM はページではなく REST の後ろに
  いる。
- 配布は GHCR のマルチアーキイメージと静的バイナリで、distroless・SBOM・
  SLSA provenance・keyless 署名・SHA 固定の Actions を持つ。

## データエージェント

`OCHAKAI_AGENT` にモデルを名指すと入る。**未設定のあいだ、ochakai は
一バイトも変わらない。**

### 入れ方と、テキストの行き先

| 値 | 動くところ |
|---|---|
| モデル id だけ(例 `gemini-2.5-flash`) | メタデータサーバが答えたプロジェクトと**リージョン**。そのリージョンで答えなければ起動を止める |
| Vertex AI の resource name | そこで動く |

推奨の `gemini-3.8-flash` は `global` にしか無いので resource name で
名指し、そのとき**問いと読んだ concept と SQL の結果は `global` で処理
される**。日本のリージョンで答えるのは一世代古いモデルである。呼ぶのは
サービスの身元で(`roles/aiplatform.user`)、API キーは読まない。リージョンが
読めない・モデルが答えない・権限が無い、のどれでも起動を拒否し、黙って
他所へ送らない。`off` のような綴りは起動エラーである。

- `public` と `sandbox` では入れられない(匿名の呼び出しに運用者の課金を
  開かない)。`read-only` では答えるが書かない。
- 共有の Web UI から SQL を走らせるには `OCHAKAI_OAUTH_CLIENT_ID`(OAuth の
  クライアント ID — 公開の識別子で、secret ではない)も要る。無ければ
  SQL を書いて見せるだけになる。

### LLM が入る場所

- **答える。** 読みは他のクライアントと同じ search → get で、近道は無い。
  使った concept の id と、それを人か確認ジョブが確かめたか(trust)を
  添えて引く。確かめられていないものはそう言う。
- **SQL を提案する。** 走らせるのは問うた人である(次節)。エラーを読んで
  直した SQL を出し直し、結果を読んで答えを続ける。
- **draft を書く。** 空いている id に、一回の答えで 5 件まで。
- **裁定されていない draft の次の版を提案する**(`propose_revision`)。
  書き込みはせず、提案時の内容ハッシュと一緒に答えと turn に残す。
  適用するのは問うた人で、
  `POST /api/v1/agent/turns/{id}/revisions/{concept}` は本文を受け取らず
  turn が残した文書を書く。前提条件は提案時のハッシュで、動いていれば 412、
  裁定されていれば 400。**適用は裁定ではない** — draft は draft のまま
  レビューのキューに残る。
- **手順に従う。** 「棚卸し」のような手順は `type: Skill` の concept から
  読み、その trust が `human-reviewed` のときだけ従う。
- **空の description を埋める。** 目的を問うた人に一〜三問訊き、行数・
  鮮度・NULL の割合を SQL で確かめ、出所のある文だけを提案する。
- **クエリ履歴は、問われたときにだけ読む。** 問うた人自身のクエリ
  (`INFORMATION_SCHEMA.JOBS_BY_USER`)を直近 30 日で数え、繰り返し走って
  いる集計を一回 5 件までの draft にする。他人のクエリ
  (`JOBS_BY_PROJECT`)は権限があっても読まない — draft はベースを読める
  全員に見える。チーム全体の履歴は運用者の定期ジョブ
  (`examples/bigquery-catalog`)の仕事である。

エージェントの書き込みは `process:ochakai via <問うた人>` として記録され
([identity.md](identity.md))、問うた人の範囲で行われる。

### LLM が入らない場所

- verify・却下・deprecate をしない。裁定済みの concept を書き換えない。
  `type: Skill` を書かない。
- 検索と読みの順位。
- 👍 は検証ではない。答えへの判定は、その答えが使った concept への
  人の結果報告になり、trust は動かさない。

### SQL を走らせるのは誰か

- **共有の Web UI では、ブラウザが本人の身元で走らせる。** Google の
  サインインで本人の短命なアクセストークン(`bigquery.readonly`)を受け、
  ページが BigQuery を直接呼ぶ。トークンはページのメモリにだけあり、
  サーバーに送らず保存しない。
- **手元の `ochakai ui` では、プロキシが本人の gcloud の身元で走らせる。**
  BigQuery の dry run で SELECT と分かったものだけを走らせる。
- どちらも課金上限 10 GiB(`maximumBytesBilled`)で、何を読めるかは本人の
  権限が決める。ochakai は SQL を検閲しない。
- 既定では SQL ごとに確かめてから走らせる。問うた人が会話ごとに同意すれば、
  その会話では以後の SQL を自動で走らせる。
- **結果はサーバーとモデルを通る**(答えを続けるため)。ナレッジにも会話の
  記録にも残さない。答えは結果を表で見せ、形が一つの読み方しか許さない
  ときは棒か列のグラフも描く。**グラフは会話と一緒に消え、保存・ピン留め・
  定期実行・共有はしない** — そこから先は BI ツールで、ochakai が競うのは
  ナレッジである。
- 始めは BigQuery だけである。本人の Google の身元がそのまま通るのが
  そこだけだからである。

### 会話の記録(turn)

軌跡はループの入力なので残す。**残すのは形であって中身ではない。**

- 残すもの: 問いの文、読んだ concept の id、提案した SQL の文、判定と
  一言、書いた draft と修正案。**SQL の結果は残さない。**
- 保持は 180 日。読めるのは問うた本人と管理者で、範囲を持つ呼び出し元は
  自分の範囲の分だけ。
- 人が 👍 を付けて「比較に使う」とした問いは、比較の問いのセットになる。
  問いのセットはベースの外(同じ PostgreSQL)に置き、**export に載せない**
  — ベースの中に置くと、問いの文が検索に当たり、答えの無かった問いが
  ミスとして数えられなくなる。
- ochakai 以外のエージェントも turn を残せ(`POST /api/v1/agent/turns`)、
  REST から読める。比較の問いの再生は `ochakai eval` で、SQL は打った人の
  手元で走る。詳しくは設計記録
  [0144](../design/0144-a-turn-is-kept-whoever-answered.md)・
  [0146](../design/0146-a-kept-question-is-replayed-where-the-person-runs-it.md)。
- **答えはナレッジにしない。** ナレッジになるのは、そこから人が裁定した
  concept だけである。

### 限度

一回の会話は 40 メッセージ・本文 64 KiB まで、一回の答えは道具の往復
16 回・4 分まで。道具の結果は一件 24 KiB で切って渡す。

### 面

REST の `POST /api/v1/agent`(`dry_run` で何も書かず何も数えない)と
turn の操作、Web UI の問いの欄・答え・👍/👎・修正案の差分と「適用する」。
**MCP には載せない** — MCP の向こうは既にエージェントである。**CLI にも
載せない** — CLI を使う人はたいてい自分のエージェントを持ち、能力は REST に
残る。

## やらないこと

- エージェントを別のサービスにすること(デプロイが二つになる)。
- サーバーがチームのサービスアカウントで SQL を走らせること(本人の権限と
  行レベルの制御を失う)、リフレッシュトークンを持つこと(secret である)。
- 順位付けに LLM を使うこと、👍 を検証にすること。
- コネクタによる自動収集、クエリ履歴の刈り取り。
- ダッシュボード、モデルが設計するグラフ。
- 却下の記憶を消すこと — 却下は削除で、理由は `log.md` が運び、エージェントは
  提案の前にそれを読む。
