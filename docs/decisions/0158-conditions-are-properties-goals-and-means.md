# 0158: 条件を性質・目的・手段の三層に分ける

Date: 2026-10-10
領域: [やらないと決めたこと](../spec/declined.md)

## 背景

表面の判断は八つの条件 C1〜C8 で行い、それとは別に、アーキテクチャの
仕様と CLAUDE.md が「サーバーは SQL を実行しない・secret を持たない・
エージェントは既定 off」をまず照らす項目として挙げていた。八つは同じ
扱いで並び、衝突したときにどれを取るかは書かれていなかった。このため
No FDE(C4)が他の項目と衝突すると、照らす項目として書かれた側が残る
構造だった。実際、埋め込み側の運用者は OAuth の認可サーバー・本人として
SQL を走らせる仲介・定期実行・チャットを自前で持っていた。チームの
最初のひと月は、自分で走らせる手順書(`docs/guides/onboarding.md`)に
任されていた。

外では、ベンダーの FDE が放棄される見通しが出ている(Gartner、
2026-09)。Palantir もオントロジーの編集をエージェントが提案する形に
移っている。自動で文脈を集める製品(Genie Ontology、Cortex Sense)は、
数値が正しいかを確かめる層を持たない。人の裁定と来歴と持ち出せる形式の
価値は下がっていない。下がっていたのは最初の一日の手数である。

## 決定

- 条件を三層に分ける。**性質** P1〜P5(裁定・資産・OKF・本人の権限・
  長期 secret)は破らない。**目的** G1〜G5 は、届いたかを数で確かめる。
  **手段** M1〜M6(Google Cloud、SQL を走らせない、エージェントは既定
  off、コネクタを持たない、MCP の既定 no、上限)は、目的と比べて入れ
  替えてよい。
- 「サーバーは SQL を実行しない」を性質から手段に移し、性質を
  「問いは本人の権限を超えない・ウェアハウスの資格情報を常設しない」
  (P4)と言い直す。「secret を持たない」は「運用者が保管し更新する長期の
  secret を持たない」(P5)と言い直す。
- 目的と手段が衝突したら、手段を保つ側が、それが実現している性質と、
  より少ない手数の手段が無いことを示す。目的どうしでは G1 を先にする。
- G1 を導入ではなく結果で定義する: 外の人の手を借りずに、最初の人が
  確かめた答えに届く。エージェントは既定 off のまま、off でも届き、
  入れれば手数が減る。
- 旧 id は一対一で写す(C1→P2、C2→P5、C3→P3、C4〜C8→G1〜G5)。

## 退けた案

- **八つを残し、C4 に重みだけ付ける。** 照らす項目が条件の外にある限り、
  衝突のたびに外の項目が勝つ構造は変わらない。
- **目的の全部に順位を付ける。** 衝突のたびに表を引くだけの判断になり、
  理由が PR に残らなくなる。
- **エージェントを既定 on にする。** 課金とデータの送り先(G5)を運用者が
  決める前に動き始める。入れたときの恩恵を大きくする方を取る。
- **C 番号のまま層だけ付ける。** 性質の二つ(P1・P4)が八つの外にあり、
  番号を振り直さずには一つの表に並ばない。

## 戻す条件

手段を入れ替えた変更が、性質を破ったと分かったとき(たとえば仲介を
通した実行が本人の権限を超えた一件)。そのときは入れ替えた手段を戻し、
三層は残す。
