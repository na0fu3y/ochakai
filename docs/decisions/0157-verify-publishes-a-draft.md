# 0157: draft への検証は、それを公開する

Date: 2026-09-28
領域: [ループ — 裁定・キュー・計測](../spec/loop.md)

## 背景

設計記録 0043 §3.2 は、確認することと公開することを別の行為にした。
verify は台帳に一行足すだけで、文書にも status にも ETag にも触れない。
draft を stable にするのは書き手の PUT である。

その後 0138 が、trust をいまの内容に対して立っている検証から導くように
した。status の書き換えは内容の変更なので、**検証してから status を
変えると、その検証は立たなくなる**。Web UI のレビューキューの ✓ は
まさにその順で二つを呼んでいて、受け入れた draft は stable かつ
unverified になり、「編集後未検証」のキューに移っていた。CLI の
`ochakai verify` は status を動かさないので、draft のキューが空かず、
UI と CLI で同じ裁定の結果が違っていた。

draft に検証を付ける人は、どの面からでも、それを受け入れるつもりで
付けている。

## 決定

- `POST /api/v1/review/{id}` の `verified` は、concept が draft なら、
  文書の `status` の一行だけを `stable` に書き換え(ほかのバイトは
  そのまま)、検証者の編集として保存し、そのあとで検証を記録する。
  書き換えは読んだ content hash を条件にし、間に入った編集は上書きせず
  失敗させる。
- stable と deprecated への検証は、今までどおり文書にも ETag にも
  触れない。再確認が、編集中の人の If-Match を無効にしないためである。
- CLI・Web UI の詳細ページ・レビューキューは同じ一回の呼び出しになり、
  キューが自分で status を書き換えることはやめる。MCP には今までどおり
  裁定が無い。

## 退けた案

- **status の変更を内容の変更と数えない。** 0138 の「いまの内容」から
  status だけを外すことになり、deprecated にしても検証が立ち続ける。
  範囲が広い。
- **検証のあとに status を変え、その書き込みだけ検証を失効させない。**
  書き込みごとに失効の例外を持つことになり、台帳の読み方が二つになる。
- **draft に対する検証を拒む。** 人が確かめた draft は OKF で表せる状態で、
  拒めば CLI での裁定が二手間になる。

## 戻す条件

「確かめたが、まだ公開しない」を記録したい、という実際の一件が出たとき
(そのときは draft への検証を stable にしない指定を足す)。
