# 0160: 裁定は門ではなく段であり、LLM の確認は人の委任の下で認める

Date: 2026-10-23
領域: [検証ループと利用測定](../spec/loop.md)

## 背景

P1 は「配る内容を変えるのは裁定だけで、LLM は裁定しない」と書いていた。
実装はそれより弱かった — MCP から書かれた draft も、編集されて失効した
concept も、裁定無しに `unverified` として配られている。裁定が実際に
守っていたのは配るかどうかではなく、**信頼の段**だった。

この書き方は二つのことを塞いでいた。ソースが変わったとき concept を
追従させること(M4 がコネクタを持たない理由は「集めたものが裁定無しに
配られない」だった)と、人が追いつけない量の確認を LLM に任せること
である。意思決定支援のエージェント基盤(Sakana AI の Aquarium、2026)は、
ソースの変更をオントロジーに反映し続けることを本体にしている。チームが
外の手を借りずに回し続ける(G1)には、人の裁定一件一件を門にしたままでは
足りない。

## 決定

- P1 を言い直す: **信頼の段を上げるのは裁定だけで、配るものは必ず
  いまの段と来歴を連れる。** 内容はどこから変わってもよく、変われば立って
  いた検証は失効して `unverified` に落ちる(今の編集と同じ規則)。
- **裁定するのは人か、人が委任した確認ジョブ**で、ジョブの中身が LLM で
  あってもよい。委任とは、人がそのジョブの `process:` の身元を置き、
  付与表で書ける範囲を決めることである。ジョブの検証は `process:` として
  台帳に残り、`machine-confirmed` と読まれ、`human-reviewed` には決して
  ならない。
- M4(コネクタを持たない)は P1 の根拠を失う。いまは表面の上限(M6)
  だけで保ち、G1 と衝突したら入れ替える側にある。
- 変わらないもの: デプロイ自身のエージェント(`OCHAKAI_AGENT`)は裁定
  しない。検索と読みの順位に LLM は入らない。MCP に裁定の道具は無い。
  委任は人の身元に化けない — `via` で人を名乗るジョブの検証は、今どおり
  その人の検証として記録されるので、委任には使わない。

## 退けた案

- **門のまま、LLM が下書きした裁定案を人が一括で通す。** 0159 が退けた
  一括の裁定と同じで、`human-reviewed` が言えることを減らす。
- **LLM の確認に新しい段(`llm-confirmed`)を足す。** 読む側に二つの
  機械の段を区別させる。区別したい人は台帳の `process:` の名前と
  producer で引ける。
- **委任を台帳の行に記録する。** 付与表は履歴を持たず、委任した人の名は
  台帳に載らない。載せるには新しい欄と語が要り、詰まった実例がまだ無い。

## 戻す条件

委任されたジョブの `machine-confirmed` を、読む側が人の確認と取り違えて
誤った答えを出した一件が出たとき。そのときは委任を戻し、段の表示は残す。
